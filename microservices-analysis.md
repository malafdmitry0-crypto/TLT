# TLT HeatCalc — Нужно ли выделять микросервисы на бэке?

**Дата:** 2026-05-10  
**Вопрос:** Стоит ли разбивать монолит FastAPI на микросервисы?

---

## Короткий ответ: нет. Modular monolith — правильная архитектура для текущего масштаба.

---

## 1. Что есть сейчас

Один процесс FastAPI обрабатывает всё:

```
┌────────────────────────────────────────────┐
│  FastAPI :8000                             │
│                                            │
│  auth · projects · objects · calculations  │
│  specifications · reports · import/export  │
│  admin · references · background-tasks     │
│                                            │
│  → PostgreSQL :5432                        │
│  → Redis :6379 (cache + rate limiter)      │
└────────────────────────────────────────────┘
```

Модули внутри разделены на:
- `api/v1/` — роутеры (auth, projects, objects, calculations, specifications)
- `services/` — бизнес-логика (project_service, calculation_service, report_service…)
- `formulas/` — чистая математика (heat_loss, electrical)
- `models/` — SQLAlchemy-модели
- `core/` — инфраструктура (cache, config, database, rate_limit)

Это **modular monolith**: модули разделены на уровне кода, но работают в одном
процессе, делят одну БД и один event loop.

---

## 2. Критерии для выделения микросервиса

Микросервис оправдан, когда выполняется **хотя бы 2** из 4 условий:

| Критерий | HeatCalc сейчас |
|---|---|
| **Независимое масштабирование** — сервис A требует 10× больше CPU/памяти, чем B | ❌ Все операции лёгкие. Batch 400 объектов = 94 мс. Расчёты не доминируют. |
| **Разные паттерны нагрузки** — сервис A CPU-bound, сервис B I/O-bound, нужны разные рантаймы | 🟡 F-02 (Crank-Nicolson) и F-03 (NSGA-II) **будут** CPU-bound. Но они ещё не реализованы. |
| **Независимый жизненный цикл** — сервис A меняется каждую неделю, сервис B раз в год | ❌ Все модули меняются в рамках одного продукта. Нет команд с разной скоростью. |
| **Разные требования к надёжности** — падение A не должно ронять B | ❌ Падение любого компонента делает продукт бесполезным. Нет сценария «пусть расчёты лежат, но CRUD работает». |

**Вывод:** ни один критерий не выполняется **сейчас**. F-02/F-03 **могут** создать потребность в будущем.

## 3. Сравнение: монолит vs микросервисы для HeatCalc

| Критерий | Монолит (сейчас) | 2–3 микросервиса |
|---|---|---|
| **Сложность разработки** | Низкая. Один процесс, одна БД, одна транзакция. | Высокая. Service discovery, API gateway, distributed tracing, circuit breaker. |
| **Деплой** | 1 контейнер. `docker compose up`. | 3+ контейнеров. Оркестрация, health checks, graceful shutdown. |
| **Отладка** | Один стектрейс. pdb в одном процессе. | Распределённая трассировка (Jaeger/Zipkin). Сложнее в 5–10×. |
| **Транзакции** | ACID. `db.commit()` для всех изменений. | Distributed sagas / 2PC. Риск inconsistency. |
| **Производительность** | Вызов функции — наносекунды. | HTTP/gRPC — 0.5–2 мс на вызов. Накладные расходы. |
| **Масштабирование** | Горизонтальное: 3 реплики монолита. | Избирательное: 5 реплик calc-svc, 1 реплика report-svc. |
| **Команда 1–3 чел.** | ✅ Идеально. | ❌ Оверхед инфраструктуры съест всё время. |
| **Команда 8+ чел.** | ⚠️ Конфликты в коде. | ✅ Независимые деплои. |

**Ключевое:** при команде 1–3 разработчика микросервисы **увеличат** время
разработки в 2–3× из-за инфраструктурного оверхеда, а не ускорят.

## 4. Что делать вместо микросервисов

### Modular monolith с чёткими границами (уже реализовано)

Текущая структура уже близка к правильной:
- Сервисы не импортируют друг друга напрямую (кроме `ProjectService` для access-check)
- Формулы (`formulas/`) — чистые функции без доступа к БД
- Роутеры (`api/v1/`) — тонкий слой, делегируют сервисам

**Что улучшить:**

1. **Выделить `calculation_service` в отдельный процесс** — только если F-02/F-03 создадут CPU-нагрузку, и только через ProcessPoolExecutor (не отдельный контейнер).
2. **Background tasks через Redis Queue** — уже частично сделано в `task_service.py`. Можно вынести batch-операции в воркер.
3. **Read-only реплики для отчётов** — если генерация PDF/DOCX станет узким местом (сейчас — нет).

Всё это — **внутрипроцессное разделение**, не микросервисы.

### Когда реально понадобится микросервис

Единственный сценарий, где микросервис оправдан **архитектурно**, а не «по моде»:

**Go-сервис для тяжёлых расчётов (F-02, F-03)**

```
                    ┌──────────────┐
                    │  FastAPI     │  (Python — CRUD, auth, reports)
                    │  :8000       │
                    └──────┬───────┘
                           │ gRPC / HTTP
                           ▼
                    ┌──────────────┐
                    │  Calc Engine │  (Go — Crank-Nicolson, NSGA-II)
                    │  :9001       │
                    └──────────────┘
```

- **Причина:** Python (GIL) не справляется с 2–8 сек Crank-Nicolson. Go даёт 80–300 мс.
- **Когда:** при реализации F-02 или F-03 (2027+).
- **Граница:** Go-сервис — stateless pure function: получает params → возвращает results. Не ходит в БД.
- **Коммуникация:** gRPC (быстрее HTTP/JSON, строгая схема).

Но даже этот сценарий — **один** микросервис, а не «разбить всё на 10 сервисов».

## 5. Что НЕ делать

| Антипаттерн | Почему плохо для HeatCalc |
|---|---|
| **Сервис на каждую таблицу** (auth-svc, project-svc, object-svc…) | 90% операций требуют JOIN данных из 2–3 таблиц. Распределённые JOIN'ы — боль. |
| **Event-driven везде** (Kafka между всеми сервисами) | Добавляет 50–200 мс latency на каждое событие. Batch 400 объектов: 94 мс → 2–8 сек. |
| **API Gateway + Service Mesh** | Оверхед для 3 сервисов. Не нужно Istio/Linkerd для монолита. |
| **Разделение БД** (database per service) | Сейчас все данные связаны (object → heat_calc → elec_calc). Разделение сломает FOREIGN KEY и каскадное удаление. |

---

## 6. Итог

| Вопрос | Ответ |
|---|---|
| Разбивать ли монолит на микросервисы **сейчас**? | **Нет.** Монолит справляется. 94 мс на batch 400 объектов. |
| Выделять ли **отдельный Go-сервис** для расчётов? | **Да, но только при реализации F-02/F-03.** Не раньше 2027. |
| Что делать **сейчас** для масштабирования? | Горизонтальные реплики монолита (3× `docker compose up --scale backend=3`). |
| Когда пересмотреть решение? | Когда: (а) команда > 5 человек, (б) F-02 требует > 1 сек CPU, (в) нужен разный стек (Go). |

**Правило:** не микросервисы ради микросервисов. Микросервис — когда **доказана**
невозможность решить проблему в монолите. Для HeatCalc эта точка не достигнута.
