# TLT HeatCalc — Тактические улучшения UX и интерфейса

**Дата:** 2026-05-09  
**Статус:** Аналитическое предложение · Этап 0 — исследования  
**Назначение:** Рекомендации по улучшению повседневного пользовательского опыта  

---

## Введение

Стратегические фичи (BIM, ML, SCADA) — это рывок на годы вперёд. Но инженер,
работающий в HeatCalc каждый день по 6–8 часов, оценит не столько BIM-импорт,
сколько **отзывчивый интерфейс**, **быстрые фильтры**, **тёмную тему** (глаза
устают к вечеру) и **горячие клавиши** (руки не отрываются от клавиатуры).

Этот документ — 15 конкретных тактических предложений, нацеленных на
**сокращение трения** в повседневной работе. Каждое предложение занимает
1–3 спринта, может делаться параллельно, не требует изменения расчётного
ядра и даёт немедленный эффект для пользователя.

Ориентир — лучшие практики из Tableau, Notion, Linear, Google Sheets, VS Code,
Figma и других инструментов, где UX-полировка доведена до стандарта де-факто.

Ни одной строчки кода. Никаких правок в исходники. Только спецификации,
wireframe-описания и инженерные оценки.

## T-01. Тёмная тема и переключатель оформления

**Категория:** UI / Темы

**Приоритет:** P1 — тактический (быстрый выигрыш в восприятии продукта)

**Аналоги:** VS Code (система тем: system/light/dark/high-contrast, определяемая
по `prefers-color-scheme` автоматически), GitHub (три темы: light, dark dimmed,
dark high contrast), Figma (переключение тем в один клик из меню профиля),
Notion (следование системной теме + ручной override).

**Проблема, которую решаем:**

Инженер работает в HeatCalc по 6–8 часов в день. Белый фон на мониторе — это
~300 люкс светового потока в глаза. К концу дня — зрительная усталость,
снижение концентрации, рост ошибок. Особенно остро в зимний период (короткий
световой день, работа при искусственном освещении). Тёмная тема — это не
«красиво», а **эргономическая необходимость** для профессионального инструмента.

Текущий интерфейс жёстко завязан на светлую тему Ant Design. Тёмной альтернативы
нет.

**Инженерное описание:**

Три режима, переключаемых из дропдауна в header'е (иконка ☀/🌙/🖥):

- **🌙 Тёмная** — тёмный фон (#141414 / #1F1F1F), светлый текст, уменьшенная
  яркость цветовых акцентов (primary blue затемнён до #177ddc на тёмном фоне)
- **☀ Светлая** — текущая тема (без изменений в дизайне)
- **🖥 Системная** — следует за `prefers-color-scheme` (на Mac — автосмена
  при закате по Night Shift; на Windows — по настройкам темы)

Технически реализуется через:

1. **Ant Design 5 ConfigProvider** — `theme.algorithm: theme.darkAlgorithm` для
   мгновенного переключения **всех** antd-компонентов (таблицы, модалки, инпуты,
   кнопки) без ручного перекрашивания каждого компонента.
2. **CSS-переменные** для кастомных компонентов (тех, что не под antd —
   `Trajectory3DViewer`, `ThermalProfileChart`, `ObjectWizard`): переменные
   `--bg-primary`, `--text-primary`, `--border-color` переопределяются в
   `document.documentElement` при смене темы.
3. **Графики и диаграммы:** Plotly.js и ECharts получают тему при инициализации
   (`plotly.layout.template = 'plotly_dark'`; `echarts.registerTheme('heatcalc-dark',
   {...})`).
4. **Сохранение выбора** в `localStorage` (ключ `tlt-theme-preference`) и в
   профиле пользователя (серверное сохранение — чтобы тема следовала за
   пользователем между устройствами).

Дополнительно: **настраиваемый акцентный цвет** — пользователь выбирает из
палитры (синий / зелёный / оранжевый / фиолетовый) для персонализации
интерфейса (особенно ценно в white-label для корпоративных цветов заказчика).

**Технический контур:**

Фронтенд: `Ant Design 5 ConfigProvider` + `theme.darkAlgorithm` (уже встроено
в antd v5, работает из коробки с минимальными усилиями). Кастомные CSS-переменные:
добавить в `index.css` набор `:root` переменных для светлой темы, `[data-theme="dark"]`
для тёмной. Переключение: `ThemeContext` (React Context) или Zustand-слайс
`themeSlice`. Plotly/ECharts: при создании графика проверять тему и применять
соответствующий `layout.template` (Plotly) / `echarts.registerTheme` (ECharts).

Backend: никаких изменений. Опционально — эндпоинт `PUT /api/v1/user/preferences`
для сохранения темы на сервере (поле `theme` в `user_preferences` JSONB).

Сложность: Low (1.5 спринта — основное время уйдёт на полировку кастомных
компонентов и графиков; сама тема включается за день).

**Почему это «продвинуто»:**

Тёмная тема — это не rocket science, но это **сигнал качества**. Продукты
без тёмной темы в 2026 году воспринимаются как «сделанные на коленке».
Наличие авто-переключения (system follow) и акцентного цвета ставит HeatCalc
в один ряд с Figma/VS Code/Linear по уровню UI-полировки.

**Риски и ограничения:**

- Некоторые кастомные компоненты могут иметь жёстко закодированные цвета
  (#fff, #000 в inline-стилях). Потребуется аудит всех компонентов на предмет
  «зашитых» цветов — ~2–3 дня рутинной работы.
- Графики Plotly в тёмной теме требуют ручной настройки `paper_bgcolor`,
  `plot_bgcolor`, `font.color` — не всегда предсказуемо. Решение: создать
  тему Plotly один раз и применять глобально.
- Цветовая кодировка тепловых потерь (синий→красный) должна работать на
  обоих фонах. На тёмном фоне красный может «теряться». Решение: использовать
  perceptually uniform colormap (Viridis) вместо blue-red — она работает
  одинаково хорошо на светлом и тёмном фоне.

## T-02. Расширенные фильтры таблиц с сохранением пресетов

**Категория:** Таблицы и фильтры

**Приоритет:** P0 — стратегический (ежедневная экономия минут → часы в месяц)

**Аналоги:** Airtable (фильтры по каждой колонке с выбором оператора: contains,
equals, greater than, between), Google Sheets (filter views — сохранённые
конфигурации фильтров, переключаемые в один клик), Notion (фильтры в виде
«пилюль» под заголовком таблицы, наглядно видно активные фильтры), Linear
(сохранённые view с фильтрами как закладки).

**Проблема, которую решаем:**

Инженер работает с проектом из 50+ трубопроводов и 10+ резервуаров. Типичные
задачи: «показать только подземные трубы с теплопотерями > 100 Вт/м»,
«показать объекты с ошибкой электрорасчёта», «показать трубы с изоляцией ППУ».

Сегодня фильтрации нет вообще — инженер прокручивает таблицу глазами, ищет
нужные строки. Для 20+ объектов это работает. Для 50+ — время поиска нужной
строки растёт линейно. Для 100+ (лимит 50 пока, но в планах расширение) —
становится неработоспособно.

**Инженерное описание:**

**Quick Filter Bar** — строка над таблицей с «пилюлями» активных фильтров
(как в Notion/Airtable):

```
[🔍 Поиск...]  [Тип: Все ▼]  [Размещение: Все ▼]  [q, Вт/м: > 50]  [Статус: Ошибка ✕]  [+ Фильтр]
```

- Кнопка **«+ Фильтр»** — выпадающий список доступных колонок для фильтрации
- Каждая добавленная пилюля — Select с выбором оператора (=, ≠, >, <, between,
  contains, starts with, empty, not empty) и значения
- Пилюли можно убирать по одной (крестик) или все сразу («Сбросить»)
- Фильтры применяются мгновенно (без кнопки «Применить»)

**Сохранённые пресеты (Filter Views):**

Выпадающий список «🔖 Вид таблицы» с вариантами:

- «Все объекты» (без фильтров, по умолчанию)
- «⚠ Ошибки расчёта» (filter: `electrical_status = error`)
- «📍 Подземные» (filter: `placement = underground`)
- «🔥 Высокие потери» (filter: `q > 100`)
- «🛢 Резервуары» (filter: `object_type = tank`)
- «🔧 Требуют внимания» (filter: `insulation_material = other OR cable_status = error`)

Пользователь создаёт свой пресет: настраивает фильтры → «Сохранить как...» →
имя → пресет доступен всем пользователям проекта (для сотрудника — всем, кто
открыл проект). Владелец пресета может его удалить или сделать «общим».

Фильтры сохраняются в `localStorage` (persist между сессиями) и опционально в
БД для общих пресетов.

**Визуальная обратная связь:**

- Когда активны фильтры — строка фильтров подсвечивается (светло-синий фон
  в светлой теме), счётчик: «Показано 12 из 48 объектов»
- Если фильтры дали 0 результатов — Empty State с предложением изменить
  критерии

**Технический контур:**

Фронтенд: компонент `FilterBar.tsx` — строка с `antd Select` + `Input` +
`InputNumber` (в зависимости от типа колонки). Фильтры хранятся как массив
объектов `{field, operator, value}` в Zustand-слое `tableFilterSlice`.
Применение: `useMemo` поверх данных таблицы, фильтрация на фронте (для 50
объектов — мгновенно, бэкенд не нужен).

Сохранённые пресеты: `filterPresetsSlice` в Zustand + persist в localStorage.
Для общих пресетов (сотрудник): новая таблица `table_filter_presets (id,
project_id, created_by, name, filter_config JSONB, is_shared)` + API
`GET/POST/DELETE /api/v1/projects/{id}/filter-presets`.

Колонки для фильтрации определяются метаданными таблицы (из конфига колонок
`PipeTable.columns` / `TankTable.columns`).

Сложность: Medium (3 спринта — основная сложность в UI компоненте «пилюль»
и сохранении пресетов).

**Почему это «продвинуто»:**

Фильтры — это «must have» для любого табличного редактора. Их отсутствие —
это прямой сигнал «продукт сырой». Наличие сохранённых filter views поднимает
UX с уровня «Excel 2003» до «Airtable 2024». Инженер, настроивший 3–4
пресета («Ошибки», «Подземные», «ППУ-изоляция»), сокращает время навигации
по проекту с минут до секунд.

**Риски и ограничения:**

- Фильтрация на фронте для 50 объектов — мгновенно, для 500 — нужна
  пагинация или серверная фильтрация. Решение: при превышении 100 объектов
  — переходить на серверную фильтрацию (GET с query-параметрами).
- Колонки с вычисляемыми значениями (q, Q) требуют фильтрации по числовому
  значению, которое может быть результатом сложной формулы. Решение: q и Q
  уже вычислены и хранятся в состоянии — фильтруются как обычные числа.
- Сохранение пресетов в localStorage: если пользователь чистит кэш браузера
  — пресеты теряются. Решение: для зарегистрированных пользователей —
  автоматическая синхронизация пресетов на сервер (как часть профиля).

## T-03. Система горячих клавиш и shortcut cheat sheet

**Категория:** Клавиатурная навигация

**Приоритет:** P1 — тактический (power-user функция, даёт 2–3× ускорение)

**Аналоги:** VS Code (полная клавиатурная управляемость, Command Palette
Ctrl+Shift+P, shortcut cheat sheet по Ctrl+K Ctrl+S), Figma (десятки шорткатов
для каждого инструмента, cheat sheet по `?`), Linear (клавиатурная навигация
по issues: j/k стрелки, E edit, C create), Gmail (клавиатурные сокращения
для всех действий, включаемые одной настройкой).

**Проблема, которую решаем:**

Инженер вводит данные в форму SC-03 → нажимает «Добавить объект» мышью →
прокручивает таблицу мышью → кликает строку для редактирования → снова мышью
к кнопке «Сохранить». Каждое переключение «клавиатура → мышь → клавиатура»
стоит ~1.5–2 секунды и разрывает поток. За 8-часовой рабочий день это 200+
переключений = 5–7 минут чистых потерь + когнитивная нагрузка.

Power users (инженеры, работающие в HeatCalc каждый день) ожидают клавиатурной
управляемости на уровне VS Code/Excel.

**Инженерное описание:**

**Базовые шорткаты (всегда активны):**

| Клавиши | Действие | Контекст |
|---|---|---|
| `Ctrl+N` | Новый объект (очистить форму, фокус на первое поле) | Рабочий стол |
| `Ctrl+S` | Сохранить текущий объект (добавить или обновить) | Форма SC-03 |
| `Ctrl+Enter` | Запустить электрорасчёт | Рабочий стол |
| `Ctrl+Z` / `Ctrl+Shift+Z` | Undo / Redo | Рабочий стол (T-06) |
| `Ctrl+F` | Фокус в строку поиска по таблице | Рабочий стол |
| `Ctrl+D` | Дублировать выделенный объект | Таблица |
| `Delete` | Удалить выделенный объект (с подтверждением) | Таблица |
| `Escape` | Закрыть модалку / снять выделение / отменить редактирование | Глобально |
| `↑ ↓` | Навигация по строкам таблицы | Таблица |
| `Enter` | Редактировать выделенную строку (открыть в форме) | Таблица |
| `Tab / Shift+Tab` | Переход между полями формы | Форма SC-03 |
| `Ctrl+1..4` | Переключение CO1..CO4 | Электрорасчёт |
| `?` | Показать/скрыть cheat sheet (popup со всеми шорткатами) | Глобально |

**Command Palette (Ctrl+Shift+P / Cmd+Shift+P):**

Модальное окно поиска по всем действиям (как в VS Code). Пользователь нажимает
`Ctrl+Shift+P` → появляется поисковая строка → набирает «тёмная» → показывает
«Переключить тёмную тему», «Настройки темы». Набирает «экспорт» → «Экспорт в
CSV», «Экспорт в DXF», «Экспорт отчёта PDF».

Command Palette индексирует все доступные действия (кнопки, пункты меню,
переключатели) и позволяет запускать их с клавиатуры без знания точного
шортката.

**Cheat Sheet (по `?`):**

Модальное окно с таблицей всех доступных шорткатов, сгруппированных по
контексту (Глобальные, Форма объекта, Таблица, Электрорасчёт). Строка поиска
для фильтрации. Шорткаты, которые конфликтуют с браузерными (Ctrl+N — новое
окно в Chrome), снабжены пометкой «⚠ перехватывается».

**Настройка шорткатов:**

В профиле пользователя — страница «Горячие клавиши», где можно изменить любой
шорткат или отключить его. Изменения сохраняются в профиле и синхронизируются
между сессиями.

**Технический контур:**

Фронтенд: библиотека `react-hotkeys-hook` или `@tanstack/react-hotkeys` (лёгкие,
декларативные). Обёртка `useHotkeys(['ctrl+n', 'meta+n'], handler)`. Все
шорткаты регистрируются в едином модуле `utils/shortcuts.ts` с контекстной
привязкой (глобальные всегда, контекстно-зависимые — только когда фокус в
таблице / форме). Cheat Sheet: Ant Design Modal с таблицей, данные из
`shortcuts.ts`. Command Palette: `cmdk` (библиотека от создателей Vercel,
2 kB, доступна как `<Command>` компонент — такое же поведение, как в
VS Code/Linear/Raycast).

Backend: опционально — сохранение пользовательских переопределений шорткатов
в `user_preferences.shortcut_overrides` (JSONB).

Сложность: Low (2 спринта — регистрация 15–20 шорткатов + Command Palette
и Cheat Sheet).

**Почему это «продвинуто»:**

Горячие клавиши — это разделительная линия между «софтом для occasional
use» и «профессиональным инструментом». Инженер, который выучил 5–7 шорткатов,
работает в 2 раза быстрее и воспринимает HeatCalc как «свой инструмент», а не
«очередную веб-морду». Command Palette — это вишенка: даже не зная шортката,
пользователь может выполнить любое действие с клавиатуры.

**Риски и ограничения:**

- Конфликт с браузерными шорткатами: `Ctrl+N` — новое окно, `Ctrl+D` —
  закладка, `Ctrl+S` — сохранение страницы. Решение: `preventDefault()` +
  отображение в Cheat Sheet пометки «⚠ перехватывает браузерный шорткат».
- На Mac `Ctrl` и `Cmd` — разные клавиши, многие шорткаты должны дублироваться
  (`Ctrl+N` и `Cmd+N`). Решение: библиотека `react-hotkeys-hook` обрабатывает
  это автоматически через модификатор `mod`.
- Accessibility: шорткаты не должны мешать screen reader'ам (например,
  `Ctrl+Option+Arrow` в VoiceOver). Решение: не использовать модификатор
  Option/Alt в шорткатах.

## T-04. Множественный выбор и массовые операции

**Категория:** Таблицы и UX

**Приоритет:** P0 — стратегический (критично для проектов с 20+ объектами)

**Аналоги:** Google Sheets (выделение диапазона Shift+клик, выделение
отдельных строк Ctrl+клик, групповые операции над выделенным), Gmail
(чекбоксы строк, групповые действия в тулбаре над таблицей), Mac Finder
(пространственный выбор: Shift для диапазона, Cmd для individual),
Notion (multi-select rows → batch delete/duplicate/move).

**Проблема, которую решаем:**

Инженер хочет удалить 10 трубопроводов из 50. Сегодня: клик по строке 1 →
«Удалить» → подтвердить → клик по строке 2 → ... 10 раз. Это 30+ кликов
и 2–3 минуты вместо одного действия «выделил → удалил всё сразу».

Хуже — изменение параметра для группы объектов. «У всех 15 подземных труб
поменять грунт с суглинка на песок». Сегодня: зайти в каждую строку →
изменить → сохранить. 15 раз. Это 10–15 минут работы, которая должна
занимать 30 секунд.

**Инженерное описание:**

**Множественный выбор строк:**

- **Чекбоксы в первой колонке:** клик — выделить/снять строку. Чекбокс в
  заголовке — выделить/снять все.
- **Shift+клик:** выделить диапазон от последней выделенной до кликнутой
- **Ctrl/Cmd+клик:** добавить/убрать строку из выделения
- Визуально: выделенные строки получают синий фон (как в Gmail/Google Sheets)

**Массовые операции над выделенными строками:**

При выделении 2+ строк над таблицей появляется **Batch Action Bar**:

```
[Выделено: 12 объектов]   [Применить параметр ▼]   [Удалить выбранные]   [Дублировать]   [Экспорт выбранных]
```

**«Применить параметр»** — выпадающий список полей, доступных для массового
применения:

- «Толщина изоляции» → модалка: ввести значение → применить к 12 объектам
- «Материал изоляции» → Select → применить
- «Температура среды» → InputNumber → применить
- «Размещение (надземное/подземное)» → Select
- «Тип кабеля» → Select
- «Коэффициент запаса» → InputNumber

После применения — все затронутые объекты автоматически пересчитываются
(теплопотери + электрорасчёт). Прогресс-бар для длительных операций.

**Массовое удаление:** запрос подтверждения «Удалить 12 объектов?» с
перечислением имён (первые 5 + «...и ещё 7»).

**Массовое дублирование:** создаётся N копий выделенных объектов с пометкой
«(копия)».

**Взаимодействие с фильтрами (T-02):**

Если активен фильтр «⚠ Ошибки расчёта» и нажато «Выделить все» — выделяются
только отфильтрованные строки. Массовая операция применяется только к ним.
Это даёт мощный workflow: «Отфильтровать ошибки → выделить все → применить
другой тип кабеля → пересчитать».

**Технический контур:**

Фронтенд: состояние выделения в Zustand `selectionSlice: { selectedIds: Set<string>,
lastSelectedId }`. Хэндлеры onRowClick модифицированы: простой клик — выделить
одну строку (снять предыдущее), клик с Shift/Ctrl — модифицировать множество.
Batch Action Bar: условный рендеринг над таблицей при `selectedIds.size > 1`.

Массовое применение параметра: новый API-эндпоинт
`PUT /api/v1/projects/{id}/objects/batch` — принимает `{object_ids: [...],
field: "insulation_thickness", value: 0.06}`. Сервер обновляет объекты пачкой
(один SQL UPDATE ... WHERE id IN (...)), затем запускает пересчёт теплопотерь
и электрорасчёт для затронутых объектов. Возвращает `{updated: 12, failed: 0,
errors: []}`.

Массовое удаление: `DELETE /api/v1/projects/{id}/objects/batch` с телом
`{object_ids: [...]}`.

Сложность: Medium (3 спринта — фронтенд-логика выделения + batch API на бэке
+ тесты на batch-операции).

**Почему это «продвинуто»:**

Массовые операции — это «must have» для любого табличного редактора,
претендующего на профессиональное использование. Без них HeatCalc — это
«google sheets, где можно редактировать только по одной ячейке». С ними —
полноценный инструмент пакетной обработки, сокращающий время рутинных
операций в 10–20 раз.

**Риски и ограничения:**

- Batch-обновление 50 объектов с пересчётом теплопотерь и электрорасчётом
  может занять 3–5 секунд (50 × синхронные расчёты). Решение: запускать
  пересчёт асинхронно (background task), возвращать немедленно `202 Accepted`,
  на фронте — polling статуса или WebSocket-уведомление о завершении.
- Конфликт массового применения параметра с индивидуальными настройками
  объекта (например, для одного объекта из 12 изоляция задана как «Другое»
  с ручной λ). Решение: диалог подтверждения с предупреждением: «У 2 из 12
  объектов параметр задан вручную. Перезаписать?»
- Валидация: значение, валидное для 10 объектов, может быть невалидным для
  2 других. Решение: валидация на сервере, возврат errors с указанием
  конкретных объектов и причин.

## T-05. Контекстное меню (правый клик) для объектов

**Категория:** UX / Навигация

**Приоритет:** P1 — тактический

**Аналоги:** Mac Finder / Windows Explorer (контекстное меню — основной
способ взаимодействия с объектами), Google Sheets (правый клик по строке:
вставить, удалить, скрыть, копировать), VS Code file explorer (правый клик:
rename, delete, duplicate, reveal in finder), Notion (правый клик по блоку:
меню действий).

**Проблема, которую решаем:**

Все действия над объектом (редактировать, удалить, дублировать, создать на
основании) сегодня доступны только через кнопки в строке таблицы. Это
требует точного позиционирования мыши на маленькой иконке (16×16 px — закон
Фиттса не на нашей стороне). Для 50+ объектов это 50+ микро-двигательных
актов, каждый — потенциальный miss click.

Контекстное меню — это крупная цель (меню появляется там, где курсор) и
знакомый паттерн (пользователь ожидает его подсознательно).

**Инженерное описание:**

Правый клик по строке таблицы (или по объекту в 3D-вьювере из F-04) →
нативное или кастомное контекстное меню:

```
┌──────────────────────────────┐
│ ✏️  Редактировать         Enter│
│ 📋 Дублировать          Ctrl+D│
│ ──────────────────────────── │
│ 📤 Экспорт объекта как CSV   │
│ 🔗 Копировать параметры      │
│ ──────────────────────────── │
│ 🗑  Удалить              Del │
│ ──────────────────────────── │
│ ℹ️  Показать детали          │
│ 📍 Показать в 3D-трассе     │
│ 🔍 Найти похожие объекты    │
└──────────────────────────────┘
```

- **«Копировать параметры»** — копирует все параметры объекта в буфер обмена
  как JSON или human-readable текст. Можно вставить в форму нового объекта
  (T-06) или в Excel/чат коллеге.
- **«Найти похожие объекты»** — применяет фильтр T-02: `object_type = этот.тип
  AND placement = этот.размещение AND insulation_material = этот.материал`
- **«Показать в 3D-трассе»** — переключает на вкладку 3D (если F-04
  реализована) и центрирует камеру на выбранном объекте
- **«Экспорт объекта как CSV»** — скачивается CSV из одной строки (для
  передачи одного объекта коллеге без экспорта всего проекта)

Меню адаптивно: для строки с ошибкой расчёта добавляется пункт «⚠ Показать
причину ошибки». Для строки с кабелем «Авто» — «Подобрать кабель вручную».

В 3D-вьювере (F-04) контекстное меню на цилиндре трубы: те же пункты +
специфичные: «Измерить расстояние до...», «Показать температурный профиль».

**Технический контур:**

Фронтенд: кастомный компонент `ObjectContextMenu.tsx` на основе
`@radix-ui/react-context-menu` (headless, accessible, 2 kB) или Ant Design
`Dropdown` с `trigger={'contextMenu'}`. Меню рендерится абсолютно
позиционированным по координатам события `onContextMenu`. Действия меню
диспатчат те же экшены, что и кнопки в строке таблицы (через
`useHeatCalcMutations`).

Управление с клавиатуры: `Shift+F10` или клавиша Context Menu (между правым
Alt и Ctrl) открывает меню для выделенной строки.

Сложность: Low (1.5 спринта — чистый фронтенд).

**Почему это «продвинуто»:**

Контекстное меню — это не столько «фича», сколько **завершение UX-модели**
рабочего стола. Пользователь ожидает правого клика в любой таблице —
его отсутствие вызывает микрофрустрацию. Наличие контекстного меню с
контекстно-зависимыми пунктами (разные меню для труб/баков, для ошибок/OK)
— это уровень Figma/Notion.

**Риски и ограничения:**

- Конфликт с браузерным контекстным меню (по умолчанию правый клик открывает
  «Сохранить картинку / Просмотр кода»). Решение: `preventDefault()` на
  `onContextMenu` внутри таблицы и 3D-вьювера, но **не** на остальной странице
  (чтобы не бесить пользователя).
- Мобильные устройства: контекстное меню недоступно (нет правого клика).
  Решение: long-press на строке таблицы (200ms) → то же меню.

## T-06. Глобальный Undo/Redo с историей действий

**Категория:** UX / Навигация

**Приоритет:** P1 — тактический

**Аналоги:** Figma (глобальный Undo/Redo с историей до 100+ шагов, работает
для любого действия: переместить, изменить цвет, удалить), VS Code (Undo
для текстовых правок, но не для операций с файлами), Google Sheets (Undo
для изменений ячеек, ограниченная история), Gmail (Undo Send — единственное
действие, но самое нужное).

**Проблема, которую решаем:**

Инженер случайно удалил не тот объект. Или изменил толщину изоляции с 50 на
5 мм (опечатка) и сохранил. Сегодня: отменить нельзя. Нужно вручную
восстанавливать параметры по памяти или пересоздавать объект заново.

Undo — это не просто «вернуть как было». Это **психологическая безопасность**:
зная, что любое действие обратимо, пользователь действует смелее, быстрее,
меньше времени тратит на перепроверку каждого клика.

**Инженерное описание:**

Undo-стек на уровне проекта — запись всех мутирующих действий пользователя:

- `ADD_OBJECT(id, params)`
- `UPDATE_OBJECT(id, old_params, new_params)`
- `DELETE_OBJECT(id, params)`
- `REORDER_OBJECTS(old_order, new_order)`
- `BATCH_CALC_ELECTRICAL(previous_results)`
- `UPDATE_COMMON_DATA(old, new)`

Каждое действие сохраняется в стеке (максимум 50 последних действий, FIFO).
`Ctrl+Z` — откатывает последнее действие (выполняет обратную операцию:
для ADD → DELETE, для DELETE → ADD с восстановлением params, для UPDATE →
UPDATE с old_params). `Ctrl+Shift+Z` (или `Ctrl+Y`) — повторяет отменённое.

**UI обратной связи:**

- После выполнения Undo — тост: «Отменено: Удаление объекта "Труба Ø108 мм..."»
  с кнопкой «Вернуть» (Redo).
- В нижней панели (или tooltip) — счётчик: «12 действий в истории».
- При наведении на кнопку Undo (в toolbar) — выпадающий список последних
  5 действий с временем: «2 мин. назад: Изменена толщина изоляции 50→60 мм».

**Границы Undo:**

- Undo работает в пределах сессии. При перезагрузке страницы история
  сбрасывается (как в Figma).
- Undo не отменяет действия других пользователей (для collaborative editing
  в будущем — это отдельная сложная задача).
- Некоторые действия необратимы и не попадают в Undo-стек: экспорт файла,
  печать, копирование в буфер, изменение темы, изменение фильтров.

**Технический контур:**

Фронтенд: Zustand-слайс `undoSlice: { past: Action[], future: Action[] }`.
Каждая мутация, проходящая через store, автоматически записывается в
`undoSlice.past` через middleware `zundo` или кастомный `immer` middleware.
При Undo: извлечь последний элемент из `past`, выполнить обратную операцию,
переместить в `future`. При новом действии (не Undo/Redo) — очистить `future`.

Обратные операции: требуют, чтобы store хранил достаточно данных для
восстановления. Для DELETE — нужно сохранить полные params объекта перед
удалением. Для UPDATE — сохранить `old_params` перед обновлением.

API: Undo чисто фронтендовый — при Undo фронт отправляет обратный запрос на
сервер (для DELETE → POST create, для ADD → DELETE). Это означает, что Undo
— это полноценные API-запросы, не мгновенные. Для мгновенного Undo в пределах
2–3 секунд — оптимистичное обновление (сначала меняем UI, потом шлём запрос).

Сложность: Medium (3 спринта — основная сложность в корректной реализации
`past/future` для всех типов действий, особенно для пересчёта результатов
теплопотерь).

**Почему это «продвинуто»:**

Undo — это архитектурное решение, а не косметика. Оно требует переосмысления
всего flow мутаций в приложении. Наличие Undo поднимает HeatCalc с уровня
«веб-формы» до уровня «интерактивного редактора» (Figma, Photoshop, VS Code).
Это одна из тех фич, которую пользователь не замечает, пока она есть — но
остро ощущает, когда её нет.

**Риски и ограничения:**

- Undo для batch-операций (T-04: «применить параметр к 12 объектам») —
  это 12 индивидуальных обратных запросов или 1 batch-запрос. Второе
  предпочтительнее. Решение: batch-операции записываются в Undo-стек как
  единое действие с batch-обратным вызовом.
- Конфликт: пользователь делает Undo для объекта, который уже изменён другим
  пользователем (при collaborative editing). Решение: в текущей модели
  (однопользовательской) конфликта нет. В будущем — optimistic locking
  (version number на объекте).
- Не все действия стоит откатывать: Undo электрорасчёта → нужно ли
  пересчитывать заново или восстановить кэшированный результат? Решение:
  хранить предыдущий `electrical_calculation` в стеке и восстанавливать без
  пересчёта.

## T-07. Кастомизация колонок таблицы: видимость, порядок, пресеты

**Категория:** Таблицы и UX

**Приоритет:** P0 — стратегический (базовая потребность любого табличного
инструмента)

**Аналоги:** Google Sheets (показ/скрытие колонок через правый клик по
заголовку, drag для изменения порядка), Airtable (кнопка «Hide fields» в
тулбаре таблицы, переключение видимости полей чекбоксами), Notion (кнопка
«Properties» — показать/скрыть свойства базы данных), Jira (настройка
колонок через «Configure board»).

**Проблема, которую решаем:**

Текущая таблица объектов показывает фиксированный набор колонок. Но для
разных этапов работы нужны разные колонки:

- При вводе геометрии: диаметр, толщина изоляции, длина — **важны**. Ток
  кабеля — **не нужен** (отвлекает).
- При анализе теплопотерь: q (Вт/м), Q (Вт), материал изоляции — **важны**.
  Номер задачи — **не нужен**.
- При сравнении вариантов CO: марка кабеля, мощность, длина кабеля — **важны**.
  Геометрия изоляции — менее важна.

Фиксированный набор колонок вынуждает инженера горизонтально скроллить
таблицу в поисках нужных данных или игнорировать лишние колонки (визуальный
шум).

**Инженерное описание:**

**Переключатель видимости колонок:**

Кнопка «⚙ Колонки» над таблицей → выпадающий список с чекбоксами для каждой
доступной колонки:

```
☑ Наименование
☑ Тип объекта
☑ Диаметр, мм
☑ Длина, м
☐ Толщина стенки, мм      ← скрыта
☑ Толщина изоляции, мм
☑ Материал изоляции
☑ q, Вт/м
☑ Q, Вт
☐ Марка кабеля             ← скрыта (работаем только с теплопотерями)
☐ Ток, А
☐ Статус расчёта
```

Минимум одна колонка всегда видна (блокировка снятия последнего чекбокса).

**Drag-and-drop для порядка колонок:**

В том же выпадающем списке — колонки можно перетаскивать (drag handle слева),
меняя их порядок в таблице. Или — drag заголовка колонки прямо в таблице
(как в Google Sheets).

**Пресеты колонок:**

Выпадающий список «📋 Вид колонок» с предустановками:

- «🔢 Геометрия» — только геометрические колонки (диаметр, длина, толщина)
- «🌡 Теплотехника» — геометрия + изоляция + q/Q
- «⚡ Электрика» — марка кабеля, мощность, длина кабеля, ток
- «📋 Полный» — все колонки
- «⭐ Мой вид» — сохранённый пользователем кастомный набор + порядок колонок

Пресеты сохраняются в localStorage и профиле пользователя.

**Сохранение состояния:**

При перезагрузке страницы — последний набор колонок и их порядок
восстанавливаются. Для пользователей с разными проектами — пресеты общие
(одна настройка для всех проектов, так как структура колонок одинакова).

**Технический контур:**

Фронтенд: состояние видимости и порядка колонок в Zustand-слайсе
`tableColumnsSlice: { visibleColumns: string[], columnOrder: string[],
activePreset: string }`. Конфигурация всех доступных колонок для каждого
типа таблицы (PipeTable, TankTable, ElecCalcTable) — в отдельных файлах
`tableColumnsConfig.ts`.

Реализация: Ant Design Table поддерживает скрытие колонок через
`column.hidden` и не поддерживает drag-and-drop заголовков из коробки.
Использовать `@dnd-kit` (уже в проекте) для DnD заголовков + кастомный
селектор видимости. Пресеты: выпадающий список, фильтрующий колонки по
категориям.

Backend: опционально — API `PUT /api/v1/user/preferences` с полем
`table_columns_presets` (JSONB) для синхронизации между устройствами.

Сложность: Low (2 спринта — почти чистый фронтенд).

**Почему это «продвинуто»:**

Кастомизация колонок — это ожидание по умолчанию от любого табличного
инструмента. Её отсутствие — это первое, что замечает пользователь при
переходе из Excel в веб-приложение. Наличие пресетов «Геометрия /
Теплотехника / Электрика» показывает глубокое понимание рабочего процесса
инженера.

**Риски и ограничения:**

- Не все колонки имеют смысл для обеих таблиц (PipeTable vs TankTable):
  «Диаметр» для трубы ≠ «Диаметр / Длина / Ширина» для резервуара.
  Решение: отдельные конфиги колонок для каждого типа таблицы.
- Колонка «Наименование» должна быть всегда первой и всегда видимой (это
  первичный идентификатор строки). Решение: зафиксировать первую колонку
  на уровне конфига (не давать скрывать/перемещать).
- При экспорте таблицы (скриншот, CSV) — экспортируются только видимые
  колонки. Решение: информационная подпись «Экспортируется 8 из 12 колонок».

## T-08. Глобальный поиск по объектам с быстрым переходом

**Категория:** Поиск и навигация

**Приоритет:** P0 — стратегический

**Аналоги:** VS Code (Ctrl+P — быстрый поиск по файлам с fuzzy matching,
мгновенный переход), Figma (Cmd+/ — поиск по всем меню, слоям, страницам),
Linear (Cmd+K — поиск по issues с fuzzy matching и навигацией стрелками),
Spotlight на macOS (глобальный поиск по системе).

**Проблема, которую решаем:**

В проекте 48 объектов: трубы «Труба Ø108 мм (DN100)...», «Труба Ø57 мм
(DN50)...», баки «Бак цил. Ø2000 мм...». Инженер помнит, что где-то была
«труба с ППУ изоляцией 80 мм на участке 14». Чтобы найти её, нужно:

1. Скроллить таблицу глазами — 20–30 секунд
2. Или применять фильтры (T-02) — 10 секунд

Глобальный поиск (Ctrl+P / Cmd+K) сокращает это до 1–2 секунд.

**Инженерное описание:**

`Ctrl+P` (или `Cmd+K` для единообразия с Linear/VS Code) → модальное окно
поиска в центре экрана (как Spotlight):

```
┌────────────────────────────────────────────┐
│ 🔍 ппу 80                                  │
│ ────────────────────────────────────────── │
│ 📍 Труба Ø108 мм (DN100), δ=80 мм, ППУ...  │
│    q=32 Вт/м · ТЛТ-50 · надземная          │
│                                             │
│ 📍 Труба Ø57 мм (DN50), δ=80 мм, ППУ, L... │
│    q=28 Вт/м · ТЛТ-40 · подземная          │
│                                             │
│ 📍 Бак цил. Ø2000 мм×H3000 мм, δ=80 мм...  │
│    Q=1240 Вт · ТЛТ-100 · надземный         │
└────────────────────────────────────────────┘
```

**Алгоритм поиска:**

- Fuzzy matching по подстроке: «ппу 80» находит «ППУ» + «80 мм» в любой
  части строки (поиск по полям: наименование, материал изоляции, толщина
  изоляции, марка кабеля, диаметр, длина)
- Ранжирование: точное совпадение > совпадение в начале имени > совпадение
  в середине. Строки с ошибками расчёта поднимаются в топ (чаще всего ищут
  именно их)
- Последние 5 выбранных объектов показываются первыми при пустом поисковом
  запросе («Recent»)

**Навигация:**

- `↑ ↓` — перемещение по результатам
- `Enter` — переход к объекту: фокус на строке в таблице + прокрутка к ней +
  загрузка параметров в форму SC-03 для редактирования
- `Escape` — закрыть поиск

**Индексация:**

При каждом изменении объектов (добавление/обновление/удаление) строится
поисковый индекс в памяти (Fuse.js или Lunr.js). Для 50 объектов — индекс
строится мгновенно (< 5 мс), поиск — < 1 мс. Для 500+ — использовать
Web Worker для индексации вне основного потока.

**Технический контур:**

Фронтенд: `cmdk` (библиотека Command Palette, 2 kB, accessibility из
коробки — та же, что и для Command Palette в T-03) или кастомный модал
с `Fuse.js` (fuzzy search, 5 kB). Индекс: строится при изменении объектов
(Zustand-подписка), хранится в ref (useRef) для избежания ререндеров.
Результаты: рендерятся как виртуальный список для производительности.

Backend: не требуется (поиск по 50 объектам не нуждается в серверной
индексации). Для будущего — optionally, полнотекстовый поиск PostgreSQL
(`tsvector` + GIN index) при превышении 500 объектов на проект.

Сложность: Low (1.5 спринта — практически чистый фронтенд, `cmdk` покрывает
90% функционала из коробки).

**Почему это «продвинуто»:**

Глобальный поиск — это не просто «строка поиска». Это паттерн «Command
Palette», который стал стандартом де-факто в профессиональных инструментах
(VS Code, Figma, Linear, Notion). Наличие Cmd+K/P с fuzzy matching и
мгновенным переходом к объекту — это один из самых заметных сигналов
«профессионального инструмента» для нового пользователя.

**Риски и ограничения:**

- Индексация через Fuse.js для 50 объектов — мгновенно, для 1000+ —
  может занимать 50–100 мс. Решение: дебаунсинг перестроения индекса
  (300 мс после последнего изменения), Web Worker для индексации вне
  основного потока.
- Поиск только по имени и ключевым полям — пользователь может искать по
  полю, которого нет в индексе (например, «ток 12.5 А»). Решение: включать
  в индекс все строковые представления объекта (toString() объекта).
- Конфликт шортката: `Ctrl+P` — печать в браузере. Решение:
  `preventDefault()`, альтернативный шорткат `Cmd+K` (как в Linear).

## T-09. Центр уведомлений и улучшенные тосты

**Категория:** Уведомления и обратная связь

**Приоритет:** P1 — тактический

**Аналоги:** Notion (уведомления в боковой панели: mentions, changes,
comments — с группировкой по времени и возможностью клика для перехода),
Linear (тосты с кнопкой действия: «Issue created — [View] [Undo]»),
Figma (тосты только для критических действий, ненавязчивые), GitHub
(колокольчик уведомлений с синим индикатором непрочитанных).

**Проблема, которую решаем:**

Текущие тосты (Ant Design `message.success/error`) появляются на 3 секунды
вверху экрана и исчезают. Если инженер отвернулся или моргнул — он пропустил
тост «Электрорасчёт завершён, 3 ошибки». Приходится идти на страницу
электрорасчёта и проверять вручную.

Нет истории уведомлений: «О чём система сообщала 10 минут назад?» — ответа нет.

**Инженерное описание:**

**Центр уведомлений (колокольчик 🔔 в header'е):**

- Иконка с бейджем непрочитанных уведомлений (синий кружок с числом)
- Клик → выпадающая панель (Dropdown) с лентой уведомлений:

```
🔔 Уведомления                    [Отметить все прочитанными]
──────────────────────────────────────
⚡ 2 мин. назад
   Электрорасчёт завершён (CO2)
   42 объекта · 3 ошибки    [Смотреть →]

⚠ 5 мин. назад
   Импорт из XLSX завершён
   Создано 28 объектов · 2 пропущено    [Смотреть →]

✅ 10 мин. назад
   Спецификация сформирована
   12 позиций    [Смотреть →]

📥 Вчера
   Проект «Нефтепровод уч. 14» экспортирован в CSV
──────────────────────────────────────
⚙ Настройки уведомлений
```

- Каждое уведомление кликабельно — ведёт на соответствующую страницу/объект
- Непрочитанные — с лёгким голубым фоном
- Группировка: сегодня / вчера / на этой неделе

**Улучшенные тосты:**

- Тосты с кнопками действий: «Объект удалён — [Отменить ✕]» (T-06)
- Тосты с прогресс-баром для длительных операций: «Импорт XLSX... 15/28»
- Тосты с ссылкой: «Электрорасчёт завершён — [Открыть результаты →]»
- Sticky-тосты для критических ошибок (не исчезают автоматически)

**Настройки уведомлений:**

В профиле пользователя — страница «Уведомления» с чекбоксами:

```
☑ Электрорасчёт завершён (тост)
☑ Электрорасчёт с ошибками (тост + колокольчик)
☐ Импорт завершён (тост)
☑ Спецификация сформирована (тост)
☑ Проект экспортирован (тост)
☐ Системные уведомления (обновление справочников)
```

**Технический контур:**

Фронтенд: Zustand-слайс `notificationSlice: { notifications: Notification[],
unreadCount: number }`. При каждом тосте — запись добавляется в слайс.
Тосты — Ant Design `notification` (более богатый API, чем `message`:
поддерживает `btn`, `duration: 0` для sticky). Колокольчик: Ant Design
`Badge` + `Dropdown`, список уведомлений — виртуальный (для
производительности при 100+ уведомлениях).

Backend: опционально — сохранение настроек уведомлений в
`user_preferences.notification_settings` (JSONB). Сами уведомления —
чисто фронтендовые (persist в IndexedDB/localeStorage, очищаются старше
30 дней).

Сложность: Low (2 спринта — фронтенд).

**Почему это «продвинуто»:**

Центр уведомлений — это переход от «fire and forget» (показал тост и забыл)
к асинхронной модели взаимодействия: система работает, инженер занимается
другим делом, а потом возвращается и видит историю всех событий. Это
особенно важно для фоновых операций (импорт, batch-расчёт), которые могут
занимать минуты.

**Риски и ограничения:**

- При перезагрузке страницы история уведомлений теряется (если не
  синхронизируется с сервером). Решение: сохранять в IndexedDB, при
  загрузке страницы восстанавливать последние 50 уведомлений.
- Слишком много уведомлений при активной работе (batch-операции на 50
  объектов). Решение: дедупликация (схожие уведомления в течение 1 минуты
  группируются: «Обновлено 12 объектов» вместо 12 отдельных тостов).
- Колокольчик может отвлекать частыми обновлениями счётчика. Решение:
  throttle — обновление не чаще 1 раза в 2 секунды.

## T-10. Пользовательские предпочтения и значения по умолчанию

**Категория:** Персонализация

**Приоритет:** P1 — тактический

**Аналоги:** VS Code (глобальные настройки через settings.json и UI,
синхронизация через Settings Sync), Google Sheets (региональные настройки:
десятичный разделитель, формат даты, язык формул), Jira (профиль
пользователя: часовой пояс, язык, уведомления, видимость колонок).

**Проблема, которую решаем:**

Каждый раз, добавляя новый объект, инженер выбирает:

- Материал изоляции: «Минеральная вата» (а он всегда использует ППУ)
- Размещение: «Надземное» (а у него все трубы подземные)
- Напряжение: «220 В» (а проект на 380 В)
- Коэффициент запаса: 1.1 (а в организации принят 1.15)

Эти повторяющиеся выборы — 5–10 секунд на каждый новый объект. Для 50
объектов — 4–8 минут рутины в день. Это микрофрустрация: «почему система
не запоминает мои предпочтения?»

**Инженерное описание:**

**Страница «Мои настройки»** (в профиле пользователя) с секциями:

**Значения по умолчанию для новых объектов:**

```
Материал изоляции:     [ППУ (polyurethane) ▼]
Толщина изоляции:      [50 мм                ]
Размещение:            [Подземное ▼]
Напряжение питания:    [380 В ▼]
Коэффициент запаса:    [1.15                 ]
Температура среды:     [−35 °C              ]
Количество слоёв изол.: [1 ▼]
Тип кабеля:            [Саморегулирующийся ▼]
```

Эти значения автоматически предзаполняют форму SC-03 при создании нового
объекта. Пользователь может переопределить любое поле в форме.

**Региональные настройки:**

```
Единицы измерения:     [Метрические (м, мм, °C) ▼]
Десятичный разделитель: [Точка (1.5) ▼ / Запятая (1,5)]
Формат даты:           [ДД.ММ.ГГГГ ▼]
Язык интерфейса:       [Русский ▼]
```

**Рабочие настройки:**

```
☑ Автосохранение проекта каждые 5 минут
☑ Подтверждение при удалении объекта
☐ Автоматический пересчёт при изменении объекта
☑ Показывать подсказки в полях формы
```

**Синхронизация:**

Настройки сохраняются в профиле пользователя на сервере и синхронизируются
между сессиями и устройствами. При входе с другого компьютера — настройки
подтягиваются автоматически.

**Технический контур:**

Фронтенд: Zustand-слайс `preferencesSlice` с persist в localStorage +
периодическая синхронизация с сервером (при изменении → debounce 2 сек →
PUT на сервер; при старте → GET с сервера, merge с localStorage —
сервер выигрывает при конфликте). Страница настроек: `PreferencesPage.tsx`
с формой из Ant Design `Form`.

Backend: таблица `user_preferences (user_id UUID PK, preferences JSONB,
updated_at)`. API: `GET/PUT /api/v1/user/preferences`. Значения по умолчанию
применяются на фронте при создании нового объекта (мёрджат `default_params`
из preferences с пустой формой).

Сложность: Medium (2.5 спринта — backend + фронт + синхронизация +
конфликт-резолюция).

**Почему это «продвинуто»:**

Персонализация — это невидимая фича, которая работает на удержание.
Пользователь, настроивший HeatCalc «под себя», с меньшей вероятностью
переключится на конкурента — даже если тот предлагает лучшие формулы.
Эффект «IKEA»: мы ценим то, во что вложили свой труд (пусть даже это
просто настройка параметров по умолчанию).

**Риски и ограничения:**

- Конфликт: значение по умолчанию может противоречить общим первичным
  данным проекта. Решение: общие первичные данные проекта имеют приоритет
  над пользовательскими предпочтениями (с предупреждением: «Значение
  переопределено настройками проекта»).
- Синхронизация между вкладками: если пользователь открыл HeatCalc в двух
  вкладках, изменение настроек в одной должно отразиться в другой. Решение:
  `BroadcastChannel API` или `window.addEventListener('storage')` для
  синхронизации между вкладками.

## T-11. Скелетоны загрузки и оптимистичный UI

**Категория:** Производительность восприятия

**Приоритет:** P1 — тактический

**Аналоги:** Facebook (скелетоны — серые прямоугольники на месте контента,
создают иллюзию быстрой загрузки), Notion (оптимистичный UI: при создании
блока он появляется мгновенно, запрос на сервер уходит в фоне), Linear
(скелетоны + оптимистичные обновления для всех действий), antd (Skeleton
компонент).

**Проблема, которую решаем:**

При открытии проекта на медленном соединении (3G в полевых условиях, VPN
в корпоративной сети) пользователь видит:
1. Пустой экран — 0–0.5 сек
2. Спиннер — 0.5–3 сек (загрузка объектов)
3. Таблица появляется рывком

Субъективно это воспринимается как «медленно». Объективно 2–3 секунды
загрузки — норма для SPA, но **воспринимаемая** производительность может
быть улучшена на порядок с помощью скелетонов и оптимистичного UI.

**Инженерное описание:**

**Скелетоны (Skeleton Loading):**

Вместо спиннера — серые плейсхолдеры, повторяющие форму контента:

- Для таблицы объектов: 5–8 строк из серых прямоугольников разной ширины
  (имитация строк таблицы с разной длиной текста)
- Для формы SC-03: серые прямоугольники на месте полей ввода
- Для графиков: серый прямоугольник на месте графика с лёгкой анимацией
  (пульсация)

Ant Design 5 предоставляет `<Skeleton>` из коробки — используется везде,
где есть асинхронная загрузка.

**Оптимистичный UI:**

Действия пользователя отражаются в интерфейсе **немедленно**, не дожидаясь
ответа сервера:

- **Создание объекта:** строка появляется в таблице мгновенно с пометкой
  «сохраняется...» (спиннер в ячейке имени). Серверный запрос уходит в фоне.
  При успехе — пометка исчезает. При ошибке — строка подсвечивается красным,
  тост: «Не удалось сохранить объект. [Повторить] [Удалить]».
- **Удаление объекта:** строка исчезает мгновенно с анимацией (fade out).
  Тост: «Объект удалён — [Отменить]». Серверный запрос уходит в фоне. При
  ошибке — строка возвращается.
- **Изменение параметра:** поле в форме обновляется мгновенно, кнопка
  «Сохранить» меняется на «Сохранение...». При успехе — «Сохранено ✓».
  При ошибке — «Ошибка сохранения — [Повторить]».
- **Запуск электрорасчёта:** кнопка меняется на «Расчёт... 12/48» с
  прогресс-баром. Результаты в таблице появляются по мере готовности
  (стриминг через WebSocket/SSE).

**Технический контур:**

Скелетоны: использование `<Skeleton>` из antd для всех асинхронных компонентов.
Обёртка `<Suspense>` + `<Skeleton>` для code-splitted страниц.

Оптимистичный UI: TanStack Query v5 (уже в стеке) поддерживает
`optimisticUpdate` через `onMutate` в `useMutation`. При мутации:
1. `onMutate`: отменить исходящие запросы (cancelQueries), сохранить
   предыдущее состояние (snapshot), применить оптимистичное обновление кэша
2. `onError`: откатить кэш к сохранённому снапшоту
3. `onSettled`: инвалидировать запрос (refetch для консистентности)

Прогресс-бар для электрорасчёта: бэкенд возвращает `202 Accepted` с
`task_id`. Фронт поллит `GET /api/v1/tasks/{task_id}` каждые 2 секунды
или подписывается на WebSocket `ws://.../tasks/{task_id}/progress`.

Сложность: Medium (2 спринта — скелетоны простые, основная сложность в
оптимистичных обновлениях и обработке ошибок).

**Почему это «продвинуто»:**

Скелетоны и оптимистичный UI — это разница между «приложение грузится»
и «приложение реагирует мгновенно». На медленных каналах связи (полевые
условия, удалённые месторождения) разница в восприятии — с «тормозит»
до «летает». Это не меняет функциональность, но радикально меняет
**удовлетворённость** пользователя.

**Риски и ограничения:**

- Оптимистичный UI требует аккуратной обработки ошибок: если optimistic
  update прошёл, а сервер вернул 500 — нужно откатить UI и показать
  ошибку. Забытый откат = неконсистентное состояние. Решение: TanStack
  Query `onError` + `rollback` — стандартный паттерн, покрытый тестами.
- Оптимистичное удаление: если серверный запрос упал, а строка уже
  исчезла — строка возвращается с анимацией. Это может выглядеть дёргано.
  Решение: задержка оптимистичного удаления на 300 мс (пользователь не
  заметит, а сервер успеет подтвердить).
- Скелетоны требуют знания структуры контента до его загрузки. Для
  таблицы объектов — это предсказуемо. Для динамических страниц — нет.
  Решение: для непредсказуемых страниц — fallback на спиннер.

## T-12. Специальные возможности (a11y): screen reader, фокус, ARIA

**Категория:** Доступность

**Приоритет:** P1 — тактический (социальная ответственность + требования
госзаказчиков)

**Аналоги:** GOV.UK Design System (образцовая accessibility: все компоненты
протестированы с JAWS/NVDA/VoiceOver, colour contrast AAA), Deque Systems
(инструменты axe-core для автоматического тестирования a11y), Microsoft
Fluent UI (встроенная accessibility: FocusZone, ARIA-разметка, keyboard
navigation model).

**Проблема, которую решаем:**

Госзаказчики РФ (и крупные корпорации) всё чаще включают требования
доступности в ТЗ на ПО — особенно после того, как ГОСТ Р 52872-2019
(аналог WCAG 2.1) стал обязательным для госинформационных систем.
Несоблюдение = формальная причина для отклонения продукта на тендере.

Кроме формальных требований: среди инженеров-проектировщиков есть люди с
ограниченными возможностями (слабовидящие, моторика). Инструмент, который
они **не могут** использовать — это потерянные пользователи и репутационный
ущерб.

**Инженерное описание:**

**Screen Reader поддержка:**

- Все интерактивные элементы (кнопки, инпуты, селекты, строки таблицы)
  имеют корректные ARIA-роли и лейблы
- Таблица объектов: `role="table"`, `role="row"`, `role="cell"` + скрытые
  заголовки колонок для screen reader'ов (`aria-label` на каждой ячейке)
- Форма SC-03: каждое поле имеет `<label>` (видимый или `aria-label`),
  ошибки валидации связаны с полем через `aria-describedby`
- Графики: альтернативное текстовое описание (`aria-label` или скрытый
  текстовый блок с таблицей данных графика)
- Динамические обновления (тосты, модалки, прогресс-бар): используют
  ARIA live regions (`aria-live="polite"` для некритичных, `="assertive"`
  для ошибок) — screen reader зачитывает изменения

**Управление фокусом (focus management):**

- Tab/Shift+Tab — последовательный переход между интерактивными элементами
  в логическом порядке (форма → таблица → боковая панель)
- При открытии модалки — фокус перемещается внутрь модалки, при закрытии —
  возвращается на элемент, который её вызвал (focus trap)
- В таблице: `↑ ↓` для навигации по строкам (с T-03), фокусное кольцо
  (outline) на активном элементе
- Skip-to-content ссылка (скрытая, видна только при фокусе) в начале
  страницы: «Перейти к содержимому / к таблице объектов / к форме»

**Цветовой контраст (colour contrast):**

- Все текстовые элементы соответствуют WCAG AA (contrast ratio ≥ 4.5:1
  для нормального текста, ≥ 3:1 для крупного)
- Тепловая карта (F-04) не должна быть единственным носителем информации:
  цвет всегда дополняется числовым значением в tooltip
- Ошибки обозначаются не только цветом (красная строка), но и иконкой (⛔)
  и текстом

**Автоматическое тестирование a11y:**

- В CI добавлен шаг: `npx axe --exit` (или `@axe-core/react` для unit-тестов)
  на каждую страницу приложения
- ESLint-плагин `eslint-plugin-jsx-a11y` для проверки ARIA-атрибутов
  на этапе написания кода

**Технический контур:**

Фронтенд: Ant Design 5 имеет базовую accessibility из коробки (ARIA на
всех компонентах), но требуется аудит и дополнение. Инструменты:
`@axe-core/react` (runtime-проверки в dev-режиме), `eslint-plugin-jsx-a11y`
(статический анализ), `react-focus-lock` для focus trap в модалках,
`@radix-ui/react-roving-focus` для клавиатурной навигации в таблице.
Skip-to-content: простой `<a href="#main-content">` с CSS `sr-only`
(видимый при фокусе).

Тестирование: ручное с VoiceOver (macOS) и NVDA (Windows), автоматическое
через `cypress-axe` (если используется Cypress для E2E) или `@axe-core/playwright`.

Backend: никаких изменений (accessibility — чисто фронтенд-задача).

Сложность: Medium (3 спринта — аудит + исправления + тестирование; a11y —
это не фича, а сквозное качество, требующее касания каждого компонента).

**Почему это «продвинуто»:**

Accessibility — это не «фича для 1% пользователей». Это:
- Формальное требование для госзаказчиков (= деньги)
- Маркер качества продукта (Figma, Linear, Stripe — все имеют отличную a11y)
- Защита от legal risk (в США — lawsuits за недоступность веб-приложений,
  в РФ — формальная причина отклонения на тендере)

**Риски и ограничения:**

- Полное соответствие WCAG 2.1 AA — это 50+ критериев, из которых часть
  требует дизайнерских решений (цветовой контраст), а не только кода.
  Решение: сфокусироваться на 20 критических критериях в первом релизе,
  остальные — роадмап.
- Ant Design закрывает ~60% требований a11y автоматически; кастомные
  компоненты (ObjectWizard, графики) — зона ответственности разработчика.
- Тестирование с реальными screen reader'ами (VoiceOver, NVDA) имеет
  learning curve — разработчики должны научиться ими пользоваться, иначе
  тестирование будет неэффективным.

## T-13. Мобильная адаптация таблиц и touch-жесты

**Категория:** Мобильность

**Приоритет:** P2 — на вырост (дополняет F-09 — мобильное PWA)

**Аналоги:** Google Sheets mobile (таблица адаптируется под ширину экрана:
колонки сужаются, горизонтальный скролл с заморозкой первой колонки),
Airtable mobile (таблица превращается в «карточки» — каждая строка
становится карточкой с вертикальным скроллом), Notion mobile (база данных
отображается как список карточек с возможностью раскрытия).

**Проблема, которую решаем:**

Инженер на стройплощадке открывает HeatCalc на планшете (iPad / Android
10"). Таблица из 10 колонок не помещается на экран 1024 px ширины —
горизонтальный скролл. Форма SC-03 занимает весь экран, таблица — под ней,
нужно постоянно скроллить туда-сюда. Кнопки мелкие для пальцев.

Даже без полноценного мобильного PWA (F-09) базовая мобильная адаптация
делает продукт **ситуативно доступным** — проверить параметр объекта со
смартфона, показать спецификацию заказчику на планшете.

**Инженерное описание:**

**Адаптивная таблица (responsive table):**

При ширине экрана < 1024 px таблица переключается в режим **«карточек»**:

- Каждая строка становится вертикальной карточкой
- Поля отображаются как label: value пары
- Карточки скроллятся вертикально

```
┌────────────────────────────┐
│ Труба Ø108 мм (DN100)      │
│ ────────────────────────── │
│ Тип:       Трубопровод     │
│ Диаметр:   108 мм          │
│ Длина:     50 м            │
│ Изоляция:  Минвата, 50 мм  │
│ q:         42 Вт/м         │
│ Q:         2 310 Вт        │
│ Кабель:    ТЛТ-50, 55 м    │
│ Статус:    ✅ Рассчитано    │
│ ────────────────────────── │
│ [Редактировать] [Удалить]  │
└────────────────────────────┘
```

При ширине < 640 px (смартфон) — карточки занимают 100% ширины, кнопки
действий крупнее (min 44×44 px — рекомендация Apple HIG для touch targets).

Свайп влево по карточке — показать кнопки «Удалить» / «Дублировать»
(паттерн iOS Mail). Свайп вправо — «Редактировать».

**Адаптивная форма SC-03:**

При ширине < 1024 px секции формы (Геометрия, Изоляция, Температура, Электрика)
переключаются в режим **аккордеона**: по умолчанию открыта секция «Геометрия»,
остальные свёрнуты. Пользователь тапает по заголовку секции → она
разворачивается, предыдущая сворачивается. Это экономит вертикальное
пространство.

**Touch-жесты для таблицы (планшет):**

- Pull-to-refresh: потянуть вниз → перезагрузка данных проекта
- Pinch-to-zoom в 3D-вьювере (F-04)
- Long-press на строке → контекстное меню (T-05)

**Технический контур:**

Фронтенд: CSS Media Queries + `useMediaQuery` (Ant Design) для определения
ширины экрана. Компонент `ObjectCards.tsx` как альтернатива таблице для
мобильного режима (рендерится условно). Библиотека `react-swipeable` для
свайпов. Форма SC-03: Ant Design `Collapse` для аккордеона.

Backend: никаких изменений (API не меняется — мобильный и десктопный клиент
используют одни эндпоинты).

Сложность: Medium (3 спринта — адаптация каждого экрана под 2 разрешения:
десктоп и мобильный).

**Почему это «продвинуто»:**

Мобильная адаптация — это не «отдельное приложение» (F-09), а нулевой шаг:
сделать существующий веб-интерфейс **ситуативно доступным** на планшете и
телефоне. Это стоит в 3–4 раза дешевле, чем полноценное PWA, и даёт
немедленный эффект: инженер может открыть проект на планшете на совещании
и показать спецификацию заказчику.

**Риски и ограничения:**

- Не все экраны одинаково хорошо адаптируются: 3D-вьювер (F-04) на
  мобильном — это вызов (WebGL на мобильных GPU работает хуже). Решение:
  для мобильного — автоматически показывать 2D-схему вместо 3D.
- Таблица-карточки для 50+ объектов — это длинный скролл. Решение:
  поиск (T-08) и фильтры (T-02) работают и на мобильном — пользователь
  быстро фильтрует до 5–10 карточек.
- Touch-жесты конфликтуют со скроллом страницы. Решение: горизонтальные
  свайпы только внутри карточек, вертикальный скролл — для страницы.

## T-14. Контекстная справка, тултипы и onboarding-тур

**Категория:** Обучение и поддержка пользователя

**Приоритет:** P2 — на вырост

**Аналоги:** Figma (обучающие тултипы при первом запуске: «Это ваш canvas»,
«Здесь панель инструментов»), Notion (пустые состояния с примерами: «Нажмите
/ для команд», встроенные шаблоны), Linear (Onboarding flow из 3 шагов при
первом входе: назвать workspace, пригласить команду, создать первый issue),
Intercom / Userflow (продуктовые туры — цепочка тултипов, ведущая
пользователя по ключевым функциям).

**Проблема, которую решаем:**

Новый пользователь (гость или сотрудник) открывает HeatCalc и видит:
пустую таблицу, форму с 15 полями, кнопки «Добавить объект», «Электрорасчёт»,
«Спецификация». Что делать первым? В каком порядке?

Результат: trial-and-error, фрустрация, неправильно заполненные поля,
уход с продукта («слишком сложно»). Особенно остро для гостевого режима —
пользователь не будет читать документацию, он хочет «зашёл и сразу
попробовал».

**Инженерное описание:**

**Onboarding-тур (при первом входе):**

Цепочка из 5 шагов-тултипов, последовательно подсвечивающих элементы
интерфейса:

1. «Это ваш **рабочий стол**. Здесь вы будете добавлять объекты и рассчитывать теплопотери.»
2. «Начните с **общих данных проекта** — климат, напряжение, температура среды.» (подсветка кнопки «Общие данные»)
3. «Теперь добавьте **первый трубопровод** через форму слева. Заполните диаметр, длину, изоляцию.»
4. «После добавления объектов нажмите **«Электрорасчёт»** — система подберёт греющий кабель.»
5. «Готово! Результаты — на вкладках **Спецификация** и **Отчёт**. Удачи!»

Каждый шаг — кнопка «Далее →» и «Пропустить тур». Прогресс: «Шаг 2 из 5».
Тур показывается только один раз (флаг в localStorage `onboarding_complete`).

**Контекстные тултипы (для сложных полей):**

Рядом с полями, требующими пояснения, — иконка `?` с tooltip'ом:

- «λ, Вт/(м·К)» → «Коэффициент теплопроводности. Для минеральной ваты — 0.045. Чем ниже λ, тем лучше изоляция.»
- «Шаг навива, мм» → «Расстояние между витками кабеля при спиральной навивке. 0 = прямая укладка.»
- «Коэффициент запаса» → «Учитывает тепловые мостики на опорах и фланцах. По умолчанию 1.1 (+10%). Может быть изменён администратором.»

Тултипы показываются при наведении или фокусе на иконку. Не перегружают
интерфейс (скрыты по умолчанию), но доступны в 1 клик.

**Пустые состояния (Empty States):**

Когда таблица пуста — не просто «Нет данных», а приглашение к действию:

```
┌────────────────────────────────────────┐
│                                        │
│         🛢  Нет объектов               │
│                                        │
│  Добавьте первый трубопровод или       │
│  резервуар, чтобы начать расчёт.       │
│                                        │
│  [+ Добавить трубопровод]              │
│  [+ Добавить резервуар]                │
│  [📥 Импорт из Excel/CSV]              │
│                                        │
│  💡 Совет: скачайте шаблон XLSX для    │
│  импорта 100+ объектов разом.          │
│                                        │
└────────────────────────────────────────┘
```

**Встроенная справка (Help Panel):**

Кнопка «?» в header'е (рядом с колокольчиком) → боковая панель (drawer)
с поиском по документации. Короткие статьи: «Как выбрать кабель?»,
«Что делать, если расчёт выдал ошибку?», «Чем отличается CO1 от CO2?».
Статьи хранятся как Markdown-файлы в репозитории, рендерятся через
`react-markdown`.

**Технический контур:**

Фронтенд: onboarding-тур — библиотека `react-joyride` или `shepherd.js`
(легковесные, управляют цепочкой тултипов). Контекстные тултипы —
Ant Design `Tooltip` на иконке `QuestionCircleOutlined`. Empty States —
кастомные компоненты для каждого экрана. Help Panel — Ant Design `Drawer`
с поиском через `Fuse.js` по статьям. Статьи: Markdown в
`frontend/src/help/`, загружаются как raw-строки на этапе сборки (Vite
`import.meta.glob`).

Backend: не требуется (статьи статические, onboarding — клиентский).

Сложность: Low (2 спринта — onboarding-тур и empty states; контент для
справки — отдельная работа технического писателя, не оценивается здесь).

**Почему это «продвинуто»:**

Onboarding и контекстная справка — это разница между «пользователь
разбирается сам» (30% конверсия в активного пользователя) и «пользователь
ведётся за руку» (60%+ конверсия). Для продукта с гостевой моделью
(попробовать без регистрации) onboarding — это критический фактор
удержания: если за первые 3 минуты пользователь не понял, «что здесь
делать», он уходит навсегда.

**Риски и ограничения:**

- Onboarding-тур может раздражать опытных пользователей. Решение: кнопка
  «Пропустить тур» на каждом шаге, тур показывается только 1 раз, можно
  перезапустить из меню помощи.
- Контент справки устаревает при обновлении интерфейса. Решение: скриншоты
  в статьях — только для ключевых концепций, не для UI-элементов; UI
  описывается текстом («кнопка в правом верхнем углу»), а не скриншотом.
- Перевод справки на другие языки (при интернационализации). Решение:
  Markdown + i18n (файлы `help.ru.md`, `help.en.md`).

## T-15. Виртуальный скроллинг для больших таблиц (50+ строк)

**Категория:** Производительность

**Приоритет:** P0 — стратегический (снимает техническое ограничение на
размер проекта)

**Аналоги:** Google Sheets (виртуальный скроллинг: рендерятся только видимые
строки + буфер, миллионы ячеек работают плавно), Airtable (виртуальный
скроллинг для тысяч записей), react-virtualized / react-window (библиотеки,
используемые в production Facebook/Twitter/Discord для рендеринга
100 000+ строк).

**Проблема, которую решаем:**

Текущий лимит в 50 объектов на проект — это не бизнес-требование, а
**техническое ограничение**: Ant Design Table при 50+ строках с 12 колонками
начинает тормозить (каждый рендер строки создаёт десятки DOM-узлов —
50 × 12 = 600 ячеек минимум + обёртки + иконки + тултипы = 2000+ DOM-узлов).
На слабых машинах заказчиков (офисные ПК 2018–2020 годов) это заметно.

Заказчик запрашивает лимит в 200–500 объектов на проект (крупные
нефтехимические комплексы). Без виртуального скроллинга это невозможно.

**Инженерное описание:**

Виртуальный скроллинг — это техника, при которой рендерятся **только
видимые строки** (те, что помещаются во viewport таблицы + небольшой буфер
сверху и снизу для плавного скролла). При скролле — строки за пределами
viewport удаляются из DOM, новые — создаются.

Для таблицы из 500 строк с viewport'ом в 15 строк:
- Рендерится ~25 строк (15 видимых + 5 буфер сверху + 5 буфер снизу)
- DOM-узлов: 25 × 12 = 300 вместо 500 × 12 = 6000
- Потребление памяти: ~2 MB вместо ~35 MB
- FPS при скролле: стабильные 60 вместо 15–20

**Реализация:**

Интеграция `@tanstack/react-virtual` (библиотека от создателей TanStack
Query, 3 kB, поддержка динамической высоты строк, горизонтального скролла)
с Ant Design Table.

Хитрость: Ant Design Table не поддерживает виртуальный скроллинг «из
коробки» (хотя в v5 появилась экспериментальная поддержка `virtual`).
Решение:

- **Вариант А (прагматичный):** Использовать `@tanstack/react-virtual`
  как обёртку над `<tbody>`. Ant Design Table рендерит header, а тело
  таблицы заменяется на виртуальный контейнер. Сложность: нужно сохранить
  стилизацию antd (зебру, hover, выделение).
- **Вариант Б (на вырост):** Перейти на `@tanstack/react-table` (headless
  table library, 5 kB) + кастомный рендеринг с `@tanstack/react-virtual`.
  Это даёт полный контроль над рендерингом и производительностью, но
  теряется готовая стилизация antd Table. Требует ручного воссоздания
  стилей antd для таблицы (~3–4 дня).

Рекомендуется Вариант А для быстрого выигрыша, с перспективой перехода
на Вариант Б в будущем (когда потребуется более тонкий контроль).

**Влияние на остальной функционал:**

- Drag-and-drop (T-04): `@dnd-kit` должен работать с виртуальным списком
  (поддерживается через `useSortable` + virtualizer integration)
- Выделение строк (T-04) и контекстное меню (T-05): работают корректно,
  так как видимые строки — это полноценные DOM-элементы
- Фильтры (T-02): фильтруют полный массив данных, виртуальный скроллинг
  работает поверх отфильтрованного массива
- Поиск и переход к строке (T-08): `virtualizer.scrollToIndex(id)` —
  мгновенный скролл к нужной строке

**Технический контур:**

Фронтенд: `@tanstack/react-virtual` (3 kB). Интеграция с antd Table —
использование `components.body.wrapper` для подмены `<tbody>`. Динамическая
высота строк: `virtualizer.measureElement()` для строк с разной высотой
(например, multiline наименование).

Backend: опционально — пагинация на сервере (cursor-based) для проектов
с 1000+ объектов. Пока — загружаем все объекты одним запросом, фильтруем
и виртуализуем на фронте. При 500 объектах JSON ответа — ~250 kB (с
параметрами), что приемлемо.

Сложность: Medium (2.5 спринта — интеграция виртуального скроллинга с
antd Table + тестирование на всех взаимодействиях: DnD, выделение,
контекстное меню, поиск).

**Почему это «продвинуто»:**

Виртуальный скроллинг — это архитектурный фундамент, который снимает
технический потолок в 50 объектов. Без него все остальные фичи (массовые
операции, фильтры, поиск) теряют смысл при 200+ объектах — интерфейс
просто зависнет. Это не «фича для пользователя», а **enabler для всех
остальных фич**.

**Риски и ограничения:**

- Интеграция с antd Table может быть хрупкой: antd не проектировался для
  виртуального скроллинга, внутренние API могут измениться в мажорной
  версии. Решение: зафиксировать версию antd в `package.json`, покрыть
  интеграцию e2e-тестами (скролл на 500 строк).
- Строки с разной высотой (multiline content) сложнее виртуализировать,
  чем строки с фиксированной высотой. Решение: использовать
  `virtualizer.estimateSize()` с последующим `measureElement()` для точного
  измерения.
- Виртуальный скроллинг ломает `Ctrl+F` браузера (браузер ищет по DOM,
  а там только 25 строк). Решение: глобальный поиск (T-08) как замена
  браузерному поиску.
