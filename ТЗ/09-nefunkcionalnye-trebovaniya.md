# 9. Нефункциональные требования

## 9.1. Производительность

- **НФ-01.** Время отклика API расчёта одного объекта — до 500 мс.
- **НФ-02.** Пакетный пересчёт проекта (≤ 50 объектов) — до 5 секунд.
- **НФ-03.** Рабочая область интерфейса от 1280 px; мобильная версия не
  требуется.
- **НФ-04.** Таблицы объектов и результатов — серверная пагинация; UI не
  деградирует на 50 объектах × 4 СО.

## 9.2. Безопасность

- **НФ-05.** JWT-авторизация, ролевая модель на каждом endpoint; гостевые
  данные изолированы по сессии.
- **НФ-06.** Пароли — только хэш (bcrypt или эквивалент); пароль не
  раскрывается в сообщениях об ошибках.
- **НФ-07.** Rate limit гостевых сессий (10/IP/час); при горизонтальном
  масштабировании — распределённый лимитер (Redis).
- **НФ-08.** Обфускация/минификация frontend-сборки.
- **НФ-09.** Защита расчётных формул и встроенных справочников: выбор
  варианта (А — поставка в образе как есть / Б — шифрование с ключом в
  конфигурации / С — внешнее KMS) — решение Заказчика, документ 11. Внешняя
  БД и учётные данные шифрованию не подлежат (хранятся штатно в PostgreSQL).
- **НФ-10.** CORS-список доменов задаётся конфигурацией прод-контура.
- **НФ-11.** Регулярные SAST/CVE-проверки зависимостей в конвейере сборки
  (bandit, pip-audit, eslint-security, npm audit или эквиваленты).
- **НФ-12.** Санитизация HTML-превью отчёта (защита от XSS).

## 9.3. Надёжность и развёртывание

- **НФ-13.** Развёртывание `docker compose up` локально и on-premise; работа
  в локальной сети без интернета.
- **НФ-14.** Миграции БД через Alembic (вперёд и назад).
- **НФ-15.** Каскадное удаление данных гостевых сессий (`ON DELETE CASCADE`);
  фоновая очистка просроченных сессий с настраиваемым интервалом; очистка
  при старте.
- **НФ-16.** Конфигурация через переменные окружения с задокументированным
  `.env.example`; обязательные параметры: БД, JWT-секрет, лимиты гостевых
  сессий, первичный администратор.
- **НФ-17.** Healthcheck endpoint; журналы контейнеров доступны локально.
- **НФ-18.** Бизнес-аудит мутаций/расчётов/отчётов — в БД (`audit_events`).

## 9.4. Удобство использования

- **НФ-19.** Язык интерфейса — русский.
- **НФ-20.** Каждое поле: единица измерения, диапазон в подсказке, inline
  ошибка + tooltip с полным описанием.
- **НФ-21.** Результат расчёта виден без перехода со страницы ввода.
- **НФ-22.** Фирменная цветовая схема Заказчика (тёмно-бирюзовая,
  #1a5276 / #2e86c1).
- **НФ-23.** Лейбл над контролом не уже самого контрола (без обрезания
  подписей).

## 9.5. Тестируемость и приёмка

- **НФ-24.** Unit-покрытие чистых расчётных функций — 100% ветвей.
- **НФ-25.** Интеграционные тесты на каждый API endpoint.
- **НФ-26.** E2E (Playwright) на каждый ключевой приёмочный сценарий:
  гостевой вход → объект → теплопотери → электрорасчёт → спецификация →
  отчёт; импорт/экспорт; матрица видимости полей; ошибки расчёта.
- **НФ-27.** Независимый deterministic-oracle формул (QA-registry): все
  формулы и алгоритмы документов 3–6 продублированы в machine-readable
  реестре и сверяются автоматически.
- **НФ-28.** Контрольные примеры из документов 3–6 (ТР-07, ТР-12, СП-09)
  входят в приёмочную программу как golden-тесты.
- **НФ-29.** Изменение любой формулы/справочника требует синхронного
  обновления: контракта бизнес-логики, QA-реестра, тестов и документации
  (правило изменения — документ 1, п. 1.6 и `docs/business-logic-contract.md`).
