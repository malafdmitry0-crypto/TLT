## 3. Рендер AntD Table на странице электрорасчёта

**Слой:** frontend

**Симптом:** после ускорения API основной лаг сместился в JS/render: таблица создаёт тяжёлые ячейки (`Select`, `InputNumber`, `Tooltip`) для текущей страницы и пересоздаёт `columns` на каждый render.

**Риск:** при `page_size=50-100`, частых изменениях состояния и ручном редактировании строки пользователь может видеть задержку даже если API отвечает быстро.

**Что сделать дальше:**

- Вынести `columns` в `useMemo`, а обработчики ячеек стабилизировать через `useCallback`.
- Разделить display mode и edit mode: `Select`/`InputNumber` монтировать только для активной строки, остальные строки показывать как текст/Tag.
- Если после этого long tasks останутся, включить виртуализацию строк или заменить таблицу на легковесный grid для расчётных страниц.

**Ожидаемый эффект:** меньше React reconciliation и меньше DOM-узлов; интерактивность таблицы должна зависеть от активной строки и размера страницы, а не от общего размера проекта.

## 5. CPU-bound часть batch-расчётов

**Слой:** backend/runtime

**Симптом:** текущий batch быстрый для одного пользователя, но формулы остаются синхронными Python-вычислениями внутри request lifecycle.

**Риск:** при параллельных batch-запусках event loop и worker могут проседать не из-за БД, а из-за CPU.

**Что сделать дальше:**

- Для крупных batch запусков возвращать `202 Accepted` + `task_id`, а расчёт выполнять фоновой задачей.
- Для CPU-heavy сценариев использовать process pool или отдельный worker, потому что threads не обходят GIL для чистого Python.
- Уменьшить Python overhead в hot path: не строить лишние Pydantic response модели, по умолчанию отдавать краткий payload, подробности читать отдельным endpoint.
- Добавить нагрузочный тест на 3-5 параллельных batch-запусков, чтобы контролировать p95 и max latency после выноса CPU.

**Ожидаемый эффект:** быстрые API-запросы и чтение проекта не блокируются тяжёлыми расчётами; batch становится управляемой фоновой операцией.
