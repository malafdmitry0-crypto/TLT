# Аудит алгоритма электрорасчёта Самрег

**Дата:** 2026-08-11
**Область:** production-path `self_regulating_tt`: входы, подбор кабеля,
секционирование, каталоги, snapshot и регрессионные проверки.
**Режим:** аудит с последующим исправлением найденного дефекта и регрессией.

## Итог

Расчётное ядро соответствует действующему Case1-r4 контракту и детерминировано.
Первичная оценка ошибочно сравнивала runtime с более старым TT-контрактом
`T1/T2/T3/R`. После независимой перепроверки Sol Max эти пункты исключены из
списка дефектов.

Найден и исправлен один реальный дефект уровня P1: расчёт по активному DB
power-каталогу мог сохранять `cable_snapshot` из встроенного JSON-каталога.

Отдельно подтверждён infrastructure gap: формульное ядро зелёное, но общий
`Formula QA quick` красный из-за 10 устаревших service fixtures.

## Нормативный приоритет

Действующий owner-контракт:

`docs/tnp/cases/electrical-input-contract-reconciliation.md`

Документ имеет статус «реализованный P0-контракт для self_regulating_tt» и прямо
фиксирует, что старые алгоритмы `q1*T3+q2`, выбор серии по `T1/T2` и суффикс по
`R` не являются источником текущего Case1-r4 расчёта.

Поэтому следующие особенности runtime являются правильным поведением, а не
дефектами:

- мощность кабеля берётся из паспортной `nominal_power`;
- автоматический подбор перебирает все точные BOM-марки;
- при полном техническом равенстве `СТ/СР` разрешаются алфавитным tie-break;
- ручная точная марка при `N = null` проверяется ровно с одной ниткой;
- напряжение является положительным пользовательским downstream-входом и не
  влияет на подбор марки;
- обратная совместимость со старым TT-контрактом отсутствует.

Старый `docs/tnp/cases/guest-electrical-calculation-tz.md`, где ещё указаны
`q1*T3+q2`, `R` и фиксированные 230 В, требует синхронизации или явной пометки
как superseded. Это документальный drift, но не ошибка production runtime.

## Фактическая расчётная цепочка

### 1. Канонические входы

Resolver собирает значения с явным provenance:

- температура продукта и среды;
- минимальная температура включения;
- актуальные Heat-теплопотери;
- коэффициент запаса;
- эффективная длина или отдельный tank layout;
- наружный диаметр и шаг навива только для трубы;
- ручная полная марка и число ниток;
- напряжение;
- обязательный проектный `Iдоп`;
- единственная политика `technical_minimum`.

`Iдоп` не имеет request/object fallback. Без проектного значения расчёт
завершается `SECTION_CURRENT_LIMIT_REQUIRED`.

### 2. Требуемая мощность и укладка

```text
Pтреб = qтеплопотерь × Kзапаса
Pуст.м = nominal_power × Kнав × Nнит
```

- прямая укладка трубы: `Kнав = 1`;
- навив: коэффициент вычисляет backend из диаметра и шага;
- резервуар использует отдельный layout в метрах и всегда `Kнав = 1`;
- трубные параметры навива для резервуара отклоняются типизированной ошибкой;
- для резервуара уже применённый Heat-запас снимается перед формулой, поэтому
  `K` применяется ровно один раз.

### 3. Допуск марки

Точная BOM-марка пригодна только при одновременном выполнении:

```text
Tокр ≥ Tmin
Tпродукта ≤ Tmax
Pуст.м ≥ Pтреб
Nнит ∈ {1, 2, 3}
```

Границы температур включены. `Tmin` берётся из минимальной температуры строк
секционного каталога конкретной модели. Температура холодного пуска отдельно
используется для выбора строки секционирования.

Автоматический режим проверяет `N = 1, 2, 3`. Сортировка:

1. число ниток;
2. паспортная мощность;
3. паспортная мощность × число ниток;
4. полный маркоразмер по алфавиту.

Для ручной полной марки проверяется только указанное `N`; `null` по действующему
контракту означает одну нитку.

### 4. Секционирование

```text
Lток = Iдоп / Iст.уд
Lогр = floor(min(Lмакс, Lток), 0.001 м)
Nсек = ceil(Lтреб / Lогр)
Lсек = Lогр
Lфакт = Nсек × Lсек
Lзаказ = ceil(Lфакт × 1.10, 0.001 м)
```

Для модели и температуры включения выбирается точная или ближайшая более
холодная строка. Fallback на более тёплую строку запрещён. Все автоматические
секции равны; мощность и токи пересчитываются от `Lфакт`.

### 5. Финальный gate

`ready` выдаётся только после повторной проверки:

- марки, серии и числа ниток;
- положительного напряжения;
- `Lсек ≤ Lмакс`;
- `Iстарт секции ≤ Iдоп`;
- `Lфакт ≥ Lтреб`;
- одинаковых параметров секций;
- `Pуст.м ≥ Pтреб`;
- идентичности power/section/BOM-каталогов.

## Реальный дефект

### P1 — смешивались активный DB-каталог и встроенный cable snapshot

Production-расчёт получает power/section/BOM из согласованного набора активных
DB-каталогов и правильно сохраняет их в `results.catalogs` и provenance.

До исправления `_snapshot_cable_row()` для `self_regulating_tt` повторно
загружал `list_tt_cables()` и строил `cable_snapshot` из встроенного JSON.
`cable_snapshot_statuses()` также сравнивал snapshot с JSON, а не с версией
DB-каталога, использованной расчётом.

Подтверждённый сценарий:

```text
active DB catalog: 25ТТН2 = 26 Вт/м, version=custom-v1
runtime result:     26 Вт/м, source=database, version=custom-v1
cable_snapshot:     25 Вт/м, source=builtin
status comparison:  snapshot сравнивается с builtin 25 Вт/м
```

Последствия:

- один сохранённый расчёт содержит противоречивые характеристики кабеля;
- UI/API может показывать snapshot как `current`, хотя он не соответствует
  каталогу расчёта;
- audit/provenance результата корректны, но соседний snapshot вводит в
  заблуждение;
- после активации нового DB-каталога stale/current статус нельзя считать
  надёжным.

Исправленные места:

- `CalculationService._snapshot_cable_row()`;
- `CalculationService.cable_snapshot_statuses()`;
- `build_cable_snapshot()` и `compare_cable_snapshot()`.

Реализовано:

1. TT `cable_snapshot` строится из точной `results.catalogs.power.row`;
2. snapshot сохраняет id/version/authority/checksum каталога;
3. current/stale определяется относительно текущего разрешённого источника;
4. после DB-authoritative расчёта bundled JSON повторно не читается;
5. при отсутствии активного DB-каталога весь расчёт использует единый bundled
   fallback; ошибки БД fallback не маскируются;
6. добавлены тесты custom DB power, builtin fallback, смены версии и запрета
   частичного snapshot.
