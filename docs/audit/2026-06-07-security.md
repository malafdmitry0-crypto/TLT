# Аудит безопасности

**Дата:** 2026-06-07
**Область:** FastAPI backend, JWT/гостевые сессии, PostgreSQL, React frontend.
**Контекст:** on-premise / локальное демо с намеренным гостевым доступом —
severity откалибрована под это. Код не менялся.

## Резюме

Заметно хорошо защищённая кодовая база. Object-level авторизация, rate limiting,
лимиты загрузок, защита от zip-bomb, CSRF, timing-safe login, ротация
refresh-токенов, autoescape шаблонов и DOMPurify — на месте. **Критически
эксплуатируемых IDOR, инъекций или обхода аутентификации не найдено.** Находки —
в основном hardening/конфигурация.

---

## HIGH

### H1. Прод-guard безопасности не срабатывает — дефолты уходят как есть
- **Файлы:** `backend/app/core/config.py:124-140` (`is_production` /
  `validate_runtime_security`), `backend/app/main.py:111`,
  `docker-compose.yml:55-92`.
- **Проблема:** `validate_runtime_security()` выполняет проверки только при
  `APP_ENV ∈ {prod, production}`. `APP_ENV` **нигде не задан** (ни в
  `docker-compose.yml`, ни в `.dev.yml`, ни в `.env.example`) → всегда дефолт
  `"development"`. Guard, который отверг бы `SECRET_KEY="change-me-in-production"`,
  `FIRST_ADMIN_PASSWORD="admin"` и короткие секреты, в дефолтном прод-стеке —
  no-op. Compose ещё и дефолтит оба значения на небезопасные
  (`SECRET_KEY: ${SECRET_KEY:-change-me-in-production}`,
  `FIRST_ADMIN_PASSWORD: ${FIRST_ADMIN_PASSWORD:-admin}`).
- **Вектор:** деплой прод-стека без явного экспорта переменных → известный ключ
  подписи JWT (форж токенов любой роли → захват админа) и логин `admin/admin`.
- **Серьёзность:** High для реального прода; ниже для одно-пользовательского
  локального демо — но guard молча отключён в любом случае.
- **Рекомендация:** задать `APP_ENV=production` в прод-compose, убрать небезопасные
  дефолты `SECRET_KEY`/`FIRST_ADMIN_PASSWORD` (fail fast). Дополнить pitfalls
  записью про `APP_ENV`.

### H2. `AUTH_COOKIE_SECURE` по умолчанию `False`
- **Файл:** `backend/app/core/config.py:33`, используется в
  `backend/app/api/v1/auth.py:36,46,55`.
- **Проблема:** access/refresh/CSRF-куки ставятся без флага `Secure` по умолчанию.
  По HTTP (демо явно без HTTPS) — приемлемо, но если дефолт попадёт в HTTPS-прод,
  JWT-куки могут уйти по downgraded/HTTP.
- **Серьёзность:** High для HTTPS-прода; Low для локального демо (без TLS by design).
- **Рекомендация:** привязать дефолт `AUTH_COOKIE_SECURE` к `is_production` или
  требовать `True` в `validate_runtime_security`.

## MEDIUM

### M1. Swagger / ReDoc / OpenAPI всегда доступны
- **Файл:** `backend/app/main.py:131-133` (`docs_url="/docs"`, `redoc_url="/redoc"`,
  `openapi_url`).
- **Проблема:** интерактивная докудентация API включена безусловно (healthcheck
  даже зависит от `/docs`). Раскрывает всю поверхность API.
- **Серьёзность:** Medium (info disclosure); Low для локального демо.
- **Рекомендация:** отключать docs в проде (`docs_url=None` при `is_production`);
  healthcheck перевести на `/health`.

### M2. HTML-превью отчёта допускает `<style>` + `WHOLE_DOCUMENT`
- **Файл:** `frontend/src/components/reports/ReportPreview.tsx:8-13`.
- **Проблема:** DOMPurify корректно запрещает `script/iframe/object/embed`, но
  `ADD_TAGS: ['style']` + `WHOLE_DOCUMENT: true` допускают произвольный CSS.
  HTML приходит из Jinja2-шаблона с autoescape (`pdf_generator.py:9-11`), имена
  проекта/объектов — user-controlled. Script-XSS заблокирован, но инъекция
  `<style>` может дать CSS-based UI redressing / утечку через `url()`, если
  user-данные попадут в `<style>`-блок.
- **Серьёзность:** Medium (defense-in-depth; не подтверждённый script-XSS).
- **Рекомендация:** убедиться, что серверный шаблон не выводит user-данные внутри
  `<style>`; рассмотреть отказ от `<style>` в пользу статического stylesheet.

### M3. Гостевые сессии без привязки (по дизайну)
- **Файлы:** `backend/app/core/dependencies.py:95-110`,
  `backend/app/services/auth_service.py:38-44`.
- **Проблема:** гостевые сессии — bearer-секрет (`secrets.token_urlsafe(32)`,
  сильный) в `X-Session-Id`, не привязан к IP/origin. Кто владеет id — имеет
  доступ к проекту гостя. By design для анонимного флоу; токен высокоэнтропийный,
  риск низкий; нет ротации/привязки.
- **Серьёзность:** Low/Medium (by design).
- **Рекомендация:** приемлемо для демо. Для multi-tenant прода — привязка к
  cookie + same-site вместо header, эхо-ируемого JS.

## LOW / Информационные (проверено и в порядке)

- **L1. JWT (`decode_token`)** — `core/security.py:83-87`. Алгоритм фиксирован
  `HS256` с явным `algorithms=[...]` → `alg=none` и algorithm-confusion отвергаются
  PyJWT. Проект мигрировал с `python-jose` на `pyjwt[crypto]==2.12.0`. Тип
  access/refresh проверяется везде.
- **L2. Зависимости** — `weasyprint==68.0` + `pydyf==0.11.0` (совместимая пара),
  `fastapi==0.121.0`, `starlette==0.49.3`, `Jinja2==3.1.6`, `cryptography==48.0.0`,
  `openpyxl==3.1.5`. Нет `python-jose`, нет SheetJS на backend. `bcrypt==4.0.1`
  старее, но рабочий. Держать актуальным через `pip-audit`/`npm audit` в CI.
- **L3. IDOR / object-level авторизация** — `project_service.py:444-468`. Каждое
  чтение через `_check_access`, запись через `_check_owner`, по `session_id`
  (гость) или `user_id` (сотрудник). Сотрудник не трогает гостевые проекты, гость
  не видит чужие сессии. Объекты scoped по `project_id`. `reorder_objects`
  валидирует полный набор ID. Оптимистичная блокировка версии. IDOR не найден.
- **L4. Path traversal в артефактах отчётов** — `report_artifact_service.py:16-21`
  resolve + `assert path.parent == base`. Имя из серверного `task_id`. Безопасно.
- **L5. Загрузка файлов / DoS** — `core/uploads.py`, `main.py:207-253`
  (`MaxBodySizeMiddleware`), `excel_import_service.py:383-399`. Streamed cap 10 MB,
  zip-bomb-защита (`MAX_XLSX_FILES`, `MAX_XLSX_UNCOMPRESSED_BYTES`, ratio >100
  reject), `MAX_IMPORT_ROWS`/`MAX_IMPORT_SHEETS`, `read_only=True`. Тяжёлые расчёты
  в worker-очереди с cap по проекту/principal/глобально. Сильно.
- **L6. SQL-инъекции** — не найдено. Все запросы — параметризованный SQLAlchemy 2.x
  `select/update/delete`. Raw SQL / f-string в запросах нет.
- **L7. CORS** — `main.py:179-185`, `config.py:55-67`. `allow_credentials=True` с
  явным списком origin (без `"*"`), comma-separated `CORS_ORIGINS`.
  `allow_methods/headers=["*"]` ОК при явных origin. Нет wildcard+credentials.
- **L8. Утечка секретов / обработка ошибок** — login timing-safe (dummy bcrypt
  против user enumeration), generic-сообщение. Refresh-токены ротируются с
  reuse-detection (revoke-all на replay); JTI хранятся SHA-256. `DEBUG=False`
  дефолт. CSRF double-submit для cookie-auth мутаций (`main.py:255-292`). Stack
  traces клиенту не утекают.
- **L9. Обход rate-limiter через `X-Forwarded-For`** — `rate_limit.py:245-264`.
  `X-Forwarded-For` доверяется только если прямой клиент в `TRUSTED_PROXY_IPS`,
  иначе `request.client.host`. In-memory limiter сбрасывается при рестарте
  (задокументировано); есть Redis-бэкенд для HA.

## Приоритеты

1. **H1** — задать `APP_ENV=production` в прод-compose, убрать небезопасные дефолты
   `SECRET_KEY`/`FIRST_ADMIN_PASSWORD`, чтобы `validate_runtime_security()`
   реально работал. **Важнейшее — guard сейчас молча отключён.**
2. **H2** — дефолт `AUTH_COOKIE_SECURE` → `True`/`is_production`.
3. **M1** — отключить `/docs`,`/redoc`,`/openapi.json` в проде; healthcheck с `/docs`.
4. **M2** — пересмотреть `<style>`/`WHOLE_DOCUMENT` в `ReportPreview`.

Остальное (IDOR, SQLi, path traversal, upload/DoS, CORS, JWT alg, CVE
зависимостей, утечка секретов, CSRF) проверено и в хорошем состоянии. H/M-пункты —
конфигурация / defense-in-depth, для локального демо в основном безвредны, но
важны для любого реального деплоя.
