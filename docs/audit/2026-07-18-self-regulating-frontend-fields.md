# Functional Accuracy Report

**Mode:** `/audit-only`  
**Scope:** поля фронта SC-04 «Электрорасчёт» для саморегулирующихся кабелей
`self_regulating` (ТЛТ) и `self_regulating_tt` (ТТН/ТТВ/ТТХ); поиск лишних,
дублирующих и скрыто влияющих на расчёт данных.  
**Status:** **NEEDS VERIFICATION / есть подтверждённые findings**.  
**Ограничение проверки:** код, тесты и браузер не запускались по условию
пользователя; выполнена статическая трассировка документации, frontend payload и
backend precedence.

## Краткий вывод

Да, на фронте есть лишние и дублирующие данные. Главный риск, однако, не в
визуальной перегруженности: frontend хранит глобальные значения по умолчанию и
отправляет их в каждый batch-расчёт, даже когда пользователь их не менял. Для
`self_regulating_tt` скрытый `windingCoefficient=1` может заменить backend-default
`1.1` и изменить подбор кабеля. Аналогично глобальный `aggressiveProduct=false`
имеет приоритет над объектным значением и может выбрать исполнение `-СТ` вместо
`-СР`.

Одновременно действительно необходимые поля `Шаг навива` и `Количество ниток`
нельзя отредактировать до первого успешного расчёта: таблица разрешает их ввод
только при уже существующем результате и выбранной марке.

### Как соотносятся два XLSX

Прямого противоречия между файлами нет: они отвечают на разные вопросы и могут
использоваться совместно.

- `список переменных трубопроводы.xlsx` — словарь переменных: имя, обозначение,
  единица измерения, диапазон и источник значения. В проверенной версии нет
  легенды, которая распределяет поля по экранам: цветом выделена только шапка.
- `Расчет_спецификации_трубы_самрег29_05_26.xlsx` — расчётная книга. Именно в ней
  цветом разделены этапы алгоритма и поэтому по ней можно понять, на каком шаге
  используется переменная.

Документ `sc03-heat-form-cleanup-2026-06-10.md:3-7` подтверждает легенду второй
книги:

- серый — расчёт теплопотерь;
- оранжевый — выбор кабеля;
- зелёный — спецификация.

Следовательно, корректная трактовка такая: список переменных описывает состав и
тип данных, а цветная расчётная книга — этап их использования. Неопределённость
не в том, что frontend «построен по другому XLSX», а в том, что приоритет этих
источников и правила переноса полей на конкретные экраны не закреплены единым
формальным контрактом. Findings ниже основаны не на разнице файлов, а на
фактическом frontend/backend data flow.

## Как сейчас формируется спецификация

Цепочка в приложении:

`объекты проекта -> электрорасчёт выбранного СО -> генератор basic/full -> авто-позиции + ручные позиции -> upsert в БД -> таблица frontend`

### 1. Пользователь выбирает вариант системы

На странице спецификации выбирается `СО1...СО4`. Frontend передаёт его как
числовой query-параметр `variant` в `POST /specifications/{project_id}/generate`
(`SpecificationPage.tsx:515-535`, `api/specifications.ts:33-43`). Спецификации и
электрорасчёты разных СО хранятся раздельно.

### 2. Backend берёт сохранённые результаты электрорасчёта этого СО

`SpecificationService.generate()` загружает записи `ElectricalCalculation` по
`project_id + variant_number` и передаёт в builder:

- полную марку кабеля;
- тип кабеля;
- snapshot каталожной/коммерческой строки;
- результаты расчёта, в том числе длины и число ниток/секций;
- `object_id` для связи с геометрией объекта.

Ошибочный или устаревший электрорасчёт не может породить кабельную позицию.
Поэтому поля SC-04 влияют на спецификацию опосредованно: сначала они меняют
марку, число ниток и длину в электрорасчёте, затем эти сохранённые результаты
становятся входом спецификации (`specification_service.py:90-107`).

### 3. Выбирается один из двух алгоритмов

#### Базовая спецификация (`mode=basic`)

Доступна гостю и сотруднику. Кабельные метры группируются по полной марке и
суммируются. Приоритет источника заказной длины:

1. `cable_snapshot.commercial_context.required_order_length`;
2. `commercial.required_order_length`;
3. `order_cable_length`.

То есть basic использует уже рассчитанную **заказную/коммерческую длину**, а не
повторяет геометрическую формулу кабеля. Затем на каждый объект проекта, включая
объекты с неуспешным электрорасчётом, добавляется фиксированный минимальный
набор из `backend/app/reference_data/accessories.json`:

- комплект концевой заделки — 1 шт./объект;
- комплект соединительный — 1 шт./объект;
- алюминиевая крепёжная лента — 2 м/объект;
- терморегулятор — 1 шт./объект;
- датчик температуры — 1 шт./объект;
- УЗО — 1 шт./объект.

Реализация: `backend/app/formulas/specification/builder.py:20-109`.

#### Полная спецификация (`mode=full`)

Доступна только сотруднику/администратору; для гостя backend возвращает 403.
Этот режим реализует автоматическую формульную часть листа «Список материалов
Самрег» из `Расчет_спецификации_трубы_самрег29_05_26.xlsx`. Он принимает только
саморегулирующиеся типы `self_regulating` и `self_regulating_tt`; резистивные,
mineral и skin-позиции пропускаются и учитываются в `skipped_objects`.

Для каждого успешного результата берутся:

- `M,секц` — полная марка кабеля;
- `N,секц` — сейчас фактически `num_circuits`;
- `L,секц × N,секц` — `installed_cable_length`;
- `dтр` — `outer_diameter` объекта, в коде переводится из метров в мм;
- `Lтр` — сначала `results.effective_length`, затем `params.pipe_length`;
- `T,секц` — класс по марке: ТТВ/ТТХ = high, всё остальное = low;
- опции формы спецификации: `R,гр`, `Ex`, `К1i`, `К2i`, `Кiu`, `L,К2i`.

Основные формулы и ветвления:

| Позиция | Текущее правило |
|---|---|
| Кабель | `Σ(installed_cable_length × R,гр)` с группировкой по марке |
| КСН-1 / КСВ-1 | `Σ(N,секц × R,гр)` по low/high классу |
| КСН-2 / КСВ-2 | `Σ(N,секц × R,гр × 2)`, только если К2i включён и длина одной секции `>= L,К2i` |
| КСР-1 / КСР-2 | `ceil(Σ длины low/high / 150)` |
| Коробки СКВ | для каждого объекта `ceil(N,секц / 3)`, выбор одной из 12 корзин по `dтр > 57`, `N >= 3`, К1i, К2i и Кiu |
| Хомут ХК30 | по периметру трубы и числу коробок большого диаметра |
| ЛКС / ЛКВ | по диаметру, длине кабеля, шагу 0,3 м и запасу 10% |
| Этикетка | для каждого объекта `ceil(Lтр / 3,5)` |
| ЛА, клей, герметик, Z-профиль | производные от длин, заделок и коробок |

После расчёта применяется `package_factor` из
`backend/app/reference_data/spec_accessories.json`, затем штучные позиции
округляются вверх. Например, расчетные метры ленты превращаются в число рулонов.
Реализация: `backend/app/formulas/specification/full_builder.py:97-289`;
независимое описание oracle: `docs/audit/spec-bom-oracle.md`.

В автоматический full BOM не входят КИП, шкаф управления, монтажные кабели,
лотки/трубы и ЗИП: в источнике для них нет автоматических формул. Их сотрудник
добавляет вручную из расширенной БД.

### 4. Автоматические и ручные позиции объединяются

Перед регенерацией сервис извлекает старые строки `source=manual`, заново строит
все `source=auto`, затем объединяет их. Ручная позиция должна сохраняться при
пересчёте (`specification_service.py:63-79,149-168`). Это подтверждено
интеграционным тестом `test_regenerate_preserves_manual_items`, хотя в текущей
модалке frontend написано обратное — см. F-08.

### 5. Результат сохраняется и восстанавливается

Сервис делает upsert по `project_id + variant_number`, сохраняя:

- `items`;
- фактический `generation_mode`;
- `generation_options` полного BOM;
- связь с вариантом электрорасчёта;
- признаки устаревания.

После изменения объекта или перерасчёта исходных данных спецификация помечается
`is_stale=true`; старые строки остаются видимыми, но UI предупреждает, что их
нельзя использовать для закупки. При регенерации stale-флаг снимается
(`specification_service.py:189-227,229-281`, `SpecificationPage.tsx:424-469`).

### Что это означает для полей frontend

- Поля SC-03/SC-04 нужны в спецификации только тогда, когда они формируют
  сохранённые `installed_cable_length`, `num_circuits`, марку или геометрию
  объекта.
- `R,гр`, `Ex`, `К1i`, `К2i`, `Кiu`, `L,К2i` — отдельные входы именно полной
  спецификации и оправданно находятся на странице спецификации.
- Марка, количество ниток и обе длины нельзя считать «лишними результатами»:
  они непосредственно формируют закупочную ведомость.
- Basic и full сейчас используют разные базы длины кабеля: заказную длину против
  установленной длины, умноженной на `R,гр`. Это зафиксированный открытый
  бизнес-вопрос Б-6 в `docs/analysis/spec-bom-open-issues-2026-06-09.md`.

### Незакрытые риски корректности full BOM

Формула спецификации зарегистрирована в
`codex-docs/business-formula-contracts.json` как
`specification_from_electrical_variant`, но инженерный контракт пока не закрывает
несколько существенных случаев:

- `N,секц` в Excel и число ниток — разные понятия, а код сейчас использует
  `num_circuits` как число секций;
- весь ТЛТ попадает в low-класс, хотя высокотемпературный ТЛТ может требовать
  другой комплект;
- Excel не определяет ветку для `dтр = 57 мм`, код относит её к малому диаметру;
- алгоритм для труб применяется к резервуарам без подтверждённого tank-oracle;
- basic и full дают кабельную длину из разных источников;
- КИП, шкафы, монтажные материалы и ЗИП автоматически не рассчитываются.

Поэтому текущее описание — точная трассировка реализации, но не подтверждение,
что каждый результат full BOM инженерно верен. Для такого подтверждения нужны
решения по вопросам Б-1…Б-10 и golden/boundary-прогон по Excel-oracle.

## Findings

### F-01 — CRITICAL: скрытый `windingCoefficient=1` меняет формулу TT

**Evidence:**

- `useElecCalcRecalculationParams.ts:9` создаёт глобальный default
  `windingCoefficient=1`;
- `useElecCalcBatchJobOrchestration.ts:109` отправляет его в каждый batch;
- для `self_regulating_tt` контрол коэффициента не отображается
  (`ElecCalcElectricalTypeControls.tsx:61-88`), то есть пользователь не видит
  передаваемое значение;
- backend для TT вызывает `_winding_coefficient(..., default=1.1)`
  (`calculation_service.py:2599`), но frontend override `1` имеет приоритет.

**Риск:** расчётная установленная мощность уменьшается примерно на 9,1% по
сравнению с `Kn=1.1`; может измениться марка и количество ниток. Это не просто
лишнее поле, а скрытая подмена формульного входа.

**Рекомендация:** nullable/tri-state override. Если пользователь явно не задавал
коэффициент или шаг, frontend должен отправлять `null/undefined`, чтобы backend
применил договорённый default/формулу. Для саморегулирующегося кабеля не хранить
общий `w=1` как активное значение.

### F-02 — HIGH: `aggressiveProduct=false` затирает объектную агрессивность

**Evidence:**

- frontend default `false`: `useElecCalcRecalculationParams.ts:14`;
- значение всегда передаётся: `useElecCalcBatchJobOrchestration.ts:114`,
  `frontend/src/api/calculations.ts:308`;
- backend schema также имеет не-null default `false` и безусловно включает его в
  overrides: `backend/app/schemas/calculation.py:1299,1325`;
- service выбирает override при наличии ключа и только иначе читает объект:
  `calculation_service.py:2583-2588`;
- объектная форма хранит `environment=normal|aggressive`, а не
  `aggressive_product`; отсутствие маппинга уже зафиксировано в
  `sc03-heat-form-cleanup-2026-06-10.md:30,46-48`.

**Риск:** агрессивный объект может получить обычное исполнение марки (`-СТ`
вместо `-СР`). При массовом расчёте один глобальный checkbox также не способен
корректно выразить смешанный набор объектов.

**Рекомендация:** один канонический объектный field. Например,
`environment=aggressive -> aggressive_product=true`, а глобальный checkbox
сделать tri-state «не переопределять / нормальная / агрессивная» только для
выбранных строк. Backend schema должна отличать «не передано» от `false`.

### F-03 — HIGH: нужные поля шага и ниток недоступны до первого расчёта

**Evidence:**

- SRS требует поля на объект (`docs/srs/03-elements-list.md:357-370`);
- frontend разрешает редактирование только при существующем успешном расчёте и
  выбранной марке: `elecCalcLayoutModel.ts:31-39`;
- controls для `self_regulating` показывают только напряжение:
  `ElecCalcElectricalTypeControls.tsx:43-59`;
- controls для TT показывают T2/T3/агрессивность/U, но не шаг и нитки:
  `ElecCalcElectricalTypeControls.tsx:61-88`.

**Риск:** пользователь вынужден сначала выполнить расчёт с неявными defaults,
затем изменить укладку и пересчитать. Невозможно заранее воспроизвести требуемый
инженерный вариант одной операцией.

**Рекомендация:** показывать `Шаг навива` и `Количество ниток` в модалке расчёта
до запуска. Значения должны быть per-object; массовое применение — отдельное
явное действие.

### F-04 — MEDIUM: два одновременных поля «Тип кабеля»

**Evidence:**

- раскрытая панель рисует Select типа: `ElecCalcParamsPanel.tsx:52-63`;
- action bar независимо всегда рисует второй Select типа; при показе панели
  скрывается только `typeControls`, но не сам Select:
  `ElecCalcPage.tsx:1110-1129` + `ElectricalBatchActionBar.tsx`.

**Риск:** два контрола одного state визуально создают впечатление разных scopes.

**Рекомендация:** оставить один control. Рядом явно написать scope:
«тип для выбранных строк» или «тип для пересчёта всех».

### F-05 — MEDIUM: поле U лишнее для встроенного саморегулирующегося каталога

**Evidence:**

- U всегда показано для ТЛТ и TT:
  `ElecCalcElectricalTypeControls.tsx:43-59,86`;
- API-контракт говорит, что ТЛТ/ТТ используют паспортное напряжение строки
  каталога; `supply_voltage` — только fallback для кастомного кабеля без
  паспортного `voltage`: `docs/api.md:356-360`.

**Риск:** пользователь думает, что ввод 380 В изменит расчёт встроенного ТЛТ,
хотя результат останется на паспортных 220 В. Кроме того, глобальный default
220 переопределяет сохранённое объектное U до стадии выбора каталожного
напряжения.

**Рекомендация:** для встроенного ТЛТ/ТТ показывать паспортное U как read-only
результат. Редактируемое U оставлять для резистивных типов и кастомных строк без
паспортного напряжения.

### F-06 — MEDIUM: скрытый `layingStep=0.1` может переопределять объект

**Evidence:**

- frontend state создаётся с `layingStep=0.1`:
  `useElecCalcRecalculationParams.ts:11`;
- всегда передаётся batch: `useElecCalcBatchJobOrchestration.ts:111`;
- UI показывает поле только в резистивной ветке:
  `ElecCalcParamsPanel.tsx:128-165`;
- backend для геометрии резервуара отдаёт приоритет override над params объекта:
  `calculation_service.py:2238-2245`.

**Риск:** для TT-резервуара может использоваться скрытый шаг 0,1 м вместо
сохранённого объектного значения.

**Рекомендация:** убрать ненамеренные non-null defaults из общего recalc-state;
показывать геометрию укладки для всех типов, где backend её использует.

### F-07 — MEDIUM: не формализованы scope и наследование полей между источниками

SRS ожидает карточки объектов с четырьмя полями, тогда как реализация — большая
таблица, глобальный action bar, отдельная раскрываемая панель и модалки. API
поддерживает расширенные inputs, но SRS не определяет их scope и правила
наследования. Два XLSX здесь не противоречат друг другу, но ни один из них не
задаёт полный UI/API-контракт переноса значения от объекта к массовому override.
Документ cleanup называет часть решений открытыми вопросами.

**Рекомендация:** перед удалением полей утвердить один контракт:

1. какие значения принадлежат объекту;
2. какие принадлежат CO;
3. какие являются временным массовым override;
4. что означает пустое значение — inheritance или business default.

### F-08 — LOW: frontend неверно сообщает судьбу ручных позиций

В модалке добавления написано: «При пересчёте они удаляются»
(`SpecificationPage.tsx:571-574`). Backend, наоборот, специально сохраняет
строки `source=manual` при генерации (`specification_service.py:63-79,153`), и
это закреплено интеграционным тестом
`backend/app/tests/integration/api/test_specifications.py:130-168`.

**Риск:** сотрудник может повторно добавить уже сохранённые позиции и получить
дубликаты.

**Рекомендация:** заменить подсказку на: «Ручные позиции сохраняются при
пересчёте; автоматические позиции формируются заново».

## Что не следует считать лишним

- `Марка`, `Шаг навива`, `Количество ниток` — обязательные для инженерного
  управления вариантом;
- `T2`, `T3`, агрессивность — нужны для TT, если правильно определены scope и
  inheritance;
- `q`, мощность кабеля, установленная мощность, длина, ток — нужны как
  read-only evidence корректности;
- две длины (`уложенная` и `заказная +10%`) не дублируют друг друга, если
  последняя действительно используется спецификацией.

## Рекомендуемый состав формы для саморегулирующегося кабеля

### На каждой строке/объекте

1. Тип кабеля.
2. Марка: `Авто` или конкретная.
3. Шаг навива, мм.
4. Количество ниток: `Авто` или явное число.
5. Для TT: T2, T3 и среда воздействия — наследуются из объекта, рядом виден
   источник; доступны как явное переопределение.

### Только как read-only результат

1. Паспортная/фактическая мощность, Вт/м.
2. Установленная мощность с навивом и нитками, Вт/м.
3. Уложенная и заказная длина.
4. Общая мощность и ток.
5. Паспортное применённое напряжение.
6. Источник марки/ниток и диагностический код.

### Глобально

- база каталога и критерий подбора — только когда commercial feature доступен;
- массовые overrides — только после выбора строк и с пустым состоянием
  «не переопределять» по умолчанию;
- один Select типа кабеля, без дубликата.
