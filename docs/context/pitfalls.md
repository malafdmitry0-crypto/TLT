# Подводные камни (pitfalls)

Ошибки, на которые уже наступали в этом проекте, с диагнозом и решением.

| Симптом | Причина | Решение |
|---|---|---|
| Frontend в проде стучится в `http://localhost:8000` из браузера, `ERR_CONNECTION_REFUSED` | `docker compose build` подхватывает `.env` в корне, где `VITE_API_BASE_URL=http://localhost:8000/api/v1`. Значение зашивается в prod-бандл через build-arg. | В корневом `docker-compose.yml` build-arg захардкожен: `VITE_API_BASE_URL: /api/v1`. Относительный путь → nginx-прокси внутри frontend-контейнера. Не переопределять без необходимости. |
| Админ `admin@heatcalc.io` / `admin` не логинится после свежего старта | Если `FIRST_ADMIN_EMAIL` не задан в env — backend использует **дефолт из `config.py`: `admin@heatcalc.local`**. Сиды создают админа, но с другим email. | Всегда указывать `FIRST_ADMIN_EMAIL` и `FIRST_ADMIN_PASSWORD` явно в `docker-compose.yml` (для demo — уже прописаны). |
| PDF-экспорт возвращает 500 `AttributeError: 'super' object has no attribute 'transform'` | WeasyPrint 62.3 несовместим с `pydyf >= 0.11`. `requirements.txt` пинит только `weasyprint`, pip при установке берёт свежайший pydyf. | Пинить транзитивные зависимости: `pydyf==0.10.0`. Лучше — `pip-compile` / lockfile (см. `backend/requirements-lock.txt`). |
| Сиды падают на `Резервуар РВС-100 (цилиндр)` с `diameter ≤ 3` | В сиде захардкожен `diameter=5.0` м, а `TankHeatLossParams` валидирует `≤ 3`. | Либо расширить валидатор, либо поправить сид. На работу приложения не влияет — просто шум в логах. |
| `docker compose exec backend pytest` в prod-образе — `executable not found` | Тесты исключены из prod-образа через `.dockerignore` (`app/tests`, `conftest.py`). | Осознанное решение. Для приёмки — `scripts/smoke.sh` извне стека. Для unit-тестов — dev-образ (`Dockerfile.dev`) через `scripts/test.sh`. |
| E2E из репо не видят UI | `playwright.config.ts` дефолтит `E2E_BASE_URL=http://localhost:3001` (порт из `docker-compose.e2e.yml`). Для demo-стека фронт на `:8080`. | `E2E_BASE_URL=http://localhost:8080 ADMIN_EMAIL=admin@heatcalc.io ADMIN_PASSWORD=admin npx playwright test` |
| `docker compose build` игнорирует изменения `entrypoint.sh` | Docker-кэш может застрять. | `docker compose build --no-cache backend` |
| `docker compose build` с кастомным build-arg всё равно берёт из `.env` | `.env` override'ит командные аргументы для `docker compose`. | Захардкодить значения в build-args `docker-compose.yml` (как сделано для `VITE_API_BASE_URL`). |
| Импорт CSV проекта с JSON-полями падает `В файле отсутствует секция [SECTION];metadata` | `csv.Sniffer()` выбирает `,` из-за запятых внутри JSON в ячейках, а реальный разделитель — `;`. Парсер видит `[SECTION];metadata` как одну ячейку → секция не опознана. | `project_io_service.py:_detect_delimiter` теперь читает символ сразу после `[SECTION]` в первой строке — детерминированный якорь. Sniffer остался fallback'ом. Regression-тест: `test_project_io.py::test_roundtrip_export_import_with_json_commas` + e2e round-trip. |
| Импорт обратно не работает, если экспорт и импорт через разные кнопки (одиночный vs пакетный) | Ранее `import-csv` требовал секцию `[SECTION];metadata` (одиночный формат), а `import-csv-bulk` — `[SECTION];projects` (пакетный). Они не были взаимозаменяемы. | Оба импортёра теперь принимают оба формата: `import-csv` обрабатывает первый проект из `projects`, `import-csv-bulk` «виртуализует» одиночный `metadata` в один проект. Тесты `test_cross_format_*` проверяют обе комбинации. |
| `MultipleResultsFound` при повторном bulk-импорте | `scalar_one_or_none()` при проверке конфликта `task_number`: у сотрудника могло быть 2+ проектов с одинаковым номером после нескольких импортов (task_number не UNIQUE). | Заменено на `.first()` на запрос `Project.id`. Regression-тест: `test_bulk_import_repeat_without_MultipleResultsFound`. |
| Demo-образы не запускаются у заказчика: `platform linux/arm64/v8 does not match host platform linux/amd64` → `container heatcalc_backend is unhealthy` | Сборка на Apple Silicon производит arm64-образы, тогда как у заказчиков обычно amd64 (Windows/Linux). Эмуляция через QEMU работает нестабильно, особенно для Python с native-расширениями (psycopg/bcrypt). | С версии **1.2.1-demo** шлём 4 файла (по одному на сервис на арку, формат `docker save`). Скрипт `demo/load.sh` определяет арку через `uname -m` и грузит правильный. Сборка: `scripts/build-multiarch-demo.sh` использует `docker buildx --platform linux/<arch> --output type=docker`. |
| `docker load` падает с `open /var/lib/docker/tmp/docker-import-XXX/blobs/json: no such file or directory` при загрузке multi-arch OCI tarball | Классический Docker engine (без containerd image store) **не понимает** OCI manifest list через `docker load`. На Docker Desktop с включённым containerd store (Settings → General) работает, на дефолтном Linux-демоне — нет. | Не использовать `--output type=oci` для distribution-tarball'ов. Использовать `--output type=docker` — это формат `docker save`, совместим с любой версией Docker. За одну сборку получается tar только под одну арку — ОК, делаем по файлу на каждую (см. предыдущую запись). |
| Multi-arch buildx падает на arm64-стейдже с `Exec format error` или висит на apt | QEMU/binfmt не зарегистрирован в ядре хоста. На Docker Desktop ставится автоматически, но после рестарта Docker может слететь. | `docker run --rm --privileged tonistiigi/binfmt --install all` — переустанавливает binfmt-handlers. Скрипт `build-multiarch-demo.sh` делает это автоматически в начале. |
| Multi-arch сборка под Apple Silicon идёт мучительно долго (15+ мин) на amd64-стейдже | Эмуляция x86 через QEMU медленнее нативного arm64 в 5-10 раз, особенно на компиляции wheel'ов (gcc, cython). | Включить **Rosetta 2 acceleration** в Docker Desktop (Settings → General → "Use Rosetta for x86_64/amd64 emulation"). Дёт ускорение ~3-5×. Для CI/прода — собирать на natively amd64 раннере. |
| `ProtectedRoute` редиректил аутентифицированного пользователя на `/` при reload | `useAuthStore.hydrate()` вызывался в `useEffect(App)` — асинхронно после первого рендера. ProtectedRoute видел `role=null` и Navigate('/'). | Перенесено в `readInitialState()` — синхронно при импорте модуля. `App.tsx` больше не вызывает `hydrate()`. |
| `xlsx` (SheetJS) — high-severity CVE (prototype pollution, ReDoS), upstream без фикса | Использовался только в неподключённых утилитах (`utils/excel.ts`) — мёртвый код. Вся работа с Excel идёт через backend (`openpyxl`). | Удалён пакет, файл и тест. Один CVE-high закрыт без замены библиотеки. |
| `MultipleResultsFound` / 18 CVE / тесты падают при апгрейде | Major-апгрейд `fastapi` 0.115→0.118, `weasyprint` 62.3→68.0 + `pydyf` 0.10→0.11 (раньше пинили 0.10 из-за бага), `python-jose` 3.3→3.4 | Пин обновлён в `requirements.txt` с комментариями-CVE. 18 → 9 уязвимостей (остаток — `pip`/`wheel` базового образа + dev-only `pytest` + транзитивный `pyasn1`). |
| In-memory rate limiter сбрасывался при рестарте + не работал на N инстансах | Защита `/auth/guest` от ботов держалась в `dict[ip → deque]` в RAM | Добавлен `RedisRateLimiter` (sliding window через `ZADD`/`ZREMRANGEBYSCORE`). Factory `_build_limiter` выбирает Redis если `REDIS_URL` задан, иначе in-memory. Redis service добавлен в `docker-compose.yml` и `demo/docker-compose.yml`. |

| Prod-фронт открывается, но на каждом запросе — `Access-Control-Allow-Origin` ошибка в Console; авторизация не работает | `CORS_ORIGINS` в `backend/app/core/config.py` забит дефолтом на `localhost:*`, реальный домен заказчика туда не попал. | В prod **обязательно** задать `CORS_ORIGINS=https://мойдомен.ru,https://www.мойдомен.ru` в `.env`. Конфиг теперь читает comma-separated формат через `_split_cors_origins`. См. `.env.production.example` и `docs/playbooks/deploy-reg-ru.md`. |
| Caddy первый запуск висит на ACME challenge, сертификат не выпускается | Порт 80 на VPS закрыт фаерволом — Let's Encrypt не может достучаться через HTTP-01. Либо DNS A-запись ещё не пропагировалась. | `ufw allow 80` обязательно. Проверка DNS — `nslookup мойдомен.ru` должен показать IP сервера. Caddy retry'ит ACME до 5 минут — если всё ещё нет, `docker compose logs caddy` покажет детали. |

## Как пополнять

Когда встречаете баг, диагностика которого заняла > 10 минут —
добавьте сюда строку. Формат: **Симптом** (что видно пользователю) ·
**Причина** (root cause) · **Решение** (конкретный фикс).
