# Расчётный контур TLT: инженерный путеводитель

**Сверено:** 2026-07-19

Документ объясняет сквозной поток простым инженерным языком. Он не заменяет
формульный контракт. При расхождении приоритет имеют
`docs/business-logic-contract.md`, первичные ТНП, machine-readable registry,
код и тесты согласно `codex-docs/source-documents.md`.

## Сквозной поток

```text
Проект и объект
  -> теплопотери трубы/резервуара
  -> распределение объекта в именованный UUID ЭР
  -> подбор кабеля и электрические результаты
  -> спецификация выбранных ЭР
  -> preview/print/export отчёта
```

Каждый downstream-результат должен оставаться в scope конкретного проекта,
объекта и UUID ЭР. Числовой `variant_number` — временная migration metadata, а
не пользовательская identity решения.

## Общие инварианты

- Геометрические единицы нормализуются до единиц, ожидаемых формулой; UI/API не
  должны незаметно смешивать миллиметры и метры.
- Коэффициент запаса применяется один раз. Тепловой результат, передаваемый в
  электрический подбор, не должен уже содержать тот же множитель повторно.
- `location_indoor=0.9` и `wind_factor` являются явно отмеченной app policy с
  source gap, пока не подтверждены отдельным первичным источником.
- Фактическая длина кабеля и заказная длина различаются. Заказная длина
  включает утверждённый монтажный резерв и коммерческое округление.
- Ошибочные, unsupported и stale результаты не смешиваются с успешными
  итогами спецификации и отчёта.
- `mineral` и `skin` видимы как типы/исторические assignments, но остаются без
  утверждённой расчётной методики.

## Трубопровод: как читать расчёт

Минимально нужны геометрия трубы, длина, температуры продукта и среды,
конкретный материал/слои изоляции и условия размещения. Для подземной ветки
добавляются глубина и теплопроводность грунта; для локальных элементов — их
количество и эквивалентная длина.

Физическое ядро:

```text
R_total = R_wall + sum(R_insulation) + R_external
q = delta_T / R_total
Q = q * effective_length * approved_factors
```

Проверяйте в результате:

- `heat_loss_per_meter`, Вт/м — удельные потери для передачи в подбор;
- `total_heat_loss`, Вт — полные потери объекта;
- `effective_length`, м — длина с локальными элементами;
- составляющие сопротивления и диагностические поля;
- source/category/error metadata, если расчёт неуспешен.

Быстрые инженерные проверки:

- увеличение длины при прочих равных увеличивает `Q`, но не должно менять
  чистое `q`;
- увеличение толщины корректной изоляции должно уменьшать потери;
- подземная ветка включается фактической глубиной, а не только подписью режима;
- различие `Q` и `q * pipe_length` объясняется effective length и утверждёнными
  коэффициентами, а не скрытым вторым запасом.

## Резервуар: как читать расчёт

Нужны форма и размеры резервуара, температуры, стенка, изоляция и наружные
условия. Поддерживаются базовые формы, закреплённые текущим контрактом;
подземная модель разделяет площадь в воздухе и грунте.

Физическое ядро:

```text
q = delta_T / (R_wall + R_insulation + R_external)
Q = q * surface_area * approved_factors + Q_additional
```

Для частично подземного объекта воздушная и грунтовая части считаются
раздельно. `Q_additional` добавляется согласно первичному контракту и не должен
скрыто получать повторный тепловой коэффициент.

Проверяйте `surface_area`, `air_surface_area`, `ground_surface_area`,
`heat_loss_per_m2`, `total_heat_loss` и составляющие сопротивления. Идеальная
геометрия не моделирует автоматически люки, патрубки, опоры и тепловые мосты;
такие эффекты требуют доказанного правила или явной добавки.

## Электротехнический расчёт

Перед подбором объект должен быть явно распределён в UUID ЭР с поддерживаемым
`system_type`. Расчёт использует требуемую мощность из теплового контура,
условия эксплуатации, напряжение, укладку и выбранную политику каталога.

Поддерживаемые расчётные семейства:

- саморегулирующийся ТЛТ;
- ТТН/ТТВ/ТТХ с температурным выбором серии и расчётом числа ниток;
- резистивные ТТ Р1/ТТ Р3 в утверждённых manual/auto режимах.

Автоподбор фильтрует технически допустимые позиции и затем применяет явную
commercial policy. Ручной выбор не отменяет температурные, токовые и иные hard
limits. Для результата важны марка, фактическая/заказная длина, число ниток,
мощность, ток, напряжение, режим выбора, источник каталога и diagnostics.

Ключевые проверки:

- выбранная марка действительно принадлежит разрешённому источнику каталога;
- расчёт не читает assignment или cache другого ЭР;
- `order_cable_length >= installed_cable_length`;
- ручной выбор после reload остаётся ручным и не подменяется автоподбором;
- error/unsupported/stale состояние сохраняется и диагностируется.

## Спецификация и отчёт

Спецификация строится только для явно выбранного непустого списка UUID ЭР.
Generation использует versioned project defaults и сохраняет immutable snapshot
resolved options. Изменение defaults не регенерирует результаты скрыто, а
stale-ит несовпадающие snapshots.

При проверке спецификации отдельно считайте:

- кабельные суммы по фактической и заказной длине;
- штучные позиции и упаковочные коэффициенты;
- успешные, исключённые, stale и unsupported строки;
- независимость глав и итогов разных ЭР.

Report обязан использовать тот же явный UUID-list и не выводить stale данные в
успешные итоги/печать/export.

## Диагностический чек-лист

1. Зафиксировать project/object/UUID ЭР и входные единицы.
2. Найти требование и formula/source version.
3. Сверить нормализованный API payload с backend schema.
4. Проверить сохранённый результат после reload.
5. Проследить тот же UUID через specification/report.
6. Подтвердить число независимым oracle и boundary/metamorphic cases.
7. Не принимать результат без понятного `error_code`/category для неуспеха.
