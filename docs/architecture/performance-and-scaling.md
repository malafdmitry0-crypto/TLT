# Производительность и масштабирование

**Обновлено:** 2026-07-19

**Статус:** действующая архитектурная позиция и план доказательства; не отчёт о
пройденном performance gate.

## Контракт масштаба

| Уровень | Объём | Назначение | Статус |
|---|---:|---|---|
| S | 50 объектов | Текущий runtime guard и исторический NFR-контур | Поддерживается текущей конфигурацией |
| Target | 500 объектов × 5 именованных ЭР | Целевой контракт PDL-ER-27 | Не доказан полным gate |
| Stress | 1000–3000 объектов | Проверка линейности, утечек и деградации | Только изолированный стенд; не продуктовая гарантия |

PDL-ER-27 требует доказать импорт, расчёты, таблицы, спецификацию и отчёт на
500 объектах и пяти ЭР. Расчёт 500 объектов и спецификация одного ЭР должны
укладываться в 30 секунд на минимальной согласованной конфигурации. До такого
evidence значение `GUEST_MAX_OBJECTS_PER_PROJECT=50` остаётся rollout guard;
простое изменение константы не означает поддержку 500 объектов.

Источники требования:

- `docs/tnp/cases/guest-specification/product-decisions.md`, PDL-ER-27;
- `codex-docs/requirements-map.md`;
- `docs/srs/03-elements-list.md`.

## Архитектурная позиция

Текущий выбор — модульный монолит FastAPI + отдельный worker для длительных
задач, PostgreSQL и Redis. Границы API, расчётного ядра, очереди и хранения
следует сохранять явными, но выделять микросервисы только по измеренному
независимому workload или организационной границе.

- Скалярные стационарные формулы и перебор небольшого каталога остаются на
  Python. Переход на Go, Cython, PyPy, `numpy` или `scipy` без CPU-профиля и
  воспроизводимого bottleneck не обоснован.
- Длительный CPU-bound расчёт не должен блокировать API event loop. Сначала
  используются существующие worker/process boundaries; threads не считаются
  универсальным решением для чистого Python CPU-bound кода.
- `numpy`/`scipy` или отдельный расчётный сервис можно повторно оценить, если
  появятся утверждённые сегментные, нестационарные, гидравлические или
  оптимизационные алгоритмы и профиль покажет значимую стоимость вычислений.
- Расчётный модуль, если он когда-либо будет выделен, должен оставаться чистой
  функцией входных данных и не владеть БД, авторизацией или workflow.
- Горизонтальное масштабирование API и worker вводится по очереди, latency,
  CPU/RAM и числу DB connections, а не заранее.

## Обязательный gate перед повышением лимита

Один воспроизводимый прогон должен доказать всю цепочку, а не отдельную быструю
функцию:

1. Импорт детерминированного набора из 500 объектов, частичные ошибки и
   идемпотентный повторный запуск.
2. Сохранение и повторная загрузка 500 объектов; отсутствие N+1, full scan и
   недиагностируемых ошибок.
3. Теплотехнический расчёт и пять независимых ЭР с корректными UUID,
   traceability и итоговыми категориями.
4. Постраничные query/search/filter/sort API и UI-таблицы без clipping,
   horizontal-scroll регрессий и серии long tasks.
5. Спецификация выбранного ЭР, правильные бизнес-суммы и отсутствие смешения
   successful/error/unsupported/stale результатов.
6. Отчёт/PDF, время генерации, размер ответа и сохранение выбранного ЭР по всей
   цепочке.
7. `db-invariants` после пользовательского сценария, включая изоляцию проектов
   и ЭР.

Для каждого этапа сохраняются конфигурация стенда, seed/source-файл, commit,
число API/worker процессов, p50/p95/max, CPU/RAM, DB connections, SQL count,
payload size, число успешных/ошибочных записей и итоговый артефакт. Результат
без этих метаданных не является release evidence.

## Диагностика до оптимизации

1. Разделить время на upload/parse, DB, queue wait, calculation, query,
   serialization, network и render.
2. Проверить `pg_stat_statements`, число SQL-запросов и `EXPLAIN (ANALYZE,
   BUFFERS)` конкретного медленного запроса.
3. Снять CPU/память API, worker, PostgreSQL и Redis; проверить lag/pending и
   dead-letter очереди.
4. Для frontend использовать React Profiler/Playwright trace, long tasks,
   geometry/overflow assertions и размер загруженных данных.
5. Повторить одинаковый seed минимум на S=50 и Target=500. Нелинейный рост
   исследовать отдельно; 1000–3000 строк использовать только как stress.

Индекс, GIN/expression index, изменение пула или batch rewrite добавляются
только под наблюдаемый запрос и проверяются сравнительным планом. Без evidence
не вводятся partitioning, read replica, PgBouncer, денормализация, speculative
Redis caching, микросервисы или смена языка.

## Текущее evidence и его границы

- `backend/app/tests/integration/api/test_performance_nfr.py` покрывает
  исторические NFR и отдельные stress-пробы, но не заменяет full-flow gate
  500 × 5 ЭР.
- `backend/app/tests/integration/db/test_perf_rollout_guard.py` намеренно держит
  default 50; будущий full-flow тест на 500 помечен `skip`.
- `docs/audit/2026-06-07-performance.md` и
  `docs/audit/2026-06-07-frontend-performance.md` — датированные статические
  аудиты. Их findings нужно перепроверять по текущему коду перед работой.
- `scripts/codex-functional-audit.sh smoke`, `user-flows`, `layout` и
  `db-invariants` дают функциональные части evidence, но не заменяют измерения
  на зафиксированной минимальной конфигурации.

Пока skipped full-flow gate не реализован и не зелёный, статус Target остаётся
`needs verification`, а runtime guard — 50.
