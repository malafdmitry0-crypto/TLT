# Промпт: можно ли вернуть сферический резервуар

**Тип:** read-only инвестигация. Код, формулы, API, UI и тесты не менять.

**Цель:** ответить, можно ли добавить сферу в текущую архитектуру, какие
формулы для этого нужны и куда они встают. Не реализовывать.

**Конвейер кейса 1 неделим:** тепло → электрорасчёт → спецификация. Сфера
считается добавленной только если объект проходит все три шага, а не только
теплопотери.

## Контекст, который нельзя потерять

1. Кейс 1, ред. 4 от 07.07.2026, стр. 25, требует форму резервуара
   «цилиндрический, прямоугольный или сферический».
2. Сферу уже делали (Slice 4, 2026-08-02): точная радиальная тепломодель,
   `formula_model=tank_heat_loss_spherical_radial`, запрет подземки,
   критический радиус изоляции. Коммит ориентир: `fa74cba`.
3. 2026-08-05 сферу выпилили целиком (`921d347`, миграция `0044`). Причина
   не «не умеем считать тепло», а отсутствие утверждённой раскладки кабеля
   в §6.13. До удаления ЭР отдавал типизированную ошибку: тепло есть,
   формула укладки не утверждена.
4. В §6.13 длина на резервуаре задана только для цилиндра и параллелепипеда:
   `P = πD` или `P = 2(A+B)`, затем `L = (P/2)·(Hоб/Sукл)`.
5. Отдельного поля «метод укладки» в продукте нет. У бака на тепловой форме
   есть «Высота обогрева» и «Шаг укладки». У трубы в таблице ЭР — шаг навива
   и нитки. Спецификация форму бака не читает.

Работай с текущим HEAD, не с памятью чата. Коммиты и отчёты ниже — вход для
трассировки, не замена чтения кода.

## Что расследовать

### A. Можно ли добавить

Ответь отдельно по каждому шагу конвейера: **да / да с оговоркой / нет**.

- Тепло, воздух и помещение.
- Тепло, подземно.
- Электрорасчёт (длина → марка → секции → заказ).
- Спецификация.
- Импорт / экспорт / сиды / e2e, которые сейчас отвергают `spherical`.

«Можно» означает: формулы и точки вставки понятны, стопоры перечислимы,
чужие объекты (труба, цилиндр, параллелепипед) можно не ломать. Не означает
«уже реализовано».

### B. Какие формулы нужны

Разложи на три полки. Для каждой напиши фактическую запись, входы, единицы,
что уже есть в коде и чего нет.

**1. Тепло**

Сравни два допустимых варианта, не выбирая молча:

- плоская стенка, как у текущего бака: \(R=\delta/\lambda\), \(S=\pi D^2\),
  \(Q=qS\), затем \(Q_{\text{расч}}=Q_{\text{баз}}K+Q_{\text{доп}}\);
- точная сферическая оболочка Slice 4:
  \(R=(1/(4\pi\lambda))(1/r_{\text{вн}}-1/r_{\text{нар}})\),
  \(Q=\Delta T/R_\Sigma\), критический радиус
  \(r_{\text{кр}}=2\lambda_{\text{нар}}/\alpha\).

Для каждого варианта: indoor/outdoor α как сейчас (`9` и `11,6+7√v`);
нужна ли высота; что делать с подземкой; какой `formula_model` / version.

**2. Длина кабеля**

Сравни два варианта укладки на поясе высотой \(h\) с шагом \(s\),
\(0{,}1\le s\le 0{,}4\) м, \(0<h\le D\):

- как цилиндр: \(P=\pi D\), \(L=(P/2)\cdot(h/s)\) — уже живёт в
  `compute_tank_cable_length` для `cylindrical`;
- от площади пояса: \(S_{\text{пояс}}=2\pi R h=\pi D h\), \(L=S_{\text{пояс}}/s=\pi D h/s\).

Покажи на одном примере (\(D\), \(h\), \(s\)), насколько длины расходятся.
Зафиксируй: поля `heating_height` и `laying_step` уже есть; отдельный
«метод укладки» не нужен, если выбран один вариант.

Дальше ЭР стандартный и от формы не зависит:

```text
P_треб = q · K
P_каб · Kнав · N ≥ P_треб     (у бака Kнав = 1)
n = ceil(Lтреб / Lогр), далее секции и Lзаказ = ceil(Lфакт · 1.10)
```

Для бака `q` сейчас считается как
`(total_heat_loss_design / Kтепл) / Lбазы`. Проверь, что это останется
верным для сферы (в том числе с `Qдоп`).

**3. Спецификация**

Подтверди по коду, что генератор не ветвится по `shape`. Если ветвится —
перечисли где.

### C. Как это вписывается в архитектуру

Нарисуй путь данных сферы от поля формы до спецификации и пометь каждый
стоп, который сейчас режет `spherical`.

Минимальный список стопоров для проверки (ищи и другие):

```text

```

Для каждого стопора: файл, условие, что случится, если только добавить
`'spherical'` в enum без формулы / с формулой цилиндра / с формулой пояса.

Отдельно ответь:

- нужна ли миграция БД, или достаточно снять запрет записи (после `0044`
  сферических строк в БД нет);
- ломает ли новый `formula_model` сохранённые результаты цилиндра и
  прямоугольника;
- должен ли `heating_height` быть `≤ diameter` только у сферы;
- трогает ли это фронтенд-очередь (`docs/frontend/refactor-backlog.md`)
  или это узкий enum/visibility slice.

### D. Рекомендация, не реализация

В конце дай одну рекомендацию владельцу методики:

| Путь | Когда выбирать |
|---|---|
| A. Сфера как цилиндр по укладке, тепло \(S=\pi D^2\) плоской стенкой | Быстрее закрыть пункт кейса, одна формула с баком |
| B. Тепло — радиальная оболочка; кабель — \(L=\pi D h/s\) | Честнее физика, другой `formula_model`, чуть больше тестов |
| C. Не добавлять, пока нет подписи под формулой длины | Если владелец не готов зафиксировать L |

Подземную сферу в первый заход включай только если в коде и кейсе уже есть
готовая модель. Иначе вынеси в «не в этом объёме».

Не предлагай вернуть сферу «только в тепле». Это снова тупик 2026-08-05.

## Формат отчёта

Один файл `docs/audit/YYYY-MM-DD-spherical-tank-feasibility/snapshot.md`:

1. HEAD и вердикт в 8–10 строк.
2. Таблица «шаг конвейера → можно ли → условие».
3. Формулы с единицами и выбранным вариантом A/B/C.
4. Карта архитектуры и таблица стопоров (файл / символ / эффект).
5. Что не входит в первый объём.
6. Открытые решения владельца методики — списком, без реализации.

Не пиши план внедрения, не оценивай дни, не открывай PR. Если чего-то не
читал в коде — так и напиши, не закрывай догадкой.
