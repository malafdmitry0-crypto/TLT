# Сверка входного контракта электрорасчёта с Case 1

Статус: реализованный P0-контракт для `self_regulating_tt`.

Единственный нормативный источник расчётной логики — [Case 1, редакция 4 от
07.07.2026](<../../../ТНП/1_Кейс_«Расчёт_спецификации_для_неавторизованных_пользователей» (1).pdf>),
прежде всего §6.13, §6.14 и §6.18. [«Параметры
Кабеля.xlsx»](<../../../ТНП/Параметры Кабеля.xlsx>) используется только там,
где Case 1 прямо на него ссылается: для секционирования по марке и минимальной
температуре включения. Старые PDF/Excel-алгоритмы выбора серии, `q1*T3+q2` и
суффикса по `R` не являются источником этого контракта.

## Принятое решение

Электрорасчёт выполняется по паспортным строкам каталога, а не по старому
контракту `T1/T2/T3/R`:

- мощность марки — паспортная `nominal_power`;
- температурный допуск — `T_env >= T_min` и `T_product <= T_max`, включая
  равенство на границе;
- автоматический подбор перебирает все точные марки и `N = 1, 2, 3`;
- ручная точная марка никогда не заменяется автоматически, а при незаданном
  `N` проверяется ровно с одной ниткой;
- напряжение не участвует в допуске или сортировке марки, но остаётся явным
  downstream-входом для тока и секций;
- цилиндрические и прямоугольные резервуары считаются по формулам §6.13;
- проектные файлы с неподдерживаемой формой резервуара отклоняются до
  электрорасчёта без автоматического преобразования геометрии;
- спецификация допускается только по актуальным успешным результатам ЭР.

Обратной совместимости с прежним TT-контрактом нет. Версия формулы нужна не для
ветвления алгоритмов, а только для определения устаревшего сохранённого
результата.

## Источники входов

| Канонический вход | Источник UI/данных | Правило |
|---|---|---|
| `product_temperature_c` | Heat: температура продукта | Обязателен; проверяется против `T_max` точной марки |
| `ambient_temperature_c` | Heat: температура среды | Для обычной прокладки — воздух; для подземной трубы — грунт; для подземного резервуара берётся более холодное из доступных значений |
| `cold_start_temperature_c` | Heat: минимальная температура включения | Обязательное поле для трубы и резервуара, диапазон UI `-40…+10 °C`; применяется только в §6.14 |
| `heat_loss_per_meter_w` | Актуальный Heat-результат | Для трубы — теплопотери на метр до запаса; для резервуара рассчитываются из общей теплопотери без повторного `K` |
| `safety_factor` | Heat-результат/параметр объекта | Применяется ровно один раз |
| `base_length_m` | Heat-геометрия | Труба: актуальная эффективная длина; резервуар: расчёт по периметру, высоте обогрева и шагу укладки |
| `outer_diameter_mm` | Геометрия трубы | Нужен только при заданном шаге навива; для резервуара недопустим |
| `winding_pitch_mm` | ЭР: строка трубы/окно подбора | `null`/`0` означает прямую укладку; коэффициент вычисляет backend |
| `thread_count` | ЭР: строка/окно подбора | `1…3`; `null` означает автоподбор, кроме ручной марки, где `null => 1` |
| `manual_cable_model` | ЭР: точная марка из backend options | Это полный `full_mark`, включая исполнение; сокращение до базовой модели запрещено |
| `nominal_voltage_v` | ЭР, с сохранением в assignment | Начальное проектное значение `230 В`, пользователь может задать любое положительное `U`; на выбор марки не влияет |
| `max_section_start_current_a` | Настройка проекта | Обязательный `Iдоп` для §6.14; object/request override и скрытого значения нет |
| `selection_policy` | ЭР | В P0 разрешён только `technical_minimum` |
| `tank_shape`, размеры, `heating_height`, `laying_step` | Геометрия Heat + явная раскладка резервуара в UI | Поддержаны `cylindrical` и `rectangular`; трубные `D`/шаг навива для резервуара отклоняются |

### Смежные поля Heat

Case 1 на стр. 26–27 отдельно называет данные карточки объекта, которые могут
понадобиться следующим этапам, но §6.13 не использует их для выбора TT-марки:

- `environment`;
- `zone_classification`;
- `temperature_group`;
- `steam_tracing`;
- `vapor_temperature`;
- `maintain_temperature`.

Они сохраняются в карточке объекта, но не отправляются как входы TT-selector.
Напряжение перенесено из Heat в явный UI электрорасчёта. Ложные поля
`aggressive_product`, вводимый `winding_coefficient` и `connection_type` из
Heat удалены.

Если клиент всё же передаёт в TT query/internal override старые selector-поля
`maintain_temperature(_c)`, `vapor_temperature`, `steam_temperature_c`,
`steam_tracing`, `aggressive_product`, `winding_coefficient` или
`connection_type`, `max_section_start_current_a` или
`max_start_current_per_section`, backend отвечает `ELECTRICAL_INPUT_RETIRED`. Эти имена не
игнорируются и не преобразуются в новые входы. В типизированном JSON body те же
удалённые поля отсекаются схемой `extra="forbid"` как ошибка валидации запроса.

## Формулы §6.13

### Требуемая мощность

Для трубы:

```text
q = heat_loss_per_meter
P_req = q * K
```

Для цилиндрического резервуара:

```text
perimeter = pi * diameter
L_base = (perimeter / 2) * (heating_height / laying_step)
```

Для прямоугольного резервуара:

```text
perimeter = 2 * (length + width)
L_base = (perimeter / 2) * (heating_height / laying_step)
```

Затем для резервуара:

```text
Q_without_repeated_K = total_heat_loss_design / K
q = Q_without_repeated_K / L_base
P_req = q * K
```

Так `K` применяется один раз, а дополнительные теплопотери резервуара не
теряются.

### Навив трубы

```text
прямая укладка: K_nav = 1
S = winding_pitch_mm / 1000
если S <= D: ошибка
K_nav = sqrt(1 + (pi * D / S)^2)
```

Допустимый максимум:

| Наружный диаметр | `K_nav_max` |
|---|---:|
| `D_mm < 57` | `1.0` |
| `D_mm = 57` | `1.1` |
| `57 < D_mm <= 75` | `1.2` |
| `75 < D_mm <= 89` | `1.3` |
| `89 < D_mm <= 108` | `1.4` |
| `D_mm > 108` | `1.5` |

Резервуар всегда имеет `K_nav = 1`; его `laying_step` измеряется в метрах и не
является шагом навива трубы.

### Допуск и сортировка марки

Для каждой точной марки и проверяемого `N`:

```text
T_env >= T_min
T_product <= T_max
P_installed_per_meter = P_cable * K_nav * N
P_installed_per_meter >= P_req
```

Автоматические кандидаты сортируются строго по:

1. `N` по возрастанию;
2. `P_cable` по возрастанию;
3. `P_cable * N` по возрастанию;
4. полной марке по алфавиту.

Исполнения `-СР`/`-СТ` не синтезируются из среды или отдельного `R`. Backend
перебирает точные BOM-марки с номенклатурным кодом. При полном техническом
равенстве действует только алфавитный tie-break из Case 1.

### Длина, мощность и ток

До секционирования:

```text
installed_length = L_base * K_nav * N
order_length = installed_length * 1.1
total_power = P_cable * installed_length
current = total_power / supply_voltage
```

После §6.14 физической установленной длиной становится `L_fact` одинаковых
секций. Итоговые мощность, ток и заказная длина считаются от `L_fact`, поэтому
заполнение последней секции не скрывается из результата и спецификации.

## Секции §6.14

По базовой модели и `cold_start_temperature_c` выбирается точная строка
`Параметры Кабеля.xlsx`, а если её нет — ближайшая более холодная. Более тёплая
строка никогда не используется как fallback.

```text
L_tok = I_dop / I_start_specific
L_ogr = round_down(min(L_max, L_tok), 0.001 m)
N_sections = ceil(L_required / L_ogr)
L_section = L_ogr
L_fact = L_section * N_sections
L_excess = L_fact - L_required
```

Последняя секция не укорачивается. Final gate проверяет для каждой секции
одинаковые длину, напряжение, мощность, рабочий ток и стартовый ток, а также:

- `L_section <= L_max`;
- `I_start_section <= I_dop`;
- `L_fact >= L_required`;
- установленная мощность не меньше требуемой;
- идентичность power/section/BOM snapshot.

## Каталоги и точная марка

Расчёт объединяет три активных immutable snapshot:

- power: базовая модель, `nominal_power`, `T_max`;
- section: строки минимальной температуры включения, `L_max` и удельный
  стартовый ток; минимальная поддержанная температура модели задаёт `T_min`;
- BOM: точный `full_mark` и `nomenclature_code` для спецификации.

Отсутствующая строка, дубликат полной марки, неположительная паспортная
мощность или каталог без идентичности закрывают расчёт ошибкой. Старые `q1`,
`q2`, `max_vapor_temp` и каталожное `voltage_v` могут оставаться метаданными
источника, но формулы Case 1 их не читают.

## Fail-closed и отсутствие совместимости

- Поддерживается только `self_regulating_tt`; условные марки `ТЛТ-*` и старые
  cable types не пересчитываются.
- Формула имеет идентичность `electrical-tt-v3-case1-r4`; результат другой
  версии/отпечатка становится stale и должен быть пересчитан.
- Любое положительное пользовательское напряжение допустимо; отсутствие или
  неположительное значение делает результат невалидным.
- Нет fallback `T3 = T_product`, скрытого `Tвкл = -20`, скрытого `R = false`,
  фиксированного `U = 230` внутри формулы или молчаливой подмены ручной марки.
- Для коммерческих политик P0 отвечает
  `ELECTRICAL_SELECTION_POLICY_UNSUPPORTED`. Коммерческий постфильтр Case 1
  будет отдельной задачей после появления подтверждённых price/stock/lead-time
  данных; до этого UI предлагает только технический минимум.
- Ошибка расчёта сохраняется в строке ЭР и остаётся видимой после reload.
- Пакетный пересчёт по умолчанию пропускает ручные марки.

Версия здесь не означает поддержку нескольких алгоритмов. В runtime существует
только текущая формула; версия служит маркером актуальности сохранённого
результата и каталогов.

## UI-контракт

Heat:

- собирает температуры объекта, среду, `K`, геометрию и обязательную
  минимальную температуру включения;
- для резервуара показывает высоту обогрева и шаг укладки;
- сохраняет смежные параметры карточки, но не выдаёт их за входы TT-selector;
- не показывает `aggressive_product`, `connection_type`, напряжение или ручной
  коэффициент навива.

Электрорасчёт:

- показывает редактируемое `U` с начальным значением `230 В`;
- объясняет, что `T_env`, `T_product` и `K` приходят из Heat;
- получает точные марки и паспортные `P/Tmin/Tmax` только от backend;
- позволяет задать трубный шаг навива, `N`, точную ручную марку и раскладку
  резервуара;
- сохраняет `U` и поддерживаемые per-object overrides в assignment конкретного UUID ЭР;
- читает `Iдоп` только из project electrical settings.

## Допуск в спецификацию, §6.18

Кнопка «Сформировать спецификацию» не является обходом backend preflight:

- disabled при loading/error readiness, пустом ЭР, `stale`, `error` или
  `unsupported`;
- enabled, если есть хотя бы один `ready` объект и остальные строки только
  `unassigned`;
- `unassigned` исключаются лишь после явного подтверждения пользователя;
- распределённые строки без кабеля, секций или с критической ошибкой блокируют
  спецификацию своего ЭР;
- в кабельную часть попадают только успешные расчёты и точные
  `nomenclature_code`;
- если для аксессуара есть несколько каталожных позиций, UI показывает их в
  модальном окне, требует выбор и сохраняет его до повторного preflight.

Старый `SPEC_RESULT_STALE` после изменения объекта означает именно
несовпадение актуальных ревизий. Пользователь сначала пересчитывает ЭР; кнопка
не переводит его в заведомо заблокированную спецификацию.

## P0: до и после

| Было | Стало |
|---|---|
| Серия выбиралась по старым `T1/T2`, мощность — по `q1*T3+q2` | Перебираются все точные марки по паспортным `P/Tmin/Tmax` |
| Суффикс марки строился из скрытого `R` | Используется только точный BOM `full_mark` |
| `T3` подменялась температурой продукта | `T3` не является входом §6.13 и не отправляется в selector |
| UI собирал поля, которые backend игнорировал | Ложные поля удалены; необходимые `Tвкл`, `U`, навив и tank-layout видимы |
| Напряжение было скрытой константой 230 В | 230 В — начальное значение UI; расчёт и assignment поддерживают положительное `U` |
| Резервуар мог унаследовать трубный шаг/диаметр | Tank-layout отделён; трубные входы дают typed error |
| Запас резервуара мог применяться дважды | `K` применяется ровно один раз, включая `Qдоп` |
| Старая/ошибочная строка могла вести пользователя в спецификацию | Кнопка и backend preflight требуют актуальный валидный ЭР |

## Проверка

Фактически выполнены только целевые проверки этого изменения:

- backend unit/integration: selector, секции, resolver, pipeline, схемы и
  сквозной API acceptance;
- frontend unit/integration и typecheck: Heat registry/mappers/forms, TT
  controls/options, формулы admin и readiness спецификации;
- Playwright desktop Chromium: Case 1 regression, Heat → ЭР, stale после
  изменения Heat и валидный/невалидный переход к спецификации;
- ручная desktop QA на ширинах `1000`, `1280` и `1440`: горизонтального
  overflow нет, явное `U` доступно, блокирующее состояние спецификации видно,
  runtime error/warning в console нет.

Ветка `SPEC_ACCESSORY_SELECTION_REQUIRED` покрыта frontend integration-тестом.
Отдельного E2E для неё нет: в тестовом каталоге пока отсутствует
детерминированная fixture с несколькими позициями одного аксессуара.

Mobile browser QA и mobile Playwright-проекты отсутствуют. Общий прогон suite
по прямому указанию владельца задачи не выполняется; зелёными считаются только
фактически запущенные целевые проверки.
