## 0. Главное правило

**Меняем только представление.** Критерий проверяемый, а не на словах:

> Существующие тесты состояния и поведения должны проходить **без правок**.
> Если для прохождения теста нужно изменить логику — значит слайс вышел за рамки, откатываем.

Править разрешено только те тесты, которые фиксируют **числа вёрстки**
(перечислены в §5): их значения обновляются вместе с макетом, но набор проверок
не сокращается.

### Ловушка №1 — не копировать технику из HTML

HTML-кадры собраны **абсолютным позиционированием**: каждый элемент по `left/top`.
Это способ рендера макета, а не образец вёрстки. В React так нельзя:
сломается ратчет координатной раскладки (§5) и адаптив.

Из HTML берутся **значения** (размеры, цвета, отступы, число колонок, тип контрола,
тексты), реализация — существующим гридом на CSS-переменных.

## 3. Что меняем — целевые значения

### 3.1 Токены — объявляем глобально, применяем локально

> **Ловушка №2 — самая дорогая.** `tokens.css` глобальный. `--tlt-field-control-height`
> используется не только зоной heat: через `components/form-controls/index.ts` он
> доходит до `TltNumberField` / `TltSelect`, а их рендерят **13 файлов электрорасчёта
> и спецификации**. Поменять значение в `:root` — значит перекрасить чужие зоны и
> уронить их e2e. Это выход за рамки задачи.
>
> **Правило:** новые значения **объявляются** новыми токенами в `tokens.css`
> (сырые цвета разрешены только там), а **применяются** переопределением на корне
> **своего** острова — `.heat-object-fields`, `.object-wizard-cable-panel`,
> `.insulation-layers-table`. Глобальные значения существующих токенов не трогаем.
> `.inline-object-form` для этого **не годится**: это корень всего визарда, правило
> на нём двигает все три острова сразу — см. §5.4.

> **Правило владельца — кегль не увеличиваем.** Из макета берём **геометрию и
> цвет**; размер шрифта остаётся тот, что в приложении. Кадр нарисован в другом
> масштабе, чем экран, и его 10.5px подписи на реальную форму не переносятся.
> Любой слайс, который увеличивает `font-size` в зоне heat, — ошибка.

|---|---|---|---|
| Высота поля | `--tlt-field-control-height: 26px` | **28px** | решение владельца (36 из макета отклонено) |
| Кегль подписи | `--tlt-field-label-font-size: 8.5px` | **8.5px — не меняется** | правило владельца |
| Начертание подписи | нет токена | **600** (уже так) | `ROLE_STYLE['field-label']` |
| Цвет подписи | `--tlt-field-label-color: #53667b` | **#26364a** | там же |
| Ширина подписи | `--tlt-field-label-width: 98px` | по месту в слайсе раскладки | блоки в `penpot_screens` |
| Кегль значения | `--tlt-field-control-font-size: 12px` | **12px — не меняется** | `TPL_STYLE['Text'].size` |
| Кегль единицы | `--tlt-field-unit-font-size: 9px` | **9px — не меняется** | правило владельца |
| Радиус | `--tlt-field-radius: 2px` | **6px** | `TPL_STYLE['hbtn'].radius` |

**Новых цветовых токенов не требуется, и места для них нет.** `tokens.css` — 331
строка при пороге 332, вырасти он не может, а сырые цвета разрешены только в нём.
Проверено: всё нужное уже объявлено — заливка обязательного поля
`--color-swatch-fffdf6`, его полоса `--color-swatch-d48806`, граница поля
`--color-border` (`#d9d9d9`), шапка таблицы `--color-swatch-f4f7fa`, её граница
`--color-swatch-d1dce8`, разделитель колонок `--color-swatch-dce5ee`, цвет подписи
`--color-swatch-26364a`. Макет рисовал обязательное поле как `#fffdf4`/`#e8a33d` —
расхождение с продуктом на два деления; **выровнен макет**, а не код
(`scripts/penpot_kit.py`, `scripts/render_html.py`).

**Ширины контролов.** Сейчас пофилдово: `--tlt-field-ctrl-num: 4rem`, `-name: 7.5rem`,
`-climate: 8.75rem`, `-tm: 8rem`, `-layers: 5rem`; e2e фиксирует итог как `96px`

Решение по каждому треку принимается в слайсе раскладки и синхронно правится в e2e.

### 3.1a Что макет НЕ задаёт

**Состав полей берётся из приложения, а не из макета.** В реестре у трубы и у
резервуара по **43** неслужебных поля с правилами видимости; на кадре показано
5 текстовых и 8 числовых — это выборка для демонстрации вида, а не полный экран.

**Удалять поля, которых нет на кадре, запрещено.** То же про порядок: он задан
слотами `ObjectWizardFormSlots.tsx` и зафиксирован интеграционным тестом.

Макет отвечает на вопрос «как выглядит поле и ряд», приложение — на вопрос
«какие поля есть и когда они видны».

### 3.2 Заголовок панели

`ROLE_STYLE['panel-title']`: `10px / 700 / #4b5563`, шапка панели высотой 26px.
Сейчас `.inline-form-section-banner` / `.side-form-section-banner`.

### 3.3 Ритм ряда

Высота ряда = `max(высота поля + 4, строк подписи × 13 + 8)`.
Подписи из приложения переносятся на 2–3 строки — `FieldLabel.tsx` это уже делает,
компонент не переписывать, только согласовать line-height с новым кеглем.

### 3.4 Единица измерения — по-разному в двух панелях

В панели теплопотерь единица стоит **отдельной ячейкой с разделителем** слева от
края поля. В панели выбора кабеля — **серым суффиксом внутри поля, без разделителя**
(так в приложении, см. кадр «Исходные — труба (заполнено)»).

Правило вытекает из состава блока: ячейка рисуется, когда единицы есть у всех полей
блока, иначе поля без единицы читаются шире соседних.

### 3.5 Подсказка панели кабеля

Строка `<p class="cable-algorithm-hint">` «Марка кабеля, нитки и подбор — на шаге
«Электротехнический расчёт»» в макете **сохранена** — это не та подпись, что мы
убирали. Снятые элементы (плашка «Без регистрации…» и строка про 230 В) в React-форме
теплопотерь отсутствуют изначально, трогать нечего.

### 3.7 Форма существует в двух раскладках — макет покрывает одну

`HeatCalcWizardFormPanel.tsx:61` выводит вариант из размещения блока параметров:

```
formPlacement = left | right  →  layoutVariant = 'side'
formPlacement = top  | bottom →  layoutVariant = 'wide'
```

Это **не косметика**. У вариантов разное распределение шагов по слотам
(`ObjectWizardFormSlots.tsx:136,169,192`), разные компоненты панели
(`ObjectWizardSidePanel` / `ObjectWizardWidePanel`) и разный CSS.
`heatcalc-side-form-layout.css` — 373 строки и **35 из 71** объявлений
координатной раскладки всего проекта.

**Макеты нарисованы только под `wide`.** Требуется решение владельца — см. §10.

### 3.6 Типы контролов

В макете различаются визуально: **`select`** — шеврон справа, **`reference`** — лупа,
`number` / `text` — простое поле. Сейчас тип зашит в JSX каждого шага.
Цель — брать из реестра (см. §4).

## 4. Модульность — что вводим

Сейчас общего компонента поля в боевой форме **нет**: каждый шаг сам собирает
`Form.Item` + класс + `withHelp` + хардкод единицы. Единица измерения продублирована
строковым литералом примерно в 15 файлах, хотя `input.unit` есть в конфиге и не
используется. Тип контрола тоже зашит в JSX, хотя `editorFromInput` в реестре уже
существует и используется таблицей.

**Вводим один компонент поля** — `components/wizard/HeatFormField.tsx`:

```tsx
<HeatFormField id="outer_diameter_mm" objectType="pipe" />
```

Он берёт из `domain/heatCalcFields`: подпись, описание-подсказку, единицу,
тип контрола, правила, min/max/step, опции селекта — то есть всё то, что шаги
сейчас собирают руками. Внутри рендерит тот же `Form.Item` с теми же классами
и тем же `HelpedControl`, поэтому DOM-контракт и поведение не меняются.

**Что это даёт:** единицы и типы контролов перестают быть литералами в JSX;
новый стиль применяется в одном месте, а не в пятнадцати; шаги худеют.

**Чего НЕ делаем:** не переписываем `FieldLabel`, `HelpedControl`, `ReferencePicker`,
`InsulationLayersTable`, `CompactFieldGrid`. Не заменяем antd `Form`.
Не трогаем `CompactField` из ui-kit — он живёт своей жизнью на `/ui-kit`.

## 4a. Агент-френдли архитектура: Storybook для этой зоны

**Проблема, которую решаем.** Сейчас проверить одно поле формы можно только подняв
всё приложение: страницу, react-query, стор проекта, бэкенд. Историй для
`components/wizard/*` и `pages/heatcalc/*` **нет ни одной** — Storybook сканирует
только `src/components/ui-kit/**` (`.storybook/main.ts:9`). Отсюда и слабое место
в метриках репозитория: «Browser/E2E доказуемость 7,2» при общей оценке 8,41.

Для переверстки это дорого: цикл «поменял → посмотрел» упирается в полный стенд,
а визуальная проверка сводится к скриншотам целой страницы, где непонятно,
что именно поехало.

### Что делаем

**1. Открываем Storybook для зоны — одна строка в конфиге.**

```diff
- stories: ['../src/components/ui-kit/**/*.stories.@(ts|tsx)'],
+ stories: [
+   '../src/components/ui-kit/**/*.stories.@(ts|tsx)',
+   '../src/components/wizard/**/*.stories.@(ts|tsx)',
+ ],
```

Истории не считаются production-файлами, поэтому LOC-ратчеты не затрагиваются.

**2. Выносим фикстуры справочников из тестового харнесса.**

`src/__tests__/integration/components/ObjectWizardDependencies.test-harness.tsx`
содержит готовые строки климата, изоляции, материалов и грунтов, но импортирует
`vi` из vitest — в Storybook такой модуль не подключить. Чистые данные переезжают
в `src/components/wizard/__fixtures__/wizardReferenceFixtures.ts`, харнесс и
истории импортируют их оттуда. Дублирования не возникает.

**3. Истории пишем до правок стиля — они и есть characterization.**

Для `HeatFormField`, `HeatCalcObjectFieldsPanel`, `CableAlgorithmPanel`,
`InsulationLayersTable`. Каждое состояние — отдельная история: тип контрола
(`number` / `text` / `select` / `reference`), обязательное поле, пустое значение
с подсказкой, ошибка валидации, disabled. В `play`-функциях — проверки
видимого результата: подпись, единица, роль контрола, атрибут `aria-required`.

Это заменяет часть vitest-характеризации из слайса 0: контракт фиксируется там же,
где его видно глазами.

**4. Правило на будущее.** Любой компонент этой зоны, который меняет вид,
получает историю. Иначе следующий агент снова окажется без быстрой петли.

### Что это даёт

Агент меняет токен — и сразу видит все состояния поля рядом, без бэкенда.
Storybook в этом репозитории поднят с MCP-аддоном, поэтому агент может
запросить изменённые истории и получить ссылки на превью для показа человеку.

## 4b. Устранение дублирования `/ui-kit` (отдельное решение)

**Наблюдение.** `pages/uikit/UIKitHeatReferenceSection.tsx` (373 строки) плюс
`pages/ui-kit-heatcalc-reference.css` (237 строк) **вручную повторяют разметку
формы теплопотерь**, а e2e `ui-kit-heatcalc-parity.spec.ts` существует только
затем, чтобы ловить расхождение копии с оригиналом.

Это классический источник работы на ровном месте: любая правка формы требует
синхронной правки копии, иначе падает parity-тест. В плане §6 это отдельный
слайс 7 — то есть мы платим за дублирование прямо в этой задаче.

**Предложение.** Когда истории из §4a появятся, копия становится не нужна:
Storybook показывает **реальные** компоненты, а не их повторение. Тогда
`UIKitHeatReferenceSection` и его CSS удаляются, `ui-kit-heatcalc-parity.spec.ts`
тоже — его роль берут на себя истории с `play`-проверками.

**Чем платим.** Parity-тест сверяет computed styles попиксельно; истории так
не умеют. Взамен получаем отсутствие самого расхождения — сверять будет нечего.

**Решение владельца требуется до слайса 7.** Варианты: удалить дублирование
(минус ~600 строк и один e2e-спек) либо оставить и продолжать синхронизировать.
До ответа слайс 7 выполняется в прежнем виде — синхронизацией копии.

## 4d. Оценка архитектуры: что менять, а что не трогать

Разбор проводился перед стартом задачи. Вывод: **архитектуру переделывать не нужно**,
нужны три точечных изменения.

### Менять

| Что | Почему | Где в плане |
|---|---|---|
| **Общий компонент поля** | Единица измерения продублирована строковым литералом в ~15 файлах, хотя лежит в реестре; тип контрола зашит в JSX, хотя `editorFromInput` в реестре есть и используется таблицей. Без этого переверстка растекается по 15 местам | §4, слайсы 3–4 |
| **Дублирование `/ui-kit`** | 373 строки TSX + 237 CSS вручную повторяют форму; отдельный e2e существует только чтобы ловить их расхождение | §4b, слайс 7 |
| **Покрытие `HelpedControl`** | Навешивает тултип императивно: ищет `.ant-form-item-label > label` через `closest()`, создаёт div в `document.body`. Тестов — **ноль**, ни unit, ни e2e. Любая правка разметки подписи может сломать его молча | слайс 1: история + play-проверка **до** правок подписей |

### Не трогать

**Острова с гейтом изоляции.** Каждый селектор в CSS острова обязан содержать его
корневой класс — поэтому переверстка физически не может протечь в соседнюю зону.
Именно это делает задачу безопасной.

**Девять CSS-файлов на экран.** Граница между `heatcalc-field-chrome.css` и
`heatcalc-field-chrome-core.css` неочевидна, но перекладывать код между ними нельзя:

### 5.4 Радиус поражения правки — один компонент, не «зона»

> **Правило владельца.** Стиль пишем **на один компонент**. Не заводим правило,
> которое накрывает несколько компонентов сразу. И если правка тронула один
> остров — должна быть **гарантия**, что остальные не поехали. Не «вроде не
> должно», а проверка.

Практически это значит:

**Переопределять токены — на корне своего острова**, а не на общем корне зоны.
`.inline-object-form` — это корень **всего визарда**: под ним живут и поля объекта,
и панель кабеля, и таблица слоёв. Правило на нём двигает все три сразу. Правильные
адреса: `.heat-object-fields`, `.object-wizard-cable-panel`,
`.insulation-layers-table` — каждый в своём файле-острове.

**Гарантия — исполняемая.** У каждого острова есть история, и она пинует его
собственный масштаб через `getComputedStyle`: высота контрола, кегль и цвет
подписи, радиус. Правка, протёкшая на соседа, роняет его историю. Поэтому при
любой правке стиля прогоняются истории **всех трёх** островов, а не только того,
который правили.

**Исключение — общий хром.** Правила вида `.inline-object-form .ant-input`
в `heatcalc-field-chrome*.css` уже существуют и накрывают зону: это чужой
легаси-слой, переписывать его в рамках этой задачи не нужно. Но **новых**
зонных правил не добавляем, а значения в существующих переводим на токен, чтобы
остров мог задать своё.

### Найдено в панели кабеля и таблице (слайс 6)

**Панель кабеля — 390px, а не 490.** Из-за этого две колонки по 228px никогда
не помещались: `repeat(2, minmax(0, …))` молча сжимал их до 176px, контрол
падал до 76px и значения селектов резались («Нормаль…», «Выберите…»). Дефект был
не в высоте, а в том, что `minmax(0, …)` разрешает треку сжаться до нуля —
сетка не переносила, а плющила.

**Ширины пересчитаны от реального места:** 2 × (72 + 8 + 96) + 8 = 360 ≤ 368
доступных. Подпись 72px по-прежнему шире самого длинного слова
(«Температурная» ≈ 60px при 8.5px/600), поэтому переносится по словам и не рвётся.

**`width: fit-content` ломает `auto-fit`.** Пока панель сама подбирала ширину по
содержимому, `auto-fit` всегда давал одну колонку: ширина контейнера зависела от
числа колонок, а число колонок — от ширины. Панели дана определённая ширина.

**Таблица слоёв правок не потребовала.** Замер на трёх ширинах: заголовки не
обрезаются, колонки `72 216 154 124 190/216`. Ширины из макета (300/110/90/313)
переносить нельзя — они сняты с кадра шириной 900px, а панель в приложении 744.

### Найдено при раскладке (слайс 5)

**Высота — 28px, не 36.** Владелец отклонил 36 из макета. Итог: поля объекта,
панель кабеля и таблица слоёв — все 28px, одна шкала на зону, как требует
HARD RULE 2. Панель кабеля до задачи была 36px — она опущена вместе с
остальными, иначе левая и правая формы стоят разной высоты на одном экране.

**Структуру слотов макет не переопределяет.** В кадре числовые поля идут в три
колонки, а текстовые сверху в две; в приложении три семантические группы
(`wide` / `geometry-numeric` / `environment-numeric`). Порядок и состав задаёт
`ObjectWizardFormSlots.tsx` и фиксирует интеграционный тест — §3.1a это прямо
запрещает менять. Слайс раскладки правит масштаб и ритм, а не перекладывает поля.

**Прибитые line-height ломаются при смене высоты.** В `cable-algorithm-panel.css`
стояло `line-height: 34px` (= 36 − 2) в двух местах: текст селекта и суффикс
единицы. При переходе на 28px текст съехал бы вниз. Переведено на
`calc(var(--cable-control-height) - 2px)`. Искать такие литералы надо до смены
высоты, а не после.

**Узкое окно 1000px — своя раскладка.** Приложение показывает баннер
«рекомендуемая ширина от 1280 px», поля перестраиваются в один столбец, таблица
слоёв теряет колонку «Диапазон температур». Это существующее поведение, не
дефект переверстки: overflow страницы на всех трёх ширинах — 0.

### Найдено при переводе шагов (слайс 4)

**Слепая миграция добавила бы валидацию.** `heatCalcFormFieldRules` всегда
возвращает хотя бы валидатор, а у `climate_key` правил нет вовсе — поле стоит
без `rules`. Поэтому у `HeatFormField` есть проп `rules`: `rules={[]}` сохраняет
«валидации нет». Перед переводом любого поля надо смотреть, что стояло в
`Form.Item`, а не только на его тип в реестре.

**Имя в форме не всегда равно идентификатору реестра.** Глубина заложения трубы:
подпись и правила от `pipe_centerline_depth`, значение — в `burial_depth`.
Для этого есть проп `name`.

**Что переводить не надо.** Скрытые носители round-trip
(`max_ambient_temperature`, `zone_classification`, `insulation_cover_material`) —
у них нет ни подписи, ни правил, они просто возят значение; `HeatFormField`
навесил бы им подпись. Поле «Наименование объекта» в `ConfirmStep` тоже осталось
сырым: у него литеральная подпись, свои правила и `extra` — это не поле реестра.

**Электрорасчёт красный не из-за нас.** 25 интеграционных тестов
`ElecCalcPage.*` падают на «не открывается модалка подбора кабеля». Проверено
дважды: сначала откатом фасада `ui-kit` к HEAD, затем полным прогоном на чистом
дереве через `git stash` — падают одинаково. Чужая зона.

### Найдено при переверстке токенов (слайс 2)

**Подпись heat-формы не ходит через `--tlt-field-label-*`.** Её задаёт напрямую
`heatcalc-field-chrome-core.css`: `--form-label-size` и цвет literal-токеном в
правиле `.inline-object-form .ant-form-item-label > label`. Переопределение
`--tlt-field-label-font-size` на корне острова на неё **не влияет** — влияет
только на компактную сетку ui-kit (раскладка `labels-top`). Тот же разрыв был у
радиуса: `border-radius: 2px` стоял литералом в пяти правилах core-файла. Сейчас
они переведены на `var(--tlt-field-radius, 2px)`, но проверять надо замером в
браузере, а не чтением `tokens.css`.

**Высота поля живёт в трёх местах, по одному на остров.** `.heat-object-fields`
берёт `--tlt-field-control-height`; `.object-wizard-cable-panel` — свой
`--dual-form-control-height` (там уже было 36px); `.insulation-layers-table` —
свой `--ins-control-h` (28px, по решению владельца так и остаётся). Одним
переопределением на корне все три не двигаются: у двух островов литералы ближе к
элементу. Итог: поля формы и панель кабеля — 36px, таблица слоёв — 28px.

**Storybook показывал полураздетый компонент.** `ObjectWizard.tsx` вешает класс
`.inline-object-form`, но не импортирует ни одного стиля — хром формы приходит из
`HeatCalcWorkspaceLayout`. Пять формных CSS теперь импортирует
`.storybook/preview.tsx`. Класть этот импорт в фикстуру визарда **нельзя**:
зависимость `components → pages` роняет ратчет слоёв (G3).

**Почему увеличенный кегль ломает вёрстку.** При подписи 10.5px «Температурная
группа» рвалась посреди слова: `FieldLabel` заранее режет подпись на строки-спаны,
и когда одно слово перестаёт помещаться в колонку 96px, браузеру нечего переносить
— он рвёт слово. Это ещё одна причина правила «кегль не увеличиваем»: колонки
подписей рассчитаны под 8.5px.

**`tokens.css` расти не может** — 331 строка при пороге 332. Новые токены туда не
поместятся; всё нужное уже объявлено (см. §3.1).

### Найдено при вводе `HeatFormField` (слайс 3)

**Новый файл не может импортировать antd.** Ратчет прямых импортов валит любой
**новый** файл-импортёр, даже если общее число уменьшилось (проверка `newFiles`
отдельно от проверки счётчика). Поэтому `Form` проброшен через фасад:
`ui-kit/UiPrimitives.tsx` уже в базлайне, из него экспортируется `TltForm`.
Тот же приём понадобится любому следующему компоненту зоны.

**Классы `Form.Item` из реестра не выводятся.** У каждого поля свой набор
(`fit-label-form-item short-number-form-item outer-diameter-form-item
helped-form-item`), и от него зависят и раскладка, и e2e. `HeatFormField`
принимает их пропом `className` — иначе DOM-контракт поехал бы.

**Справочники и селекты идут через `children`.** Им нужны опции, плейсхолдеры и
заголовки модалки — данные времени выполнения, которых в реестре нет. Сам
компонент собирает только числовое поле.

**Файл с компонентом не должен экспортировать функции.** Правило
`react-refresh/only-export-components` уронило линт, когда хелпер гарантии лежал
рядом с `WizardStoryShell`. Хелперы историй — в отдельный модуль
(`__fixtures__/wizardIslandScale.ts`).


### Найдено при характеризации (слайс 1)

**Подписи склеиваются без пробела.** `FieldLabel` бьёт подпись из 2+ слов на
отдельные `<span>` без разделителя, поэтому `textContent` подписи выглядит как
`«Температурапропарки»`. Доступное имя поля получается слитным — это влияет на
скринридеры и любой поиск по тексту в тестах. Истории **намеренно закрепляют
текущее поведение**: если при переверстке пробел появится, история упадёт и
решение будет принято осознанно, а не по случайности.

**Защищённый компонент противоречит цели задачи.** В шапке
`HeatCalcObjectFieldsPanel.tsx` есть HARD RULE 2: «label 8.5px / #53667b /
control 12px / height 26px» и прямой запрет «локальные font-size 10–11px
для читаемости на heat». Слайс 2 меняет ровно эти значения. Комментарий-контракт
**обязан быть переписан вместе со стилем** — иначе следующий агент откатит
правку по инструкции, лежащей в коде.

**Рецепт для будущих историй.** Ратчет прямых импортов antd считает обычные
`.tsx`, но пропускает `.stories.tsx`. Поэтому `Form` создаёт сама история, а
общий `WizardStoryShell` (`__fixtures__/wizardStoryDecorators.tsx`) даёт только
react-query и корневой класс острова — и остаётся вне ратчета.

**Проверять истории по факту рендера недостаточно.** Упавшая `play`-функция не
роняет iframe: страница отрисована, ошибка видна только в панели Interactions.
Проверка должна слушать события `playFunctionThrewException` /
`storyThrewException` на канале Storybook. Скрипт: `/tmp/story-play.mjs`
(перенести в `scripts/`, если понадобится в CI).
