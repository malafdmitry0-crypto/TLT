# Промпт аудита кейса гостевой спецификации

## Режим и цель

Работать в режиме `/audit-only`. Не изменять backend, frontend, схемы БД,
конфигурацию приложения, тесты и ожидаемые значения. Разрешены только
отчётные Markdown-файлы и evidence-артефакты проверки.

Цель: определить, насколько действующее приложение соответствует кейсу
«Расчёт спецификации для неавторизованных пользователей», описанному в PDF
`ТНП/1_Кейс_«Расчёт_спецификации_для_неавторизованных_пользователей» (1).pdf`,
и дать воспроизводимый отчёт по цепочке:

`PDF/документация -> backend -> frontend -> тесты -> фактическое поведение`.

## Источники и приоритет проверки

1. Зафиксировать SHA-256, metadata и число страниц PDF.
2. Извлечь текст постранично, но не считать text extraction достаточным:
   отрендерить и визуально просмотреть все страницы, включая схемы,
   скриншоты, подписи, стрелки, таблицы и состояния контролов.
3. Представить PDF как один из источников требований, а не как
   автоматически более сильную истину. Сопоставить его с действующими:
   `AGENTS.md`, `codex-docs/*`, `docs/srs*`, `docs/api.md`,
   `docs/analysis/business-rules.md`, `docs/qa/*`,
   `docs/business-logic-contract.md` и релевантными ТНП-материалами.
4. При конфликте источников не выбирать молча победителя: указать документы,
   формулировки, влияние на продукт и требуемое решение владельца продукта.

## Что извлечь из PDF

Сформировать атомарные требования с устойчивыми ID. Для каждого требования
зафиксировать:

- страницу и фрагмент/описание визуального evidence;
- роль и предусловия;
- действие пользователя и ожидаемую реакцию интерфейса;
- поля, обязательность, дефолты, допустимые значения и единицы измерения;
- переходы между экранами, кнопки, подписи и состояния;
- API/payload, если его можно вывести из сценария;
- расчётный результат и правила формирования спецификации;
- сохранение, повторное открытие, срок жизни гостевой сессии и очистку;
- ошибки, пустые, loading, disabled и unsupported-состояния;
- доступность предпросмотра/экспорта и ограничения гостевой роли;
- неясности и допущения, которые документ не разрешает.

## Проверка реализации

Для каждого атомарного требования найти через `rg`:

- backend endpoint, dependency/RBAC guard, schema, service, formula/builder,
  model и persistence behavior;
- frontend route, page/component, API client, hook/store, validation и
  отображаемый текст;
- unit/integration/frontend/e2e тесты и существующие QA-сценарии.

Сверить входы, единицы, роли, ошибки, side effects, `variant_number`,
diagnostic fields (`formula_id`, источник/версия, category, `error_code`),
сохранение в БД и повторную загрузку. Для спецификации отдельно проверить,
что успешные, ошибочные, неподдержанные и устаревшие результаты не смешиваются,
а выбранный CO-вариант проходит через backend/frontend flow.

## Проверка живого интерфейса

Запустить реальный локальный стек репозиторными командами и пройти гостевой
сценарий теми же видимыми действиями, что описаны в PDF. Не подменять UI-proof
HTTP-запросами или рассуждением по исходникам.

Минимально проверить desktop `1440x1000` и mobile `390x844`; если SRS прямо
исключает mobile из продуктового контракта, всё равно записать наблюдение как
диагностическое, не превращая его в обязательное требование PDF.

Для каждого достигнутого состояния сохранить URL, viewport, action path,
snapshot и screenshot. Программно проверить:

- отсутствие page-level horizontal overflow;
- положительный размер ключевых контролов;
- clipping, `text-overflow`, overlap и выход элементов из контейнеров;
- читаемость длинного русского текста и идентификаторов;
- видимость/доступность нужных контролов, disabled/loading/error states;
- console warnings/errors и failed network requests.

Если браузер, Playwright, API или DB недоступны, статус соответствующего
in-scope evidence — `blocked/needs verification`, не `pass`.

## Проверки и evidence

Выбрать минимально достаточные focused-команды из репозиторного контура:

- contract matrix для спецификации;
- backend security/integration для гостевой сессии, проектов и спецификации;
- frontend tests для гостевого маршрута и `SpecificationPage`;
- релевантный Playwright user flow и layout/accessibility verifier;
- `db-invariants` после изменяющего данные UI-сценария.

Не изменять тесты и не добавлять новые тесты, поскольку режим отчётный. Если
покрытие отсутствует, оформить finding/остаточный риск с точным пробелом.

## Выходные Markdown-артефакты

1. `audit-prompt.md` — этот воспроизводимый промпт и границы работы.
2. `pdf-requirements.md` — постраничный разбор и атомарные требования PDF.
3. `traceability-matrix.md` — матрица
   `требование -> docs -> backend -> frontend -> tests -> verification`.
4. `functional-accuracy-report.md` — итоговый отчёт с severity, evidence,
   статусом и residual risk.

Каждый finding непосредственно или через явную ссылку на
`traceability-matrix.md`/`verification-log.md` должен содержать: ID, severity,
затронутое требование, ожидаемое и фактическое поведение, evidence с
`file:line`/страницей PDF, воспроизводимые шаги либо способ code inspection,
влияние и рекомендацию без реализации исправления.

## Критерий завершения

Нельзя объявлять полное соответствие, если отсутствует хотя бы одно
обязательное in-scope evidence: визуальная проверка PDF, backend RBAC,
payload/units, persistence/reload, Playwright/screenshots, программная
layout-проверка либо DB-инварианты после пользовательского сценария.
