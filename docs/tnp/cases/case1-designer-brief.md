## 0. Базис работы: существующие макеты (новое в v1.1)

**Мы не начинаем с нуля.** В `mockups/` уже лежат три кадра happy path (`01-heat-calc`, `02-elec-calc`, `03-specification`), собранные на общем `heatcalc-shared.css`. Это **визуальная копия текущего продукта** — она и есть отправная точка.

### 0.1 Два правила, старше всех остальных требований

| # | Правило | Что это значит на практике |
|---|---|---|
| **R1** | **Стили не менять** | Визуальный язык `heatcalc-shared.css` — данность: типографика, цвета, радиусы, плотность таблиц, вид кнопок/чипов/вкладок/карточек. Новые кадры собираются **из существующих классов**. Нужен компонент, которого нет (алерт, модалка, степпер) — стилизовать **в логике этого же файла** (те же токены цвета, тот же радиус 7–9 px, тот же шрифтовой ряд 12.5/13.5/14/14.5) и класть в **отдельный additive-файл**, не редактируя `heatcalc-shared.css`. Рефакторинг, ребрендинг, переход на «карточный дашборд» — **вне scope**. |
| **R2** | **Функционал расширять, а не урезать** | При сомнении «убрать или показать недоступным» — выбираем **показать недоступным** с честной подписью. Существующие возможности (Excel-режим, режим добавления, настройки колонок, пересчёт выбранных) **сохраняем** и дорисовываем их состояния. Удалять из кадра можно только то, что прямо противоречит PDF/ТЗ или является employee-функцией у гостя (список — §0.3). |

## 1. Цель дизайна

Довести UI гостевого пути до соответствия кейсу 1 и убрать расхождения, которые мешают приёмке:

1. Электрорасчёт выглядит как **MVP только «Самрег»**, а не «скоро Резистив/Скин».
2. Спецификация **раскладывается по разделам** (Трубы / Бочки / Общие), а не сваливается в «Общие».
3. Предупреждения и ошибки **ведут к действию** (Исправить, Пересчитать, Выбрать позицию).
4. Состояния экрана (пусто / loading / stale / partial / selection / blocked) читаются без «режима просмотра»-шума.

**Не цель:** редизайн визуального языка (см. R1); полный редизайн HeatCalc; **любые мобильные и планшетные раскладки** (см. §2.1); коммерческий отчёт PDF как отдельный кейс.

## 2. Аудитория и сценарий

| | |
|---|---|
| **Персона** | Инженер-проектировщик (гость) |
| **Контекст** | **Только десктоп** (контракт: 1000 / 1280 / 1440) — см. §2.1 |
| **Сценарий** | Быстрый расчёт 1–N объектов без аккаунта, выгрузка файла и просмотр спецификации |
| **Ограничения** | 1 проект на сессию, 3 дня TTL, **до 4 электрорасчётов** (§6.5, стр. 37 — жёсткое бизнес-правило), **до 500 объектов** (лимит из конфигурации `GUEST_MAX_OBJECTS_PER_PROJECT`; §3.5 PDF задаёт 500 как *минимальную* поддерживаемую ёмкость, не потолок) |

### 2.1 Платформа: только десктоп (решение владельца, 2026-08-04) — **раз и навсегда**

> **Мобильной версии приложения нет и не будет в scope кейса 1 / текущего продукта.**  
> Норматив платформы: [`../../frontend/viewport-policy.md`](../../frontend/viewport-policy.md) §0.

**Мобильных устройств и планшетов у продукта нет.** Из этого следует:

- Мобильные и планшетные раскладки **не проектируются вообще** — ни кадров, ни адаптива, ни touch-паттернов.
- Медиазапросы под &lt;1000 px, «бургер»-меню, карточная перекладка таблиц в списки — **вне scope**.
- **1000 px — это не планшет,** а минимальное окно браузера на десктопе (пользователь сузил окно или работает на ноутбуке 1280×800 с открытой панелью). Поэтому нижняя граница контракта остаётся **1000 px** и совпадает с уже действующим инженерным гейтом browser-matrix `1000×768 / 1280×800 / 1440×900` из [`case1-frontend-checklist.md`](./case1-frontend-checklist.md).
- Ниже 1000 px поведение не проектируется и не тестируется: горизонтальный скролл страницы там допустим.
- **Проценты закрытости ТЗ / release gate не штрафуются** за FAIL на `390×844` и аналогичных phone/tablet viewport. Такие строки в аудитах = **N/A (out of scope)**, не blocker.

**Что это означает практически** (замеры — [`case1-design-review.md`](./case1-design-review.md) §4): на 1000 px не помещаются ни шапка, ни одна из таблиц. Значит нужны компактный вариант шапки и скролл-контейнеры для широких таблиц — но это работа под **узкое окно десктопа**, а не адаптив под устройства.

| **Не закрывать** | settings modal при selection/confirm — диагностики должны оставаться видны |

### 6.3 Закрытые решения

#### Q1 (закрыт 2026-08-04): параметры спецификации живут в модалке настроек, не на объекте

**Решение владельца:** Ex и прочие параметры формирования спецификации вводятся **в модалке настроек спецификации**, третья форма «Исходные данные для спецификации» с PDF стр. 21 на экране объекта **не воспроизводится**.

**Решение совпадает с уже реализованным контрактом бэкенда** — это не компромисс, а приведение дизайна к коду:

- `backend/app/services/project_object_params.py` содержит `LEGACY_SPECIFICATION_OBJECT_PARAM_KEYS` = `explosion_zone_type`, `power_indication_on_boxes`, `end_of_section_indication`, `top_of_box_indication`, `min_length_for_k2i`, `hot_reserve_coefficient`.
- Попытка записать любой из них в данные объекта отклоняется с кодом **`OBJECT_SPECIFICATION_SETTINGS_SCOPE_VIOLATION`** и сообщением «Параметры спецификации запрещены в данных объекта».
- Те же величины приходят в генерацию как project-scoped опции: `backend/app/schemas/specification.py` — `Ex`, `K1i`, `K2i`, `Kiu`, `L_K2i_m`, `R_gr`.

То есть **нарисовать Ex на объекте технически невозможно** — бэкенд отвергнет запись.

**Где что вводится (карта для дизайнера):**

| Поле третьей формы PDF стр. 21 | Где на самом деле | Что рисуем |
|---|---|---|
| **Класс взрывозащиты (Ex)** | Опция генерации спецификации, project-scoped | **Модалка настроек спецификации** (§4.2), вместе с K1i / K2i / Kiu / L,K2i / R,гр |
| **Степень защиты (IP)** | Свойство **каталожной позиции** (`seeds.py`: аксессуары с `ip: IP68 / IP65 / IP55`) | Не поле ввода. Максимум — колонка/подсказка в строке спецификации |
| **Материал оболочки** | На объекте есть `insulation_cover_material` — но это **материал покровного слоя изоляции**, он относится к блоку теплопотерь, а не к оболочке кабеля | Остаётся там, где сейчас — в форме теплопотерь. Новое поле не заводим |
| **Тип монтажа** | Не реализовано нигде | Не рисуем — см. **Q5** |
| **Доп. требования** | Не реализовано нигде | Не рисуем — см. **Q5** |

**Важно не перепутать:** на объекте остаются и **должны быть нарисованы** `zone_classification`, `environment` («Среда»), `temperature_group` («Температурная группа») — это параметры **подбора кабеля**, а не формирования спецификации. Они уже есть в макете 01 и никуда не переезжают.

**Следствие:** экран «Исходные данные» остаётся с **двумя** формами (теплопотери + подбор кабеля), как в текущем макете. Пункт B8 из §0.3 снят: отсутствие третьей формы — не дефект макета, а правильное поведение.

## 7. Microcopy: канон из PDF

**Правило:** сначала берём формулировку PDF дословно; если продукт хочет другую — она попадает в microcopy sheet **с пометкой об отклонении**. Свои переформулировки без пометки — источник споров на приёмке.
