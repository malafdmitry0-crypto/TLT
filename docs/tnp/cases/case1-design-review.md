# Ревью дизайн-пакета кейса 1: ТЗ дизайнера + существующие макеты

**Дата:** 2026-08-04
**Что ревьюилось:** [`case1-designer-brief.md`](./case1-designer-brief.md) (v1.0), [`case1-design-agent-handoff.md`](./case1-design-agent-handoff.md), макеты `mockups/01-heat-calc`, `02-elec-calc`, `03-specification`
**Эталон:** PDF кейса 1, ред. 4 от 07.07.2026, 81 стр. (§3–§7), UI-референсы стр. 21 / 35 / 49 / 56
**Метод:** сплошное чтение PDF (стр. 1–81) + сверка с брифом и с HTML/PNG макетов. Браузерная проверка макетов на 1000/1280/1440 не проводилась.

> Историческая запись: упоминания лимита 5 ЭР ниже фиксируют состояние PDF и
> макетов на дату ревью. Текущий продуктовый контракт с 2026-08-06 — не более 4 ЭР.

## Вердикт в двух строках

**ТЗ дизайнера — годная основа** (приоритеты, состояния и errata сделаны честно), но у него **дыры по §5 и по гостевой шапке**, и часть microcopy написана своими словами вместо формулировок PDF. Перед отрисовкой нужно закрыть 5 пунктов из §3 этого документа.

**Макеты — это не макеты кейса 1, а визуальная реплика текущего продукта.** Покрытие ≈ 3 фрейма из ~15 обязательных P0 (~20%), нарушены все три «жёстких правила» handoff §4, и в дизайн перенесены 3 известных бага. Годятся как baseline «как есть», не годятся как целевой дизайн.

## 1. Оценка ТЗ для дизайнера

### 1.1 Что сделано хорошо

| | |
|---|---|
| Приоритизация | P0 = D-ELEC + D-SPEC — верно: это места, где UI дальше всего от PDF |
| Состояния | Перечни frames по экранам (§4.1 «Состояния экрана», §4.2 «Frames») — сильная часть, дизайнер не будет рисовать только happy path |
| Errata | `case1-docs-verification.md` честно ловит 4 неверных утверждения (Iдоп, файл проекта, скриншоты, проценты) — редкий уровень самопроверки |
| Открытые решения | §6 «Решения, которые ждём от дизайна» с рекомендацией продукта — дизайнер не блокируется |
| Handoff | Есть DoD, порядок чтения, куда класть файлы, готовый prompt-блок |

### 1.2 Пробелы — сверено с PDF

**П1. Нет гостевой шапки как объекта дизайна (критично).**
PDF стр. 21 / 35 / 56 показывает конкретный chrome: логотип HeatCalc, три вкладки **«Исходные данные / Электротех. расчёт / Спецификация»**, бейдж **«Режим: гость»**, кнопки **«Открыть проект из файла»** и **«Сохранить проект в файл»**, инфо-строка **«Без регистрации. Один временный проект.»** В брифе этого нет ни в §3.1 (список экранов), ни в §4 — только одна строка в handoff §4 как запрет. При этом именно шапка сломана во всех трёх макетах. **Нужен отдельный P0-фрейм D-CHROME с дословным copy из PDF стр. 21.**

**П2. §5 покрыт на треть.**
Бриф сводит D-HEAT к group update + capacity + floor tab + voltage. PDF требует в панели объектов ещё: «Загрузить из Excel» (§5.5, стр. 29), «Добавить на основании» (§5.7, стр. 30, активируется чекбоксом), «Настройки отображения» с кнопкой «По умолчанию» и оговоркой «действуют в рамках сессии» (§5.9, стр. 31), перетаскивание строк с показом предполагаемой позиции (§5.10, стр. 31), предупреждение о замене данных при открытии файла (§5.11, стр. 32), подсветку проблемных строк при неуспешном «Далее» (§5.13, стр. 33). Плюс §3.11 (стр. 13): единые наименования, обязательные поля визуально обозначены, недоступные кнопки неактивны или скрыты. Либо расширить D-HEAT, либо явно вынести из scope с обоснованием — сейчас это молчаливый пропуск, который всплывёт на приёмке.

**П3. Microcopy написан своими словами, а не по PDF.**
Бриф предлагает «N объектов требуют перерасчёта». PDF §6.19 (стр. 53) даёт точную фразу: **«Исходные данные некоторых объектов были изменены. Необходимо выполнить повторный электротехнический расчёт»** + количество. Аналогично §7.7 (стр. 60): **«Электротехнический расчёт был изменён. Необходимо пересчитать спецификацию»**; §7.2 (стр. 57): **«Спецификации ещё не сформированы»**; §6.20 (стр. 55): **«Укажите название электрорасчёта»**; §7.3: кнопки именно **«Исправить»** и **«Всё равно сформировать»**. Microcopy sheet должен стартовать с дословных формулировок PDF, а отклонения — помечать.

**П4. Не зафиксирован состав колонок таблиц.**
PDF даёт их явно, а бриф — нет:
- §6.14 стр. 49, вкладка «Самрег»: чекбокс, шеврон, Объект, Марка греющего кабеля, Число ниток, Длина (м), Диаметр (мм), **Тепловые потери (Вт/м)**, **Мощность обогрева (Вт/м)** (требование: рядом, чтобы инженер сравнивал), Стартовый ток (А), Рабочий ток (А), Мощность (кВт), Количество секций.
- §7.6 стр. 60: наименование, марка, номенклатурный код, поставщик (если указан), единица поставки, количество (+ «№» на скриншоте стр. 56).

**П5. Пропущены состояния и правила §6/§7.**

| PDF | Чего нет в брифе |
|---|---|
| §6.13, стр. 41–45 | Критерий подбора (дешевле / быстрее / в наличии / поставщик / сбалансированный) + откат к техническому минимуму **с предупреждением** |
| §6.13, стр. 45 | Пакетный пересчёт **не трогает** строки с ручной маркой; перезапись — только по осознанному включению → нужен чекбокс/подтверждение в UI |
| §6.16, стр. 50–51 | Редактирование **прямо в таблице, без модалки**; у трубы редактируются только «Марка» (выпадающий список в ячейке) и «Навив»; **автопересчёт без кнопки «Пересчитать»**; при ошибке введённое значение сохраняется |
| §7.2, стр. 57 | Модалка при первом формировании: **выбор одного или нескольких ЭР** + параметры; вкладки создаются только для выбранных; автоформирования по всем ЭР нет |
| §7.4, стр. 58 | Поле «база номенклатуры» показывается, но **недоступно для изменения** (в брифе это есть как read-only — ок), и настройки применяются **ко всем спецификациям проекта** с пересчётом |
| §7.1, стр. 57 | **Фильтрация и сортировка в текущей версии не реализуются** — прямой запрет, которого в брифе нет |

**П6. Отклонения от PDF не помечены как решения продукта.**
Бриф уже правильно делает это для 230 В («требование ТЗ, PDF нейтрален»). Тот же приём нужен ещё для четырёх вещей, иначе ревьюер-по-PDF их забракует:
- **Selection panel вместо выпадающего списка.** PDF §7.10–7.14 (стр. 64, 66, 68, 71, 72) пять раз повторяет «показываются в выпадающем списке, инженер выбирает». Бриф рекомендует side panel. Отклонение осознанное и, вероятно, лучше — но должно быть записано.
- **Форма ввода Iдоп.** В PDF Iдоп есть только в формулах §6.14 (стр. 47–48), UI ввода не описан вообще. Это дизайн «сверх PDF».
- **Hide Резистив/Скин.** PDF стр. 35 допускает оба варианта («недоступные элементы будущего расширения либо не отображаются») — так что hide законен, но стоит сослаться на эту строку.
- **Форматы отчёта гость/сотрудник.** Бриф утверждает «гость — HTML/печать, PDF/DOCX/XLSX — сотрудник». В §7.8 (стр. 60–61) этого нет; есть только общая фраза стр. 41 про «права на дальнейшую работу с отчётами». Источник — ТЗ/реализация, надо пометить.

**П7. Неточное обоснование лимитов.**
Бриф: «max 500 объектов, max 5 ЭР». PDF §3.5 (стр. 11) — это **минимальная** конфигурация («не менее 500», «не менее 5»), то есть floor производительности, а не потолок. Потолок 5 ЭР есть отдельно и явно: §6.5 (стр. 37) «Максимальное количество вариантов электрорасчёта в одном проекте: 5». А 500 объектов как hard cap — из кода (`GUEST_MAX_OBJECTS_PER_PROJECT`), не из PDF. UI-copy «N из 500 / осталось M» **не требуется** (нет в PDF; снято из brief/stories).

**П8. Формат поставки не согласован между брифом и handoff.**
Бриф §3.2: «Figma (или Penpot), desktop frames 1440 и 1000». Handoff §3: PNG-файлы в `guest-specification/assets/ui/case1-mockups/`. Фактически сделаны HTML+CSS в `mockups/` в корне. Три разных ответа на вопрос «в чём носитель». Учитывая, что в проекте уже есть локальный Penpot с MCP-мостом, решение стоит зафиксировать до старта, иначе следующая итерация опять уедет мимо папки.

### 1.3 Что в ТЗ подтвердилось PDF-ом (спорить не о чем)

Максимум 5 ЭР (§6.5), нитки 1–3 (§6.13, стр. 43, 45), разделы «Трубы / Бочки / Общие материалы» (§7.1, стр. 57), коэффициенты Ex / K1i / K2i / Kiu / L,K2i / R,гр в модалке (§7.4, стр. 58), два способа группировки (§7.4, стр. 59), кнопки «Исправить» / «Всё равно сформировать» и переход в первый проблемный ЭР со подсветкой (§6.18 стр. 52, §7.3 стр. 57–58), статусы «Рассчитано / Требуется корректировка» (§6.14, стр. 49) и «Требуется перерасчёт» (§6.19, стр. 53), устаревание спецификации (§7.7, стр. 60), DnD-назначение с подсветкой вкладки (§6.11, стр. 39–40), «Вернуть в нераспределённые» с подтверждением и сохранением теплопотерь (§6.17, стр. 51–52).

## 2. Оценка существующих макетов

### 2.1 Что это фактически

Статические HTML + общий `heatcalc-shared.css`, отрендеренные в PNG шириной ~1728 CSS px (3456 @2×). Комментарий в первой строке CSS честно говорит: «Общие стили макетов HeatCalc (**визуальная копия продукта**)». То есть это не проектное решение, а перерисовка текущего экрана. Handoff §3 это и предполагал: «существующие `mockups/01–03` — черновики/WIP, не считать финалом».

### 2.2 Покрытие

3 happy-фрейма против требуемых по handoff §2: 6 фреймов D-ELEC + 7 фреймов D-SPEC + P1 (help, session, home, heat). **Отсутствуют полностью:** empty, all-unassigned, Iдоп не задан, stale, max 5 ЭР, delete confirm, never generated, unassigned confirm, selection required, blocking, settings open, обе вариации группировки, session expired, help, home. Итого ~20% P0.

### 2.3 Нарушения жёстких правил handoff §4

1. **Шапка — не гостевая.** «Новый проект», «Открыть», «Выход» — по коду `ProjectMenu` это employee-only; verification-док прямо запрещает переносить их в guest happy path. Должно быть: «Режим: гость», «Открыть проект из файла», «Сохранить проект в файл», инфо-строка «Без регистрации. Один временный проект.»
2. **Навигация 4 пункта вместо 3**, с другими названиями («Расчёт тепловых потерь» вместо «Исходные данные») и красными числовыми бейджами (2, 1), которых в PDF нет — красный бейдж читается как счётчик ошибок.
3. **Названный проект «Резервуарный парк РП-2»** — у гостя временный автосозданный проект, форма создания не показывается (§4.2, стр. 16).

### 2.4 Содержательные ошибки

4. **02-elec: Резистив и Скин живые.** Сохранены саммари-карточки «Резистив» и «Скин» с нулями (выглядят как активные метрики), вкладки «Резистив»/«Скин» и **активная кнопка «Назначить: Резистив»**. Рядом стоит info-строка «в текущей версии активен Самрег» — то есть взято худшее из обоих вариантов PDF стр. 35. Бриф §4.1 требует убрать.
5. **03-spec воспроизводит баг `bomSectionOf`.** Все 7 позиций — греющий кабель, комплект концевой заделки, комплект соединительный, лента крепёжная — свалены в «Общие материалы», а «Трубы» и «Бочки» свёрнуты и пусты. PDF стр. 56 показывает ровно наоборот: кабель, муфты и лента — в разделе **«Трубы»**, а в «Общих материалах» — коробка, силовой кабель, гофра, ввод. Макет узаконивает баг, который стоит первым пунктом в Slice 0.
6. **Каталог не заполнен.** «Номенклатурный код» и «Поставщик» = «—» во всех строках. PDF стр. 56: `TLT.HTL30-2CR`, «Теплолюкс-Тюмень». Макет фиксирует незасеянный каталог как норму.
7. **Пустые состояния не показаны ни разу.** «Бочки» — просто свёрнутый заголовок. PDF стр. 56 в этом месте рисует инфо-баннер «Расчёт спецификации для данного типа объекта пока недоступен», а бриф требует **три разных** пустых состояния (не сформирована / нет позиций / тип unsupported).
8. **Добавлена сортировка, запрещённая PDF.** Значки ⇅ на всех колонках спецификации против §7.1 (стр. 57): «фильтрация и сортировка в текущей версии не реализуются».
9. **Колонки таблицы Самрег не совпадают с §6.14.** В макете: Марка, P каб., Критерий, Шаг навива, Ниток, L факт, L заказ, Мощность, Ток. По PDF стр. 49 нужны ещё Диаметр, Тепловые потери и Мощность обогрева (обязательно рядом), Стартовый ток отдельно от рабочего, Количество секций.
10. **Напряжение редактируемое.** В 01 «Рабочее напряжение 230» с кареткой (select), в 02 «U, В: 230» как поле ввода. Требование ТЗ/DEC-11 — read-only с подписью источника. Ни один макет этого не показывает.
11. **Ниток = 2 без степпера и без ошибки.** Нет ограничения 1–3 и нет состояния «трёх ниток недостаточно».
12. **Панель объектов в 01 — иконки без подписей** (＋ 🖫 🗑 ⟳ ⊞) вместо именованных кнопок PDF стр. 21: «Загрузить из Excel», «Добавить на основании», «Удалить», «Групповая корректировка», «Настройки отображения». Это против §3.11 (единые наименования) и убивает половину сценариев §5.
13. ~~**Нет третьей формы «Исходные данные для спецификации».**~~ **Снято 2026-08-04 (Q1).** PDF стр. 21 показывает три карточки, в макете две — и это **правильно**: параметры спецификации (Ex, K1i, K2i, Kiu, L,K2i, R,гр) project-scoped, бэкенд отклоняет их запись на объект (`OBJECT_SPECIFICATION_SETTINGS_SCOPE_VIOLATION`). IP оказался свойством каталожной позиции, а не полем ввода; тип монтажа и доп. требования не реализованы нигде (новый вопрос Q5). Ложный дефект — см. бриф §6.3.
14. **Продуктовые изобретения без аннотаций:** pill «Режим: добавление», чекбокс «Показать блок заполнения параметров», переключатель «Обычный режим / Excel-режим». В PDF их нет. Либо обосновать в аннотации, либо убрать.
15. **Нет счётчиков выборки.** PDF стр. 21 и 35: «Выбрано: 1 из 4», «Отображено 4 из 4 объектов», «Выбрано: 2 из 7». В 02 есть «Выбрано: 0», в 01 нет ничего.
16. **Статус — только зелёная галочка.** PDF требует именованные статусы: «Ок» / «Проверьте Т» (стр. 21), «Нераспределён» (стр. 35), «Рассчитано» / «Требуется корректировка» (§6.14), «Требуется перерасчёт» (§6.19).

### 2.5 Технические замечания

17. **Брейкпоинты провалены на всех трёх ширинах.** Рендер ~1728 px, контракт — 1000 / 1280 / 1440. Замерено (§4): страница требует 1697 px, то есть горизонтальный overflow есть и на 1440. Бриф §5 это запрещает.
18. **DoD handoff §5 не выполнен ни по одному пункту:** нет README с картой frames → story, нет `microcopy.md`, нет аннотаций.
19. **Лежат не там:** `mockups/` в корне репозитория (untracked), handoff §3 требует `docs/tnp/cases/guest-specification/assets/ui/case1-mockups/`.
20. **Мелкие шрифты:** `.field label` 12.5 px, `.btn` / таблицы 13.5 px. С учётом того, что браузер пользователя инфлирует мелкие шрифты, плотность форм надо перепроверять с `--blink-settings=minimumFontSize=12`.

## 3. Что сделать перед отрисовкой макетов

Пять правок в ТЗ (полдня работы, снимают большую часть переделок):

1. **Добавить D-CHROME как P0** — гостевая шапка с дословным copy PDF стр. 21, и запретить employee-элементы явно в брифе, а не только в handoff.
2. **Решить, где живёт Ex/IP/материал оболочки** — третья форма на объекте (PDF стр. 21) или модалка настроек спецификации (бриф §4.2). Сейчас противоречие, и макет молча выбрал «нигде».
3. **Расширить D-HEAT до §5.5–5.13** или письменно вынести из scope. Молчаливый пропуск — риск на приёмке.
4. **Зафиксировать колонки** таблицы Самрег (§6.14, стр. 49) и строки спецификации (§7.6, стр. 60) как контракт в брифе.
5. **Microcopy sheet начать с дословных фраз PDF** (§6.19, §7.2, §7.7, §6.20, §4.4), отклонения помечать. Туда же — блок «решения сверх PDF»: Iдоп-форма, side panel вместо выпадающего списка, hide Резистив/Скин, 230 read-only, форматы отчёта.

Плюс организационно: выбрать один носитель (Penpot / HTML-прототип / PNG) и одну папку.

> **Статус на 2026-08-04:** все пять правок внесены в [`case1-designer-brief.md`](./case1-designer-brief.md) v1.1 (§0 базис и правила R1/R2, §2.1 только десктоп, §4.0 D-CHROME, §4.3 расширенный D-HEAT, §6 решения и отклонения, §7 microcopy-канон) и в handoff (носитель, папка, жёсткие правила). **Q1 закрыт** — параметры спецификации в модалке настроек (бриф §6.3). Блокеров на отрисовку нет; открытые Q2–Q5 на кадры не влияют.

| 1280 | 1697 px | **+417** | `.header-right` |
| 1440 | 1697 px | **+257** | `.header-right` |

Бриф §5 запрещает page overflow. Сейчас он есть **на всех трёх контрактных ширинах**, включая 1440 — текущие макеты не проходят собственный контракт ни в одной точке. 1697 px — это минимум шапки: `logo 93 + nav 762 + header-right 814` плюс отступы.

### 4.2 Сколько стоит гостевая шапка

Три варианта, собранные на том же `heatcalc-shared.css`, минимальная ширина:

| Вариант | Состав | Минимум | 1000 | 1280 | 1440 |
|---|---|---|---|---|---|
| Текущий (employee) | 4 пункта + 6 кнопок + имя проекта | 1697 px | ✗ | ✗ | ✗ |
| **A** — PDF дословно | 3 пункта, «Режим: гость», «Открыть проект из файла», «Сохранить проект в файл», «Инструкция» | **1172 px** | ✗ (+172) | ✓ | ✓ |
| **B** — A + иконки и галочки шагов | то же + `nav-icon` и `badge-ok` | **1285 px** | ✗ | ✗ (+5) | ✓ |
| **C** — компактный | «Гость», «⇧ Открыть файл», «⇩ Сохранить файл», «?» иконкой | **935 px** | ✓ | ✓ | ✓ |

**Вывод для дизайна:** переход на гостевую шапку сам по себе чинит 1280 и 1440. Для 1000 px нужен **отдельный компактный вариант C** — сокращённые подписи либо файловые операции в меню «…». Вариант B (с галочками шагов, как сейчас) не помещается в 1280 ровно на 5 px: если галочки продукту нужны, делать их компактнее.

### 4.3 Таблицы: минимальные ширины

| Файл | Таблица | Колонок | Минимум |
|---|---|---|---|
| 01-heat-calc | список объектов | 16 | **1462 px** |
| 01-heat-calc | слои изоляции | 5 | 856 px |
| 02-elec-calc | Самрег | 12 | **1221 px** |
| 03-specification | Общие материалы | 7 | **1105 px** |

Панель пересчёта в 02 («Тип для пересчёта … Расширенные параметры») требует минимум **1138 px** — на 1000 px тоже не помещается.

**Следствие, которое надо заложить в дизайн:** починка шапки **не** закрывает page overflow. После неё узким местом становятся таблицы: на 1000 px не влезает ни одна из трёх, на 1280 — таблица объектов. Бриф §5 разрешает горизонтальный скролл **внутри** таблицы, но сейчас таблицы лежат прямыми детьми `body` без скролл-контейнера и потому распирают страницу.

Плюс контракт §6.14 (стр. 49) добавляет в таблицу Самрег Диаметр, Тепловые потери, Мощность обогрева, Количество секций и разделяет стартовый и рабочий ток — это ~17 колонок вместо 12, ориентировочно **1600–1700 px**. Без скролл-контейнера и закреплённой колонки «Объект» такая таблица на 1000 px нечитаема: уедет именно то, по чему инженер опознаёт строку.

**Требование к макетам:** каждая широкая таблица — в контейнере с `overflow-x: auto`, первая содержательная колонка закреплена; кадр на 1000 px показывается именно в состоянии со скроллом, а не обрезанным.
