# Промпт: простой контракт readiness и настроек спецификации

## Цель

Исправить readiness и хранение настроек формирования спецификации без второго
источника данных и без усложнённой синхронизации формы с проектными defaults.

Case 1 PDF, §7.2–7.4, стр. 57–59 задаёт параметры в модальном окне перед
формированием и формирование только явно выбранных ЭР. Настройки относятся к
операции формирования спецификации, а не к готовности электротехнического
расчёта конкретной ЭР.

## Канонический контракт

1. Readiness — обычный read-only `GET` по явно выбранным `variant_ids`.
2. Readiness проверяет только сохранённое состояние проекта, каталога и
   выбранных ЭР. Текущую несохранённую форму он не принимает и не валидирует.
3. Текущие значения формы передаются только в `POST generate` через `options`.
4. Backend валидирует `options` и возвращает адресные field issues. Frontend
   показывает их у соответствующих полей и переводит focus к первому полю с
   ошибкой.
5. Отдельных project-scoped настроек формирования спецификации нет. Не должно
   быть settings endpoint, project-settings fallback, dual-read или
   dual-write.
6. У уже сформированной спецификации форма заполняется из её сохранённого
   `snapshot.resolved_options`.
7. Если для ЭР спецификация ещё не сформирована, `GET` возвращает отсутствие
   записи, а форма открывается пустой: способ группировки и два числовых поля
   не заданы; четыре boolean имеют значение `Нет`.
8. Успешное формирование атомарно сохраняет в существующей записи
   `specifications` позиции, snapshot входов и настроек, статус и время.
9. Последующий `GET` читает сохранённую спецификацию из БД без скрытого
   перерасчёта.
10. Если после формирования изменились влияющие на результат данные или
    настройки проекта, старая спецификация остаётся видимой, помечается stale,
    и frontend показывает предупреждение с предложением сформировать заново.
    Старый snapshot не переписывается и автоматический перерасчёт не запускается.

## Поля формы

Пользователь задаёт:

- `grouping_mode`;
- `Ex`;
- `K1i`;
- `K2i`;
- `Kiu`;
- `L_K2i_m`;
- `R_gr`.

`Ex`, `K1i`, `K2i`, `Kiu` строго двухсостояниевые:

- `Да` → `true`;
- `Нет` → `false`.

Пустого состояния у них нет. Для несформированной спецификации значение по
умолчанию — `Нет`. Значение `false` обязательно сохраняется и передаётся, а не
отбрасывается как falsy.

Реально незаполненными могут быть только:

- `grouping_mode`;
- `L_K2i_m`;
- `R_gr`.

Значение `0` является заполненным и не должно превращаться в отсутствие.

Все семь полей постоянно помечены как обязательные штатным UI-kit способом:

- `CompactField required`;
- required-состояние самого контрола;
- без ручных звёздочек и feature-specific required CSS.

Красное invalid-состояние появляется только после ответа backend с ошибкой.
Сообщение показывается под конкретным полем; общий alert может только дополнять
field-level ошибки.

## Readiness

Readiness не должен создавать `SpecificationGenerationRequest` с фиктивными
пустыми options и не должен объявлять ЭР неготовой из-за полей формы.

Инварианты ответа:

- project/catalog blockers находятся на верхнем уровне;
- у них нет `electrical_variant_id`;
- blocker конкретной ЭР находится только в её `results[]`;
- готовая ЭР остаётся `ready`, даже если есть независимый catalog/project
  blocker;
- проверяются только переданные `variant_ids`;
- readiness ничего не сохраняет и не помечает stale;
- frontend не блокирует generate из-за отсутствующих значений формы в
  readiness: авторитетная проверка формы выполняется в generate.

## Generate и сохранение

`POST generate` получает текущий form payload. Backend:

1. Проверяет три потенциально пустых поля и доменные ограничения всех значений.
2. Возвращает `422` с `issues[].field` для ошибок формы.
3. Выполняет preflight только переданных ЭР с теми же options.
4. Формирует только ready ЭР.
5. В одной транзакции сохраняет рассчитанные auto items, сохранённые manual
   items, `snapshot.resolved_options`, каталог, selections, fingerprints,
   нормализованные расчётные входы, generation status и timestamp.
6. Только после успешного commit возвращает результат.

Не сохранять текущую форму в проект отдельно. Не использовать значения из
другой спецификации или из project settings как fallback.

Неудачная попытка не должна стирать последний успешный snapshot и позиции.
Успешное повторное формирование согласованно заменяет auto-результат и snapshot.

## Stale

Изменение входов, влияющих на уже сформированный результат, помечает сохранённую
спецификацию stale. При этом:

- сохранённые позиции и настройки остаются доступны для просмотра;
- форма этой спецификации заполняется из старого snapshot;
- показывается заметное предупреждение о необходимости сформировать заново;
- старый результат не выдаётся за актуальный в отчёте/export;
- новая спецификация не создаётся и старый snapshot не обновляется до явного
  generate.

## База и совместимость

Обратная совместимость не требуется. Не добавлять legacy endpoint, адаптеры,
fallback или поддержку старого snapshot-формата.

Миграции и изменения DDL запрещены. Использовать существующие поля таблицы
`specifications`. Dev/test БД разрешено полностью пересоздать и заново заполнить
seeds; seeds не должны создавать project-scoped settings формирования.

## Проверки

Добавить или обновить characterization/contract-тесты минимум для сценариев:

- readiness готовой ЭР не зависит от пустой формы;
- catalog blocker глобальный и не получает фиктивный UUID ЭР;
- новая форма: три пустых поля и четыре `Нет`;
- generate с пустыми `grouping_mode`, `L_K2i_m`, `R_gr` возвращает field issues;
- `false` и `0` доходят до backend и snapshot без потери;
- после успешного generate `GET` возвращает сохранённые items и options;
- при повторном открытии сформированной спецификации форма заполнена snapshot;
- при открытии несформированной спецификации нет fallback из другой записи;
- stale-спецификация остаётся видимой и получает предупреждение;
- settings API отсутствует в OpenAPI и frontend;
- readiness остаётся GET и не выполняет мутаций.

Перед завершением запустить относящиеся к slice backend/frontend-тесты,
typecheck, lint и browser QA модального окна и stale-состояния. Незапущенную
проверку не объявлять зелёной.
