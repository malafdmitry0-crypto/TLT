## 1. Терминология

**Бочка = Ёмкость = Резервуар** — одна сущность, `object_type: "tank"`.
PDF называет её тремя словами; в приложении «Резервуар». Вне объёма
теплорасчёта только «Пол» (§5.2 — вкладка недоступна, future).

## 2. Единый конверт ошибки валидации

**[СВЕРКА] В версии 1.0 этот раздел отсутствовал, хотя на него ссылались A.2,
A.3, A.6 и пункт 7 DoD.** Без него исполнитель придумает формат сам, и
проверка «старых форматов не осталось» станет непроверяемой.

Все точки записи (`add_object`, `update_object`, `group_update_objects`)
отдают **422** с одинаковым телом:

```jsonc
{
  "detail": {
    "code": "heat_loss_validation_failed",   // машинный код причины
    "message": "Некорректные параметры ёмкости",
    "fields": ["insulation_layers"],          // поля формы для подсветки
    "validation_errors": {                    // как есть из CalculationService
      "message": "…",
      "field": "insulation_layers",
      "error_context": { }
    },
    "objects": [                              // только для group-update
      { "object_id": "…", "name": "…", "message": "…", "code": "…", "fields": [] }
    ]
  }
}
```

**Правила конверта.**

1. `code` — из `validation_errors.code`, если он есть; иначе
   `heat_loss_validation_failed`.
2. `message` — из `validation_errors.message`; если payload пуст, дефолт по типу:
   труба — «Некорректные параметры трубы», ёмкость — «Некорректные параметры
   ёмкости».
3. `fields` — из `validation_errors.field` (в список), иначе `[]`.
   Имена полей — идентификаторы реестра `heatcalc-fields.default.json`, чтобы
   фронт подсвечивал без маппинга.
4. `objects` присутствует **только** в ответе `group-update`; в остальных точках
   его нет (не пустой массив, а отсутствует).
5. `validation_errors` передаётся целиком, включая `error_context` — фронт и
   тесты опираются на исходные числа.

Собирается **одним хелпером** (`_heat_validation_detail(obj)`), три точки
используют его без копипаста.

## БЛОК A — инвариант на всех каналах записи (§5.4, §5.8)

### A.1 Дефект

Откат при неуспешном пересчёте сделан только для труб. Три места, литерал
`object_type == "pipe" and not obj.is_valid` — **подтверждено:
`objects.py:166` (add), `:314` (group-update), `:555` (update)**.

`CalculationService.try_recalculate` при исключении мутирует объект
(`results=None`, `is_valid=False`, `validation_errors=payload`). Для ёмкости
отката нет → **невалидная ёмкость коммитится молча**. Нарушены §5.4 и §5.8, и в
проекте заводятся объекты, блокирующие §5.13.

### A.2 Backend: отказ вместо тихого сохранения

1. Общий предикат для расчётных типов (`pipe`, `tank`): откат + 422 при
   `not obj.is_valid`, без ветвления по типу. Все три точки — через хелпер §2.
2. Дефолтный `message` по типу объекта (§2, правило 2).
3. `group_update_objects`: собирать проблемные объекты **любого** расчётного
   типа (сейчас фильтр по `pipe`). Всё-или-ничего: при непустом списке — откат,
   без `mark_electrical_calculations_stale` и без аудит-записи об успехе.

**[СВЕРКА] Соответствие §3.6.** «Ошибка при расчёте одного объекта не должна
приводить к потере всего проекта» — жёсткий отказ этому не противоречит:
теряется одна операция записи, проект и остальные объекты не затрагиваются.
Для `group-update` откат всей операции требует прямо §5.8 («система не изменяет
данные»), это сильнее общего правила §3.6.

### A.3 Каналы, создающие объекты без расчёта

- **Импорт Excel** (`import_excel`, `objects.py:416`) — асинхронная batch-задача
  остаётся (§5.5 не требует синхронности). Требование: после завершения задачи у
  каждого созданного объекта есть либо `results`, либо `validation_errors`.
  Состояния «висящий `not_calculated` без причины» быть не должно. Проверить
  `include_errors=True` и что падение задачи не оставляет объекты
  немаркированными.

- **Дублирование проекта** (`POST /projects/{id}/duplicate`) — копии выходят
  `is_valid=False`. **[СВЕРКА] Этого сценария в кейсе 1 нет:** §4.4–4.9 «Мои
  проекты» описаны для авторизованного пользователя и прямо вынесены из
  документации, гость проекты не дублирует. Пересчёт копий — **продуктовое
  решение владельца, а не требование PDF**; обосновывать ссылкой на кейс нельзя.
  Если решение принято — делать как `duplicate-batch` для §5.7
  (`objects.py:238-284`), тест `test_projects.py:390` (сейчас утверждает
  `is_valid is False` и `results is None`) переписать. **Если решение не принято
  — пункт не делать**, он вне объёма задачи.

- **Открытие проекта из файла** (§5.11, `project_io_service.py:1329`, `:1595`) —
  `is_valid`/`validation_errors` восстанавливаются из файла как есть. Это
  **правильно**: §5.11 требует загружать «результаты расчётов» из файла.
  Такие объекты просто проблемные и обязаны блокироваться (блок B) и
  подсвечиваться (блок C).

### A.4 Frontend: визард (§5.4)

§5.4 «Ошибка заполнения»: изменения не сохраняются, проблемные поля
подсвечиваются, **пользователь остаётся в режиме редактирования**.

Раньше подсветка работала побочно: объект сохранялся невалидным и возвращался в
ответе (`useHeatCalcObjectEditor.ts:111-124`,
`HeatCalcWizardFormPanel.tsx:84`). После A.2 этого пути нет — 422, записи нет.

В `handleWizardSubmit` (`useHeatCalcObjectEditor.ts:151+`) у обеих мутаций
(`add.mutate`, `edit.mutate`) добавить `onError`: при 422 с
`detail.validation_errors` оставить визард открытым на **оптимистичном** объекте
(он уже собирается в `handleWizardSubmit`), подмешав `is_valid: false` и
`validation_errors` из `detail`. Подсветка работает существующим механизмом,
новый UI не нужен.

Иной 422 или сетевая ошибка — визард открыт, показан текст ошибки, подсветка не
выставляется. Форма не сбрасывается и в режим добавления не переключается **ни
при каком исходе ошибки**.

Ветку `notifyObjectResult` «Объект добавлен/обновлён, но расчёт не выполнен»
(`useHeatCalcMutations.ts:15-25`) удалить целиком — она становится недостижимой.

### A.5 Frontend: excel-режим

Отдельный flow не нужен: `useHeatCalcDraftSaveModel` уже ловит ошибку построчно
и кладёт её в `draftRowsById[id].errors._row`, строка остаётся грязным
черновиком с `row-excel-error` (`:200-240`). После A.2 этим путём пойдут и
ёмкости. В скоупе улучшение: если в `detail.fields` есть поле — класть ошибку в
`errors[field]`, чтобы подсветилась конкретная ячейка.

## БЛОК B — гейт §5.13 (после A)

### B.1 Дефект

В гейт передаётся `workspace.allProjectObjects`, а массив не всегда полный:
запрос «все объекты» включён только при `isAllObjectScope || excelModeEnabled`
(`useHeatCalcObjectsDataModel.ts:197-205`), префетч всех работает только при
`total <= page_size` (`:230-253`). При объёме больше страницы невалидный объект
с другой страницы не учитывается — `getHeatCalcElectricalContinueState`
(`heatCalcContinueToElectricalModel.ts:28-48`) видит неполную выборку и
**пропускает переход**. §3.5 требует ≥500 объектов на проект — это рабочий
режим, а не край.

### B.2 [СВЕРКА] Что именно считать: трубы, а не весь проект

**В версии 1.0 предлагалось считать `invalid` по всему проекту. Это
расходится с PDF.**

§5.13 «Общие бизнес-правила»: «В рамках данного раздела обрабатываются **только
объекты типа "Трубопровод"»**. То же в §6.16: «Для объектов типа "Ёмкость"
(**не входит в MVP**)». Формулировка §5.13 «Система проверяет все объекты
проекта» из основного сценария не отменяет бизнес-правило того же раздела —
проверяются все объекты, которые этот раздел обрабатывает.

Итог: **гейт считает невалидные трубы**. Невалидная ёмкость переход не
блокирует — она не передаётся в ЭР.

Из сводки (`ProjectObjectsSummaryResponse`, есть `by_type` и `valid_by_type`):

```
pipeTotal   = by_type.pipe
pipeInvalid = by_type.pipe − valid_by_type.pipe
```

### B.3 Что сделать

- `resolveObjectCountsFromSummary` (`heatCalcObjectsDataAccessors.ts:63-74`)
  сейчас не пробрасывает ни `invalid`, ни `valid_by_type` — добавить
  `pipeInvalidCount` по формуле B.2.
- `getHeatCalcElectricalContinueState` принимает готовые counts. Ветку «считать
  по списку объектов» **удалить**, а не оставлять fallback-ом: два источника
  истины разъедутся. Нет сводки — нет разрешения на переход.
- **Cold load без «мигания» ошибкой.** Сводка — обязательный слайс
  `workspaceLoadState`, кнопка гасится при его ошибке (`HeatCalcPage.tsx:167`).
  Расширить: пока сводка `isPending` — кнопка `disabled`, tooltip «Проверяем
  готовность объектов…». Никаких алертов и модалки на этом состоянии.
- Свежесть сводки: `useHeatCalcGroupUpdate.ts` инвалидирует только
  `['projects', projectId]` — добавить
  `['project', projectId, 'objects', 'summary']`; проверить то же для
  копирования и удаления.

### B.4 Приёмка B

- Проект из >`page_size` объектов, ровно одна невалидная **труба** на второй
  странице, активна вкладка «Трубопровод»: переход не выполняется.
- Число в сообщении = число невалидных труб во всём проекте.
- Невалидная **ёмкость** при всех валидных трубах: переход **разрешён**
  (§5.13 + §6.16).
- Холодная загрузка: кнопка недоступна с нейтральным tooltip, ни одного
  всплывающего сообщения об ошибке.

## БЛОК C — подсветка и перечень (после B)

§5.13 «Обнаружены ошибки»: ЭР не создаётся, остаёмся в «Исходных данных»,
**проблемные строки подсвечиваются**, система **показывает перечень объектов и
ошибок**.

### C.1 Подсветка

`buildHeatCalcNormalTableRowClassName`
(`useHeatCalcNormalTableInteractionModel.ts:70`) ставит `row-invalid` только при
`heatLossCalcStatus(record) === 'error'`. Не подсвечиваются `not_calculated`
(импорт в процессе, объект из файла) и `unsupported`
(`calculation_service.py:288-315`).

**Фикс:** условие — `heatLossCalcStatus(record) !== 'calculated'`.

**Обязательное исключение:** не красить незасейвленные черновики. Локальные
excel-строки создаются с `is_valid: false` (`heatCalcExcelRows.ts:66`) — иначе
вся сетка ввода станет красной. Исключать `isExcelNewRowId(record.id)` и строки
из `draftRowsById`; у них свои классы `row-excel-new` / `row-excel-error` /
`row-excel-dirty`.

**CSS не трогать:** `.row-invalid > td` есть (`calc-spreadsheet-base.css:7-11`),
glide красит через `isErrorRowClassName` (`glideGridPrimitives.ts:50-54`).
Меняется только условие в TS.

**[СВЕРКА] Подсвечивать объекты обоих типов.** §5.13 требует подсветки
проблемных строк без оговорки по типу; ограничение «только трубы» из B.2
касается **гейта перехода**, а не подсветки. Невалидная ёмкость видна как
проблемная, но переход не блокирует.

### C.2 Перечень объектов и ошибок

Сейчас один тост со счётчиком (`useHeatCalcContinueToElectrical.ts:37-45`).
PDF требует перечень — тост **заменяется** модалкой.

Модалка «Объекты, которые нужно исправить», открывается только по клику «Далее»
при `pipeInvalidCount > 0`:

- **Данные — отдельный запрос**, не `allProjectObjects`: `queryObjects` с
  фильтром `heat_loss_status in ['error','not_calculated','unsupported']`.
  Поле фильтруемое — подтверждено: `FieldDef("heat_loss_status", …,
  filter_ops=("in",))` (`object_query_service.py:406-417`).
  **[СВЕРКА] Добавить в запрос `object_type: 'pipe'`** — перечень должен
  показывать то, что блокирует переход.
- **Строка перечня:** наименование (`params.name`), тип, причина:
  `error` → `heatLossErrorText(record)` (`heatCalcPageUtils.ts:137-150`);
  `not_calculated` → «Теплопотери не рассчитаны»;
  `unsupported` → `validation_errors.message`, иначе «Тип/форма объекта не поддерживается».
- **Клик по строке** → закрыть модалку, переключить scope и страницу, выделить
  строку, открыть в форме (`openEditWizard` + `setPendingTableFocusObject`).
- **«Показать только проблемные»** → фильтр колонки `heat_loss_status` через
  `setColumnFilter`, страница на первую, модалка закрыта.
- Переход не выполняется, остаёмся в «Исходных данных».

### C.3 Краевые случаи (обязательны)

- **Объём.** Не больше 50 строк, ниже — «и ещё N объектов»; `page_size`
  соответствующий. Не тянуть 500 объектов в модалку.
- **Загрузка.** Пока запрос идёт — модалка со скелетоном, кнопка в loading.
- **Ошибка запроса.** Текст + «Повторить»; переход всё равно не выполнять.
- **Гонка сводка/перечень.** Сводка говорит `invalid > 0`, перечень пуст →
  «Проблемных объектов не осталось, обновите данные» + кнопка обновления;
  автоматически на ЭР **не** уводить.
- **A11y.** Focus trap, возврат фокуса на «Далее», Esc, роль списка, строки
  достижимы с клавиатуры и активируются Enter. Использовать `TltModal`;
  кастомных `div`-кнопок не делать.

### C.4 Стили

- `heatcalc-shared.css` не редактировать (стили заморожены). Новый CSS —
  отдельным файлом рядом с компонентом, как `heat-group-update-modal.css`.
- Примитивы из `@/components/ui-kit` (`TltModal`, `TltAlert`, `TltButton`);
  эталон структуры — `HeatCalcGroupUpdateModal.tsx`.
- Только десктоп: приёмка **1280 / 1440 / 1920**, горизонтальный overflow
  запрещён; проверять с `--blink-settings=minimumFontSize=12`.

## 8. Definition of Done

1. Ёмкость и труба ведут себя одинаково при записи: невалидные изменения не сохраняются при создании, правке и групповой корректировке (§5.4, §5.8).
2. При 422 визард остаётся в режиме редактирования с подсветкой полей; excel-строка остаётся грязным черновиком с ошибкой в нужной ячейке.
3. Каналы записи держат инвариант: импорт домаркирует объекты; объекты из файла проекта — проблемные, но видимые. Пересчёт копий проекта — только по решению владельца (A.3).
4. Гейт §5.13 считает **невалидные трубы** по всему проекту из сводки, единственным источником истины; на холодной загрузке кнопка недоступна без ложных ошибок.
5. Любой объект со статусом ≠ «Рассчитан» подсвечен независимо от типа; черновики — нет.
6. При блокировке показан перечень труб с причинами, переходом к объекту и фильтром «только проблемные»; краевые случаи C.3 отработаны.
7. Конверт §2 применён во всех трёх точках; старых форматов в коде не осталось.
8. Зелёные: backend pytest, frontend vitest, затронутые e2e — с командами и выводом.
9. Скриншоты 1280 / 1440 / 1920 без горизонтального overflow.
10. Перечислены все переписанные и удалённые тесты с причиной по каждому.
