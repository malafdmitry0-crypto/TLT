# Сверка корректности ТНП-документации

Сверка выполнена по конвертированным документам, текущему backend-коду и
инженерной базе знаний по теплопередаче/электрообогреву. Это не заменяет
сертифицированную проверку по СНиП/СП/ГОСТ и оригинальным таблицам
производителя.

## В целом корректно

- Теплопотери трубопровода через многослойную цилиндрическую стенку описаны
  физически корректно: сопротивления слоев суммируются, затем
  `q = ΔT / R_total`.
- Наружная теплоотдача `alpha = 11,6 + 7 * sqrt(v)` выглядит как ожидаемая
  инженерная аппроксимация для наружного воздуха. В приложении ее правильно
  стоит ограничивать диапазоном.
- Подземное сопротивление трубы через `arccosh(H / r)` эквивалентно форме
  `ln(x + sqrt(x^2 - 1)) / (2πλ)`, если `x = H / r = 2H / D`.
- Геометрия резервуаров на воздухе корректна:
  - цилиндр: `S = πdH + πd²/2`;
  - прямоугольный резервуар: `S = 2(L + B)H + 2LB`.
- Температурная поправка сопротивления резистивного кабеля должна быть
  `rho_T = rho * (1 + alpha * (Tж - 20))`; в конвертированном DOCX формулы
  читаются именно так.
- Подбор стандартного сечения резистивного кабеля как минимального
  `Sк_б >= Sк` инженерно корректен.

## Исправлено в Markdown и QA-agent

### 1. `Rвнеш` для резервуаров исправлен на flat-wall формулу

В исходной конверсии `block-heat-loss-and-cable-selection/tank-heat-loss-and-cable-selection.md`
для резервуаров было указано:

```text
R_внеш = 1 / (π * alpha_внеш * (d_тр + 2 * sum(delta_из_i)))
```

Для плоской модели резервуара, которая используется в backend, внешнее
сопротивление должно быть:

```text
R_внеш = 1 / alpha_внеш
```

Markdown исправлен на `R_внеш = 1 / alpha`. Это согласовано с плоской моделью
резервуара и текущим backend. В QA-agent добавлен deterministic primitive
`tlt_tank_external_resistance`.

### 2. Периметр прямоугольного резервуара исправлен

В исходной конверсии документа по резервуарам было:

```text
П = 2 * L * B
```

Для периметра прямоугольного сечения должно быть:

```text
П = 2 * (L + B)
```

Markdown исправлен на `П = 2 * (L + B)`. Backend
`compute_tank_cable_length` уже использует эту размерностно корректную формулу,
а QA-agent теперь проверяет прямоугольный кейс.

### 3. Коэффициент запаса в формуле трубы получил явные скобки

В исходной конверсии формула трубы читалась как:

```text
Q = q * (L + sum(Lдоп) * K)
```

Инженерно и по backend-коду должно быть:

```text
Q = q * (L + sum(Lдоп)) * K
```

Markdown исправлен на `Q = q * (L + sum(Lдоп)) * K`, чтобы коэффициент запаса
применялся ко всему объекту, а не только к дополнительной длине.

### 4. Контракт против двойного применения `K` зафиксирован

В DOCX для выбора кабеля используется:

```text
q = Q / (L + sum(Lдоп))
```

Если `Q` уже включает `K`, то удельная мощность `q` тоже включает запас. Если
потом электрический расчет снова умножит требуемую мощность на `safety_factor`,
получится двойной запас.

В Markdown добавлен явный контракт: если электрический расчет применяет
`safety_factor`, то входная удельная мощность должна быть без уже примененного
`K`. Текущий backend для саморегулирующегося кабеля передает
`required_power_per_meter = heat_loss_per_meter` без `K`, а `K` применяет в
электрическом подборе один раз. В QA-agent добавлены primitives:
`tlt_pipe_electrical_required_power_per_meter` и
`tlt_tank_electrical_required_power_per_meter`.

### 5. Климатический алгоритм выделен в deterministic oracle

Схема климата задает правила:

- для труб `D >= 100`: `K = 1,1`, `T = T1`;
- для труб `D < 100`: `K = 1,12`, `T = T0`;
- для не-труб: `K = 1,1`, `T` по холодной пятидневке `0,92`.

В QA-agent добавлен deterministic algorithm `tlt_climate_safety_factor` с
boundary cases для `D = 99` и `D = 100`. В приложении климатические значения и
коэффициенты все еще распределены между справочниками, формами и параметрами
расчета, поэтому нужен отдельный e2e/API тест на сохранение этого контракта.

### 6. Границы алгоритма навива нормализованы

В `algorithms/winding.md` схема содержит строгие интервалы:

- `57 < D < 75`;
- `75 < D < 89`;
- `89 < D < 108`;
- `D > 108`.

Чтобы не оставлять дырки и не разрешать более высокий максимум навива на
границе без прямого указания производителя, принята консервативная
нормализация:

- `D < 57 -> Kn = 1,0`;
- `D = 57 -> Kn = 1,1`;
- `57 < D <= 75 -> Kn = 1,2`;
- `75 < D <= 89 -> Kn = 1,3`;
- `89 < D <= 108 -> Kn = 1,4`;
- `D > 108 -> Kn = 1,5`.

В QA-agent добавлен deterministic algorithm `tlt_max_winding_coefficient` с
boundary cases для `75`, `89` и `108`; backend валидирует explicit/geometric
коэффициент навива как hard-limit.

### 7. Температурные пределы ТТН/ТТВ/ТТХ трактуются как включительные

VSDX-схема саморегулирующегося кабеля использует условия вида:

```text
T1 < 65, T2 < 85
T1 < 120, T2 < 210
T1 < 150, T2 < 250
```

Для паспортных предельных температур инженерно корректнее трактовать границу
как включительную: серия допускается при температуре не выше своего предела.
Итоговое правило QA/backend:

- `ТТН`: `T1 <= 65` и `T2 <= 85`;
- `ТТВ`: `T1 <= 120` и `T2 <= 210`;
- `ТТХ`: `T1 <= 150` и `T2 <= 250`.

Такой контракт уже совпадает с текущим backend. В QA-agent добавлены boundary
cases на точных предельных значениях.

### 8. T3 и число ниток ТТН/ТТВ/ТТХ

VSDX различает:

- `T1` — температура продукта для выбора серии;
- `T2` — температура пропарки для выбора серии;
- `T3` — температура поддержания для `Pi.ном(T3)`.

В backend/API `maintain_temperature` является T3. Для совместимости старых
запросов, где T3 не передан, используется fallback `T3=T1`. Автоматический
подбор следует full-version правилу: серия выбирается по температурам, а если
мощности одной нитки не хватает, `N = ceil(Pоб / Pi.ном(T3))` без ограничения
`N <= 3` и без эскалации серии только ради числа ниток.

Суффикс марки закреплен как рабочий контракт:
`aggressive_product -> СТ`, иначе `СР`. Parsed ветка `R=1 -> СР` считается
неоднозначностью OCR/VSDX.

## Остается подтвердить или доработать

### 9. PDF-справочники резистивных кабелей закрыты пользовательскими скринами по ключевым таблицам

Это ограничение относится не к блок-схемам алгоритмов: они разобраны из
исходных `Алгоритмы/*.vsdx` в Markdown, JSON и Mermaid.

Для `ТТ Р1` последние пользовательские скрины приняты как источник истины по:

- схеме питания до `~600 В`, `50 Гц`;
- подключению в одну линию, петлей или звездой;
- формату заказа и кодам оболочки `2-FEP`, `3-PFA`;
- таблице сопротивлений, сечений, диаметров и расчетных длин секций для
  `20/30/40 Вт/м`.

Для `ТТ Р3` последние пользовательские скрины приняты как источник истины по:

- общим техническим характеристикам;
- строительной длине `200 м`;
- списку сечений жил;
- видимым строкам таблицы вариантов исполнения, габаритов, массы и радиуса
  изгиба.

Эти значения внесены в `backend/app/reference_data/resistive_cables.json` и
закреплены unit-тестами. Остается отдельно подтвердить только старые поля,
которые были в JSON до этой сверки, но не видны на последних скринах:

- старые поля `standard_supply_voltage_v = 380` и `max_linear_power_w_m = 50`
  для `ТТ Р3`, потому что на последних двух скринах они не видны.

Для machine-readable проверки использовать:

- `backend/app/reference_data/resistive_cables.json`;
- последние пользовательские скрины и исходные PDF как визуальный первоисточник;
- отдельную сверку JSON против PDF/OCR.
