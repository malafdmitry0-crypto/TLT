# Промпт: безопасный запуск автоматического электрорасчёта

## Контекст

На вкладке `Электрорасчёты` есть автоматический подбор кабеля в scope выбранного
именованного ЭР. Нужно доработать только запуск автоматического/полуавтоматического расчёта:

- ручной выбор кабеля в этом шаге не делать;
- drag-and-drop блок `Было/Стало` в этом шаге не делать;
- электрорасчёт не должен запускаться сам при изменении настроек;
- пользователь должен явно выбрать область пересчёта: выбранные строки или все объекты;
- пересчёт всех объектов должен быть отдельной опасной операцией с дополнительным подтверждением `Вы уверены?`.

## Термины и режимы выбора кабеля

В продукте нужно разделять три разных сценария. Это важно для названий кнопок, API и тестов.

### 1. Автоматический расчёт

Автоматический расчёт означает:

- пользователь задаёт общие параметры выбранного ЭР;
- пользователь явно нажимает кнопку запуска;
- алгоритм сам выбирает подходящую марку кабеля для каждого объекта;
- алгоритм сам рассчитывает длину, мощность, ток, шаг/нитки, если это предусмотрено текущими формулами;
- пользователь не выбирает конкретную марку кабеля вручную.

В этом режиме кабель выбирает система.

### 2. Полуавтоматический расчёт

Полуавтоматический расчёт означает:

- пользователь всё ещё не выбирает конкретную марку кабеля вручную;
- кабель всё ещё выбирает алгоритм;
- но пользователь ограничивает или уточняет правила подбора:
  - тип кабеля;
  - источник каталога;
  - UUID выбранного ЭР;
  - параметры `T проп.`, `U`, `w`, `h`, шаг укладки;
  - количество ниток, если сценарий допускает подбор меньшей мощности с 2/3 нитками;
  - область пересчёта: выбранные объекты или все объекты.

То есть полуавтоматический режим — это автоматический подбор с пользовательскими ограничениями и выбранным scope.

В рамках этого промпта кнопки `Пересчитать выбранные` и `Пересчитать все` относятся именно к автоматическому/полуавтоматическому расчёту: алгоритм сам подбирает кабель, но пользователь явно задаёт параметры и область пересчёта.

Важно: для автоматического и полуавтоматического расчёта не нужны отдельные кнопки. Это условное разделение одного и того же запуска алгоритма.

- Если пользователь оставил параметры по умолчанию, это автоматический расчёт.
- Если пользователь перед запуском изменил ограничения подбора, тип кабеля, источник, количество ниток или область пересчёта, это полуавтоматический расчёт.
- В обоих случаях используются те же две кнопки: `Пересчитать выбранные` и `Пересчитать все`.
- UI не должен добавлять отдельные кнопки `Автоматический` / `Полуавтоматический`.
- Это разделение нужно только для понимания логики, текстов, тестов и будущего ручного режима.

### 3. Ручной расчёт

Ручной расчёт будет отдельным функционалом и не входит в этот шаг.

Будущий ручной сценарий:

- открывается отдельная модалка выбора кабеля;
- пользователь выбирает конкретный кабель/марку для одного или нескольких объектов;
- модалка показывает параметры выбранного кабеля;
- система пересчитывает объект с выбранной маркой;
- пользователь видит, подходит кабель или нет;
- можно будет сравнивать `Было/Стало`.

Важно: в текущем промпте ручную модалку не реализовывать. Её нужно только учитывать в архитектуре и названиях, чтобы текущие кнопки автоматического/полуавтоматического подбора не смешивались с будущим ручным выбором.

## Цель

Сделать безопасный и предсказуемый запуск автоматического/полуавтоматического подбора кабеля:

1. `Пересчитать выбранные` — алгоритм пересчитывает только строки, отмеченные галочкой в таблице.
2. `Пересчитать все` — алгоритм пересчитывает все валидные и совместимо
   назначенные объекты выбранного ЭР, но только после явного подтверждения.
3. Никакие изменения параметров ЭР сами расчёт не запускают.

## Функциональные требования

### 1. Электрорасчёт не запускается сам

Проверить и сохранить правило:

- изменение `cable_type`;
- переключение выбранного именованного ЭР;
- изменение источника кабелей;
- изменение `T проп., °C`;
- изменение `U`;
- изменение `w`;
- изменение `h`;
- изменение шага укладки;
- изменение признака агрессивного продукта;
- изменение фильтров, сортировки, ширины колонок;

не должно вызывать batch электрорасчёт.

Расчёт стартует только по явному нажатию:

- `Пересчитать выбранные`;
- `Пересчитать все` после подтверждения.

### 2. UI: две отдельные кнопки запуска

В actionbar вкладки `Электрорасчёты` заменить одну кнопку `Выполнить электрорасчёт СО...` на две кнопки:

- `Пересчитать выбранные`;
- `Пересчитать все`.

Поведение:

- `Пересчитать выбранные` активна только если `selectedRowKeys.length > 0`;
- `Пересчитать выбранные` показывает количество выбранных строк, например `Пересчитать выбранные (3)`;
- `Пересчитать все` активна только если есть валидные объекты для электрорасчёта;
- во время активной задачи обе кнопки заблокированы или находятся в loading-state;
- кнопка отмены задачи остаётся как сейчас;
- выделение строк не сбрасывать без причины, кроме существующих случаев смены проекта/варианта.

### 3. `Пересчитать выбранные`

При нажатии:

- взять `selectedRowKeys`;
- передать их на backend как `object_ids`;
- запустить алгоритмический подбор кабеля только для этих объектов;
- не трогать существующие результаты других объектов выбранного ЭР;
- не трогать результаты других ЭР;
- после постановки задачи показать сообщение: `СО{variant} · пересчёт выбранных поставлен в очередь`;
- после завершения показать сообщение с явным scope: `СО{variant} · пересчитано выбранных: N, пропущено: M...`.

Если выбранные строки отфильтрованы/не на текущей странице, использовать только реально выбранные `selectedRowKeys`, как они хранятся в состоянии таблицы.

Если `selectedRowKeys` пустой:

- кнопку держать disabled;
- backend всё равно должен валидировать пустой список как ошибку, если такой payload пришёл напрямую.

### 4. `Пересчитать все` как опасная операция

Кнопка:

- должна быть `danger`;
- должна визуально отличаться от `Пересчитать выбранные`;
- должна иметь текст `Пересчитать все`;
- не должна запускать расчёт сразу.

Обязательное подтверждение:

1. При нажатии открыть подтверждение.
2. В подтверждении явно показать:
   - `Пересчитать электрорасчёт для всех объектов СО{variant}?`
   - `Существующие результаты этого варианта будут обновлены.`
   - `Вы уверены?`
3. Кнопка подтверждения должна быть `danger`.
4. Текст кнопки подтверждения: `Да, пересчитать все`.
5. Кнопка отмены: `Отмена`.

Если в проекте уже используется `Popconfirm` для опасных действий, можно использовать его. Если текст и состояние получаются слишком плотными, использовать `Modal.confirm`.

Важно: одного клика по `Пересчитать все` недостаточно. Расчёт стартует только после подтверждения `Да, пересчитать все`.

После подтверждения:

- запустить batch без `object_ids`;
- запустить алгоритмический подбор кабеля для всех валидных совместимо
  назначенных объектов текущего проекта и выбранного ЭР;
- после постановки задачи показать сообщение: `СО{variant} · пересчёт всех объектов поставлен в очередь`;
- после завершения показать сообщение с явным scope: `СО{variant} · пересчитано всех: N, пропущено: M...`.

## Backend

### 1. Request schema

Проверить текущую schema batch электрорасчёта.

Добавить поле:

```python
object_ids: list[str] | None = None
```

Правила:

- `None` означает пересчитать все валидные объекты проекта;
- непустой список означает пересчитать только эти объекты;
- пустой список `[]` должен быть ошибкой `400` или `422`, выбрать статус по текущему стилю проекта;
- дубликаты в списке не должны приводить к повторному расчёту одного объекта.

### 2. API endpoint

Прокинуть `object_ids` из API в задачу:

- в endpoint batch электрорасчёта;
- в `TaskService.create_electrical_batch_task`;
- в payload фоновой задачи.

Сохранить обратную совместимость:

- старые вызовы без `object_ids` должны работать как пересчёт всех.

### 3. Проверка доступа и принадлежности объектов

Если `object_ids` передан:

- проверить, что все объекты принадлежат `project_id`;
- проверить, что пользователь/сессия имеет доступ к проекту;
- если хотя бы один `object_id` не принадлежит проекту или недоступен, вернуть ошибку и не запускать задачу;
- не делать частичный запуск при смешанном списке валидных и чужих id.

Рекомендуемое поведение:

- неизвестный/чужой object id -> `400` или `404` с понятным `detail`;
- пустой список -> `422`;
- список только невалидных по теплопотерям объектов -> задачу можно создать, но результат должен корректно вернуть skipped/heat_loss_failed по текущей логике. Если в проекте уже есть правило не создавать задачу без валидных объектов, следовать ему.

### 4. Фильтрация объектов в расчёте

В месте, где batch выбирает объекты проекта:

- если `object_ids is None`, использовать текущую логику всех объектов;
- если `object_ids` задан, выбрать только эти объекты;
- сохранять порядок по `sort_order`, если порядок важен для progress/result;
- не пересчитывать объекты, которых нет в списке.

### 5. Результат задачи

Расширять result необязательно, если уже есть поля:

- `calculated`;
- `skipped`;
- `heat_loss_failed`;
- `failed`;

Но frontend должен знать scope запуска. Можно:

- сохранить scope во frontend state по `activeJobId`;
- или добавить в task result/payload поле `scope: "selected" | "all"`.

Предпочтение: добавить scope в payload задачи и вернуть его в результате, если это не ломает текущие тесты.

## Frontend API

Обновить функцию запуска batch электрорасчёта:

```ts
enqueueElectricalBatchJob(
  projectId,
  cableSource,
  variant,
  cableType,
  options,
  objectIds?: string[],
)
```

Или, если текущий стиль проекта лучше поддерживает object options, добавить `objectIds` внутрь options.

Требования:

- для выбранных передавать `objectIds: selectedRowKeys`;
- для всех не передавать `objectIds` или передавать `undefined`;
- не передавать пустой массив с UI, потому кнопка selected disabled без выбранных строк.

- `Пересчитать все` — `danger`;

  - нет валидных объектов;

- для disabled selected: `Выберите строки галочками`;


Кнопки:

Важно:

- при подтверждении вызывается ровно один batch.

## Сообщения пользователю

При постановке задачи:

- selected: `СО{variant} · пересчёт выбранных поставлен в очередь`;
- all: `СО{variant} · пересчёт всех объектов поставлен в очередь`.

При успехе:

- selected: `СО{variant} · пересчитано выбранных: {calculated}, пропущено: {skipped}`;
- all: `СО{variant} · пересчитано всех: {calculated}, пропущено: {skipped}`.

Если есть `heat_loss_failed`:

- добавить `, ошибок теплопотерь: {heat_loss_failed}`.

Если задача failed:

- оставить текущую ошибку, но желательно добавить scope:
  - `Пересчёт выбранных завершился ошибкой`;
  - `Пересчёт всех объектов завершился ошибкой`.

## Инвалидация данных

## Критерии готовности

- Электрорасчёт не стартует сам при изменении настроек.
- Есть две разные кнопки: `Пересчитать выбранные` и `Пересчитать все`.
- `Пересчитать выбранные` запускает алгоритмический подбор только для отмеченных строк.
- `Пересчитать все` требует подтверждение с текстом `Вы уверены?`.
- Отмена подтверждения не запускает batch.
- Остальные объекты не затрагиваются при selected scope.
- Старый сценарий batch без `object_ids` работает как пересчёт всех.
- Тесты backend/frontend покрывают scope и подтверждение.
- В тексте/коде не смешаны автоматический/полуавтоматический подбор и будущий ручной выбор кабеля в отдельной модалке.
