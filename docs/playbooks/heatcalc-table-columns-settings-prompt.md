# HeatCalc Table Columns Settings Prompt

## Контекст

На странице `HeatCalcPage` таблица исходных данных стала центральным рабочим
местом после удаления внутренних вкладок. Сейчас для труб и резервуаров есть
фиксированные наборы колонок:

- трубы: `№`, `Тип`, `Наименование`, `Ø, мм`, `DN`, `L, м`, `Слоёв ИЗ`,
  `δ ИЗ, мм`, `Материал ИЗ`, `T подд.`, `T окр.`, `Зад.`, `Флн.`, `Опр.`;
- резервуары: `№`, `Тип`, `Наименование`, `Форма`, `Габариты`, `Размещение`,
  `Слоёв ИЗ`, `δ ИЗ, мм`, `Материал ИЗ`, `T подд.`, `T окр.`, `Q доп., Вт`.

При большом количестве данных пользователю нужно быстро убрать лишние поля из
таблицы, чтобы видеть только нужный набор параметров. Это должно работать
отдельно для труб и резервуаров.

## Цель

Добавить компактную кнопку настройки отображаемых полей таблицы. Кнопка должна
открывать модальное окно, где пользователь может выбрать, какие колонки
показывать для `Трубы` и для `Резервуара`.

Главная цель: повысить управляемость таблицы без изменения модели хранения
объектов и без увеличения высоты рабочей зоны.

## Важное Ограничение

Не менять принцип хранения расчётных объектов в БД.

Настройки колонок являются UI-предпочтением пользователя, а не частью
расчётных данных. Нельзя записывать их в `ProjectObject.params`, результаты
расчёта, экспортные файлы или проектные параметры.

Отдельно разделить два вида настроек:

- `HeatCalcTableColumnSettings` — какие поля видны в экранной таблице
  `HeatCalcPage`;
- `HeatCalcExportColumnSettings` — какие поля включаются в экспортируемый
  XLSX/CSV-документ.

Эти настройки не должны переиспользовать один ключ, один modal и один backend
preference endpoint. Пользователь может хотеть узкую таблицу на экране, но
полный экспортный документ для обмена с коллегами, или наоборот.

Для экспортируемого XLSX/CSV-документа дефолт противоположный экранной таблице:
по умолчанию нужно
экспортировать все доступные поля для соответствующего типа объекта. Сужение
состава экспорта допускается только после явной пользовательской настройки
`HeatCalcExportColumnSettings`.

Правило хранения зависит от типа пользователя:

- новый гость: дефолтный JSON-пресет из этого документа;
- гость, который уже менял настройки: `localStorage`;
- новый зарегистрированный пользователь без записи настроек в БД: дефолтный
  JSON-пресет из этого документа;
- зарегистрированный пользователь с записью настроек в БД: БД как источник
  истины, `localStorage` можно использовать только как кеш.

Для зарегистрированных пользователей допустимо добавить отдельное backend/API
хранилище пользовательских UI-настроек. Это должна быть независимая сущность
вроде `user_preferences` / `ui_preferences`, а не изменение схемы расчётных
объектов.

## UI Требование

В `actionbar-srs` добавить icon-only кнопку настройки колонок.

Рекомендуемая позиция:

```text
[Труба] [pipe icon] [tank icon] │ [+] [copy] [apply] ... │ [columns/settings] │ [.xlsx] [.csv] │ [status]
```

Допустимые иконки Ant Design:

- `SettingOutlined`;
- `SlidersOutlined`, если доступна в используемой версии;
- `TableOutlined` + tooltip, если хочется точнее связать действие с таблицей.

Текст на кнопке не показывать. Обязательно:

- `aria-label="Настроить поля таблицы"`;
- tooltip `Поля таблицы`;
- высота и ширина такие же, как у остальных icon-only кнопок actionbar;
- кнопка не должна менять высоту панели действий.

## Модальное Окно

Заголовок:

```text
Поля таблицы
```

Структура:

- сверху короткий переключатель/табы `Трубы` и `Резервуары`;
- ниже список полей текущего типа с checkbox;
- снизу действия:
  - `Сбросить`;
  - `Отмена`;
  - `Применить`.

Не добавлять длинный поясняющий текст внутрь модального окна. Интерфейс должен
быть самодостаточным: заголовки, чекбоксы и кнопки достаточно объясняют смысл.

## Поведение

1. По умолчанию показывать текущий компактный набор колонок, который уже есть
   в таблице до реализации настройки полей.
2. Для труб и резервуаров хранить независимые настройки.
3. При переключении `Труба / Резервуар` таблица применяет настройки выбранного
   типа.
4. Изменения внутри модального окна не должны применяться мгновенно, если
   пользователь нажал `Отмена`.
5. `Применить` сохраняет настройки и сразу обновляет таблицу.
6. `Сбросить` возвращает дефолтный набор колонок только для активного таба
   модального окна.
7. Для гостя `Применить` сохраняет настройки только в `localStorage`.
8. Для зарегистрированного пользователя `Применить` сохраняет настройки в БД и
   только после успешного ответа обновляет `localStorage` как кеш. UI не
   должен зависать, если backend-запрос идет медленно.
9. При открытии страницы выбирать настройки строго по алгоритму из раздела
   `Алгоритм Инициализации Настроек`.
10. Если настройки в `localStorage` или БД повреждены/устарели, silently
   fallback к дефолтному JSON-пресету.
11. Новые колонки, добавленные в коде в будущем, должны появляться по умолчанию,
   если их нет в старой пользовательской настройке.

## Обязательные Колонки

Не давать скрывать:

- колонку выбора строк checkbox, потому что она управляется AntD rowSelection;
- `Наименование`, потому что это главный идентификатор объекта.

`№` и `Тип` можно сделать скрываемыми, но по умолчанию они включены.

Если пользователь снял все доступные чекбоксы кроме обязательных, таблица всё
равно должна оставаться читаемой: минимум `Наименование` должно быть видно.

## Алгоритм Инициализации Настроек

Не смешивать источники хаотично. На старте страницы нужно выбрать один
источник настроек по роли пользователя и наличию сохраненной записи.

```text
if role == guest:
  if localStorage[heatcalc.tableColumns.v1] exists and valid:
    use localStorage settings
  else:
    use DEFAULT_TABLE_COLUMN_SETTINGS_JSON

if role == employee/admin:
  settingsFromDb = GET /users/me/ui-preferences/heatcalc-table-columns

  if settingsFromDb exists and valid:
    use settingsFromDb
    replace localStorage cache with settingsFromDb
  else:
    remove localStorage[heatcalc.tableColumns.v1]
    use DEFAULT_TABLE_COLUMN_SETTINGS_JSON
```

Для зарегистрированного пользователя `localStorage` не должен побеждать БД,
если в БД уже есть запись. Это важно: пользовательские настройки должны
восстанавливаться между браузерами и устройствами.

`localStorage` для зарегистрированного пользователя нужен только для:

- быстрого локального кеша после успешной загрузки из БД;
- чтения последней подтвержденной backend-версии при краткой недоступности API.

Лучшая практика для дефолта: не записывать дефолтный JSON в тот же
`localStorage`-ключ, где лежит пользовательская настройка. Дефолт должен
оставаться кодовой/JSON-константой приложения. Иначе через несколько релизов
старый дефолт в браузере начнет выглядеть как пользовательский выбор и будет
мешать обновлять дефолтный набор колонок для новых пользователей.

Если в будущем понадобится кешировать сам факт применения дефолта, использовать
отдельный технический ключ с явным metadata, например:

```json
{
  "source": "default",
  "defaultVersion": 1
}
```

Но для этой реализации предпочтительно не кешировать дефолт вообще.

Если зарегистрированный пользователь изменил настройки, кеш в `localStorage`
нужно считать устаревшим до подтверждения backend. Не оставлять измененный
`localStorage` как источник истины, если запись в БД еще не сохранена.

Алгоритм сохранения для зарегистрированного пользователя:

```text
on Apply:
  nextSettings = modal draft
  update visible columns in memory optimistically
  remove localStorage[heatcalc.tableColumns.v1]
  PUT /users/me/ui-preferences/heatcalc-table-columns nextSettings

  if PUT success:
    use response settings as confirmed settings
    write response settings to localStorage as cache

  if PUT failed:
    keep/restore last confirmed settings from DB if available
    keep DEFAULT_TABLE_COLUMN_SETTINGS_JSON if DB record did not exist
    keep localStorage cache empty
    show non-blocking sync error
```

Если для зарегистрированного пользователя записи в БД нет, дефолтный
JSON-пресет используется напрямую. Не записывать дефолт в `localStorage` как
будто это пользовательская настройка из БД. `localStorage` для registered
заполняется только подтвержденной записью из БД.

Если backend недоступен для зарегистрированного пользователя:

- можно временно показать настройки из `localStorage`, если они валидны;
- но после восстановления backend БД снова становится источником истины;
- ошибку синхронизации нужно показать ненавязчиво, без блокировки таблицы.

## Дефолтный JSON Пресет

Текущий набор колонок должен быть дефолтным пресетом. Полный каталог доступных
полей может быть шире, но первый экран таблицы после открытия страницы должен
оставаться таким же, как сейчас.

Дефолтные visible keys хранить как JSON-совместимую структуру:

```json
{
  "version": 1,
  "visibleKeys": {
    "pipe": [
      "index",
      "type",
      "name",
      "pipe_outer_diameter",
      "pipe_dn",
      "pipe_length",
      "insulation_layer_count",
      "insulation_thickness",
      "insulation_material",
      "process_temperature",
      "ambient_temperature",
      "valve_count",
      "flange_count",
      "support_count"
    ],
    "tank": [
      "index",
      "type",
      "name",
      "tank_shape",
      "tank_dimensions",
      "placement",
      "insulation_layer_count",
      "insulation_thickness",
      "insulation_material",
      "process_temperature",
      "ambient_temperature",
      "q_additional"
    ]
  }
}
```

### Дефолтные Поля Трубы

| Key | Заголовок | Источник | Комментарий |
| --- | --- | --- | --- |
| `index` | `№` | derived | Порядковый номер видимой строки. |
| `type` | `Тип` | object | Сейчас отображается как `Тр.`. |
| `name` | `Наименование` | `params.name` | Обязательное поле, нельзя скрывать. |
| `pipe_outer_diameter` | `Ø, мм` | `params.outer_diameter` | Хранится в метрах, отображается в мм. |
| `pipe_dn` | `DN` | derived | Вычисляется по наружному диаметру. |
| `pipe_length` | `L, м` | `params.pipe_length` | Длина трубопровода. |
| `insulation_layer_count` | `Слоёв ИЗ` | `params.insulation_layer_count` / `params.insulation_layers` | Количество слоёв изоляции. |
| `insulation_thickness` | `δ ИЗ, мм` | `params.insulation_thickness` | Хранится в метрах, отображается в мм. |
| `insulation_material` | `Материал ИЗ` | `params.insulation_material` | Отображать label из справочника, если он доступен. |
| `process_temperature` | `T подд.` | `params.process_temperature` | Требуемая/поддерживаемая температура объекта. |
| `ambient_temperature` | `T окр.` | `params.ambient_temperature` | Температура окружающей среды. |
| `valve_count` | `Зад.` | `params.valve_count` | Количество задвижек. |
| `flange_count` | `Флн.` | `params.flange_count` | Количество фланцев. |
| `support_count` | `Опр.` | `params.support_count` | Количество опор. |

### Дефолтные Поля Резервуара

| Key | Заголовок | Источник | Комментарий |
| --- | --- | --- | --- |
| `index` | `№` | derived | Порядковый номер видимой строки. |
| `type` | `Тип` | object | Сейчас отображается как `Рез.`. |
| `name` | `Наименование` | `params.name` | Обязательное поле, нельзя скрывать. |
| `tank_shape` | `Форма` | `params.shape` | Цилиндр, прямоугольный резервуар или сфера. |
| `tank_dimensions` | `Габариты` | derived from geometry params | Агрегированная колонка из `diameter`, `height`, `length`, `width`. |
| `placement` | `Размещение` | `params.placement` / `params.location` | На открытом воздухе, в помещении или подземно. |
| `insulation_layer_count` | `Слоёв ИЗ` | `params.insulation_layer_count` / `params.insulation_layers` | Количество слоёв изоляции. |
| `insulation_thickness` | `δ ИЗ, мм` | `params.insulation_thickness` | Хранится в метрах, отображается в мм. |
| `insulation_material` | `Материал ИЗ` | `params.insulation_material` | Отображать label из справочника, если он доступен. |
| `process_temperature` | `T подд.` | `params.process_temperature` | Требуемая/поддерживаемая температура объекта. |
| `ambient_temperature` | `T окр.` | `params.ambient_temperature` | Температура окружающей среды. |
| `q_additional` | `Q доп., Вт` | `params.q_additional` | Дополнительная мощность для резервуара. |

Эти ключи должны быть частью полного registry и иметь `defaultVisible: true`.
Все остальные доступные поля могут быть включены пользователем вручную через
modal и должны иметь `defaultVisible: false`, если отдельно не согласовано
другое поведение.

## Архитектура Реализации

Не размазывать логику колонок по JSX.

Рекомендуемый подход:

1. Вынести описание колонок в registry:

```ts
type ColumnKey =
  | 'index'
  | 'type'
  | 'name'
  | 'pipe_outer_diameter'
  | 'pipe_dn'
  | 'pipe_length'
  | 'tank_shape'
  | 'tank_dimensions'
  | 'placement'
  | 'insulation_layer_count'
  | 'insulation_thickness'
  | 'insulation_material'
  | 'process_temperature'
  | 'ambient_temperature'
  | 'valve_count'
  | 'flange_count'
  | 'support_count'
  | 'q_additional';
```

2. Для каждого типа объекта определить ordered list дефолтных ключей. Значения
   должны совпадать с JSON-пресетом выше:

```ts
const DEFAULT_PIPE_COLUMN_KEYS: ColumnKey[] = [
  'index',
  'type',
  'name',
  'pipe_outer_diameter',
  'pipe_dn',
  'pipe_length',
  'insulation_layer_count',
  'insulation_thickness',
  'insulation_material',
  'process_temperature',
  'ambient_temperature',
  'valve_count',
  'flange_count',
  'support_count',
];

const DEFAULT_TANK_COLUMN_KEYS: ColumnKey[] = [
  'index',
  'type',
  'name',
  'tank_shape',
  'tank_dimensions',
  'placement',
  'insulation_layer_count',
  'insulation_thickness',
  'insulation_material',
  'process_temperature',
  'ambient_temperature',
  'q_additional',
];
```

3. Рендер AntD columns строить из registry и текущего списка visible keys.
4. Настройки хранить отдельно от проектных и расчётных данных:

```ts
interface HeatCalcTableColumnSettings {
  version: 1;
  visibleKeys: {
    pipe: ColumnKey[];
    tank: ColumnKey[];
  };
  updatedAt?: string;
}
```

5. Ключ `localStorage`:

```text
heatcalc.tableColumns.v1
```

Если уже есть локальный helper для persisted UI state, использовать его вместо
ручного доступа к `localStorage`.

6. Для зарегистрированных пользователей добавить слой синхронизации с backend.
   Предпочтительный контракт:

```text
GET  /users/me/ui-preferences/heatcalc-table-columns
PUT  /users/me/ui-preferences/heatcalc-table-columns
```

Для настроек экспортируемого документа использовать отдельный ключ и отдельный
backend preference:

```text
localStorage key: heatcalc.exportColumns.v1
GET  /users/me/ui-preferences/heatcalc-export-columns
PUT  /users/me/ui-preferences/heatcalc-export-columns
```

Этот playbook реализует только настройки экранной таблицы. Настройки
экспортируемого XLSX/CSV-документа нужно описывать и реализовывать отдельной
задачей, чтобы не смешать поведение таблицы и экспорта.

В отдельной задаче для `HeatCalcExportColumnSettings` дефолт должен быть:

```json
{
  "version": 1,
  "visibleKeys": {
    "pipe": ["*"],
    "tank": ["*"]
  }
}
```

Смысл `["*"]`: экспортировать все поля из полного registry для данного типа.
Это не то же самое, что дефолт экранной таблицы.

Если в проекте уже есть другой namespace для user settings, использовать
существующий паттерн.

7. В БД хранить только пользовательские настройки UI:

```ts
{
  key: 'heatcalc.tableColumns.v1',
  value: HeatCalcTableColumnSettings,
  user_id: currentUser.id,
  updated_at: string
}
```

Не привязывать эти настройки к guest session, project id или object id.

8. Конфликты решать просто и предсказуемо:

- если пользователь меняет настройки в текущем браузере, локальное изменение
  считается черновиком до успешного сохранения в БД;
- при начале сохранения для зарегистрированного пользователя очищать
  `localStorage`-кеш, чтобы не закрепить неподтвержденное изменение;
- после успешного сохранения записывать в `localStorage` только ответ backend;
- если сохранение в БД не удалось, держать `localStorage` пустым и вернуться к
  последней подтвержденной версии из БД или дефолтному JSON-пресету;
- при загрузке страницы для зарегистрированного пользователя БД побеждает
  `localStorage`, если запись в БД существует и валидна;
- если записи в БД нет, используется дефолтный JSON-пресет, а не старый
  случайный `localStorage` из другой сессии/роли.

## Табличное Поведение

Настройка колонок должна влиять только на отображение таблицы.

Не менять этой настройкой:

- состав колонок экспортируемого XLSX/CSV;

Для экспорта нужен отдельный UI и отдельное хранилище настроек:
`HeatCalcExportColumnSettings`.

При этом дефолт для XLSX/CSV уже сейчас должен пониматься как полный экспорт:
если пользователь не настраивал экспорт, XLSX/CSV отдаёт все доступные поля.
Настройка экранной таблицы не должна случайно урезать экспорт.

Проверить отдельно:

- выбор строк продолжает работать;
- подсветка выбранной строки не ломается;
- сортировка `sort_order` и порядок данных не меняются;
- клик по строке по-прежнему открывает форму редактирования;
- расчётные допущения над таблицей продолжают обновляться по выбранной строке;
- empty state не меняется.

### Copy To Clipboard

Если в коде есть копирование выбранных строк через `Ctrl+C`, оно должно
использовать тот же набор видимых колонок, что и таблица. Пользователь ожидает,
что скопируется именно видимый набор, а не скрытые поля.

Если это усложняет реализацию, допустим первый этап: оставить копирование как
есть, но явно покрыть TODO/issue в отчёте. Предпочтительный вариант — синхронно
обновить copy logic.

## Доступность

Обязательно:

- кнопка настройки имеет точный `aria-label`;
- checkbox-список имеет понятные текстовые label;
- modal закрывается по `Esc`;
- `Отмена` не сохраняет изменения;
- фокус после закрытия возвращается на кнопку настройки;
- активный таб модального окна видим через keyboard navigation.

## Визуальные Правила

- Не увеличивать высоту `actionbar-srs`.
- Не добавлять текстовую кнопку, если достаточно icon-only с tooltip.
- Не делать modal шире `560-640px`.
- Внутри modal использовать плотный, но читаемый список.
- Не использовать крупные карточки внутри modal.
- Не добавлять декоративные фоны.
- Не менять типографику всей страницы ради этой задачи.
- Не делать настройки колонок глобальным баннером или отдельной строкой над
  таблицей.

## Тесты

Добавить unit/integration tests на frontend.

Минимальный набор:

1. Кнопка `Настроить поля таблицы` открывает modal `Поля таблицы`.
2. Для труб можно скрыть `DN`, после `Применить` колонка `DN` исчезает.
3. Для резервуаров настройка независимая: скрытие `DN` у труб не влияет на
   резервуары.
4. `Отмена` не применяет изменения.
5. `Сбросить` возвращает дефолтный набор активного типа.
6. `Наименование` нельзя отключить.
7. Для гостя настройки восстанавливаются из `localStorage` после remount
   страницы.
8. Для нового гостя без `localStorage` используется дефолтный JSON-пресет.
9. Для нового зарегистрированного пользователя без записи в БД используется
   дефолтный JSON-пресет.
10. Для зарегистрированного пользователя настройки сохраняются в БД и
    только после успешного ответа backend дублируются в `localStorage` как кеш.
11. Для зарегистрированного пользователя запись из БД побеждает `localStorage`,
    если оба источника существуют.
12. Для зарегистрированного пользователя backend-настройки восстанавливаются
    после очистки `localStorage`.
13. Если зарегистрированный пользователь меняет настройки и backend-сохранение
    падает, неподтвержденные изменения не остаются в `localStorage`.

Если обновляется copy logic, добавить тест:

- `Ctrl+C` копирует только видимые колонки.

## Проверка Через Playwright

После реализации выполнить smoke через браузер:

1. Открыть гостевой проект с несколькими трубами и резервуарами.
2. Открыть modal полей.
3. На трубах скрыть `DN`, `Зад.`, `Флн.`, `Опр.`.
4. Убедиться, что таблица стала уже и эти колонки исчезли.
5. Переключиться на резервуары и убедиться, что их набор колонок не затронут.
6. Скрыть у резервуаров `Q доп., Вт`.
7. Обновить страницу и проверить, что настройки сохранились.
8. Нажать `Сбросить` для резервуаров и проверить возврат `Q доп., Вт`.
9. Для зарегистрированного пользователя повторить сохранение настройки,
   очистить `localStorage`, обновить страницу и проверить восстановление из БД.

## Acceptance Criteria

- В actionbar есть компактная кнопка настройки полей таблицы.
- Modal позволяет настраивать видимость колонок отдельно для труб и резервуаров.
- Для гостя настройки сохраняются только в `localStorage`.
- Для нового гостя и нового зарегистрированного пользователя используется
  дефолтный JSON-пресет.
- Для гостя с измененными настройками используется `localStorage`.
- Для зарегистрированного пользователя с записью настроек используется БД, а
  `localStorage` работает как кеш.
- Для зарегистрированного пользователя настройки сохраняются в БД как user UI
  preference и дублируются в `localStorage` только после успешного ответа
  backend.
- Дефолтный JSON не записывается в user settings `localStorage`-ключ; он
  используется как кодовая/JSON-константа приложения.
- Настройки не меняют расчётные объекты, результаты расчёта, экспорт объектов
  и проектные параметры.
- Таблица не ломает выбор строк, открытие формы и расчётные допущения.
- `Наименование` всегда остается видимым.
- Высота верхней рабочей зоны не увеличивается.
- Frontend typecheck, lint и тесты проходят.
- Playwright smoke подтверждает работу на реальном гостевом проекте.
