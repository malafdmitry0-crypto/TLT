# HeatCalc Table Column Layout Prompt

## Контекст

В HeatCalc уже есть модальное окно настройки таблицы, где пользователь управляет
видимостью колонок для `Трубы` и `Резервуара`. Также таблица уже поддерживает
поиск, фильтры, сортировку, backend-query и отдельные настройки экранной
таблицы, не влияющие на расчёты.

Следующий шаг - сделать настройки колонок полноценным инструментом компоновки:
пользователь должен не только включать и выключать поля, но и управлять порядком
столбцов, менять их ширину и получать предсказуемое восстановление этих
настроек при следующем открытии проекта.

## Цель

Расширить `Настройки таблицы` так, чтобы для каждого типа объектов пользователь мог:

- включать и выключать отображаемые поля;
- задавать порядковый номер столбца явным числовым полем;
- менять порядок колонок drag-and-drop в списке полей;
- менять ширину столбцов и сохранять её как пользовательскую настройку;
- независимо хранить layout для `pipe` и `tank`;
- получать стабильное поведение после перезагрузки страницы, смены проекта,
  входа в аккаунт и обновления версии приложения.

Главная цель: дать пользователю управляемую плотную таблицу, где нужные поля
стоят рядом и занимают разумную ширину, без изменения расчётных данных и без
влияния на результаты.

## Этапы Выполнения

Prompt intentionally делится на этапы, чтобы не смешать layout таблицы,
metadata полей, импорт и будущую админку в один большой рискованный релиз.

Этап 1 - обязательный для этой задачи:

- ввести явную `fieldRegistry/default JSON` как источник списка полей,
  дефолтных заголовков и дефолтных ширин;
- перевести table layout preference на `visibleOrder` и `widthPct`;
- убрать `visible/order` из канонической схемы пользовательских настроек;
- сделать `type` доступным, но скрытым по умолчанию;
- реализовать миграцию старых настроек.

Этап 2 - обязательный для этой задачи:

- обновить modal `Настройки таблицы`: видимость, порядок через `№`, drag-and-drop,
  ширина, draft/apply/cancel;
- подключить layout к реальной таблице;
- сохранить layout отдельно для `pipe` и `tank`;
- покрыть сценарии unit/component/Playwright тестами.

Не входит в этот prompt и не должно протекать в остальные изменения:

- admin UI и admin overrides названий полей;
- `importAliases`, `legacyExternalCodes` и importer matching;
- `externalCode` или другие внешние коды интеграций;
- отдельные настройки экспортируемых колонок.

Если такие поля уже существуют в старом коде, текущая задача не должна их
расширять, мигрировать, сохранять или использовать в новых payload. Максимум -
не дать им попасть в table layout preference при нормализации legacy-настроек.

## Не Менять

Эта задача не должна менять доменную модель объектов.

Запрещено:

- менять `ProjectObject.params`;
- менять `ProjectObject.sort_order`;
- использовать порядок колонок как порядок объектов;
- влиять на расчёт теплопотерь;
- влиять на электротехнический расчёт;
- влиять на фильтры, поиск и сортировку строк, кроме корректной работы колонок
  по их стабильным `key`;
- смешивать экранные настройки таблицы с настройками экспорта;
- смешивать table layout с editable metadata полей;
- добавлять или менять admin/editor metadata слой;
- добавлять или менять `importAliases`, `legacyExternalCodes`, importer matching,
  `externalCode` или любые внешние integration codes;
- записывать layout колонок в экспортные файлы как скрытую настройку проекта;
- считать дефолтный JSON пользовательской настройкой и сохранять его в
  `localStorage`.

Порядок и ширина колонок - это `UI preference`, а не расчётное состояние.

## Источники И Хранение

Использовать ровно тот же принцип хранения и синхронизации, что у остальных
UI-конфигов HeatCalc. Не придумывать отдельный источник истины, отдельную
очередь синхронизации или специальное поведение только для layout колонок.

Для registered-пользователя БД является source of truth, а `localStorage` -
только кеш подтвержденной backend-записи. Это должно работать так же, как в
остальных пользовательских конфигах: если backend вернул настройку, UI берет ее;
если backend сообщает, что записи нет, UI использует дефолтный JSON и очищает
устаревший кеш; если пользователь сохранил настройку, кеш обновляется только
после успешного ответа backend.

Layout колонок должен расширять существующую настройку экранной таблицы, а не
создавать параллельную несовместимую preference-модель. Если в проекте уже есть
общий helper для чтения, валидации, миграции, сохранения и cache invalidation
UI preferences, использовать его.

Правила по ролям:

- новый гость: дефолтный JSON layout;
- гость с пользовательскими изменениями: `localStorage`;
- новый зарегистрированный пользователь без записи в БД: дефолтный JSON layout;
- зарегистрированный пользователь с записью в БД: БД как источник истины,
  `localStorage` только как кеш подтвержденной записи.

Для зарегистрированного пользователя:

- если записи в БД нет, очистить cache-key в `localStorage` и использовать
  дефолтный JSON;
- если записи в БД нет, `localStorage` не может восстановить пользовательскую
  настройку как source of truth, даже если там лежит валидный старый кеш;
- если запись в БД есть, заменить localStorage-кеш ответом БД;
- при сохранении сначала считать localStorage-кеш устаревшим, затем писать в
  БД, и только после успешного ответа обновлять кеш;
- если backend недоступен, можно временно показать валидный кеш, но после
  восстановления связи БД снова становится источником истины.

Дефолтный JSON не записывать в пользовательский localStorage-key. Иначе старый
дефолт из браузера начнет блокировать будущие продуктовые дефолты.

Чтение, нормализация и мягкая миграция должны быть side-effect free, пока
пользователь явно не сохранил настройки или не завершил resize колонки. Нельзя
при простом открытии страницы перезаписывать гостевой `localStorage` дефолтным
JSON или автоматически сохранять нормализованный layout как пользовательскую
настройку. Исключение - очистка явно устаревшего cache-key зарегистрированного
пользователя, когда backend подтвердил отсутствие записи.

## Версия Настроек

Повысить версию настроек колонок, потому что прежняя структура `visibleKeys`
уже недостаточна. Если в проекте уже внедрена версия `2`, изменение порядка
только для видимых колонок считать следующей миграцией схемы и повысить
версию layout до `3`.

Рекомендуемая структура table layout preference:

```json
{
  "version": 3,
  "types": {
    "pipe": {
      "visibleOrder": [
        "index",
        "name"
      ],
      "columns": {
        "index": {
          "widthPct": 4
        },
        "type": {
          "widthPct": 5
        },
        "name": {
          "widthPct": 24
        }
      }
    },
    "tank": {
      "visibleOrder": [
        "index",
        "name"
      ],
      "columns": {
        "index": {
          "widthPct": 4
        },
        "type": {
          "widthPct": 5
        },
        "name": {
          "widthPct": 24
        }
      }
    }
  },
  "updatedAt": "2026-05-09T00:00:00.000Z"
}
```

Правила:

- `key` колонки - единственная обязательная immutable identity поля, а не
  заголовок таблицы;
- `visibleOrder` - канонический список видимых ключей в порядке отображения;
- колонка считается видимой только если ее `key` есть в `visibleOrder`, кроме
  обязательных колонок, которые нормализатор принудительно добавляет в список;
- `columns[key].widthPct` хранит каноническую ширину в процентах или весе, а не
  пиксельную ширину конкретного экрана;
- `columns[key]` в table layout не хранит `labels`, `unit`, `helpText` или любые
  другие display/integration metadata;
- названия, подсказки и единицы живут в `fieldRegistry/default JSON`, а не в
  пользовательском layout;
- `visible` и `order` не писать в `columns` в новой схеме, эти поля допустимы
  только как legacy-вход для миграции старых настроек;
- технические поля вроде `updatedAt` не использовать для сравнения бизнес-логики;
- selection checkbox Ant Design не хранить как обычную колонку, потому что это
  часть `rowSelection`.

## Идентичность Поля

`key` - единственная обязательная identity поля. Он не переименовывается
пользовательскими настройками и используется для связи registry, table layout,
фильтров, сортировок, форм, backend mapping и расчетной логики.

Правила:

- `key` обязателен для каждого поля и уникален внутри object type;
- frontend не должен использовать `labels.short/full` как идентификатор поля;
  labels нужны только для отображения;
- `visibleOrder`, фильтры, сортировки, resize, copy и table settings ссылаются на
  поле по `key`;
- в рамках этой задачи не вводить второй идентификатор поля вроде `serviceName`,
  `externalCode` или import alias. Если когда-нибудь понадобится внешний код, это
  должна быть отдельная задача, не часть table layout.

## Field Registry И Названия Полей

Все человеко-читаемые названия полей по умолчанию должны переехать из
TypeScript/JSX в дефолтный JSON/registry. Registry нужен таблице, modal
`Настройки таблицы`, формам и тестам как единый каталог полей. Пользовательский
table layout берет из registry список доступных `key`, дефолтный порядок,
заголовки и дефолтные ширины, но не сохраняет эти display metadata внутри
пользовательской preference.

Ключевой принцип: registry/default JSON описывает поле; table layout описывает
только пользовательскую компоновку таблицы.

Дефолтный JSON должен быть источником default display metadata, default layout
metadata и capabilities, которые нужны именно экранной таблице:

```json
{
  "key": "pipe_outer_diameter",
  "labels": {
    "short": "Ø, мм",
    "full": "Наружный диаметр трубопровода"
  },
  "unit": "mm",
  "helpText": "Наружный диаметр трубы в миллиметрах.",
  "valueType": "number",
  "defaultVisible": true,
  "sortable": true,
  "filterable": true,
  "resizable": true,
  "defaultWidthPct": 7.6,
  "minWidthPx": 72
}
```

В этом prompt registry не должен получать import/admin/integration metadata. Он
нужен для таблицы: список полей, labels, display unit, help text, defaultVisible,
sortable/filterable/resizable и дефолтные размеры.

Правила merge:

- пользовательские настройки таблицы (`visibleOrder`, `widthPct`) не должны
  хранить копию `labels` и не должны блокировать обновление названий из
  дефолтного JSON;
- `unit` считать display metadata из registry. Не разрешать менять `unit` через
  `localStorage` или table layout в этой задаче, чтобы не создать ложное
  впечатление конвертации физических величин;
- localStorage/БД пользовательских table preferences не являются источником
  названий полей;
- если в старых пользовательских настройках найдены metadata-поля, они
  игнорируются и не переносятся в новую layout-схему.

## Metadata Вне Scope

В этом prompt не проектировать хранение пользовательских переименований,
админские названия, import aliases или внешние коды. Для текущей задачи
достаточно дефолтного JSON/registry и пользовательского table layout. Любые
будущие metadata-задачи должны жить в отдельном prompt и не менять контракт
`HeatCalcTableColumnSettings`.

## Правило Порядка Видимых Колонок

Порядок должен храниться не как `order` внутри каждой колонки, а как отдельный
массив видимых ключей `visibleOrder`. Это проще валидировать, проще
синхронизировать и исключает неоднозначность: скрытая колонка физически не может
занимать место в порядке таблицы.

Каноническое правило:

- `visibleOrder` содержит только известные keys текущего типа объекта;
- порядок в таблице равен порядку keys внутри `visibleOrder`;
- скрытые поля отсутствуют в `visibleOrder`;
- `columns[key]` не содержит `order` и `visible`;
- вычисляемый номер в UI равен индексу `key` в `visibleOrder` + 1;
- обязательные колонки считаются видимыми всегда и поэтому всегда участвуют в
  `visibleOrder`;
- скрытые поля могут хранить `widthPct`, потому что ширина должна
  восстанавливаться при повторном включении, но не могут хранить позицию.

Поведение при переключении видимости:

- если видимую колонку выключили, удалить ее `key` из `visibleOrder`;
- если скрытую колонку включили, добавить ее `key` в конец `visibleOrder`;
- если пользователь нажал `Все поля`, ранее скрытые поля добавляются в конец
  после уже видимых колонок, в порядке registry/catalog;
- если пользователь нажал `Сбросить текущий тип`, порядок берется из дефолтного
  JSON для видимых по умолчанию колонок, скрытые поля остаются вне
  `visibleOrder`.

Поведение в modal:

- числовое поле `№` активно только для видимых колонок;
- drag-and-drop работает только между видимыми колонками;
- скрытые поля остаются доступными для включения, но показываются без номера
  порядка и без drag handle;
- список modal должен визуально разделять видимые и скрытые поля: сначала
  видимые по `visibleOrder`, затем скрытые в порядке registry/catalog;
- включение скрытого поля не должно пытаться восстановить его старую позицию:
  новое правило всегда добавляет поле в конец.

Миграция старых настроек:

- если найден legacy layout с `columns[key].visible/order`, построить
  `visibleOrder` из колонок с `visible: true`;
- обязательные колонки добавить в `visibleOrder`, даже если legacy-настройка
  пыталась их скрыть;
- если есть дубли legacy `order`, отсортировать по `order`, затем по
  registry/catalog и записать только итоговый `visibleOrder`;
- если у legacy-видимой колонки нет `order`, добавить ее в конец видимой части;
- после сохранения писать уже нормализованную структуру без `visible` и
  `order` внутри `columns`.

## Миграция Со Старой Версии

Если найдена настройка версии `1` с `visibleKeys`, выполнить мягкую миграцию:

```text
for each objectType:
  visibleOrder = known keys from visibleKeys[objectType] in saved order
  append required keys if missing
  for each known column in registry default order:
    columns[column.key].widthPct = defaultWidthPct from field registry
```

Правила миграции:

- поврежденные настройки молча отбрасывать и использовать дефолтный JSON;
- неизвестные старые keys игнорировать;
- новые keys, которых нет в старой настройке, добавлять из дефолтного registry;
- человеко-читаемые названия, единицы и подсказки брать только из дефолтного
  JSON/registry, а не из user preference, и не записывать их в table layout;
- обязательные колонки принудительно добавлять в `visibleOrder`;
- скрытые колонки оставлять вне `visibleOrder`;
- после успешного сохранения новой настройки писать уже актуальную версию
  layout.

## Дефолтный Layout

Дефолт должен соответствовать текущему компактному виду таблицы.

Для труб порядок по умолчанию:

1. `index` - `№`
2. `name` - `Наименование`
3. `pipe_outer_diameter` - `Ø, мм`
4. `pipe_dn` - `DN`
5. `pipe_length` - `L, м`
6. `insulation_layer_count` - `Слоёв ИЗ`
7. `insulation_thickness` - `δ ИЗ, мм`
8. `insulation_material` - `Материал ИЗ`
9. `process_temperature` - `T подд.`
10. `ambient_temperature` - `T окр.`
11. `valve_count` - `Зад.`
12. `flange_count` - `Флн.`
13. `support_count` - `Опр.`

Для резервуаров порядок по умолчанию:

1. `index` - `№`
2. `name` - `Наименование`
3. `tank_shape` - `Форма`
4. `tank_dimensions` - `Габариты`
5. `placement` - `Размещение`
6. `insulation_layer_count` - `Слоёв ИЗ`
7. `insulation_thickness` - `δ ИЗ, мм`
8. `insulation_material` - `Материал ИЗ`
9. `process_temperature` - `T подд.`
10. `ambient_temperature` - `T окр.`
11. `q_additional` - `Q доп., Вт`

Колонка `type` - `Тип` остается доступной в списке полей для обоих типов
объектов, но не входит в дефолтный `visibleOrder`. Пользователь может включить
ее вручную; при включении она добавляется в конец видимых колонок по общему
правилу `visibleOrder`.

Дефолтные ширины подбирать не как равные доли, а по смысловой плотности:

- `name` шире остальных, потому что это главный идентификатор объекта;
- числовые короткие поля компактные;
- enum/label поля средние;
- `tank_dimensions` шире коротких чисел, но уже `name`;
- служебные `№` и `Тип` минимальные, но `Тип` по умолчанию скрыт;
- сумма видимых `widthPct` может быть 100, но система должна корректно работать
  и после скрытия части колонок.

## UI В Модальном Окне

Заголовок modal:

```text
Настройки таблицы
```

Структура modal:

```text
Настройки таблицы

[Трубы] [Резервуары]

┌ drag ┬ show ┬ № ┬ Поле ┬ Ширина ┬ Сброс ширины ┐
│  ⋮⋮  │  ☑   │ 1 │ Наименование │ 24 % │ ↺ │
│  ⋮⋮  │  ☑   │ 2 │ Ø, мм        │  7 % │ ↺ │
└──────┴──────┴───┴───────────────┴──────┴───┘

[Сбросить текущий тип] [Отмена] [Применить]
```

Требования:

- список должен быть плотным, без карточек внутри карточек;
- использовать `drag handle`, а не перетаскивание всей строки без явного
  признака;
- числовое поле `№` показывает и меняет порядковый номер столбца;
- изменение `№` и drag-and-drop меняют один и тот же draft `visibleOrder`;
- ширина задается в процентах через компактный number input;
- для ширины показывать единицу `%`;
- скрытые поля остаются в списке, но не имеют номера порядка;
- обязательные поля показывать disabled-checkbox с tooltip;
- не добавлять длинные инструкции в тело modal.

## Drag-And-Drop

Использовать существующую зависимость `@dnd-kit`, если она уже подключена в
frontend. Не писать собственный drag-and-drop на raw mouse events.

Правила DnD:

- перетаскивание работает внутри активного типа (`pipe` или `tank`);
- нельзя перетаскивать поле из труб в резервуары;
- после drop переставить ключи внутри `visibleOrder`;
- drag должен работать только для видимых полей;
- обязательные поля можно перемещать, но нельзя скрывать;
- во время drag строка не должна менять высоту modal;
- после drop фокус возвращается на перемещенную строку;
- keyboard-accessibility обязательна: пользователь должен иметь способ
  переместить поле без мыши, например через dnd-kit keyboard sensor или
  compact-кнопки `вверх/вниз` для сфокусированной строки.

## Числовой Порядок Колонок

Поле `№` нужно для точного управления порядком без drag-and-drop.

Правила:

- допустимые значения `1..N`, где `N` - количество видимых полей текущего типа;
- ввод дробного числа округлять или запрещать на уровне input;
- пустой ввод не применять, показывать inline validation;
- если пользователь вводит уже занятый номер, перемещать поле в эту позицию и
  сдвигать остальные поля;
- после любого изменения перестраивается `visibleOrder`;
- сортировка видимой части modal всегда идет по `visibleOrder`;
- у скрытых полей поле `№` disabled или отсутствует;
- при повторном включении скрытое поле получает последний номер среди видимых
  колонок, а не прежнюю позицию.

## Ширина Колонок

Ширина должна запоминаться отдельно для каждого типа объектов и каждого поля.

Канонический формат хранения - `widthPct`. В UI таблицы можно конвертировать
проценты в пиксели, если Ant Design или текущая реализация resize требует
числовую ширину. Пиксели конкретного viewport не должны становиться главным
форматом хранения.

Рекомендуемая модель:

```text
renderWidthPx = clamp(minWidthPx, tableViewportWidth * widthPct / 100, maxWidthPx?)
```

Правила:

- у каждой колонки в registry должны быть `defaultWidthPct`, `minWidthPx` и
  при необходимости `maxWidthPx`;
- для коротких числовых колонок min width меньше, для `name` больше;
- `name` не должна ужиматься до нечитаемого состояния;
- если сумма `widthPct` видимых колонок меньше 100, таблица может распределить
  свободное место между гибкими колонками, но сохраненные `widthPct` не должны
  самопроизвольно перезаписываться;
- если сумма больше 100, таблица использует горизонтальный scroll, а не ломает
  текст и не сжимает всё до нечитаемости;
- width resize в заголовке таблицы применяется визуально во время drag;
- сохранять новую ширину только на drag end, а не на каждом mousemove;
- после drag end нормализовать ширину в проценты относительно текущей ширины
  таблицы;
- autosave ширины должен использовать тот же persistence layer, что modal
  `Настройки таблицы`;
- если autosave зарегистрированного пользователя не прошел, показать
  ненавязчивую ошибку синхронизации и не записывать неподтвержденный кеш как
  источник истины.

## Поведение Modal Apply/Cancel

Изменения в modal работают через draft:

- `Отмена` закрывает modal и полностью отбрасывает draft;
- `Применить` сохраняет `visibleOrder` для каждого измененного типа и
  `widthPct` для всех известных полей;
- `Сбросить текущий тип` возвращает только активный тип к дефолтному layout;
- `Сбросить ширину` у строки возвращает только `widthPct` конкретного поля;
- переключение таба `Трубы` / `Резервуары` внутри modal не теряет draft;
- после успешного `Применить` таблица сразу перестраивает колонки.

Не применять изменения порядка и видимости мгновенно до `Применить`, иначе
`Отмена` станет нечестной. Исключение - resize заголовка таблицы вне modal,
который является прямым действием пользователя над таблицей и сохраняется на
drag end.

## Интеграция С Таблицей

Формирование колонок таблицы должно идти через единый registry:

```text
columnRegistry + userLayout + backendCapabilities -> renderedColumns
```

Правила:

- порядок rendered columns определяется `visibleOrder`;
- видимость определяется наличием `key` в `visibleOrder` плюс обязательные
  поля, которые добавляет нормализация;
- фильтры и сортировки привязаны к `column.key`, а не к индексу столбца;
- frontend-логика таблицы, фильтры, сортировки, отчеты, автоматизация и
  автотесты должны ссылаться на стабильный `key`, но никогда на редактируемые
  `labels.short/full`;
- normalized table settings всегда используют только `key` как identity поля;
- при переупорядочивании колонок активные фильтры и сортировки остаются на тех
  же полях;
- при скрытии колонки ее активный фильтр нужно снять или показать явное
  поведение в UI. Лучший вариант: при `Применить` скрытые поля удаляются из
  table filter state, потому что пользователь больше не видит, что фильтр
  активен;
- backend-query request не должен зависеть от визуального порядка колонок;
- экспорт XLSX/CSV не должен использовать этот экранный layout. Для экспорта
  нужен отдельный `HeatCalcExportColumnSettings`.

## Минимальные И Обязательные Колонки

Обязательные:

- `name` - нельзя скрыть;
- selection checkbox - не входит в список пользовательских колонок;
- технические action columns, если появятся, не смешивать с data columns.

Рекомендуемые ограничения:

- `name` можно перемещать, но нельзя скрывать;
- `index` дефолтно включен, `type` доступен для включения, но дефолтно скрыт;
- если пользователь отключил всё, что можно отключить, таблица всё равно
  показывает минимум `name`;
- если обязательная колонка отсутствует в поврежденной настройке, добавить ее
  из registry.

## Backend/API Для Registered

Если уже есть endpoint пользовательских UI preferences, расширить существующий
ключ настроек таблицы до актуальной версии layout.

Если endpoint еще не обобщен, рекомендуемый контракт:

```http
GET /api/v1/users/me/ui-preferences/heatcalc-table-columns
PUT /api/v1/users/me/ui-preferences/heatcalc-table-columns
```

Payload должен хранить только layout актуальной версии. Backend не должен
понимать математику колонок и не должен принимать display/integration metadata
как часть `heatcalc-table-columns`.

Backend должен валидировать:

- `version`;
- `types.pipe.visibleOrder`;
- `types.tank.visibleOrder`;
- `types.pipe.columns`;
- `types.tank.columns`;
- отсутствие неизвестных object types;
- отсутствие неизвестных keys в `visibleOrder`;
- отсутствие дублей в `visibleOrder`;
- отсутствие `labels`, `unit`, `helpText` и любых других metadata-полей в table
  layout payload;
- отсутствие `visible` и `order` в каноническом payload;
- разумные границы `widthPct`;
- максимальный размер payload;
- принадлежность preference текущему пользователю.

Registry/default JSON должен валидироваться отдельно от пользовательского table
layout. `heatcalc-table-columns` не является источником истины для названий,
unit, подсказок или любых integration metadata.

Backend не должен доверять списку ключей, присланному с frontend, как источнику
схемы. Допустимые `key` нужно проверять по server-known registry, exported shared
schema или capabilities-слою той же версии. Если backend в текущей архитектуре
пока не знает registry, это нужно явно зафиксировать как временное ограничение и
всё равно валидировать форму payload, object type, дубли, размер, отсутствие
metadata-полей и права пользователя.

Backend не должен писать layout в проект, объект или расчётные таблицы.

## Validation

Валидация на frontend:

- `visibleOrder` содержит только известные keys текущего object type;
- в `visibleOrder` нет дублей;
- скрытые колонки отсутствуют в `visibleOrder`;
- legacy `visible/order` внутри `columns` игнорируются при чтении и не пишутся
  обратно после сохранения;
- `widthPct` число в допустимом диапазоне, например `2..60`;
- `key` является единственной обязательной identity поля;
- frontend-идентификация полей не завязана на `labels.short/full`;
- `labels.short` и `labels.full` есть у каждого поля registry/default JSON и не
  строятся из hardcoded JSX/TSX-строк;
- `defaultWidthPct` и `minWidthPx` есть у каждого поля registry/default JSON;
- пользовательские table preferences не содержат `labels`, `unit`, `helpText` или
  другие metadata-поля;
- обязательные поля входят в `visibleOrder`;
- все известные поля текущего registry присутствуют после merge;
- неизвестные поля из сохраненной настройки игнорируются;
- после reorder нет дублей в `visibleOrder`.

Валидация на backend для registered:

- payload JSON-object, не строка;
- `version` поддерживается;
- object type только `pipe`/`tank`;
- `visibleOrder` массив известных keys без дублей;
- payload не содержит display/integration metadata (`labels`, `unit`, `helpText`
  или любые поля вне разрешенной layout-схемы);
- `widthPct` в допустимом диапазоне;
- payload не содержит подозрительно больших массивов/объектов;
- пользователь может читать и писать только свои preference.

## Тесты

Добавить или обновить тесты.

Frontend unit:

- дефолтный layout применяется для нового гостя;
- старая `visibleKeys` настройка мигрирует в актуальную layout-схему;
- `key` остается единственной обязательной identity поля;
- пользовательская настройка из БД/localStorage не может подменить `key` из
  registry;
- изменение `labels.short/full` в registry не ломает фильтры, сортировки,
  отчеты и автотесты, потому что они используют `key`;
- все `label/title/copyTitle/helpText/unit` для колонок берутся из дефолтного
  JSON/registry, а не из разбросанных hardcoded строк в компонентах;
- user preference с устаревшими metadata-полями нормализуется в layout-only
  структуру и не блокирует новые default labels;
- поврежденный localStorage fallback к дефолту;
- registered без записи в БД очищает localStorage cache и использует дефолт;
- registered с записью в БД применяет БД и обновляет кеш;
- чтение дефолтного layout новым гостем не создает пользовательскую запись в
  `localStorage`;
- мягкая миграция legacy-настройки не записывает новую схему в `localStorage` или
  БД до явного `Применить`, успешного resize-save или подтвержденного save flow;
- `№` перемещает видимую колонку внутри `visibleOrder`;
- drag-and-drop меняет тот же `visibleOrder`, что числовое поле;
- скрытая колонка отсутствует в `visibleOrder`, а при включении добавляется в
  конец;
- скрытие видимой колонки удаляет ее key из `visibleOrder`;
- `Отмена` отбрасывает draft;
- `Применить` сохраняет видимость, порядок и ширину;
- `Сбросить текущий тип` не трогает второй тип;
- скрытие колонки снимает фильтр по этой колонке;
- сортировка/фильтр остаются привязанными к key после reorder.

Frontend integration/component:

- пользователь открывает `Настройки таблицы`, меняет порядок, применяет, таблица
  перестраивается;
- пользователь включает скрытое поле, и оно появляется последней видимой
  колонкой;
- пользователь меняет ширину заголовка, перезагружает страницу, ширина
  восстанавливается;
- настройки труб не влияют на резервуары;
- обязательная колонка `name` не скрывается.

Backend tests, если используется БД для registered:

- `GET` возвращает настройку текущего пользователя;
- `PUT` сохраняет актуальную версию layout;
- другой пользователь не читает чужую настройку;
- invalid payload возвращает `422`;
- дефолтный JSON не создаёт запись в БД сам по себе.

Playwright smoke:

- изменить порядок колонок через modal;
- изменить ширину одной колонки;
- перезагрузить страницу;
- убедиться, что порядок и ширина восстановились;
- переключиться на другой тип и убедиться, что его layout независимый.

## Acceptance Criteria

Готово, если:

- в `Настройки таблицы` есть видимость, порядок, drag-and-drop и ширина;
- порядок можно менять через `№` и DnD только у видимых колонок;
- порядок и видимость хранятся в `visibleOrder`, а не в `order/visible` внутри
  каждой колонки;
- скрытые колонки отсутствуют в `visibleOrder`, а при повторном включении
  добавляются в конец видимой части;
- ширина колонок сохраняется и восстанавливается;
- `key` является единственной обязательной identity поля для frontend, layout,
  фильтров, сортировок, форм и расчетных связей;
- `key` не редактируется пользователем и не подменяется из localStorage/БД;
- все названия полей по умолчанию (`labels.short`, `labels.full`), подсказки,
  единицы и дефолтные ширины описаны в JSON/registry;
- table layout payload не содержит `labels`, `unit`, `helpText` или другие
  metadata-поля;
- layout хранится отдельно для труб и резервуаров;
- guest хранит пользовательские изменения в `localStorage`;
- registered использует БД как источник истины, а localStorage только как кеш;
- дефолтный JSON не записывается как пользовательская настройка;
- скрытие/перемещение колонок не ломает фильтры, сортировку, backend-query и
  расчёты;
- экспорт не зависит от экранного layout;
- тесты покрывают миграцию, хранение `visibleOrder`, включение скрытого поля в
  конец, reorder, resize и независимость типов.
