# Prompt: Thoughtful UI Improvement For HeatCalc Workspace

## Цель

Провести вдумчивое улучшение UI рабочих экранов HeatCalc, прежде всего страницы
`Расчёт тепловых потерь`, без изменения бизнес-логики, схемы БД и API-контрактов.

Это не задача "сделать красиво". Цель — сделать рабочий интерфейс плотнее,
понятнее и спокойнее для инженера, который многократно добавляет объекты,
сравнивает расчёты, переключает варианты СО, исправляет ошибки и экспортирует
результаты.

Частный пример желаемого направления: вместо текстовой кнопки `Добавить`
разместить компактную кнопку с иконкой `+`, а текст `Добавить` показывать в
tooltip при наведении и через `aria-label`. Но этот пример не должен быть
единственной правкой. Его нужно использовать как принцип: очевидные частые
команды могут быть иконками с подсказками, а важные или рискованные действия
должны оставаться текстовыми там, где текст снижает риск ошибки.

## Контекст

Интерфейс сейчас похож на инженерную рабочую таблицу, и это правильно. Его не
нужно превращать в лендинг, маркетинговую страницу или карточный dashboard.
Основной сценарий пользователя:

1. Выбрать тип объектов: `Трубопровод` или `Резервуары`.
2. Добавить или импортировать объекты.
3. Быстро проверить исходные данные в таблице.
4. Исправить конкретную строку через inline-form.
5. Перейти на результаты расчёта.
6. Запустить или уточнить электрорасчёт.
7. Экспортировать данные.

UI должен поддерживать этот поток без лишних визуальных препятствий.

## Главные Принципы

1. **Рабочая плотность важнее декоративности.**
   Таблицы, toolbars и формы должны быть компактными, но не тесными. Не добавлять
   большие декоративные блоки, лишние карточки, hero-секции или поясняющие
   тексты внутри приложения.

2. **Команды должны читаться по форме и контексту.**
   Частые и очевидные команды можно делать icon-only, если есть tooltip и
   `aria-label`. Неочевидные, опасные или редко используемые команды должны
   сохранять текст или icon+text.

3. **Каждый элемент toolbar должен иметь понятную роль.**
   Смешение фильтров, действий, статусов и экспорта в одной линии допустимо
   только при визуальном разделении: группы, отступы, divider, consistent size.

4. **Состояния важнее статичной картинки.**
   Для кнопок, фильтров, таблиц и форм должны быть продуманы состояния:
   default, hover, active, disabled, loading, selected, error, empty.

5. **Нельзя скрывать важную информацию только в tooltip.**
   Tooltip подходит для названия команды, расшифровки иконки или пояснения
   disabled-состояния. Критичные статусы расчёта, ошибки и выбранный тип объекта
   должны быть видимыми без hover.

6. **Не менять модель данных ради UI.**
   Все улучшения должны использовать существующие данные и контракты. Если
   хочется нового backend-поля только для красоты, вынести это в отдельную задачу.

7. **Визуальный дефект требует визуального доказательства.**
   Для layout/readability/clipping/overlap задач обязательны before screenshot,
   root cause в DOM/CSS, after screenshot и программная проверка. Если
   Playwright/Chrome не запускается, задача blocked, а не завершена успешно.

## Область Работы

Основной экран:

- `frontend/src/pages/HeatCalcPage.tsx`

Вероятные соседние файлы:

- `frontend/src/components/ImportExcelButton.tsx`
- `frontend/src/components/ExportObjectsButton.tsx`
- `frontend/src/components/wizard/ObjectWizard.tsx`
- CSS/стили, которые обслуживают `actionbar-srs`, таблицу и inline-form
- unit/integration tests по странице HeatCalc
- Playwright smoke/seed, если он проверяет визуальные сценарии

Не нужно в этой задаче менять backend, расчётные формулы, формат `params`,
импорт XLSX/CSV или структуру проекта.

## Actionbar: Целевая Компоновка

Первая строка действий должна быть разделена на логические группы:

1. **Контекст таблицы**
   - переключатель `Трубопровод` / `Резервуары`;
   - активный тип должен визуально читаться сразу.

2. **Создание и редактирование**
   - `+` / `PlusOutlined` для добавления активного типа;
   - `Создать на основании`, если кнопка остаётся текстовой, должна быть
     вторичной и визуально слабее `+`;
   - `Применить к одному`, `Применить ко всем`, `Удалить`, `Отменить` должны
     иметь понятную disabled-логику и подсказку, если disabled.

3. **Сохранение**
   - не фиксировать заранее, что `Сохранить изменения` обязательно должно быть
     текстовой кнопкой;
   - допустимы варианты `text`, `icon+text` и `icon-only`, если выбранный вариант
     лучше работает в текущей плотности toolbar;
   - если сохранение становится icon-only, обязательно нужны tooltip,
     `aria-label="Сохранить изменения"`, заметный focus state и понятные
     `loading`/`disabled`/success-состояния;
   - состояние несохранённых изменений должно быть видно пользователю через
     кнопку, статус или другой стабильный индикатор, а не только через hover.

4. **Импорт/экспорт**
   - `Импорт XLSX/CSV`, `.xlsx`, `.csv` сгруппировать отдельно;
   - если есть иконки загрузки/скачивания, использовать их стабильно;
   - не смешивать импорт с созданием вручную.

5. **Статусы**
   - счётчики `Труб: N`, `Рез.: N`, `Объектов: N`;
   - статус `Все рассчитаны` / `Не рассчитано`;
   - выбранные строки `Выбрано: N` показывать рядом с действиями над selection.

## Частный Пример: Кнопка Добавить

Текущая идея:

- вместо кнопки с текстом `Добавить` сделать компактную иконку `+`;
- при наведении показывать tooltip `Добавить`;
- для доступности добавить `aria-label="Добавить"`;
- логика остаётся прежней: добавить объект активного типа.

Рекомендуемая реализация:

```tsx
<Tooltip title="Добавить">
  <Button
    className="action-icon-button add"
    icon={<PlusOutlined />}
    aria-label="Добавить"
    onClick={() => openAddWizard()}
  />
</Tooltip>
```

Важные детали:

- кнопка должна иметь стабильный размер, например `32x32` или размер,
  соответствующий текущему `size="small"`;
- иконка должна быть центрирована;
- hover/focus state должны быть заметны;
- disabled state должен быть визуально понятен, если он появится;
- не использовать просто текстовый символ `+`, если уже подключён
  `PlusOutlined` из Ant Design;
- в тестах искать кнопку по role/name `Добавить`, чтобы `aria-label` был
  проверен автоматически.

## Правила Для Icon-Only Кнопок

Icon-only допустимы для команд:

- добавить;
- удалить, если рядом есть подтверждение;
- обновить;
- скачать;
- загрузить;
- копировать;
- перейти дальше/назад;
- раскрыть/свернуть;
- открыть настройки.

Icon-only не подходит или требует особой осторожности для команд:

- `Применить ко всем`;
- действия, которые массово меняют данные;
- действия, которые запускают расчёт для большого набора объектов;
- действия, смысл которых не очевиден по иконке.

Сохранение не запрещено делать icon-only. Его нужно оценивать отдельно:

- если рядом много текстовых кнопок и toolbar перегружен, icon-only сохранение
  может быть лучше;
- если сохранение является главным действием текущей формы, icon+text может быть
  понятнее;
- если выбран icon-only вариант, использовать устойчивую иконку сохранения,
  tooltip `Сохранить изменения`, accessible name и явную обратную связь после
  успешного сохранения.

Для каждой icon-only кнопки обязательно:

- `Tooltip title`;
- `aria-label`;
- keyboard focus;
- понятный disabled tooltip, если кнопка недоступна;
- тест, который находит кнопку по доступному имени.

## Таблица

Таблица должна оставаться главным рабочим инструментом.

Требования:

- не помещать таблицу внутрь дополнительной декоративной карточки;
- сохранить плотность строк;
- не увеличивать высоту header без причины;
- не добавлять многоцветные заливки без функционального смысла;
- ошибки расчёта подсвечивать стабильно и умеренно;
- статусные теги должны быть короткими и сканируемыми;
- длинные значения должны иметь ellipsis и tooltip только там, где это полезно;
- числовые колонки выравнивать вправо;
- текстовые колонки выравнивать влево;
- единицы измерения держать в заголовке колонки, не повторять в каждой ячейке,
  если это ухудшает плотность.

Для таблицы исходных данных:

- сохранить отдельные колонки труб и резервуаров, введённые переключателем типа;
- не возвращать массовые прочерки из-за неприменимых колонок;
- пустое состояние должно быть коротким и контекстным:
  - для труб: `Трубопроводы не добавлены`;
  - для резервуаров: `Резервуары не добавлены`.

Для таблицы результатов:

- статус электрорасчёта должен быть виден без hover;
- подробную ошибку можно оставлять в tooltip;
- строка с ошибкой должна отличаться, но не ломать читаемость всей таблицы;
- `q, Вт/м` и `q, Вт/м²` должны быть визуально различимы через заголовок.

## Inline-Form И Верхняя Панель Параметров

Inline-form должен ощущаться как рабочая панель редактирования выбранной строки,
а не как отдельная страница.

Требования:

- заголовок панели должен показывать режим:
  - выбран объект;
  - новая запись;
  - ничего не выбрано;
- поля должны быть сгруппированы по инженерному смыслу;
- не использовать длинные объясняющие тексты внутри формы;
- для редких или неочевидных полей использовать tooltip/help, но не перегружать;
- не менять порядок полей без причины, если пользователь уже привык к текущему
  сценарию;
- если форма закрывается при переключении типа объекта, это должно происходить
  без визуального мусора и остаточного selection.

## Цвет И Визуальная Иерархия

Интерфейс должен оставаться спокойным инженерным инструментом.

Рекомендации:

- primary цвет использовать только для ключевого действия в текущем контексте;
- зелёный использовать для успешного статуса и сохранения;
- красный использовать только для ошибок и destructive-действий;
- серые/синие оттенки использовать для навигации, табов и пассивных групп;
- не строить палитру на одном насыщенном цвете;
- не добавлять декоративные градиенты, orbs, bokeh, большие тени;
- radius элементов держать умеренным и согласованным с текущим Ant Design style.

## Типографика И Размеры

Типографика должна помогать быстро сканировать инженерные данные. Нельзя
улучшать внешний вид ценой читаемости чисел, единиц измерения и длинных русских
названий объектов.

### Базовые Правила

- не масштабировать font-size от ширины viewport;
- не использовать отрицательный letter-spacing;
- не подключать декоративные, display или случайные web-fonts ради визуального
  эффекта;
- использовать системный стек Ant Design или уже принятый в проекте font-family;
- не делать крупные hero-заголовки внутри рабочих панелей;
- не использовать глобальный uppercase для кнопок, табов и заголовков таблиц;
- не смешивать больше двух семейств шрифтов в рабочем интерфейсе;
- не использовать monospace для обычных числовых данных, если это не ID, код,
  формула или технический лог;
- не делать текст светло-серым там, где пользователь должен читать значение;
- disabled text должен быть слабее активного, но всё ещё различимым.

### Размеры

Рекомендуемые диапазоны:

- основной интерфейс: `13px` или `14px`;
- таблицы и плотные toolbar: `12px` или `13px`;
- служебные подписи, captions, compact hints: `11px` или `12px`;
- заголовки рабочих панелей: `14px` или `16px`;
- крупнее `18px` использовать только для настоящих page-level заголовков, если
  они уже есть в layout.

Правила:

- внутри одного toolbar не смешивать несколько размеров без причины;
- текст в таблице, header и фильтрах должен выглядеть как одна система;
- line-height должен оставлять строку читаемой, но не раздувать таблицу;
- высота строки таблицы должна оставаться стабильной при hover, error state и
  inline controls.

### Вес И Акценты

- `400` использовать для обычных значений;
- `500` использовать для labels, активных табов, важных коротких статусов;
- `600` использовать дозированно для заголовков групп и ключевых счётчиков;
- не использовать `700+` в плотных таблицах и toolbar без сильной причины;
- не заменять цветовой статус жирным шрифтом, если статус уже обозначен tag/icon;
- активный segmented item должен читаться не только цветом, но и весом/контрастом
  в рамках возможностей Ant Design.

### Числа И Единицы

- числовые колонки выравнивать вправо;
- для плотных числовых колонок использовать `font-variant-numeric: tabular-nums`,
  если это не ломает текущий шрифт;
- единицы измерения держать в заголовках колонок: `q, Вт/м`, `Q, Вт`, `L, м`;
- не повторять единицы в каждой ячейке, кроме случаев, где без этого значение
  неоднозначно;
- десятичные знаки форматировать стабильно в рамках одной колонки;
- не смешивать `кВт` и `Вт` в одной колонке без понятного правила отображения;
- длинные числа не должны менять ширину кнопок, tags или toolbar-счётчиков.

### Русский Текст И Сокращения

- сокращения должны быть инженерно узнаваемыми: `Труб`, `Рез.`, `Зад.`, `Флн.`,
  `Опр.`;
- не вводить новые сокращения, если они не очевидны целевому пользователю;
- если сокращение может быть неясным, добавить tooltip;
- не использовать слишком длинные labels в toolbar, если действие можно
  корректно выразить иконкой с подсказкой;
- названия объектов в таблице должны иметь ellipsis, но полное значение должно
  быть доступно через tooltip или native title там, где это уже принято.

### Кнопки И Контролы

- кнопки toolbar должны иметь одинаковую высоту;
- icon-only кнопки должны иметь одинаковую ширину;
- текст внутри кнопок не должен переноситься или обрезаться;
- если текст слишком длинный, лучше заменить на иконку с tooltip или сократить
  label осознанно.

## Responsive И Узкие Экраны

Даже если приложение ориентировано на desktop, layout не должен ломаться.

Нужно проверить:

- 1280px desktop;
- 1440px desktop;
- широкий desktop;
- узкий viewport, если Playwright/тесты проекта это поддерживают.

На узком экране:

- actionbar может переноситься по группам;
- группы не должны накладываться друг на друга;
- таблица должна использовать horizontal scroll;
- счётчики не должны выталкивать ключевые действия за пределы экрана;
- icon-only кнопки особенно полезны для экономии ширины, но tooltip/aria-label
  остаются обязательными.

## Accessibility

Минимальные требования:

- все интерактивные элементы доступны через keyboard;
- icon-only кнопки имеют `aria-label`;
- segmented control имеет понятные accessible names;
- tooltip не является единственным носителем критичной информации;
- disabled controls либо имеют видимую причину рядом, либо tooltip с причиной;
- тесты используют role/name там, где это возможно.

## Технические Ограничения

Не делать:

- не менять backend API;
- не менять схему БД;
- не менять расчётные формулы;
- не переписывать Ant Design на другую UI-библиотеку;
- не добавлять новый глобальный design system, если достаточно локальных
  классов и существующих компонентов;
- не делать массовый рефакторинг всех страниц без необходимости;
- не менять seed-данные ради визуального удобства;
- не удалять существующие тесты вместо адаптации.

## Ожидаемые Изменения В Коде

Минимальный первый проход:

1. Привести actionbar `HeatCalcPage` к более плотной структуре групп.
2. Заменить `Добавить` на icon-only `PlusOutlined` с `Tooltip` и `aria-label`.
3. Проверить, какие соседние кнопки стоит оставить текстовыми, а какие можно
   сделать icon-only.
4. Убедиться, что disabled-кнопки имеют понятное объяснение.
5. Подправить CSS так, чтобы toolbar не прыгал по высоте.
6. Обновить тесты, которые ищут кнопку `Добавить`.
7. Проверить Playwright seed/screenshot.

Возможный второй проход:

1. Унифицировать размеры toolbar-кнопок.
2. Упорядочить группы импорта/экспорта.
3. Сделать статусы компактнее и стабильнее по ширине.
4. Проверить таблицу результатов на визуальную перегруженность.
5. Убрать лишние inline style, если они уже мешают поддержке.

## Тесты

Обязательные frontend-тесты:

1. Кнопка добавления доступна по role/name `Добавить`.
2. Tooltip `Добавить` появляется при hover или хотя бы компонент имеет
   ожидаемый accessible name.
3. Нажатие на `+` открывает форму активного типа объекта.
4. Переключатель `Трубопровод` / `Резервуары` продолжает фильтровать таблицу.
5. Disabled-состояния ключевых кнопок не ломают layout и не вызывают ошибок.
6. Если сохранение сделано icon-only, оно доступно по role/name
   `Сохранить изменения` и показывает loading/disabled/success-состояние.
7. Таблица исходных данных и результатов продолжает рендериться без изменения
   бизнес-данных.

Рекомендуемые Playwright-проверки:

1. Открыть seed-проект в гостевом режиме.
2. Проверить, что actionbar не перекрывается на viewport `1440x900`.

6. Сделать screenshot после seed для визуального контроля.

## Acceptance Criteria

Задача считается выполненной, если:

1. Кнопка добавления стала компактной icon-only кнопкой с `PlusOutlined`.
2. Tooltip и accessible name для добавления равны `Добавить`.
3. Нажатие на кнопку добавления сохраняет текущую логику активного типа.
4. Toolbar стал визуально плотнее и логичнее сгруппирован.
5. Решение по `Сохранить изменения` выбрано осознанно: text, icon+text или
   icon-only допустимы, если действие доступно, заметно и даёт обратную связь.
6. Disabled-состояния не выглядят как сломанные элементы.
7. Таблица не потеряла плотность и не получила декоративные лишние контейнеры.
8. Шрифты, веса, line-height и числовое форматирование соответствуют правилам
   типографики из prompt.
9. Unit/integration tests проходят.
10. Playwright seed/screenshot подтверждает, что рабочий сценарий не сломан.
11. Нет изменений backend, БД и расчётных формул.

## Критерии Хорошего Решения

Хорошее решение не бросается в глаза как редизайн. Пользователь просто быстрее
понимает, где добавить объект, где сохранить изменения, где импортировать данные
и что сейчас рассчитано.

После улучшения экран должен ощущаться:

- плотным;
- предсказуемым;
- инженерным;
- спокойным;
- сканируемым;
- устойчивым к длинным названиям, пустым состояниям и ошибкам расчёта.
