# Prompt: Object Type Switch For HeatCalc Tables

## Цель

Изменить UX страницы расчёта теплопотерь так, чтобы пользователь явно работал
либо с трубопроводами, либо с резервуарами. Не менять принцип хранения данных в
БД: объекты остаются в одной коллекции проекта и различаются существующим полем
`object_type`.

Нужно убрать ситуацию, когда в одной таблице одновременно показаны трубы и
резервуары, а часть колонок заполнена прочерками из-за неприменимости к другому
типу объекта.

## Главные требования

1. Добавить на странице расчёта теплопотерь две кнопки-переключателя:
   - `Трубопровод`
   - `Резервуары`

2. Активная кнопка определяет текущий тип объектов:
   - `pipe` для `Трубопровод`
   - `tank` для `Резервуары`

3. Таблица должна показывать только объекты активного типа.

4. Кнопка `+ Добавить` больше не должна открывать dropdown с выбором типа.
   Она должна сразу открывать форму создания объекта активного типа.

5. При переключении типа:
   - таблица обновляется на отфильтрованные объекты;
   - выбранная строка сбрасывается, если она относится к другому типу;
   - открытая форма создания/редактирования не должна показывать объект другого типа;
   - счётчики и выбранные строки должны относиться только к текущему типу там,
     где это визуально связано с таблицей.

6. Не менять backend-модели, миграции, API-контракты и JSON-структуру хранения
   объектов. Существующий `ProjectObject.object_type` остаётся источником правды.

## UX Поведение

### Переключатель типа

Разместить переключатель рядом с actionbar таблицы, до кнопки `+ Добавить` или
в начале строки действий. Визуально это должен быть понятный segmented control
или две кнопки с active-состоянием.

Рекомендуемый вариант:

- `Segmented` из Ant Design с вариантами:
  - `Трубопровод`
  - `Резервуары`

Состояние по умолчанию: `pipe`.

### Кнопка Добавить

Текущее поведение:

- пользователь нажимает `+ Добавить`;
- открывается dropdown;
- пользователь выбирает `Трубопровод` или `Резервуар`.

Новое поведение:

- пользователь выбирает тип верхним переключателем;
- нажимает `+ Добавить`;
- форма сразу открывается для активного типа.

Текст кнопки можно оставить `Добавить`, но логика должна быть:

```ts
openAddWizard(activeObjectType)
```

Dropdown убрать.

### Таблица исходных данных

Использовать отфильтрованный список:

```ts
const visibleObjects = objects.filter((obj) => obj.object_type === activeObjectType)
```

В таблицу передавать `visibleObjects`, а не полный `objects`.

Для трубопроводов оставить трубные колонки:

- `№`
- `Тип`
- `Наименование`
- `Ø, мм`
- `DN`
- `L, м`
- `Слоёв ИЗ`
- `δ ИЗ, мм`
- `Материал ИЗ`
- `T подд.`
- `T окр.`
- `Зад.`
- `Флн.`
- `Опр.`

Для резервуаров сделать отдельный набор колонок без трубных прочерков:

- `№`
- `Тип`
- `Наименование`
- `Форма`
- `Габариты`
- `Размещение`
- `Слоёв ИЗ`
- `δ ИЗ, мм`
- `Материал ИЗ`
- `T подд.`
- `T окр.`
- `Q доп., Вт`

Формат `Габариты`:

- цилиндр: `Ø{diameter_mm} × H{height_mm} мм`
- прямоугольный: `{length_mm} × {width_mm} × {height_mm} мм`
- сфера: `Ø{diameter_mm} мм`

Если параметр отсутствует, показывать `—` только внутри этой релевантной
колонки, а не из-за трубной структуры таблицы.

### Таблица результатов расчёта

Для трубопроводов оставить текущую семантику:

- `q, Вт/м`
- `Q, Вт`
- электрические колонки: марка кабеля, шаг, нитки, длина кабеля, мощность, ток,
  статус.

Для резервуаров заменить удельную колонку на:

- `q, Вт/м²`
- `Q, Вт`
- электрические колонки оставить, потому что электрорасчёты уже привязаны к
  объекту и варианту.

Для сферических резервуаров в СО1/СО2 ошибка электрорасчёта допустима при
текущем backend-контракте: геометрия укладки саморегулирующегося кабеля
поддерживает только `cylindrical` и `rectangular`. UI должен показывать ошибку
так же, как сейчас, но только в таблице резервуаров.

### Счётчики

Глобальный бейдж `Объектов: N` должен быть понятным. Возможны два варианта:

1. Показывать количество объектов активного типа:
   - при `Трубопровод`: `Объектов: 6`
   - при `Резервуары`: `Объектов: 8`

2. Показывать оба значения рядом:
   - `Труб: 6 · Резервуаров: 8`

Предпочтительно использовать вариант 2, если помещается без ухудшения layout.

Статус `Все рассчитаны` должен считаться по видимым объектам активного типа,
потому что пользователь смотрит на конкретную таблицу.

### Selection И Редактирование

При переключении `activeObjectType`:

- очистить `selectedRowKeys`;
- если `wizardState.editingObject?.object_type !== activeObjectType`, закрыть
  wizard или открыть пустое состояние;
- не оставлять подсвеченной строку из другого типа;
- `rowSelection` должен работать только по видимым строкам.

При клике по строке открывать редактирование объекта как сейчас, но только для
видимого типа.

### Электрорасчёт

Важно не поломать текущий batch-расчёт:

- кнопка `Выполнить электрорасчёт СО...` может продолжать считать все валидные
  объекты проекта, если backend endpoint остаётся проектным.
- Если в UI текст рядом с таблицей говорит `рассчитано X/Y`, для таблицы лучше
  считать `Y` по видимым объектам, а `X` по видимым объектам с расчётом.

Если нужно ограничить batch-электрорасчёт только активным типом, это уже новое
API-требование и его не делать в этой задаче, потому что пользователь явно
попросил не менять принцип хранения в БД.

## Ожидаемые Изменения В Коде

Основной файл:

- `frontend/src/pages/HeatCalcPage.tsx`

Вероятные изменения:

- добавить state:

```ts
const [activeObjectType, setActiveObjectType] = useState<WizardObjectType>('pipe');
```

- добавить derived arrays:

```ts
const visibleObjects = useMemo(
  () => objects.filter((obj) => obj.object_type === activeObjectType),
  [objects, activeObjectType],
);
```

- использовать `visibleObjects` в:
  - `Table.dataSource`;
  - расчёте `validCount`, `totalCount`, `selected`;
  - copy-to-clipboard;
  - status badges/legend для текущей таблицы;
  - `sort_order` при создании объекта, если порядок должен быть локальным для
    типа, либо оставить `objects.length`, если порядок общий по проекту.

Рекомендуется оставить `sort_order: objects.length`, чтобы не менять общий
порядок хранения проекта.

- заменить `Dropdown` вокруг кнопки `Добавить` на обычный `Button`.
- построить разные `sourceColumns` и `resultColumns` для `pipe` и `tank`.

Дополнительные файлы тестов:

- `frontend/src/__tests__/unit/pages/HeatCalcPage.test.tsx`
- `frontend/src/__tests__/integration/pages/ElecCalcPage.test.tsx`, только если
  там есть зависимость от общего поведения таблицы или счётчиков.

## Тесты

Добавить/обновить тесты на frontend:

1. По умолчанию активен тип `Трубопровод`.
2. Таблица показывает только `pipe`-объекты.
3. При переключении на `Резервуары` таблица показывает только `tank`-объекты.
4. Кнопка `Добавить` без dropdown открывает форму:
   - при активном `Трубопровод` — форму трубы;
   - при активном `Резервуары` — форму резервуара.
5. При переключении типа очищается selection.
6. Для таблицы резервуаров отображается колонка `Габариты`, и там нет трубных
   `DN`, `L, м`, `Зад.`, `Флн.`, `Опр.`.
7. Для таблицы трубопроводов остаются `DN`, `L, м`, `Зад.`, `Флн.`, `Опр.`.
8. Результаты расчёта:
   - для труб показывают `q, Вт/м`;
   - для резервуаров показывают `q, Вт/м²`.

Если есть Playwright smoke:

- обновить seed/use-case так, чтобы после заполнения проекта переключатель
  проверял `6` труб и `8` резервуаров.

## Acceptance Criteria

Задача считается выполненной, если:

1. В БД и backend API нет миграций и изменений схем хранения.
2. На странице расчёта есть переключатель `Трубопровод` / `Резервуары`.
3. `+ Добавить` сразу открывает форму выбранного типа.
4. Таблица не смешивает трубы и резервуары.
5. У резервуаров больше нет массовых прочерков в трубных колонках.
6. Прямоугольные резервуары показывают свои размеры через колонку `Габариты`.
7. Тепловые и электрические расчёты сохраняют текущую работоспособность.
8. Unit/integration tests проходят.
9. Playwright seed-проект визуально показывает две осмысленные таблицы:
   - 6 труб;
   - 8 резервуаров.

## Не Делать В Этой Задаче

- Не менять таблицы БД.
- Не добавлять новые backend endpoint только ради фильтрации.
- Не делить проект на две коллекции объектов.
- Не менять формат `params` в существующих объектах.
- Не исправлять поддержку саморегулирующегося кабеля на сферических резервуарах:
  это отдельная backend/formula задача.
- Не менять seed-данные так, чтобы скрыть текущие ограничения формул.
