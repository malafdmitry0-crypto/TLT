# HeatCalc Table Findability Prompt

## Контекст

На странице `HeatCalcPage` таблица исходных данных является основным рабочим
местом для труб и резервуаров. В таблице уже есть:

- переключение типа объектов `Труба` / `Резервуар`;
- настройка видимых колонок экранной таблицы;
- отдельные формы редактирования параметров объекта;
- расчётные статусы и переходы к следующим разделам.

При росте количества объектов пользователю нужно быстро находить нужные строки:
по имени, типу, диаметру, длине, материалу, температуре, количеству элементов,
геометрии резервуара и другим отображаемым полям. Для этого нужны поиск,
фильтры и сортировка по каждому полю таблицы.

## Цель

Добавить в таблицу HeatCalc инструменты поиска, фильтрации и сортировки по
колонкам, чтобы пользователю было удобно находить объекты в большой таблице.

Главное правило: фильтры, поиск и сортировка влияют только на отображение
таблицы. Они не должны влиять на расчёты, сохранённые объекты, результаты,
экспорт, порядок объектов в БД или статус готовности проекта.

## Важное Ограничение

Это не расчётная функция и не изменение модели данных.

Запрещено:

- менять `ProjectObject.params`;
- менять `sort_order` объектов;
- удалять или пересчитывать объекты, скрытые фильтром;
- использовать отфильтрованный список как вход в расчёт теплопотерь;
- использовать отфильтрованный список как вход в электротехнический расчёт;
- менять состав экспортируемых XLSX/CSV/PDF/DOCX документов из-за фильтра
  экранной таблицы;
- записывать фильтры в расчётные результаты, проектные параметры или объектные
  параметры;
- считать объект "нерассчитанным" только потому, что он скрыт фильтром.

Фильтры и сортировка - это `view state`, а не `domain state`.

## Термины

- `allObjects` - полный список объектов проекта из backend/store.
- `typeObjects` - объекты текущего типа: только трубы или только резервуары.
- `visibleTableObjects` - строки, которые видны в таблице после поиска,
  фильтров и сортировки.
- `calculationObjects` - полный набор объектов, который участвует в расчётах.
  Он не зависит от `visibleTableObjects`.
- `tableViewState` - временное состояние поиска, фильтров и сортировки.

## Базовое Поведение

1. При открытии страницы поиск пустой, фильтры пустые, сортировка отсутствует.
2. Таблица показывает все объекты выбранного типа в текущем проектном порядке.
3. Пользователь может применить поиск/фильтр/сортировку к видимым колонкам.
4. Таблица отображает только найденные строки, но расчётные статусы и переходы
   продолжают учитывать полный набор объектов.
5. Сброс фильтров возвращает таблицу к полному списку объектов выбранного типа.
6. Переключение `Труба` / `Резервуар` использует отдельный `tableViewState` для
   каждого типа.
7. Сортировка меняет только визуальный порядок строк в таблице.
8. Клик по строке, редактирование, копирование, удаление и создание на
   основании должны работать по `object.id`, а не по визуальному индексу.

## UI Требования

Не добавлять отдельную высокую панель над таблицей. Интерфейс должен оставаться
плотным, чтобы не отнимать высоту у таблицы и формы.

Рекомендуемый паттерн:

- в заголовке каждой колонки использовать compact column menu/filter dropdown;
- в dropdown показывать поиск/фильтр, подходящий типу данных колонки;
- сортировка доступна из заголовка колонки: клик по заголовку или пункт меню;
- активный фильтр подсвечивает иконку фильтра в заголовке;
- активная сортировка показывает направление `asc` / `desc`;
- в actionbar добавить только compact-индикатор активных фильтров, если есть
  активное состояние;
- рядом с индикатором дать icon-only кнопку `Сбросить фильтры`, когда есть что
  сбрасывать.

Пример компактного состояния в actionbar:

```text
Труба [pipe] [tank] │ [+] [copy] ... │ [columns] [filter-active 8/17] [clear-filter]
```

Если места мало, индикатор можно свернуть до icon-only кнопки с tooltip:

```text
tooltip: "Показано 8 из 17. Есть активные фильтры"
aria-label: "Фильтры таблицы активны, показано 8 из 17"
```

Не показывать длинные пояснения внутри интерфейса. Смысл должен быть понятен по
иконкам, заголовкам, placeholder и tooltip.

## Поиск По Полям

Для каждой видимой колонки должен быть доступен поиск или фильтр, соответствующий
типу данных.

### Текстовые Поля

Применять case-insensitive поиск по подстроке:

- `Наименование`;
- `Материал ИЗ`;
- `Материал трубы`;
- `Размещение`;
- `Среда`;
- `Климат`;
- `DN`, если он отображается как строка;
- другие текстовые/label поля.

Правила:

- `trim()` для введенного значения;
- искать по отображаемому label, а не только по raw key;
- поддерживать кириллицу и латиницу;
- не требовать точного регистра;
- пустой ввод снимает фильтр по колонке.

### Числовые Поля

Для числовых колонок использовать range filter:

```text
от [min] до [max]
```

Применять к значениям в тех же единицах, которые видит пользователь в таблице:

- `Ø, мм` - миллиметры;
- `δ ИЗ, мм` - миллиметры;
- `L, м` - метры;
- `T подд.` и `T окр.` - градусы Цельсия;
- `Зад.`, `Флн.`, `Опр.` - штуки;
- `Q доп., Вт` - ватты.

Правила:

- если заполнено только `от`, фильтровать `>= min`;
- если заполнено только `до`, фильтровать `<= max`;
- если `min > max`, показать inline validation и не применять фильтр;
- пустые значения и прочерки не проходят числовой фильтр, если отдельно не
  выбран пункт `Пустые`;
- сортировка числовых колонок должна быть числовой, а не лексикографической.

### Справочники И Enum Поля

Для колонок с ограниченным набором значений использовать multi-select:

- материал изоляции;
- материал покрытия;
- тип размещения;
- форма резервуара;
- среда;
- температурная группа;
- классификация зоны;
- рабочее напряжение;
- пропарка.

Правила:

- список опций строить по отображаемым значениям текущего типа объектов;
- если есть справочник, показывать label из справочника;
- добавить поиск внутри списка опций, если опций больше 8;
- поддерживать `Пустые`, если в данных встречаются пустые значения.

### Агрегированные И Derived Поля

Некоторые колонки не лежат напрямую в `params`, а считаются для отображения:

- `№`;
- `Тип`;
- `DN`;
- `Габариты`;
- `Слоёв ИЗ`;
- итоговые/сводные label поля.

Для них нужно явно определить `filterValue` и `sortValue` в registry колонок.
Нельзя парсить React-узел или DOM-текст заголовка. Таблица должна фильтровать
по typed value, который возвращает колонка.

## Сортировка

Для первой реализации использовать один активный sort на таблицу.

Цикл клика по заголовку:

```text
нет сортировки -> по возрастанию -> по убыванию -> нет сортировки
```

Правила:

- сортировка стабильная;
- при равенстве значений сохранять исходный проектный порядок как secondary
  sort;
- `null`, `undefined`, пустые строки и прочерки помещать в конец для `asc` и в
  конец для `desc`, чтобы пустые значения не всплывали наверх;
- текст сортировать через `Intl.Collator('ru', { numeric: true, sensitivity:
  'base' })`;
- числа сортировать по числовому значению;
- даты, если появятся, сортировать по timestamp;
- сортировка не должна менять `sort_order` и не должна вызывать API сохранения.

## Состояние И Хранение

Фильтры, поиск и сортировка должны быть временным UI-состоянием.

Для первой реализации:

- не сохранять `tableViewState` в БД;
- не сохранять `tableViewState` в `localStorage`;
- не записывать его в настройки колонок;
- не включать его в экспорт;
- не восстанавливать фильтры после нового открытия проекта.

Причина: пользователь может забыть активный фильтр и ошибочно решить, что
объекты пропали или не участвуют в расчёте. Для поискового слоя безопаснее
начинать с пустого состояния.

Допустимое будущее расширение: `sessionStorage` на время текущей вкладки и
текущего project id, но только при явном индикаторе активных фильтров и кнопке
сброса. В рамках этого промпта не реализовывать.

## Взаимодействие С Настройкой Колонок

Фильтры доступны для колонок, которые сейчас видимы в таблице.

Если пользователь скрывает колонку через `Поля таблицы`:

- активный фильтр по этой колонке нужно сбросить;
- активную сортировку по этой колонке нужно сбросить;
- остальные фильтры и сортировки сохранить.

Если пользователь снова показывает колонку, фильтр не восстанавливается
автоматически. Это снижает риск скрытого состояния, которое трудно заметить.

Полный registry колонок должен содержать для каждой колонки:

```ts
type HeatCalcColumnDefinition = {
  key: HeatCalcColumnKey;
  title: string;
  dataType: 'text' | 'number' | 'enum' | 'boolean';
  group: string;
  render: (object: ProjectObject, context: ColumnRenderContext) => ReactNode;
  filterValue: (object: ProjectObject, context: ColumnRenderContext) => unknown;
  sortValue: (object: ProjectObject, context: ColumnRenderContext) => unknown;
  filterConfig?: ColumnFilterConfig;
  sortable?: boolean;
};
```

Не дублировать вычисление значений в JSX, helper фильтрации и helper сортировки.
Один источник истины - registry колонок.

## Взаимодействие С Выбором Строк

Сортировка должна сохранять выбранные строки по `object.id`.

Фильтрация может скрыть выбранную строку. Чтобы пользователь не выполнил
действие над невидимым объектом, при изменении фильтров нужно:

- оставить выбранными только строки, которые остались видимыми;
- скрытые строки убрать из `selectedRowKeys`;
- не удалять и не менять сами объекты.

Если открыта форма редактирования объекта, а фильтр скрывает этот объект:

- форму не закрывать;
- объект продолжает редактироваться по `object.id`;
- таблица может не показывать строку до сброса фильтра;
- заголовок формы должен оставаться источником понимания, какой объект открыт.

## Создание И Сохранение При Активных Фильтрах

Если пользователь создаёт или сохраняет объект при активных фильтрах:

- объект сохраняется в полный список проекта;
- расчёт выполняется как обычно;
- если объект не проходит текущие фильтры, он может не появиться в таблице;
- в этом случае показать ненавязчивое сообщение:

```text
Объект сохранён, но скрыт текущими фильтрами
```

В сообщении дать действие `Сбросить фильтры`, если используемый UI-kit это
позволяет без утяжеления интерфейса.

## Расчёты И Статусы

Расчётный контур всегда работает по полному набору объектов.

Не менять:

- `canProceedToElectrical`;
- количество рассчитанных объектов;
- badges разделов;
- статус `Все рассчитаны`;
- расчётные допущения;
- исходные результаты теплопотерь;
- электротехнический расчёт;
- спецификацию и отчёт.

Если нужна видимая информация о фильтрах, показывать её отдельно:

```text
Показано: 8 из 17
```

Существующие badges `Труб:`, `Рез.:`, `Объектов:` должны оставаться счётчиками
полного набора объектов, а не видимых после фильтра строк. Это важно, чтобы
пользователь не спутал поиск с расчётным составом проекта.

## Архитектура Реализации

Рекомендуемый data flow:

```ts
const typeObjects = filterObjectsByCurrentType(allObjects, activeObjectType);
const visibleColumns = getVisibleColumns(activeObjectType, columnSettings);
const tableViewState = tableViewStateByType[activeObjectType];

const filteredObjects = applyColumnFilters(
  typeObjects,
  visibleColumns,
  tableViewState.filters,
  columnRegistryContext,
);

const visibleTableObjects = applyTableSort(
  filteredObjects,
  visibleColumns,
  tableViewState.sort,
  columnRegistryContext,
);
```

Важно:

- `allObjects` не мутировать;
- `typeObjects` не мутировать;
- `applyColumnFilters` и `applyTableSort` должны быть pure functions;
- использовать `object.id` как row key;
- визуальный `№` считать после фильтра и сортировки, если он означает номер
  видимой строки;
- если нужно сохранить проектный номер, добавить отдельную колонку в будущем.

Тип состояния:

```ts
type HeatCalcColumnFilter =
  | { kind: 'text'; value: string }
  | { kind: 'numberRange'; min?: number; max?: number; includeEmpty?: boolean }
  | { kind: 'enum'; values: string[]; includeEmpty?: boolean }
  | { kind: 'boolean'; value: boolean | 'empty' };

type HeatCalcTableSort = {
  columnKey: HeatCalcColumnKey;
  direction: 'asc' | 'desc';
};

type HeatCalcTableViewState = {
  filters: Partial<Record<HeatCalcColumnKey, HeatCalcColumnFilter>>;
  sort?: HeatCalcTableSort;
};
```

Хранить независимо для типов:

```ts
type HeatCalcTableViewStateByType = {
  pipe: HeatCalcTableViewState;
  tank: HeatCalcTableViewState;
};
```

## Производительность

На проектах с большим числом объектов фильтры не должны создавать заметные
задержки ввода.

Рекомендации:

- мемоизировать `visibleTableObjects`;
- debounce для текстового ввода 150-250 мс;
- не пересчитывать справочники опций на каждый keypress без необходимости;
- не вызывать backend при изменении фильтра;
- не запускать расчёт при изменении фильтра;
- не пересоздавать весь registry колонок на каждый render.

## Доступность

Обязательно:

- у кнопок фильтра и сброса есть `aria-label`;
- активное состояние фильтра видно не только цветом, но и через tooltip/text;
- column dropdown открывается с клавиатуры;
- `Esc` закрывает dropdown без применения незавершенного ввода;
- `Enter` применяет фильтр в dropdown;
- `Сбросить` внутри dropdown снимает фильтр только текущей колонки;
- общий `Сбросить фильтры` снимает все фильтры и сортировку текущего типа.

## Пустые Состояния

Если фильтры не нашли строк:

```text
Нет строк по текущим фильтрам
```

Действия:

- `Сбросить фильтры`;
- не показывать стандартный empty state проекта, чтобы пользователь не подумал,
  что объектов нет вообще.

Если объектов текущего типа нет вообще, показывать текущий empty state создания
объекта. Это не состояние фильтра.

## Тесты

Покрыть unit-тестами pure helpers:

- text filter: кириллица, латиница, case-insensitive, trim;
- number range: min only, max only, min/max, invalid range, empty values;
- enum filter: multi-select и пустые значения;
- sort: text, number, nulls last, stable fallback на проектный порядок;
- очистка filter/sort при скрытии колонки.

Покрыть компонентными тестами `HeatCalcPage`:

- фильтр по `Наименование` скрывает неподходящие строки, но badges расчёта не
  меняются;
- сортировка по `Ø, мм` меняет только визуальный порядок;
- фильтр по `Материал ИЗ` работает по label материала;
- range filter по температуре работает в отображаемых единицах;
- переключение `Труба` / `Резервуар` не переносит фильтры между типами;
- `Сбросить фильтры` возвращает все строки выбранного типа;
- скрытая фильтром выбранная строка удаляется из `selectedRowKeys`;
- открытая форма не закрывается, если текущий объект скрыт фильтром;
- при сохранении объекта, который не проходит фильтр, появляется сообщение;
- настройки видимых колонок очищают фильтры скрытых колонок.

Проверить E2E/Playwright:

- в гостевом режиме создать набор труб и резервуаров;
- применить поиск, enum-фильтр, number range и сортировку;
- убедиться, что расчётные статусы и переход к электротехническому расчёту не
  меняются от фильтров;
- сделать screenshot таблицы с активным фильтром и пустым результатом.

## Критерии Готовности

- Поиск, фильтры и сортировка есть для всех видимых колонок таблицы.
- Для труб и резервуаров состояние независимое.
- Расчёты, badges, экспорт и `sort_order` не зависят от фильтров.
- Активные фильтры заметны и быстро сбрасываются.
- Нет скрытых фильтров по невидимым колонкам.
- Table helpers покрыты unit-тестами.
- Основные сценарии покрыты компонентными тестами.
- Playwright подтверждает, что это работает в гостевом режиме на реальных
  данных.
