# Отклонение от ТЗ: температурная поправка сопротивления резистивного кабеля

Дата фиксации: 2026-05-30.

Статус: confirmed issue, код не изменен.

Затронутый контур: электротехнический расчет резистивных кабелей
`single_core` / `three_core`, ручной и auto-подбор, QA-agent oracle и
существующие unit-тесты.

## Суть отклонения

Первичные DOCX ТНП для трубопроводов и резервуаров задают расчет мощности
резистивного кабеля через сопротивление жилы при рабочей температуре `Tж`:

```text
Sк = (Q / U^2) * rho * N * [1 + alpha * (Tж - 20)]
P  = (U^2) / (rho * N * [1 + alpha * (Tж - 20)]) * Sк_б
```

Для трехжильного ТТ Р3 формулы имеют те же температурные множители и
дополнительные схемные множители `* 3`, `/ 3` по типу подключения.

Текущий backend применяет `rho_T = rho * [1 + alpha * (Tж - 20)]` только в
diagnostic-поле `required_cross_section`. Фактическая мощность, ток и
auto-кандидаты считаются по холодному паспортному сопротивлению `R20` из
каталога:

```text
R = resistance_ohm_km / 1000 * L * factor_R
P = U^2 / R * factor_P
I = P / U
```

То есть `process_temperature` приходит в расчет, но не участвует в `P/I` для
паспортных строк `resistance_ohm_km`.

## Golden-проверка

Контрольный пример:

```text
Кабель: ТТ Р3 х 1,5-1,0
Sк_б: 1.5 мм2
R20: 0.0175 * 1000 / 1.5 = 11.667 Ом/км
L: 1000 м
U: 220 В
Схема: line_1ph
alpha: 0.0042 1/К
```

Код возвращает одинаковые `P/I` при любой `Tж`, потому что использует `R20`.
Первоисточник требует делить мощность и ток на:

```text
factor_T = 1 + 0.0042 * (Tж - 20)
```

| Tж, C | `factor_T` | Отклонение кода от первоисточника по `P/I` |
|---:|---:|---:|
| 5 | 0.937 | -6.3% |
| 60 | 1.168 | +16.8% |
| 150 | 1.546 | +54.6% |

Дополнительная ручная проверка на backend:

```text
Tж=150 C, Q=10000 Вт
code_total_power=12445.714 Вт, code_margin=+2445.714 Вт
source_total_power=8050.268 Вт, source_margin=-1949.732 Вт
```

То есть при высокой `Tж` приложение может принять кабель как достаточный, хотя
по первичной формуле он не покрывает требуемую мощность.

## Риск

Риск существенный для высоких температур:

- backend завышает фактическую мощность и ток резистивного кабеля;
- auto-подбор может выбрать недостаточный кабель;
- manual-проверка может пропустить кабель, который не покрывает `Q`;
- `required_cross_section` и `total_power/current` внутренне используют разные
  температурные модели: горячую для diagnostic-сечения и холодную для
  фактического результата.

## Почему не исправлено этим документом

Этот документ только фиксирует проблему. Исправление требует согласованного
изменения:

- backend `resistive.py` для ручного и auto-подбора;
- QA-agent oracle;
- `docs/business-logic-contract.md` и `docs/context/formulas-summary.md`;
- focused golden/boundary tests по `Tж < 20`, `Tж = 20`, `Tж > 20`;
- регрессионной проверки коммерческого ранжирования резистивных auto-кандидатов.

## Варианты закрытия

| Вариант | Решение | Последствие |
|---|---|---|
| A | Исправить расчет на горячее сопротивление `R_T = R20 * [1 + alpha * (Tж - 20)]` | Соответствие первичным DOCX; изменятся мощности, токи, подбор и expected-тесты |
| B | Оставить холодное паспортное `R20` как продуктовую политику | Нужен отдельный подписанный источник, потому что это расходится с найденными DOCX-формулами |
| C | Развести режимы методики | Нужен явный параметр методики и миграция отчетов/тестов |

Рекомендуемый вариант для функциональной точности: A.
