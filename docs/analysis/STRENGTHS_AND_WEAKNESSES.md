# Сильные и слабые стороны приложения HeatCalc

Аудит архитектуры, кода, тестов, безопасности и процессов по состоянию на 2026-05-08.

---

## Сильные стороны

### 1. Архитектура и разделение ответственности

- **Чистые формулы как чистые функции.** Файлы `formulas/heat_loss/pipe.py`, `tank.py`, `electrical/self_regulating.py`, `resistive.py` — stateless-функции без импортов БД. Принимают Pydantic-параметры, возвращают Pydantic-результаты. Это даёт изолированное unit-тестирование без подъёма базы.
- **Трёхслойная модульная структура backend:** `api/v1/` (HTTP-endpoints) → `services/` (бизнес-логика + БД) → `formulas/` (чистая математика). Сервисы оркестрируют, формулы считают. Чёткая граница.
- **Typed domain primitives** в `contracts.py`: `ProjectId`, `ObjectId`, `UserId`, `SessionId` через `NewType`. MyPy ловит перепутанный порядок ID-аргументов без рантайм-оверхеда.
- **Result-тип (Ok/Err)** в `result.py` для операций, которые могут упасть — вызывающий код получает checked error вместо try/except.

### 2. Валидация и безопасность типов

- **Pydantic v2 с model_validator.** `PipeHeatLossParams.check_insulation_provided`, `TankHeatLossParams.check_ranges_and_layers` — бизнес-правила проверяются на границе входа, до попадания в формулы. Все диапазоны из `coefficients.MD` зашиты как `Field(ge=…, le=…)`.
- **Frontend ↔ backend конвертация единиц.** Форма работает в мм, API — в метры. Конвертация централизована в `objectWizardUtils.ts` (`pipeFormToApiParams` / `pipeApiParamsToForm`). Исключает путаницу.
- **Enum'ы вместо магических строк:** `CableType`, `Installation`, `TankShape`, `PipeMaterial`, `CableSource` — все через `str, enum.Enum`, так что и в JSON, и в коде сохраняется типобезопасность.

### 3. Качество тестов

- **781 backend-тест** (589 unit + 192 integration). Покрытие формул близко к 100%: тесты на граничные значения, краевые случаи, double-safety-factor protection, arccosh для подземных труб.
- **171 frontend-тест** (Vitest + React Testing Library). Плюс **48 e2e** (Playwright) — сквозные пользовательские сценарии.
- **Mutation testing** (mutmut) настроен в `pyproject.toml` — проверка качества тестов, а не только coverage-процента.
- **`pyproject.toml` требует `--cov-fail-under=85`** на уровне проекта.
- **Bandit + pip-audit + eslint-plugin-security + npm audit** — 4 сканера уязвимостей, запускаются одним скриптом `scripts/security-scan.sh`.

### 4. Документация

- **63 Markdown-файла** в `docs/`: архитектура, формулы, пользовательские сценарии, UI-спецификации, тест-кейсы, бизнес-правила, SRS, диаграммы, playbooks.
- **`CLAUDE.md`** — 600+ строк архитектурной правды: навигационная карта, структура репозитория, матрица доступа, API-endpoints, конфигурация лимитов, pitfalls.
- **`formules.md`** — формулы с человеческим объяснением, численными примерами и сводной таблицей «что вводим → что получаем». Понятно инженеру без бэкграунда в разработке.
- **`pitfalls.md`** — журнал граблей проекта: симптом → root cause → фикс. 20 записей, от CORS/деплоя до double safety factor.
- **Playbooks** (`docs/playbooks/`) — пошаговые процедуры для demo-релиза, деплоя, добавления формул, отладки PDF.

### 5. Инфраструктура и DevOps

- **Docker Compose с тремя оверлеями:** dev (hot-reload), prod (nginx), e2e (изолированные порты).
- **Multi-arch сборка** (`buildx`): отдельные образы под linux/amd64 и linux/arm64, скрипт `build-multiarch-demo.sh`, `demo/load.sh` с автоопределением архитектуры.
- **Makefile** с 40+ целями: dev, test, lint, migrate, seed, shell-*, package, release.
- **Redis для distributed rate limiting и кэша** с graceful fallback на in-memory. Лимитер переключается по наличию `REDIS_URL`.
- **Healthcheck'и для всех сервисов** в docker-compose: `pg_isready`, `redis-cli ping`, HTTP-check backend, wget frontend.
- **Защита от ботов и утечек данных:** rate limit `/auth/guest` (10/IP/час), TTL гостевых сессий (20 мин), фоновый cleanup (каждые 10 мин), каскадное удаление `ON DELETE CASCADE`.

### 6. Расчётное ядро

- **Полная поддержка 4 типов кабеля с формулами:** ТЛТ (10 марок), ТТН/ТТВ/ТТХ (14 марок, формула `q1·T+q2`), ТТ Р1 (одножильный, 3 схемы), ТТ Р3 (трёхжильный, 5 схем).
- **Многослойная изоляция (1–3 слоя)** с ручным переопределением λ для каждого слоя.
- **Подземный расчёт** с разделением площади на надземную/подземную части для резервуаров.
- **Защита от двойного safety factor** — залочена контрактами в коде и тестами (`test_no_double_safety.py`).
- **Формула α_внеш исправлена** с линейной `11.6+7v` на `11.6+7√v` по SNiP 41-03-2003 (2026-05-06).
- **Встроенные справочники:** 539 городов РФ с климатическими данными, 6 материалов изоляции, 5 материалов труб с λ(T), грунты, аксессуары.

### 7. Frontend

- **Zustand с persist в localStorage** — мгновенное восстановление состояния после перезагрузки.
- **Синхронная инициализация authStore** через `readInitialState()` при импорте модуля — устранён race-condition с ProtectedRoute.
- **Ant Design 5** — consistent UI, готовая таблица с DnD, form validation.
- **Drag-and-drop сортировка** через `@dnd-kit` с `activationConstraint: distance=6` — клики и drag не конфликтуют.
- **Импорт/экспорт Excel/CSV** с автоопределением разделителя и кодировки, human-readable ошибками по строкам.

## Слабые стороны и области для улучшения

### 1. Безопасность и надёжность продакшена

| Проблема | Серьёзность | Пояснение |
|---|---|---|
| **In-memory rate limiter без Redis** | Средняя | При пустом `REDIS_URL` лимитер живёт в RAM одного инстанса — сбрасывается при рестарте, не работает при горизонтальном масштабировании. Решение (Redis) уже есть, но fallback остаётся уязвимым. |
| **In-memory cache игнорирует TTL** | Низкая | `_InMemoryBackend` не эвиктит записи по сроку — только ручная инвалидация. При долгоживущем dev-сервере кэш может раздуваться. |
| **Слабые дефолты SECRET_KEY / пароля админа** | Высокая | `SECRET_KEY=change-me-in-production`, `FIRST_ADMIN_PASSWORD=admin` — переопределяются только через `.env`. В demo-стеке админ-пароль жёстко зафиксирован. Нет проверки при старте на не-дефолтный SECRET_KEY. |
| **Нет email-верификации для сотрудника** | Средняя | Сотрудники создаются только администратором, self-service регистрации нет. Компрометация админки = компрометация всех учётных записей. |
| **Нет audit trail расчётов** | Высокая | Результаты хранятся без снапшота справочников и коэффициентов на момент расчёта. Воспроизвести расчёт полугодовой давности невозможно — изменились коэффициенты, справочники кабелей. |
| **Нет rate limit на расчётные эндпоинты** | Средняя | `/calc/electrical/batch` не лимитирован — бот может гонять CPU-тяжёлые расчёты без ограничений. |

### 2. Архитектурные ограничения

| Проблема | Серьёзность | Пояснение |
|---|---|---|
| **Монолитный backend** | Низкая | Все сервисы в одном процессе. Для текущего масштаба (1–10 пользователей) оправдано, но при росте утяжелит деплой. |
| **Нет API versioning strategy** | Средняя | Только `/api/v1/`. При breaking changes в схемах некуда отступать без ломания всех клиентов. |
| **Отсутствие фоновых задач / очередей** | Средняя | Batch-расчёты идут синхронно в HTTP-ответе. При 50 объектах + сложных формулах возможен таймаут. Нет Celery / ARQ / фоновых тасков. |
| **Единая БД для гостей и сотрудников** | Низкая | Гостевые и постоянные данные в одной схеме. При росте гостевого трафика — шум в той же БД. |
| **Нет pagination на списках объектов** | Низкая | При 50+ объектах таблица рендерится целиком. Пока лимит 50 — терпимо. |

### 3. Расчётное ядро: пробелы

| Проблема | Серьёзность | Пояснение |
|---|---|---|
| **MI и скин-системы без формул** | Средняя | Типы кабеля видны в UI, но при выборе возвращают ошибку «расчётная формула не реализована». Вводит пользователя в заблуждение. |
| **Температурная зависимость изоляции не реализована** | Средняя | λ изоляции берётся константой из справочника, без поправки на среднюю температуру — как у материалов труб `λ(T)`. Для ППУ и минваты зависимость слабая, для пенополистирола — значимая. |
| **q_additional не валидируется на отрицательные значения** | Низкая | `ge=0` есть в Pydantic, но в `calc_tank_heat_loss` проверка только `or 0.0`. |
| **Нет учёта тепловых мостиков** | Низкая | Опоры, фланцы, арматура — только через эмпирический `K=1.1`. Инженерно приемлемо, но не точно. |
| **Справочник климата — только РФ** | Низкая | 539 городов РФ. Для международного использования нужны другие климатические базы. |

### 4. Frontend

| Проблема | Серьёзность | Пояснение |
|---|---|---|
| **Мало тестов относительно кодовой базы** | Средняя | 171 vitest-тест на 118 файлов — ~1.4 теста на файл. Многие компоненты не покрыты. |
| **Единое состояние — один проект** | Низкая | `projectStore` держит ровно один `currentProject`. Для гостя это ок (один авто-проект), но сотрудник с проводником проектов вынужден переключаться через API. |
| **Нет optimistic updates** | Низкая | TanStack Query v5 используется, но мутации ждут ответа сервера перед обновлением UI. При медленной сети — lag. |
| **Нет error boundary на уровне страниц** | Средняя | Ошибка рендеринга одного виджета может уронить всю страницу. |
| **Встроенная форма (ObjectWizard) — монолит** | Низкая | Одна большая форма на 4 секции без разбиения на подкомпоненты. При добавлении новых полей сложнее поддерживать. |

### 5. DevOps и процессы

| Проблема | Серьёзность | Пояснение |
|---|---|---|
| **Нет CI/CD пайплайна** | Высокая | Makefile покрывает локальные сценарии, но нет GitHub Actions / GitLab CI. Тесты, линтеры, security scan не запускаются автоматически на push/PR. |
| **Нет staging-окружения** | Средняя | Только dev (локальный) и prod/demo. Негде тестировать релиз-кандидаты перед деплоем. |
| **Бэкапы БД не автоматизированы** | Средняя | `pgdata` volume — единственное хранилище. Нет `pg_dump` по расписанию, нет стратегии восстановления. |
| **E2E тесты тонкие** | Средняя | 48 тестов / 1456 строк. Не покрывают негативные сценарии, сетевые ошибки, edge cases авторизации. |
| **Нет structured logging** | Средняя | Используется стандартный `logging` без структурированных полей (request_id, user_id, duration). Сложно отлаживать в проде. |
| **Нет мониторинга / алертинга** | Низкая | Нет Prometheus-метрик, health-check dashboard'а, уведомлений о падении. |
| **PyPI-зависимости без хэшей** | Средняя | `requirements.txt` без `--hash`. `requirements-lock.txt` есть, но он без хэшей пакетов. Supply-chain risk. |
| **Нет `.env.example` в одном месте** | Низкая | Есть в `frontend/.env.example` и в корне `.env.example`, но нет единого канонического перечня всех переменных с пояснениями. Конфиг размазан. |

### 6. Документация: пробелы

| Проблема | Серьёзность | Пояснение |
|---|---|---|
| **Нет ADR (Architecture Decision Records)** | Средняя | Ключевые решения (почему Zustand а не Redux, почему монолит, почему Pydantic v2) не задокументированы. |
| **Нет runbook для инцидентов** | Средняя | Что делать при падении БД, утечке JWT, DoS-атаке — не описано. |
| **API-документация авто-генерируется, но без примеров** | Низкая | FastAPI даёт Swagger, но body-примеры для нетривиальных эндпоинтов (import, batch calc) отсутствуют. |
| **`changes.md` не существует** | Низкая | Упоминается в CLAUDE.md как актуальное ТЗ, но файла нет — история требований потеряна. |

### Приоритетные действия (Top-5)

1. **Внедрить CI/CD** (GitHub Actions) — авто-запуск тестов, линтеров, security scan на push/PR.
2. **Добавить audit trail расчётов** — снапшот справочников и коэффициентов в каждом результате.
3. **Заменить дефолтный SECRET_KEY проверкой при старте** — отказ запускаться с `change-me-in-production`.
4. **Реализовать self-service регистрацию сотрудников** с email-верификацией.
5. **Добавить фоновые задачи** (ARQ / Celery) для batch-расчётов — исключить таймауты HTTP.
