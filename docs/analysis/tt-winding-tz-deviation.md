# Отклонение от ТЗ: учет навива в подборе ТТН/ТТВ/ТТХ

**Дата фиксации:** 2026-05-30  
**Статус:** требует продуктового подтверждения / подписи заказчика  
**Затронутый контур:** электротехнический расчет `self_regulating_tt`
для кабелей ТТН/ТТВ/ТТХ.

## Суть отклонения

Первичный алгоритм ТНП/VSDX для саморегулирующихся кабелей ТТН/ТТВ/ТТХ
задает количество ниток как:

```text
N = ceil(Pоб / Pi.ном(T3))
```

В текущей реализации приложения проверка достаточности мощности и расчет
количества ниток учитывают коэффициент навива:

```text
N = ceil(Pоб / (Pi.ном(T3) * k_навива))
Pi.эфф = Pi.ном(T3) * k_навива * N
```

То есть приложение принимает кабель как достаточный, если его установленная
мощность на базовый метр объекта с учетом навива и количества ниток покрывает
требуемую мощность.

## Где источник расхождения

Первичный источник:

- `Алгоритмы/Алгоритм Самрег.трубы.vsdx`
- производный markdown: `docs/tnp/algorithms/self-regulating-pipe-selection.md`

В VSDX-ветке для ТТН/ТТВ/ТТХ явно зафиксирована формула:

```text
N = Округл. Вверх. (0) PОб. / Pi.ном(Т3)
```

В этой формуле коэффициент навива не указан.

Текущий продуктовый контракт после фикса:

- `docs/context/formulas-summary.md`
- `docs/business-logic-contract.md`
- `backend/app/formulas/electrical/self_regulating.py`

## Почему приложение отклоняется от буквального VSDX

До фикса приложение было внутренне противоречивым:

- итоговая длина кабеля считалась как `L_каб = L_баз * k_навива * N`;
- установленная мощность считалась как `Pi.ном(T3) * k_навива * N`;
- но проверка достаточности кабеля и auto-подбор сравнивали только
  `Pi.ном(T3) * N` с требуемой мощностью.

Из-за этого backend мог показывать, что установленной мощности хватает, но
одновременно отклонять ручной выбор или выбирать более мощный кабель в auto.

Пример:

```text
Кабель: 30ТТВ2-СР
T3: 50 °C
Pi.ном(T3): 24.95 Вт/м
k_навива: 1.1
Требуется: 27 Вт/м

Без учета навива: 24.95 < 27     -> кабель не проходит
С учетом навива: 24.95 * 1.1 = 27.445 >= 27 -> кабель проходит
```

Решение было принято как фиксация внутренней консистентности текущего
приложения: критерий достаточности теперь использует ту же эффективную
мощность, которую приложение выводит в результате расчета.

## Влияние

Потенциальное отличие от буквального ТНП/VSDX:

- auto-подбор может выбрать менее мощный номинал, если навив делает его
  достаточным;
- расчет может дать меньшее количество ниток, если `k_навива > 1`;
- ручной выбор кабеля может проходить там, где буквальный VSDX без навива
  потребовал бы более мощный кабель или больше ниток.

На энергобаланс текущего приложения это влияет осознанно: установленная
мощность уже считается через фактическую длину кабеля с учетом навива.

## Риск приемки

Если приемка требует буквального соответствия VSDX без инженерной
интерпретации, это место может быть признано отклонением от ТЗ.

Если заказчик подтверждает, что навив увеличивает установленную мощность на
базовый метр объекта и должен участвовать в критерии достаточности, текущее
поведение следует считать утвержденным уточнением методики.

## Варианты закрытия решения

| Вариант | Решение | Последствие |
|---|---|---|
| A | Утвердить текущую реализацию | Оставить `Pi.ном(T3) * k_навива * N >= Pоб`; документировать как уточнение методики |
| B | Вернуться к буквальному VSDX | Проверять `Pi.ном(T3) * N >= Pоб`; `k_навива` влияет только на длину/закупку, но не на достаточность мощности |
| C | Развести режимы | Добавить явный режим методики: `strict_vsdx` и `effective_installed_power` |

Рекомендуемый вариант для текущего продукта: **A**, потому что он устраняет
противоречие между проверкой мощности и отображаемой установленной мощностью.
