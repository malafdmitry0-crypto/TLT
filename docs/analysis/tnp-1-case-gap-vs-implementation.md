## 1. Краткий итог

Документ описывает **гостевой (неавторизованный)** сценарий:

```text
Исходные данные → Электротехнический расчёт → Спецификация
```

Базовый расчётный контур продукта уже существует (тепло → кабель → спецификация),  
но **целевой UX и процессная модель «1_Кейс» не закрыты**.

| Область | По документу | Сейчас | Статус |
|---|---|---|---|
| Гостевой вход + 1 временный проект | Да | Да | **Есть** |
| Теплопотери трубы/ёмкости | Да | Да | **Есть** |
| Импорт Excel/CSV, таблица, настройки колонок | Да | Да | **Есть** |
| Подбор самрег-кабеля (база) | Да | Да (ТЛТ + ещё типы) | **Частично** |
| Навигация 3 шага + gate «готовности» | Да | 4 шага, свободный переход | **Нет** |
| Динамические **ЭР 1…ЭР 5** | Да | Фикс. **СО1…СО4** | **Нет** |
| Нераспределённые / Самрег / Резистив / Скин | Да | Плоская таблица всех объектов | **Нет** |
| Нагревательные секции (иерархия + алгоритм §6.14) | Да | Нет UI секций; алгоритм не по PDF | **Нет / частично** |
| Спецификация по нескольким ЭР + мастер | Да | Один `variant_number` | **Нет** |
| Лимиты гостя 500 объектов / TTL 3 дня | Да | **50** объектов / **20 мин** | **Нет** |
| «Данные гостя не в БД» | Да (текст PDF) | **Есть в PostgreSQL** | **Расхождение** |

**Оценка покрытия интерфейсных механик документа:**  
примерно **40–45% есть**, **55–60% ещё нет**.  
Главная дыра — не «красота», а **модель ЭР + распределение объектов + секции**.

## 4. Что по PDF ещё не сделано

### P0 — доменная модель (без этого «1_Кейс» не закрывается)

#### 4.1. ЭР вместо СО (`§6.3–6.7`, `§6.20`)

**Документ требует:**
- динамические вкладки **ЭР 1…ЭР 5**
- создать / создать на основании / удалить с подтверждением
- **переименовать** (Enter/Esc), имя = имя вкладки спецификации
- max **5** вариантов в проекте

**Сейчас:**
- всегда **4 фиксированных СО**
- `variant_number ∈ [1..4]` в API, DB check constraint, store, отчётах
- нет сущности «ЭР» с id / именем / жизненным циклом
- copy — между готовыми слотами СО, не «новый ЭР №5»

**Критичная техническая граница:**

```text
variant_number 1…4
  → DB check constraint
  → Pydantic ge/le
  → Zustand / ElecCalc / Spec / Report
  → UNIQUE(object_id, variant_number)
```

Замена «СО → ЭР» **нельзя** сделать переименованием кнопок.

#### 4.2. Распределение объектов (`§6.9–6.11`, `§6.15`, `§6.17`)

**Документ требует:**
- вкладки: **Нераспределённые / Самрег / Резистив / Скин**
- «Выбрать тип» + **DnD на вкладку**
- один объект — только в одной вкладке **текущего** ЭР
- возврат в нераспределённые: сброс кабеля/секций, **подтверждение**
- MVP: активен только Самрег; Резистив/Скин — disabled

**Сейчас:**
- все объекты сразу в одной таблице
- нет статуса «нераспределён»
- нет assignment `object → system_type` внутри варианта

#### 4.3. Нагревательные секции (`§6.12`, `§6.14`)

**Документ требует:**
- после назначения Самрег: подбор кабеля + **секционирование**
- `Lогр = min(Lмакс, Iдоп / Iст.уд)`
- `N = ceil(Lтреб / Lогр)`
- **равные** секции (не «остаток» на последней)
- иерархия в таблице: `Объект → Секция 1…N`
- стартовый/рабочий ток секции и объекта
- сводки: объекты, длина, **число секций**, мощность, Iраб, **Iстарт**
- 4 summary-блока: Самрег / Резистив / Скин / Итого

**Сейчас:**
- автоподбор кабеля есть
- UI **плоский**, без вложенных секций
- алгоритм §6.14 (Lмакс/Iст.уд, равные секции) — **не как в PDF**
- один summary, без 4 блоков

#### 4.4. Спецификация multi-ЭР (`§6.18`, `§7.1–7.7`)

**Документ требует:**
- мастер: выбрать **один/несколько ЭР**
- вкладки «Спецификация ЭР 1…» (имена из ЭР)
- предупреждение о нераспределённых: **Исправить / Всё равно сформировать**
- разделы **Трубы / Бочки / Общие материалы**
- способ: разделять / объединять по типам объектов
- колонки: наименование, **марка**, **ном. код**, **поставщик**, ед. поставки, кол-во
- настройки: база номенклатуры, Ex, К1i, К2i, Кiu, L,К2i, R,гр

**Сейчас:**
- одна спецификация на активный `variant_number`
- нет multi-select ЭР и partial-form
- full BOM в основном у сотрудника; у гостя — basic
- нет секционной структуры Трубы/Бочки/Общие как в §7

### P1 — лимиты и «гость» (NFR `§3.5`, `§3.10`, `§4.2`)

| PDF | Код (`backend/app/core/config.py`) | Статус |
|---|---|---|
| ≥ **500** объектов в проекте | `GUEST_MAX_OBJECTS_PER_PROJECT = 50` | ❌ |
| ≥ **5** вариантов ЭР | max **4** (СО1–4) | ❌ |
| Удаление временного проекта после **3 дней** неактивности | `GUEST_SESSION_TTL_MINUTES = 20` | ❌ |
| «Данные гостя **не** в БД» | Гость **хранится в PostgreSQL** до cleanup | ⚠️ продуктовое |
| Расчёт до 500 объектов ≤ **30 с** | Нет release-gate proof | ❌ / not proven |
| ≥ 50 проектов на зарегистрированного | Не сверялось как hard limit в этом аудите | ⚠️ |
| ≥ 10 000 записей в справочниках | Частично (каталоги JSON/БД) | ⚠️ |

**Противоречие в PDF:** текст говорит «гость не сохраняет в БД»,  
но серверные расчёты почти неизбежно держат session-state.  
Это **продуктовое решение**, не баг UI.

### P1 — stale / пересчёт после правки исходных (`§6.19`)

**Документ требует:**
- после изменения heat → в каждом ЭР объект **«Требуется перерасчёт»**
- кнопка **«Пересчитать»** на строке
- старые кабель/секции не считаются актуальными
- пересчёт **per-ЭР**, не «за всех разом молча»
- связанная спецификация становится неактуальной

**Сейчас:**
- batch «пересчитать всё»
- нет явной пометки «изменены исходные» + per-object «Пересчитать» по PDF
- stale в основном у **спецификации**, не у строки электрорасчёта в том виде

### P2 — формулы спецификации `§7.9–7.15`

В коде есть **`full_builder`** (коробки, комплекты, ленты, Ex, индикация и т.д.) — близко к разделу 7, но:

- завязано на **full mode / сотрудник**
