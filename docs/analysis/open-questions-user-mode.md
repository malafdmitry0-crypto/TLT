# Уточняющие вопросы по режиму «Пользователь» (без регистрации)

**Адресат:** Заказчик
**Тема:** Поведение приложения в режиме «Пользователь» (гостевой доступ)
**Дата:** 2026-04-15
**Статус:** Ожидает решения

## Почему мы задаём эти вопросы

В ходе доработки MVP мы упростили флоу для роли «Пользователь» до схемы
«зашёл → посчитал → ушёл»: один авто-проект, 20 минут неактивности → данные
удаляются. Это повышает приватность и снижает нагрузку на БД, но **расходится
с буквой ТЗ** (п. 4.2.1 — «создать новый проект»), где явно упоминается
возможность создания проектов пользователем.

Перед тем как зафиксировать поведение, нам нужны ваши решения по 5 пунктам.
Под каждым вопросом — варианты, последствия, и наша рекомендация.

**Как отвечать:** отметьте один из вариантов (или допишите свой) в поле
«Ответ» под каждым вопросом.

## Вопрос 1. Сколько проектов может быть у одного пользователя одновременно?

### Контекст

- **ТЗ (п. 4.2.1):** «Создать новый проект» перечислено как функция пользователя
  без указания лимита.
- **Сейчас в коде:** ровно 1 авто-проект, создаётся при входе. Второй —
  запрещён (HTTP 429).
- **Риск без лимита:** один недобросовестный клиент/бот может создать тысячи
  проектов и нагрузить БД.

### Варианты

| Вариант | Описание | Плюсы | Минусы |
|---|---|---|---|
| **A** | **1 проект** (текущая реализация) | Максимально простой UX «зашёл — посчитал — ушёл». Минимум мусора в БД | Неудобно, если нужно вести несколько объектов параллельно |
| **B** | **Без лимита** | Полное соответствие ТЗ, свобода пользователя | Риск DoS, захламление БД |
| **C** | **Фиксированный лимит N (3 / 5 / 10)** | Баланс: ТЗ соблюдено, DoS защищён | Нужно выбрать N |

### Наша рекомендация

**Вариант C, N = 5.** Достаточно для реальной работы, но ограничено настолько,
что бот-атака бессмысленна. Rate limit на создание сессий (10/IP/час) уже есть,
но он не защищает от создания проектов внутри одной сессии.

### Ответ заказчика

> ☐ A (1 проект) ☐ B (без лимита) ☐ C: N = ______ ☐ Свой вариант: ______________

## Вопрос 2. Видит ли пользователь список своих проектов?

### Контекст

Если у пользователя может быть >1 проекта (Варианты B/C по вопросу 1), нужно
дать ему способ переключаться между ними.

- **ТЗ (п. 4.3.5):** «Проводник проектов с поиском и фильтрацией» — явно
  указан как функция **сотрудника**.
- **Сейчас:** страница `/projects` доступна только сотрудникам; у пользователя
  в меню проектов скрыты кнопки «Новый» / «Открыть».

### Варианты

| Вариант | Описание |
|---|---|
| **A** | Отдельной страницы нет. В шапке — простой дропдаун со списком (максимум N — тот же, что в вопросе 1). Кнопки «Новый», «Удалить» внутри дропдауна |
| **B** | Полноценный `/projects` как у сотрудника, но без фильтра «Чужие/Мои» (он всегда видит только свои) |
| **C** | Только первый активный проект; второй/третий можно создать, но только один открыт в каждый момент времени (без явного переключения в UI — через API/скрипты) |

### Наша рекомендация

**Вариант A (дропдаун в шапке).** Соответствует духу ТЗ: «проводник проектов»
остаётся фичей сотрудника, но даём пользователю минимальный переключатель,
если он решил вести несколько проектов.

Если по вопросу 1 выбран Вариант A (1 проект) — этот вопрос не актуален,
никакого переключателя не нужно.

### Ответ заказчика

> ☐ A (дропдаун) ☐ B (полноценная страница) ☐ C (один активный) ☐ Не актуально (если 1 проект)

## Вопрос 3. Что происходит при повторном заходе на главную страницу?

### Контекст

Пользователь закрыл вкладку, через некоторое время (до истечения TTL 20 мин)
снова открыл главную страницу `/`.

- **Сейчас:** при нажатии «Начать без регистрации» всегда создаётся **новая**
  сессия и новый авто-проект. Старый остаётся «висеть» до cleanup.
- **В localStorage** остаётся `session_id` от предыдущего визита — он может
  быть ещё жив на бэке.

### Варианты

| Вариант | Поведение |
|---|---|
| **A** | Всегда новая сессия (текущая реализация). Старый проект теряется (чистится по TTL). Просто и предсказуемо |
| **B** | Если `session_id` из localStorage ещё жив — переиспользовать его, восстановить контекст. Иначе — новая сессия |
| **C** | Спросить пользователя: диалог «Продолжить прошлый сеанс?» / «Начать заново» |

### Наша рекомендация

**Вариант B.** UX «я случайно закрыл вкладку» — частый кейс. Терять данные без
предупреждения обидно. Восстановление через `session_id` — тривиально
(сессия всё равно живёт до TTL), и полностью совместимо с авто-очисткой.

### Ответ заказчика

> ☐ A (всегда новая) ☐ B (тихое восстановление) ☐ C (диалог) ☐ Свой вариант: _____

## Вопрос 4. Подтверждаете ли авто-очистку «20 мин неактивности → удаление»?

### Контекст

Это ваше изначальное требование: «Не позднее чем через 10 мин вся информация
должна чиститься». Мы реализовали как:
- `GUEST_SESSION_TTL_MINUTES = 20` (сессия неактивна 20 мин → помечается
  как протухшая)
- `GUEST_CLEANUP_INTERVAL_MINUTES = 10` (фоновая задача чистит раз в 10 мин)

Максимальное реальное время жизни данных после ухода: ~30 мин (в худшем
случае совпадения моментов).

### Варианты

| Вариант | TTL | Интервал cleanup | Макс. время жизни после ухода |
|---|---|---|---|
| **A** | 20 мин | 10 мин | ~30 мин (текущее) |
| **B** | 10 мин | 2 мин | ~12 мин (строгое соответствие вашему «не позднее 10 мин») |
| **C** | 5 мин | 1 мин | ~6 мин (агрессивная очистка) |

### Наша рекомендация

**Вариант A** остаётся, но мы хотим явно услышать «да, 30 мин приемлемо» или
«нет, нужно жёстче». Слишком агрессивная очистка (Вариант C) рискует удалить
данные пользователя, который отвлёкся на звонок.

### Ответ заказчика

> ☐ A (20/10) ☐ B (10/2) ☐ C (5/1) ☐ Другие значения: TTL = ___ мин, интервал = ___ мин

## Вопрос 5. Доступна ли функция «Дублировать проект» пользователю?

### Контекст

Мы реализовали копирование проекта — полезно при итерации вариантов обогрева.
Сейчас доступно **только сотруднику** (endpoint требует JWT).

- **ТЗ:** явно про дублирование ничего не сказано (это сверх-MVP фича).
- **Если Вариант 1.A (один проект):** функция логически не применима.
- **Если Варианты 1.B/C (несколько):** имеет смысл включить.

### Варианты

| Вариант | Описание |
|---|---|
| **A** | Только сотрудник (текущая реализация) |
| **B** | И пользователь тоже — но в пределах своего лимита N из вопроса 1 (если N>1) |

### Наша рекомендация

**Вариант A** — оставить как есть. Дублирование — это фича для итеративной
работы, которая ближе к профессиональному использованию сотрудника.
Пользователь в режиме «посчитал — ушёл» вряд ли будет итерировать варианты.

### Ответ заказчика

> ☐ A (только сотрудник) ☐ B (и пользователь тоже)

## Вопрос 6. Защита от DoS-атак через пользовательский режим

### Контекст

Пользовательский режим **анонимный**: достаточно нажать кнопку, чтобы получить
доступ к ресурсоёмким операциям. Это создаёт вектор атаки — злонамеренный
пользователь (или бот) может перегрузить приложение, создавая массу сессий,
проектов, объектов или запуская тяжёлые расчёты.

### Что атакующий может сделать сейчас

| Поверхность атаки | Защита сейчас | Риск |
|---|---|---|
| **Создание сессий** | Rate limit 10 сессий/IP/час (in-memory) | Средний: VPN/прокси даёт новые IP, in-memory лимитер сбрасывается при рестарте |
| **Создание проектов** | `GUEST_MAX_PROJECTS=1` (авто-проект) | Низкий (пока лимит = 1). Если поднять до N — вектор открывается |
| **Создание объектов** | `GUEST_MAX_OBJECTS_PER_PROJECT=50` | Средний: 50 труб × батч-расчёт кабеля = несколько секунд CPU |
| **Импорт Excel/CSV** | Нет явного лимита размера файла | **Высокий**: атакующий может загрузить файл на 10 МБ с 10 000 строк |
| **Пакетный электрорасчёт** (`/calc/electrical/batch`) | Нет rate limit | Средний: один запрос = N×подбор кабеля из каталога |
| **Обновление объекта** (триггерит автопересчёт) | Нет | Низкий: одиночная операция, но можно зацикливать |
| **Cleanup протухших сессий** | Раз в 10 мин | Если за 10 мин злоумышленник создал 10k сессий — БД распухает до момента очистки |

### Варианты усиления защиты

| Вариант | Что добавить | Стоимость реализации |
|---|---|---|
| **A. Минимум (статус-кво + точечные лимиты)** | 1. Лимит размера файла импорта (500 КБ, ~2000 строк). 2. Rate limit на `/calc/electrical/batch` (напр. 10/мин/сессия). 3. Лимит объектов на сессию суммарно (не на проект) | 0.5 дня |
| **B. Полноценный анти-DoS** | Всё из А + Redis-based rate limiter (переживает рестарт, работает на нескольких инстансах) + лимит запросов на любой endpoint по сессии (100/мин) + CAPTCHA на `/auth/guest` | 2–3 дня |
| **C. Жёсткий режим** | Всё из B + требовать подтверждение email/SMS для роли «Пользователь» | 5+ дней, по сути отменяет «анонимность»

**Вариант A**, как обязательный минимум. Это закроет самые
дешёвые векторы (файл 100 МБ, спам batch-расчётом) без архитектурных изменений.

**Вариант B** планировать как пост-MVP улучшение, если приложение будет
выставлено во внешнюю сеть. Для локального развёртывания в корпоративной
сети (как сейчас по ТЗ) — избыточно.

**Вариант C** применим только если бизнес готов отказаться от анонимного
доступа, что противоречит духу режима «Пользователь».
