# Анализ логики «Применить к одному» / «Применить ко всем»

Дата исходного аудита: 2026-05-08.
Актуализация: 2026-05-17.
Файлы: `HeatCalcPage.tsx`, `useHeatCalcMutations.ts`, `api/projects.ts`

> Статус документа: исторический аудит. Текущий actionbar уже не содержит
> отдельных кнопок «Применить к одному» / «Применить ко всем»: сохранение
> вынесено в одну кнопку «Сохранить», есть inline-draft controls, удаление и
> копирование выбранных строк. Выводы ниже полезны как контекст UX-решений, но
> не являются текущим описанием реализации.

## Текущее состояние

### Кнопки на панели действий

```
[＋ Добавить]  [Создать на основании]  [Применить к одному]  [Применить ко всем ⛔]  [Удалить]  |  [Сохранить изменения]  [Отменить]
```

| Кнопка | Действие | Статус |
|---|---|---|
| **Добавить** | Открывает форму новой трубы/резервуара | ✅ |
| **Создать на основании** | Копирует текущий объект с суффиксом «(копия)» | ✅ |
| **Применить к одному** | `getElementById('inline-object-save').click()` → `handleFinish` → `validateFields` → `handleWizardSubmit` | ⚠️ |
| **Применить ко всем** | **`<Button disabled>`** — заблокирована | ❌ |
| **Удалить** | `Popconfirm` → `remove.mutate` | ✅ |
| **Сохранить изменения** | То же, что «Применить к одному» | ⚠️ |
| **Отменить** | `closeWizard()` | ✅ |

## Проблемы

### 1. Дублирование действий

«Применить к одному» и «Сохранить изменения» — **две кнопки, один обработчик**:

```tsx
// Применить к одному
<Button disabled={!wizardState}
  onClick={() => document.getElementById('inline-object-save')?.click()}>
  Применить к одному
</Button>

// Сохранить изменения
<Button className="save" disabled={!wizardState}
  onClick={() => document.getElementById('inline-object-save')?.click()}>
  Сохранить изменения
</Button>
```

Обе кликают скрытый `<Button id="inline-object-save">`, который вызывает `handleFinish`.
Разница только в CSS-классе `save`.

**Следствие:** пользователь видит 6 кнопок в ряд, из которых 2 делают одно и то же.
Это раздувает actionbar и сбивает с толку.

### 2. «Применить ко всем» — заглушка

```tsx
<Tooltip title="Массовое применение будет доступно после согласования правил переноса параметров">
  <Button disabled>Применить ко всем</Button>
</Tooltip>
```

Кнопка **навсегда заблокирована**. Тултип ссылается на нерешённый продуктовый вопрос:
какие поля формы можно безопасно перенести на другие объекты, а какие — нет.

**Необходимые продуктовые решения (не код):**

| Группа полей | Можно применять ко всем? | Пример |
|---|---|---|
| Изоляция (материал, толщина) | ✅ Да | Все трубы в проекте часто с одинаковой изоляцией |
| T° среды, ветер, климат | ✅ Да | Единый климат для площадки |
| Kзап, α внеш | ✅ Да | Общие коэффициенты |
| Геометрия (Ø, длина, форма) | ❌ Нет | У каждого объекта своя |
| Арматура (задвижки, фланцы) | ❌ Нет | У каждого объекта своя |
| Размещение (outdoor/underground) | ⚠️ Условно | Может совпадать для группы |

### 3. Чекбоксы таблицы не связаны с применением

Таблица имеет `rowSelection` с `selectedRowKeys`, но выделение используется **только** для:
- Отображения счётчика «Выбрано: N»
- Копирования через Ctrl+C

Нет логики «применить к выбранным». При реализации «Применить ко всем» нужно решить:
- Применять ко **всем** объектам проекта?
- Или только к **выделенным** чекбоксами?

### 4. Нет бэкенд-эндпоинта для пакетного обновления

API поддерживает только пообъектное обновление:

```
PUT /api/v1/projects/{pid}/objects/{oid}   ← один объект
```

Нет эндпоинта вида:
```
PUT /api/v1/projects/{pid}/objects/batch   ← несколько объектов за один запрос
```

При реализации «Применить ко всем» на 50 объектах фронту пришлось бы отправить 50 последовательных PUT-запросов. Это медленно и неатомарно (часть объектов обновится, часть — нет при ошибке).

### 5. Неоднозначное поведение в разных режимах

`handleWizardSubmit` меняет поведение в зависимости от наличия `editingObject`:

| Режим | `wizardState` | Что делает «Применить к одному» |
|---|---|---|
| Новый объект | `{ type: 'pipe' }` | `add.mutate()` — создаёт объект |
| Редактирование | `{ type: 'pipe', editingObject: {...} }` | `edit.mutate()` — обновляет объект |

Лейбл кнопки **не меняется**. Пользователь, редактирующий существующий объект, видит «Применить к одному» — но объект уже существует. Ожидаемая надпись: «Сохранить изменения».

### 6. Нет индикатора «грязной» формы

Пользователь меняет поля в форме, но не видит, сохранены ли изменения:
- Нет маркера `*` в заголовке
- Нет `unsaved changes` предупреждения при клике на другую строку
- Нет визуального отличия между «форма заполнена и сохранена» и «форма изменена, но не сохранена»

Единственный признак — кнопка «Сохранить изменения» не disabled, если `wizardState` активен. Но это бинарный индикатор (форма открыта / закрыта), а не признак изменений.

### 7. Скрытая кнопка — хрупкий паттерн

Обе кнопки используют `document.getElementById('inline-object-save')?.click()` для триггера отправки формы. Это:
- Привязывает логику к DOM-элементу вне React-дерева
- Ломается, если ID меняется или элемент не отрендерен
- Обходит нормальный поток событий React

Правильный подход: вызов `form.submit()` через ref формы (`formRef.current?.submit()`).

### 8. Нет защиты от потери изменений при переключении строк

Клик по строке в таблице (в режиме «Исходные данные») вызывает `openEditWizard(record)`. Если форма уже открыта с несохранёнными изменениями — они теряются без предупреждения.

## Сравнение с аналогами

| Поведение | HeatCalc | TraceCalc Pro | CompuTrace |
|---|---|---|---|
| Пакетное изменение параметров | ❌ (disabled) | ✅ (multi-select → apply) | ✅ (circuit defaults → apply to segments) |
| Индикатор несохранённых изменений | ❌ | ✅ (диалог при закрытии) | ⚠️ (частично) |
| Выделение + применение к выбранным | ❌ (только Ctrl+C) | ✅ | ✅ |
| Отмена изменений (undo) | ❌ | ❌ | ❌ |
| Копирование объекта как нового | ✅ «Создать на основании» | ✅ | ✅ |
| Массовый импорт | ✅ XLSX/CSV | ❌ | ⚠️ |

**Вывод:** конкуренты реализуют batch-применение через выделение строк и общий диалог «какие поля копировать». HeatCalc имеет лучший массовый импорт (Excel/CSV), но не имеет оперативного batch-применения. Это разные сценарии: импорт — для начальной загрузки, batch-apply — для изменения существующих объектов в проекте.

## Рекомендации

### P0 — Убрать дублирование

Оставить **одну** кнопку, меняющую лейбл по контексту:

| Режим | Лейбл |
|---|---|
| Новый объект | «Добавить объект» |
| Редактирование | «Сохранить изменения» |

Текущие «Применить к одному» и «Сохранить изменения» объединить в одну.

### P1 — Реализовать «Применить к выбранным»

1. Использовать существующий `selectedRowKeys` для определения целевых объектов.
2. При клике показывать модалку с чекбоксами: «Какие поля скопировать?»
   - [x] Изоляция (материал, толщина, слои)
   - [x] Температура среды
   - [x] Скорость ветра
   - [x] Климатический город
   - [x] Kзап
   - [ ] Геометрия (⛔ заблокировано)
3. Добавить бэкенд-эндпоинт `PUT /projects/{pid}/objects/batch` с полем `{object_ids: [...], fields: {...}}`.
4. Или, как временное решение: отправлять N отдельных `PUT /objects/{oid}` запросов параллельно через `Promise.all`.

### P2 — Добавить защиту от потери изменений

При клике на другую строку с несохранённой формой показывать `Modal.confirm`:
«У вас есть несохранённые изменения. Сохранить перед переходом?»

### P3 — Заменить скрытую кнопку на form ref

Вместо `document.getElementById('inline-object-save')?.click()` использовать `formRef.current?.submit()`.

### P3 — Добавить индикатор dirty

Показывать `*` в заголовке формы при наличии несохранённых изменений. Реализовать через `Form.useWatch` + сравнение с `initialParams`.
