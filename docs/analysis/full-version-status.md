## II. Коэффициенты — детальный статус

### Что реализовано

**Таблица `correction_coefficients` + админка `/admin/coefficients`:**

| Ключ | Значение | Реально применяется? |
|---|---|:---:|
| `safety_factor` | 1.1 | ✅ **Да** — множитель K для Q (трубы + резервуары) |
| `wind_factor` | 1.0 | ✅ **Да, частично** — множитель `α_внеш` для надземных труб после `α = 11.6 + 7√v`; для резервуаров не применяется |
| `location_indoor` | 0.9 | ✅ **Да** — множитель итоговых `Q` для труб и резервуаров с `location="indoor"` через `location_key()` |
| `location_outdoor` | 1.0 | ✅ **Да** — множитель итоговых `Q` для труб и резервуаров с `location="outdoor"` через `location_key()`; default 1.0 не меняет результат |

**Архитектурно правильно:**
- Чистые формулы (`pipe.py`, `tank.py`) принимают `coefficients: dict[str, float]` параметром.
- `CalculationService.get_coefficients` подгружает текущие значения из БД.
- `apply_coefficients()` в `formulas/heat_loss/common.py` применяет мультипликативно по списку ключей.
- Покрыто тестами: `test_calculation_service_unit.py` + property-based на устойчивость.

### Чего нет

**Из `coefficients.MD` (физические параметры) — захардкожено, не редактируется:**

| Параметр | Где сейчас | Что нужно для «Полной версии» |
|---|---|---|
| `lambda_iz_i(T)` — температурозависимая теплопроводность изоляции | Реализовано через `lambda(tm)` из ТНП, конкретные коды материалов и `insulation_temperature_basis` | Поддерживать справочник конкретными материалами/плотностями; generic названия остаются только draft/import warning |
| `lambda_tp` — теплопроводность стенки трубы | Поддержан режим материала трубы / ручной λ | Не подставлять скрытое значение без материала или ручного режима |
| `lambda_gr` — теплопроводность грунта | Есть справочник грунта и расчёт подземного размещения | Уточнить финальные UX-сценарии выбора/override |
| `L_ekv` — эквивалентная длина локальных элементов (фланцы, арматура) | Поле и формула `L_eff = L + N × L_ekv` реализованы | Если нужны разные `L_ekv` по типам фиттингов, требуется отдельный справочник |
| `alpha_vnesh` диапазон 7–52 Вт/(м²·К) | Считается через ветер / ручной ввод | Уточнить, нужен ли справочник по типу поверхности |

**Со стороны управления:**

- ✅ CRUD коэффициентов через UI
- ❌ **Audit log изменений** — в БД хранится только текущее значение, истории нет
  (UC-3 из `question-missing-scenarios.md` — **критично для ГОСТ-аккредитации**)
- ❌ **Привязка снапшота к проекту** — нельзя воспроизвести старый расчёт после изменения коэффициентов

### Приоритеты по коэффициентам

**P0 (закрыть мелкие баги, 0.5 дня):**
- Привести БД к консистентному виду: `wind_factor` уже влияет на надземные трубы, а `location_*` нужно либо подключить по утверждённому правилу, либо убрать/пометить как legacy. Сейчас админ может менять `location_*`, но это ни на что не влияет — путаница для пользователя.

**P1 (для аккредитации, ~3 дня):**
- **Audit log** изменений коэффициентов (`coefficient_history` + endpoint + UI «История»). **1 день.**
- **Снапшот коэффициентов к проекту/расчёту** — JSON-поле `snapshot_coefficients` в `ProjectObject.results` или отдельная таблица, фиксируется в момент расчёта. **2 дня.**

**P2 (Полная версия, ~2 дня + ожидание формул):**
- Production-настройка справочника изоляции и импорта: реальные конкретные материалы/плотности должны поддерживаться в JSON/БД без возврата к generic кодам.
- При необходимости: детализированный справочник `L_ekv` по типам локальных элементов.

## III. Рекомендации по следующим шагам

Три пути вперёд (выбор стратегии за заказчиком):

### A. Закрыть блокеры «Полной версии»
**Зависит от заказчика.** Пнуть по:
- Методики MI и skin; для ТТ Р1/ТТ Р3 остаются только production-override политика для `p3` и коммерческие критерии
- Формулы для pump / platform / other
- Финальную сверку всех новых поставок ТНП/СРС
- Решению по варианту шифрования (А/Б/С)

### B. Закрыть quality-of-life (без ТЗ-блокеров) — ~15 дней
- Inline-edit таблиц (3 дня)
- Audit log коэффициентов (1 день) — **критично для аккредитации**
- Снапшот коэффициентов к расчётам (2 дня)
- Архивирование проектов (1 день)
- Split-view СО1..СО4 (2 дня)

- Копирование СО1→СО2 (0.5 дня)

- Резерв на полировку

### C. Подготовка к прод-деплою — ~5 дней
- Обфускация frontend-бандла (1 день)
- Docker Secrets для конфигов (1 день)
- Справочник кодов ошибок (0.5 дня)
