# SRS · UI-схемы и сценарии в действии

## 1. Назначение папки

В этой папке каждый сценарий использования (Use Case) из SRS
«отыгран» текстом и UI-схемой: что видит пользователь на экране на
каждом шаге сценария. Файлы предназначены для демонстрации
Заказчику и для согласования визуального и функционального поведения
системы перед разработкой.

## 2. Структура папки

UI-схемы **разделены по ролям** на две независимые подпапки. В
каждой подпапке повторяются все сценарии, применимые к
соответствующей роли, с учётом её специфики.

```
ui/
├── README.md                 (этот файл)
├── guest/                    UI-схемы и сценарии для роли «Гость»
│   ├── README.md
│   ├── 01-screen-main.md
│   ├── 02-screen-workspace-heatcalc.md
│   ├── 03-screen-workspace-electrical.md
│   ├── 04-screen-workspace-specification.md
│   ├── 05-screen-workspace-report.md
│   ├── 06-csv-flows.md
│   └── 07-session-lifecycle.md
└── employee/                 UI-схемы и сценарии для роли «Сотрудник»
    ├── README.md
    ├── 01-screen-main.md
    ├── 02-screen-projects-explorer.md
    ├── 03-screen-workspace-heatcalc.md
    ├── 04-screen-workspace-electrical.md
    ├── 05-screen-workspace-specification.md
    ├── 06-screen-workspace-report.md
    └── 07-csv-flows.md
```

### Что лежит где

**`guest/`** — все 22 сценария, применимые к роли «Гость»: вход
без регистрации, работа с одним активным проектом (создание с
заменой / удаление с автосозданием нового), ввод объектов и расчёт
теплопотерь, электрорасчёт, спецификация, предпросмотр и печать
отчёта (без экспорта в файлы), экспорт / импорт CSV (импорт с
заменой текущего), фоновое завершение сессии по неактивности.

**`employee/`** — все 24 сценария, применимые к роли «Сотрудник»:
авторизация, проводник проектов с поиском и фильтрами, полный
жизненный цикл нескольких проектов (создание без замены,
редактирование свойств, удаление, копирование, импорт CSV без
замены), просмотр и редактирование чужих проектов, тот же
расчётный контур с теми же экранами, что и у Гостя, плюс
**экспорт отчёта в файлы PDF / DOCX / XLSX**.

## 3. Общие сценарии расчётного контура

Большая часть сценариев (заполнение общих первичных данных, ввод
объектов, расчёт теплопотерь, электрорасчёт, спецификация,
предпросмотр отчёта) **общие для обеих ролей**. Они отыграны в
обеих папках с учётом ролевой специфики:

- В `guest/` — в контексте единственного активного проекта.
- В `employee/` — в контексте одного из множества проектов,
  открытого из проводника (с указанием владельца, если это чужой
  проект).

## 4. Условные обозначения для UI-схем

Все макеты выполнены в монопространственном тексте Markdown
(в `code`-блоках) и используют единый набор символов:

```
┌──────────┐  ── рамка экрана / модального окна / блока
│ Текст    │  
└──────────┘

[ Кнопка ]   ── активная кнопка
[ ━━━━━ ]   ── неактивная кнопка
( ) Radio    ── переключатель (выбран — (●))
[ ] Checkbox ── флажок (выбран — [✓])
▼            ── выпадающий список (Select)
🔍           ── поле поиска
ⓘ            ── активная подсказка
●            ── маркер активного шага в навигации
○            ── маркер неактивного шага

Поле:        ── обозначение лейбла поля формы
[__________] ── ввод текста / числа
[••••••••]   ── ввод пароля (звёздочки)
ⓘ ...        ── активная подсказка под/рядом с полем
⚠ Ошибка     ── inline-ошибка валидации (красная подсветка)
```

## 5. Обозначения применимости

В шапке каждого UC указано:

- **Роль:** Гость / Сотрудник.
- **US:** связанная пользовательская история (документ 01).
- **FR / NFR:** связанные функциональные / нефункциональные требования (документ 05).
- **VAL:** связанные правила валидации (документ 04).

## 6. Связь с остальным комплектом SRS

Этот комплект UI-схем — **иллюстративный**. Он не заменяет, а
дополняет основные документы:

1. Пользовательские истории (`01-user-stories.md`) — что и зачем делает пользователь.
2. Сценарии использования (`02-use-cases.md`) — формальное описание шагов.
3. Перечень элементов (`03-elements-list.md`) — формальный реестр всех элементов UI.
4. Валидация (`04-validation.md`) — правила проверки.
5. Функциональные / нефункциональные требования (`05-functional-nonfunctional.md`).
6. Программа испытаний (`06-test-program.md`).
7. Требования к отчёту (`07-report-requirements.md`).

При несогласованности между UI-схемой и основным документом
**преимущество имеет основной документ**.
