# Манифест расположения элементов верхней формы HeatCalc

**Статус:** целевой UI-контракт для согласования и последующей реализации.
**Область:** `HeatCalcObjectFieldsPanel`, верхний блок параметров объекта над
таблицей слоёв изоляции.
**Платформа:** desktop-only, CSS viewport от `1000px`.

Интерактивный макет:
[`heatcalc-object-fields-grid.mockup.html`](./heatcalc-object-fields-grid.mockup.html).

Документ определяет информационную и визуальную иерархию формы. Он не разрешает
самостоятельно менять названия полей, units, validation, доступность,
keyboard-порядок или бизнес-условия.

## Манифест

1. **Сначала смысл, потом геометрия.** Поле получает постоянную семантическую
   группу до назначения строки и координат.
2. **Длинные поля идут первыми.** Первая колонка содержит только text, select и
   reference picker. Числовые поля не вклиниваются между ними.
3. **Малые поля находятся рядом с малыми.** Вторая и третья колонки содержат
   только numeric controls.
4. **Ширина следует validation-контракту столбца.** Длинный control получает
   fluid-трек `5fr`. Все numeric controls одного столбца равны по ширине,
   вычисленной по самому широкому допустимому значению этого столбца.
5. **Свободное место не является зазором.** Между label и control всегда
   `8px`. Лишняя ширина отдаётся длинному control, а не раздвигает пару.
6. **Края важнее отдельных строк.** Labels одной группы начинаются на общей
   вертикали; controls имеют общие левую и правую вертикали.
7. **Скрытие не меняет смысл.** Условное поле исчезает только из своей группы.
   Оно не переносит соседей в другую колонку.
8. **Пустых дыр после hidden нет.** Оставшиеся поля поднимаются внутри своей
   группы, сохраняя относительный порядок.
9. **Значение не управляет layout.** Длинный текст сокращается внутри control;
   максимальное число и unit обязаны помещаться в заранее рассчитанный размер.
10. **Сетка одна.** Форма, диагностическая линейка и overlay-направляющие
    используют одну фактическую координатную систему.
11. **Required не съедает optional.** Optional control имеет видимую серую
    рамку со всех сторон; required заменяет только левую сторону акцентом.
12. **DOM следует чтению.** В production DOM-, visual- и keyboard-порядок
    внутри каждой группы должны совпадать.

Если предлагаемое изменение нарушает хотя бы один пункт, оно не считается
локальной косметикой и требует пересмотра этого контракта.

## Рабочая область

На широком desktop HeatCalc занимает `40%`, соседняя область алгоритма выбора
кабеля — `60%`.

```text
workspace
├─ HeatCalc: minmax(780px, 2fr)
│  ├─ wide group: 1fr
│  │  └─ label 96px | gap 8px | text/select/reference 5fr
│  ├─ pipe numeric group: max-content
│  │  └─ label 88px | gap 8px | control 96px
│  └─ environment numeric group: max-content
│     └─ label 120px | gap 8px | control 92px
└─ cable: minmax(300px, 3fr)
```

| Параметр | Контракт |
|---|---:|
| HeatCalc / cable | `40% / 60%` на широком workspace |
| Количество семантических групп | `3` |
| Wide label | `96px` |
| Wide control | fluid `5fr` |
| Pipe numeric control вместе с unit | `96px` |
| Environment numeric control вместе с unit | `92px` |
| Label → control | `8px` |
| Между группами | `10px` |
| Высота control | `36px` |
| Вертикальный шаг между полями | `4px` |
| Максимум строк label | `3` |

Нормативная схема:

```css
.workspace {
  grid-template-columns: minmax(780px, 2fr) minmax(300px, 3fr);
}

.heat-fields {
  grid-template-columns: minmax(0, 1fr) max-content max-content;
  column-gap: 10px;
}

.wide-field {
  grid-template-columns: 96px 8px minmax(0, 5fr);
}

.pipe-numeric-field {
  grid-template-columns: 88px 8px 96px;
}

.environment-numeric-field {
  grid-template-columns: 120px 8px 92px;
}
```

Это геометрический контракт, а не готовый набор business-селекторов.
Production-реализация остаётся у owner-root секции и использует
`CompactFieldGrid`.

## Реестр всех пользовательских полей

Группа и порядок поля постоянны во всех режимах.

| Группа | Порядок | Поле | Тип | Видимость |
|---|---:|---|---|---|
| Wide | 1 | Наименование | text | всегда |
| Wide | 2 | Материал трубы | reference | всегда |
| Wide | 3 | Размещение | select | всегда |
| Wide | 4 | Тип грунта | reference | `placement=underground` |
| Wide | 5 | Климат | reference | всегда |
| Wide | 6 | Режим температуры изоляции (tm) | select | всегда |
| Pipe numeric | 1 | Наружный диаметр | number + `мм` | всегда |
| Pipe numeric | 2 | Длина трубопровода | number + `м` | всегда |
| Pipe numeric | 3 | Толщина стенки | number + `мм` | всегда |
| Pipe numeric | 4 | Количество локальных элементов | number + `шт` | всегда |
| Pipe numeric | 5 | Теплопроводность трубы λ | number + `Вт/мК` | `material=other` |
| Environment numeric | 1 | Температура окружающей среды | number + `°C` | всегда |
| Environment numeric | 2 | Требуемая температура объекта | number + `°C` | всегда |
| Environment numeric | 3 | Скорость ветра | number + `м/с` | `placement=outdoor` |
| Environment numeric | 4 | Глубина заложения | number + `м` | `placement=underground` |
| Environment numeric | 5 | Теплопроводность грунта | number + `Вт/мК` | `placement=underground` |

### Базовое состояние

Для `placement=underground` и стандартного материала:

| Строка | Wide | Pipe numeric | Environment numeric |
|---:|---|---|---|
| 1 | Наименование | Наружный диаметр | Температура окружающей среды |
| 2 | Материал трубы | Длина трубопровода | Требуемая температура объекта |
| 3 | Размещение | Толщина стенки | Глубина заложения |
| 4 | Тип грунта | Количество локальных элементов | Теплопроводность грунта |
| 5 | Климат | — | — |
| 6 | Режим температуры изоляции (tm) | — | — |

Чтение формы идёт слева направо по группам: сначала все длинные поля, затем
геометрия трубы, затем температуры и условия среды.

## Алгоритм размещения

Для каждого render:

1. Определить видимые поля по business state.
2. Не менять назначенную полю семантическую группу.
3. Отсортировать видимые поля по постоянному `order` внутри группы.
4. Удалить hidden-поля из layout и accessibility tree.
5. Сжать строки независимо внутри каждой группы.
6. Не переносить поле для заполнения визуально свободной ячейки соседней
   группы.
7. Пересчитать диагностическую линейку и overlay по фактическим трекам.

Следствие: в разных режимах количество строк в колонках может отличаться. Это
нормальная цена устойчивой информационной архитектуры, а не дефект, который
надо заполнять переносом полей.

## Условные режимы

| Состояние | Скрыто | Показано |
|---|---|---|
| `placement=outdoor` | Тип грунта, глубина заложения, λ грунта | Скорость ветра |
| `placement=indoor` | Тип грунта, глубина заложения, λ грунта, скорость ветра | постоянные поля |
| `placement=underground` | Скорость ветра | Тип грунта, глубина заложения, λ грунта |
| `material=standard` | Ручная λ трубы | выбранный справочный материал |
| `material=other` | — | Ручная λ трубы |

Диагностический режим `Все поля` одновременно показывает несовместимые
условные ветки. Он существует только для проверки композиции и не является
production-состоянием. Макет по умолчанию открывается в
`underground + standard`.

### Всегда скрытые служебные поля

Следующие значения участвуют только в round-trip данных и никогда не занимают
место в layout:

- `climate_city`;
- `climate_region`;
- `climate_temperature_basis`;
- `ambient_temperature_source`;
- `wind_speed_source`;
- `safety_factor_source`;
- `max_ambient_temperature`;
- `max_process_temperature`;
- `zone_classification`.

## Numeric-контракт

Все numeric controls внутри одного столбца имеют одинаковую внешнюю ширину.
Ширина вычисляется один раз по полю столбца с самым широким максимальным
отображением и применяется ко всем его полям, включая hidden/conditional.
Между столбцами ширина может различаться.

| Поле | Допустимый диапазон | Проверочное максимальное отображение | Unit |
|---|---:|---:|---:|
| Наружный диаметр | `10,8…3000` | `3000` | `мм` |
| Длина трубопровода | `0,5…200000` | `200000` | `м` |
| Толщина стенки | `0,1…40` | `40` | `мм` |
| Количество локальных элементов | `0…100` | `100` | `шт` |
| λ трубы | `0,001…400` | `400` | `Вт/мК` |
| Температура окружающей среды | `−70…70` | `−70` | `°C` |
| Требуемая температура объекта | `−90…600` | `600` | `°C` |
| Скорость ветра | `0…20,0` | `20` | `м/с` |
| Глубина заложения | `0…200,00` | `200` | `м` |
| Теплопроводность грунта | `0,50…3,00` | `3,00` | `Вт/мК` |

Источник диапазонов и точности:
`frontend/src/config/heatcalc-fields.default.json`.

Результат расчёта:

- Pipe numeric: ширину задаёт `200000 м` → общий control `96px`;
- Environment numeric: ширину задаёт `3,00 Вт/мК` → общий control `92px`.

В ширину входят value, unit, разделитель, border и внутренние отступы.
Acceptance проверяет фактический rendered overflow максимальных значений,
а не только арифметику `ch`. Переключение режима не меняет ширину столбца.

## Wide-контракт

Общий label-трек равен `96px`. Значение получено округлением вверх natural
width самого длинного однострочного фрагмента: `Наименование` занимает около
`90px` в текущей метрике.

- label может занимать до трёх строк;
- после label всегда идут `8px`;
- control заполняет оставшийся `5fr`;
- все wide controls имеют общие левую и правую вертикали;
- длинное значение обрезается внутри control и не меняет треки;
- reference icon и select chevron входят в control, а не создают новый трек.

## Рамки, required и ошибки

- Optional control имеет серый `1px` border со всех четырёх сторон.
- Required control заменяет левую сторону на акцентный `3px` border.
- Прозрачный placeholder-border запрещён: он визуально съедает левый край
  optional control.
- Изменение толщины required-border не меняет внешнюю ширину control.
- Hint и validation message увеличивают высоту строки и не перекрывают
  следующую строку.
- Error state меняет chrome, но не координаты поля.

## Диагностическая сетка

Верхняя линейка не вычисляет собственный `max-content`. После render, смены
режима и resize она получает фактический `grid-template-columns` формы.

Overlay `Показать сетку` рисует двенадцать реальных вертикалей:

- `label-left`;
- `label-right`;
- `control-left`;
- `control-right`;

для каждой из трёх семантических групп.

Направляющая строится по DOM-геометрии representative field. Она считается
корректной, только если её координаты пиксель-в-пиксель совпадают с краями
видимых полей. Диагностическая сетка не входит в production UI.

## Таблица слоёв

Таблица слоёв изоляции не участвует в сетке верхних полей и занимает всю
ширину HeatCalc-контейнера. У неё отдельная пятиколоночная grid-система:

```css
grid-template-columns:
  72px
  minmax(216px, 1fr)
  154px
  124px
  minmax(190px, 1fr);
```

Толщина слоя использует control `128px` внутри собственной колонки `154px`.
Она не наследует numeric-треки верхней формы. Изменение верхней формы не
должно сдвигать заголовки или строки таблицы.

## Поддерживаемая ширина

- Product contract начинается с CSS viewport `1000px`.
- На широком workspace сохраняется отношение HeatCalc/cable `40% / 60%`.
- Минимальная содержательная ширина HeatCalc — `780px`; она имеет приоритет
  над точными `40%`, чтобы labels и units не обрезались.
- При `1000…1400px` макет может скрыть соседнюю демонстрационную область и
  отдать HeatCalc доступную ширину.
- Mobile layout, отдельный одноколоночный reflow и правила для `<1000px` не
  проектируются.

Источник product contract:
[`viewport-policy.md`](./viewport-policy.md).

## Инварианты production-реализации

1. Внешняя grid-система владеет отношением HeatCalc/cable.
2. Семантическая группа и order поля задаются данными, а не цепочкой
   business-классов в CSS.
3. DOM order внутри группы равен visual и keyboard order.
4. Все поля группы используют общие label/control tracks.
5. Runtime state только показывает или скрывает поле внутри назначенной
   группы.
6. Layout не зависит от внутренних `.ant-*` узлов.
7. Используется существующий `CompactFieldGrid`; второй form-grid kit не
   создаётся.
8. Заменённый `max-content`/вложенный coordinate path удаляется в том же
   implementation slice.

## Acceptance будущего UI-slice

Проверяются состояния:

- `outdoor + standard`;
- `indoor + standard`;
- `underground + standard`;
- `material=other`;
- диагностический atlas всех условных полей;
- максимальные numeric values;
- длинные select/reference values;
- required, optional и validation error;
- labels в одну, две и три строки.

Проверяются viewport:

- `1000×768`;
- `1280×800`;
- `1366×768`;
- широкий desktop, на котором HeatCalc занимает `40%`.

Обязательные geometry assertions:

- фактические треки линейки равны трекам формы;
- двенадцать overlay-направляющих совпадают с DOM-краями;
- wide label = `96px`;
- label/control gap = `8px`;
- pipe numeric control = `96px`;
- environment numeric control = `92px`;
- control height = `36px`;
- скрытые поля не оставляют дыр и не мигрируют между группами;
- нет clipping, overlap, неожиданного переноса unit и page-level horizontal
  overflow;
- tab order повторяет документированный DOM-order.

Browser proof также включает console errors/warnings и failed network
requests. Незапущенная проверка не считается зелёной.
