## Часть 1. Нужно ли переписывать расчётные модули на Go?

### 1.1 Что считаем сегодня

Расчётное ядро — четыре файла чистого Python:

| Модуль | Что делает | Время (1 объект) | Характер нагрузки |
|---|---|---|---|
| `heat_loss/pipe.py` | Многослойная цилиндрическая стенка, 1–3 слоя, грунт, ветер, λ(T) | 2–8 мс | CPU: арифметика + `math.log` |
| `heat_loss/tank.py` | Плоская стенка, цилиндр/параллелепипед/шар, подземная часть | 1–5 мс | CPU: арифметика |
| `electrical/self_regulating.py` | Подбор ТЛТ/ТТН/ТТВ/ТТХ по мощности и температуре | 0.5–2 мс | CPU: перебор 10–14 марок |
| `electrical/resistive.py` | Расчёт ТТ Р1/Р3: длина, мощность, ток, навив | 1–3 мс | CPU: арифметика |

Для 50 объектов суммарно: **50 × (2–8 мс) = 100–400 мс** на теплопотери +
**50 × (0.5–3 мс) × 4 CO = 100–600 мс** на электрорасчёт.  
Итого: **200–1000 мс** чистого CPU на проект из 50 объектов.

### 1.2 Где реально болит

Проведём мысленный эксперимент: пользователь нажимает «Добавить объект» →
что происходит?

| Шаг | Операция | Время |
|---|---|---|
| 1 | Валидация Pydantic | 0.1 мс |
| 2 | **Расчёт теплопотерь (Python)** | **2–8 мс** ← CPU |
| 3 | **Сохранение в БД (INSERT)** | **3–10 мс** ← I/O |
| 4 | Сериализация ответа JSON | 0.5 мс |
| 5 | Передача по сети | 1–5 мс |
| **Итого** | | **7–24 мс** |

**Вывод:** расчёт занимает 2–8 мс из 7–24 мс — то есть **25–35% времени
запроса**. Остальное — это БД, сеть, сериализация. Ускорение расчёта в 10 раз
(Go) сократит общее время с 24 мс до 22 мс — пользователь не заметит разницы.

### 1.3 Когда Python реально становится узким местом

Python станет bottleneck'ом только при реализации **тяжёлых вычислительных фич**
из `proposed-advanced-features.md`:

| Фича | Вычислительная сложность | Время в Python | Время в Go |
|---|---|---|---|
| F-01 Теплогидравлика (50 сегментов × итерации) | O(N × M), N=50, M=5 итераций | 50–150 мс | 3–8 мс |
| F-02 Нестационарный расчёт (Crank-Nicolson, 200×200 матрица × 1000 шагов) | O(T × N³) без sparse, O(T × N) с sparse | 2–8 **секунд** | 80–300 мс |
| F-03 NSGA-II оптимизатор (100 объектов × 30 марок × 100 поколений) | O(G × P × O), G=100, P=100, O=3000 | 30–90 **секунд** | 1–4 секунды |

Для **текущих** формул (стационарные теплопотери, подбор кабеля перебором) —
Python более чем достаточен. Для **будущих** (F-01, F-02, F-03) — Python без
numpy/scipy станет bottleneck'ом; с numpy/scipy — погранично; Go даст
радикальное ускорение.

### 1.4 Сравнение вариантов

| Критерий | Оставить Python | Python + numpy/scipy | Вынести в Go-микросервис | Переписать всё на Go |
|---|---|---|---|---|
| Скорость (текущие формулы) | 2–8 мс ✅ | 1–4 мс ✅ | 0.2–0.5 мс ✅ | 0.2–0.5 мс ✅ |
| Скорость (F-02 transient) | 2–8 сек ❌ | 200–800 мс ⚠️ | 80–300 мс ✅ | 80–300 мс ✅ |
| Скорость (F-03 NSGA-II) | 30–90 сек ❌ | 3–10 сек ⚠️ | 1–4 сек ✅ | 1–4 сек ✅ |
| Сложность разработки | — | +1 день (добавить import numpy) | +3–5 спринтов (новый сервис, API, деплой) | +15–20 спринтов (переписать всё) |
| Поддержка | 1 язык ✅ | 1 язык ✅ | 2 языка ⚠️ | 2 языка ⚠️ |
| Деплой | 1 контейнер ✅ | 1 контейнер ✅ | 2 контейнера ⚠️ | 2 контейнера ⚠️ |
| Отладка формул инженером-теплотехником | Легко (Python читаем) ✅ | Легко ✅ | Сложно (Go) ❌ | Сложно (Go) ❌ |
| Тестирование | pytest (799 тестов) ✅ | pytest ✅ | pytest + go test ⚠️ | go test (переписать 799 тестов) ❌ |

### 1.5 Рекомендация

**Не переписывать на Go сейчас. Использовать поэтапный подход:**

```
Этап 0 (сегодня):
├── Оставить текущие формулы на Python
├── O-01: вынести в run_in_executor (не блокировать event loop)
└── O-02: закэшировать справочники в памяти

Этап 1 (при реализации F-01 теплогидравлики):
├── Использовать Python + numpy. F-01 — это итерации с простой арифметикой.
│   numpy ускорит векторизованные операции в 5–10× без смены языка.
│   Время: 50–150 мс → 10–30 мс. Достаточно.
└── Выполнять через ProcessPoolExecutor (обход GIL для batch)

Этап 2 (при реализации F-02 нестационарного расчёта):
├── Python + scipy.sparse для Crank-Nicolson. Разреженные матрицы —
│   это C/Fortran под капотом. Время: 2–8 сек → 200–800 мс.
└── Если 800 мс всё ещё много (пользователь жмёт кнопку и ждёт) —
    вынести в Go-микросервис. Формулы F-02 стабильны, редкие правки,
    идеальный кандидат для компилируемого языка.

Этап 3 (при реализации F-03 оптимизатора):
├── НЕ писать NSGA-II на чистом Python — это гарантированные 30–90 сек.
├── Сразу Go (или Rust). Генетический алгоритм — это CPU-bound loops,
│   GIL убьёт производительность. Go с горутинами: популяция 100 особей
│   × 3000 генов — параллельная оценка фитнеса даст линейное ускорение.
└── Альтернатива: Python + pymoo + ProcessPoolExecutor (8 workers).
    pymoo использует numpy внутри — 3–10 сек. Приемлемо для v1,
    переписать на Go для v2.
```

### 1.6 Если всё-таки Go — как именно

Если решите вынести тяжёлые расчёты в Go, правильный способ:

**Архитектура: Go как расчётный микросервис (sidecar или отдельный контейнер)**

```
                    ┌─────────────┐
                    │  FastAPI    │  (Python — маршрутизация, CRUD, auth)
                    │  :8000      │
                    └──────┬──────┘
                           │ gRPC / HTTP POST
                           ▼
                    ┌─────────────┐
                    │  Calc Engine│  (Go — только расчёты)
                    │  :9001      │
                    └─────────────┘
```

Контракт — простые структуры:

```go
// На входе
type PipeHeatRequest struct {
    OuterDiameter  float64 `json:"outer_diameter"`
    WallThickness  float64 `json:"wall_thickness"`
    InsulationLayers []InsulationLayer `json:"insulation_layers"`
    TProduct       float64 `json:"t_product"`
    TAmbient       float64 `json:"t_ambient"`
    // ...
}

// На выходе
type PipeHeatResponse struct {
    QPerMeter      float64 `json:"q"`
    QTotal         float64 `json:"Q"`
    ThermalResistance []LayerResistance `json:"resistances"`
    // ...
}
```

**Важно:** Go-сервис **не должен** ходить в БД. Он получает все данные на входе
и возвращает только результат расчёта. Это сохраняет разделение концернов:
Python = state management, Go = pure computation.

**Сборка и деплой:**

```dockerfile
# Multi-stage: собираем Go-бинарник (~8 MB), кладём в scratch-образ
FROM golang:1.23 AS builder
WORKDIR /app
COPY go.mod go.sum ./
RUN go mod download
COPY cmd/ ./cmd/
COPY internal/ ./internal/
RUN CGO_ENABLED=0 go build -o /calc-engine ./cmd/engine

FROM scratch
COPY --from=builder /calc-engine /calc-engine
EXPOSE 9001
ENTRYPOINT ["/calc-engine"]
```

Итоговый образ — 8 MB, стартует за миллисекунды. Для сравнения: Python-образ
с numpy/scipy — 400+ MB.

### 1.7 Итог по Go

| Вывод | Обоснование |
|---|---|
| Сейчас — **нет** | Текущие формулы занимают 2–8 мс. Go сократит до 0.5 мс, но пользователь не заметит (остальное время — БД и сеть). Овчинка выделки не стоит. |
| Для F-01 — **Python + numpy** | Достаточно для 50-сегментной теплогидравлики. 10–30 мс. |
| Для F-02 — **Python + scipy, потом Go** | Scipy разреженные матрицы дают 200–800 мс. Если нужна интерактивность — вынести в Go. |
| Для F-03 — **Go сразу** | NSGA-II на чистом Python — неработоспособно (30–90 сек). Даже с pymoo — 3–10 сек. Go даст 1–4 сек с горутинами. |
| **Золотое правило:** | Python для всего, что < 100 мс. Go для всего, что > 1 сек и CPU-bound. Между ними — numpy/scipy как компромисс без смены языка. |

## Часть 2. Нужно ли оптимизировать БД?

> **Устарело.** Этот раздел написан до аудита кодовой базы и ссылается на
> таблицу `heat_calculations`, которой не существует в реальной модели.
> Результаты теплопотерь хранятся как JSONB-колонка `results` в `project_objects`.
>
> **Актуальный документ:** [`database-optimization-v2.md`](database-optimization-v2.md) —
> definitive source, сверенный с реальным кодом.
>
> **Краткий вердикт:** БД уже хорошо оптимизирована. Все индексы на месте,
> N+1 предотвращён архитектурно, автовакуум настроен, кэш работает.
> Осталось только добавить 4 строки в docker-compose (PG-01) и batch UPDATE (PG-02).
> Ни партицирование, ни PgBouncer, ни read replica не нужны на текущем масштабе.

### 2.1 Что с БД сегодня

Стек: PostgreSQL 16, SQLAlchemy 2.x async, Alembic-миграции. Схема из
`CLAUDE.MD` — типичная нормализованная реляционная модель:

- `projects`, `project_objects` (1:N)
- `heat_calculations`, `electrical_calculations` (1:1 и 1:N к объекту)
- `specifications` (1:N к проекту)
- `guest_sessions` → каскадное удаление
- Поля `params`, `results`, `items` — JSONB

Объём данных для одного проекта из 50 объектов: ~1–3 MB. Для 1000 проектов
(многопользовательский режим) — 1–3 GB. Это копейки для PostgreSQL.

Тем не менее, есть несколько **реальных** проблем и несколько **надуманных**.

### 2.2 Что реально болит (и это нужно чинить)

#### Проблема 1: N+1 запросов при загрузке объектов

**Диагноз:** Детально разобрано в O-03 optimization-guide. 251 SQL-запрос
вместо 3 для страницы с 50 объектами.

**Решение:**
```python
# selectinload вместо lazy loading
stmt = select(ProjectObject).options(
    selectinload(ProjectObject.heat_calculation),
    selectinload(ProjectObject.electrical_calculations),
)
```

**Приоритет:** P0. Делать немедленно. Один день работы.

#### Проблема 2: Отсутствие индексов на внешних ключах

**Диагноз:** Без индекса на `project_objects.project_id` — seq scan всей
таблицы при каждом `WHERE project_id = ...`. На 50 строках незаметно, на
5000 — latency растёт с O(1) до O(n).

**Решение:**
```sql
CREATE INDEX IF NOT EXISTS idx_objects_project_sort ON project_objects (project_id, sort_order);
CREATE INDEX IF NOT EXISTS idx_heat_calc_object ON heat_calculations (object_id);
CREATE INDEX IF NOT EXISTS idx_elec_calc_object_co ON electrical_calculations (object_id, variant_number);
CREATE INDEX IF NOT EXISTS idx_projects_owner ON projects (owner_id, updated_at);
```

**Приоритет:** P0. Делать немедленно. Один час (проверить существующие, создать недостающие).

#### Проблема 3: JSONB без индексов

**Диагноз:** Поля `params` и `results` — JSONB. Если есть запросы вида
`WHERE params->>'insulation_material' = 'mineral_wool'` — это seq scan
с разбором JSONB каждой строки.

**Как проверить:**
```sql
-- Посмотреть, есть ли такие запросы
SELECT query FROM pg_stat_statements WHERE query LIKE '%params%';
```

**Решение (если такие запросы есть):**
```sql
-- GIN-индекс на JSONB для оператора @> (contains)
CREATE INDEX idx_objects_params_gin ON project_objects USING GIN (params jsonb_path_ops);

-- Или — частичный индекс для частого фильтра
CREATE INDEX idx_objects_insulation ON project_objects ((params->>'insulation_material'))
    WHERE params->>'insulation_material' IS NOT NULL;
```

**Приоритет:** P2. Делать только если `pg_stat_statements` показывает такие запросы с высоким `mean_exec_time`. Скорее всего, фильтрация по JSONB-полям идёт на фронте (фильтры T-02), а не в SQL.

#### Проблема 4: Раздувание таблицы guest_sessions

**Диагноз:** Фоновая очистка каждые 10 минут удаляет просроченные сессии.
Но `DELETE` не освобождает место на диске — нужен `VACUUM`. При активной
гостевой нагрузке (100+ сессий в час) таблица guest_sessions фрагментируется.

**Решение:**
```sql
-- Настроить агрессивный autovacuum для этой таблицы
ALTER TABLE guest_sessions SET (
    autovacuum_vacuum_scale_factor = 0.01,  -- вакуумить при 1% изменённых строк
    autovacuum_vacuum_cost_limit = 2000     -- больше I/O за раз
);
```

**Приоритет:** P1. Делать при нагрузке > 50 гостевых входов в час.

### 2.3 Что не болит (и это не нужно чинить прямо сейчас)

#### Миф 1: «Нужно партицирование»

Нет. Партицирование нужно, когда таблица > 50–100 GB и запросы всегда
фильтруются по ключу партиции. HeatCalc — это не телеметрия (пока нет F-10).
Самая большая таблица — `electrical_calculations`, ~4 строки на объект ×
50 объектов × 1000 проектов = 200 000 строк. Это даже не warm cache для
PostgreSQL.

**Когда станет нужно:** при реализации F-10 (телеметрия — 10 000 зон × 1
измерение в минуту = 14.4 млн строк в день). Тогда — TimescaleDB hypertable.
До этого — не трогать.

#### Миф 2: «Нужен PgBouncer»

Нет. PgBouncer нужен, когда > 200 одновременных соединений. SQLAlchemy async
с `pool_size=20` + 5 инстансов бэкенда = 100 соединений. PostgreSQL держит
500 без проблем на 2 GB RAM. Добавление PgBouncer — это ещё одна точка отказа
без реальной необходимости на текущем масштабе.

**Когда станет нужно:** при SaaS (F-15) с 50+ тенантами и 100+ одновременных
пользователей. Тогда — да, PgBouncer в transaction pooling mode.

#### Миф 3: «Нужно денормализовать»

Нет. Денормализация — это когда вы жертвуете нормальной формой ради
производительности чтения. Для HeatCalc денормализация не даст выигрыша:
- `q` и `Q` (результаты расчёта) уже хранятся в `heat_calculations.results` JSONB — читаются за 1 запрос с `selectinload`
- JOIN трёх таблиц (objects + heat_calc + elec_calc) с индексами — 3–5 мс
- Денормализация в одну плоскую таблицу сэкономит 1–2 мс ценой аномалий обновления и дублирования данных

**Когда станет нужно:** для аналитических запросов (отчёт «средние теплопотери по всем проектам за квартал»). Тогда — материализованное представление, обновляемое раз в час. Но не денормализация основных таблиц.

#### Миф 4: «Нужна read replica»

Нет. Read replica нужна, когда read load превышает возможности одного
инстанса. 95% запросов HeatCalc — это `SELECT` по первичному ключу (объект,
расчёт) — indexed scan, ~0.5–1 мс. Один инстанс PostgreSQL на 2 vCPU
держит 5000 таких запросов в секунду. У HeatCalc — 10–50 запросов в секунду.

**Когда станет нужно:** при SaaS с 1000+ одновременных пользователей.

### 2.4 Что нужно сделать (приоритетный план)

| # | Действие | Приоритет | Трудозатраты | Эффект |
|---|---|---|---|---|
| 1 | **N+1 → eager loading (O-03)** | P0 — сейчас | 1 день | −80% SQL-запросов |
| 2 | **Индексы на FK (O-03)** | P0 — сейчас | 1 час | Линейный → константный доступ |
| 3 | **pg_stat_statements — найти долгие запросы (O-03)** | P0 — сейчас | 30 мин | Обнаружить скрытые проблемы |
| 4 | **Тюнинг пула соединений (O-04)** | P1 — скоро | 2 часа | Стабильность при росте пользователей |
| 5 | **VACUUM для guest_sessions (п. 2.2.4)** | P1 — скоро | 15 мин | Не раздувать БД |
| 6 | **GIN-индекс на JSONB (если нужен)** | P2 — потом | 30 мин | Ускорение фильтрации в БД (если есть) |
| 7 | **Материализованные представления для отчётов** | P2 — потом | 1 день | Быстрые aggregate-запросы |
| 8 | **PgBouncer** | P2 — SaaS | 2 дня | 200+ соединений без оверхеда |

### 2.5 Схема БД — что проверить прямо сейчас

Запусти в psql:

```sql
-- 1. Какие запросы самые долгие?
SELECT queryid, LEFT(query, 120), calls, mean_exec_time
FROM pg_stat_statements
ORDER BY mean_exec_time DESC
LIMIT 10;

-- 2. Каких индексов не хватает? (seq scans на таблицах > 1000 строк)
SELECT schemaname, relname, seq_scan, seq_tup_read, 
       idx_scan, seq_tup_read / seq_scan AS avg_seq_tup
FROM pg_stat_user_tables
WHERE seq_scan > 0
ORDER BY seq_tup_read DESC
LIMIT 10;

-- 3. Есть ли неиспользуемые индексы? (тормозят INSERT/UPDATE, не помогают SELECT)
SELECT schemaname, relname, indexrelname, idx_scan
FROM pg_stat_user_indexes
WHERE idx_scan = 0
ORDER BY relname;

-- 4. Размер таблиц (куда растёт место?)
SELECT relname, pg_size_pretty(pg_total_relation_size(relid))
FROM pg_stat_user_tables
ORDER BY pg_total_relation_size(relid) DESC;

-- 5. Bloated tables (фрагментация после DELETE/UPDATE)
SELECT relname, 
       n_dead_tup,
       n_live_tup,
       round(100.0 * n_dead_tup / NULLIF(n_live_tup + n_dead_tup, 0), 2) AS dead_pct
FROM pg_stat_user_tables
WHERE n_dead_tup > 0
ORDER BY n_dead_tup DESC;
```

Эти 5 запросов дадут полную картину состояния БД за 5 минут. Дальше —
действовать по результатам, а не по предположениям.

| **Не нужно — read replica** | 50 запросов/сек на инстанс — это смешно для PostgreSQL. |
| **Будущее — TimescaleDB** | Обязательно при реализации F-10 (телеметрия). Не сейчас. |
| **Будущее — PgBouncer** | Обязательно при SaaS с 50+ тенантами. Не сейчас. |
