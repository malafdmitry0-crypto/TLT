# Границы температуры окружающей среды — план реализации

**Статус:** PROPOSED implementation package; продуктовое решение принято,
производственный код ещё не изменён.

**Дата:** 2026-08-19

**Промпты:** [prompts.md](prompts.md)

Этот документ не является второй ACTIVE frontend-очередью и не меняет
[docs/frontend/refactor-backlog.md](../../docs/frontend/refactor-backlog.md).
Каждый выбранный слайс выполняется отдельным запуском и отдельным commit.
Динамические результаты прогонов и timings хранятся только в датированном
audit snapshot.

## Цель

Показать пользователю две однозначные границы температуры окружающей среды,
не изменив текущую физику расчёта:

- минимальная температура остаётся расчётным холодным случаем;
- максимальная температура становится редактируемыми метаданными объекта;
- формульное ядро, климатический алгоритм и электрический подбор не получают
  новый вход.

## Зафиксированный продуктовый контракт

| Свойство | Минимальная граница | Максимальная граница |
|---|---|---|
| Технический ключ | ambient_temperature | max_ambient_temperature |
| Обязательность | По действующему placement-контракту | Необязательна |
| Источник | Климат или ручной ввод | Только ручной ввод |
| Значение по умолчанию | Действующая климатическая политика | Нет |
| Диапазон | Действующий −70…+70 °C | −70…+70 °C |
| Участие в теплопотерях | Да | Нет |
| Участие в подборе кабеля | Да, как холодная граница | Нет |
| Формульная трассировка | ambient_temperature_applied | Не добавляется |

Дополнительные правила:

1. Внешний label существующего поля меняется на «Минимальная температура
   окружающей среды». Сам ключ ambient_temperature не переименовывается.
2. При двух заполненных значениях max_ambient_temperature должен быть не меньше
   ambient_temperature. Равные границы допустимы.
3. Максимум не сравнивается с температурой процесса и не меняет действующую
   проверку process_temperature > ambient_temperature.
4. Для pipe с placement=underground оба воздушных поля неприменимы. Поле
   максимума скрывается; при явном сохранении такого объекта отправляется
   пустое значение, чтобы не показывать устаревший максимум. Массовой миграции
   существующих JSONB не требуется.
5. Для tank, включая частично заглублённый, воздушная часть расчёта остаётся,
   поэтому обе границы доступны.
6. В таблице теплорасчёта обе границы видимы по умолчанию. Для неприменимого
   underground pipe выводится прочерк.
   Существующие пользовательские порядок и ширины колонок сохраняются:
   newly introduced default-visible column добавляется только если её ещё не
   было в сохранённом catalog snapshot. Table settings version не сбрасывается.
7. В электрической таблице новая колонка не добавляется: электрический алгоритм
   продолжает показывать и использовать только минимальную расчётную
   температуру.
8. В Excel/CSV старый заголовок «T° среды» продолжает импортироваться как
   минимум. Новые явные заголовки различают минимум и максимум.
9. В отчёте границы выводятся раздельно; пустой максимум отображается прочерком.
10. Подсказка максимума прямо сообщает: «Справочное значение; в текущем
    расчёте не используется».

## Инварианты безопасности

- max_ambient_temperature не входит в COMMON_HEAT_PARAM_KEYS,
  PIPE_HEAT_PARAM_KEYS, TANK_HEAT_PARAM_KEYS и deprecated/forbidden heat keys.
- Поле не добавляется в PipeHeatLossParams, TankHeatLossParams и результаты
  формул.
- Одинаковый объект с максимумом и без него даёт полностью одинаковый
  расчётный результат.
- Нет новой Alembic-миграции и автоматического значения 30 °C.
- Климат.xlsx, climate.json и apply_climate_policy не меняются.
- Административный formula-check не получает справочные метаданные.
- Старые проекты и файлы без максимума продолжают открываться и импортироваться.

## Контракты слайсов

### ATB-00 — защита расчётной границы

- Characterization сначала фиксирует существующее разделение heat-owned полей
  и произвольных метаданных.
- Добавляется явный regression guard для max_ambient_temperature:
  сохранение при heat replacement, отсутствие в formula schemas и идентичность
  результатов с полем и без него.
- Производственное ядро и схемы формул не меняются.
- Слайс допускается как test-only.

### ATB-01 — backend persistence и object query

- Создание, обновление и последующий пересчёт сохраняют необязательный number
  либо null без default.
- Отдельная metadata-валидация на API-границе проверяет finite number,
  диапазон −70…+70 °C и max ≥ min, не добавляя максимум в formula schema.
- Object-query capability для pipe/tank содержит max_ambient_temperature как
  числовое поле; backend sort/filter используют JSON number.
- Existing generic JSON boundary используется как есть. Project service
  меняется только при доказанной потере поля.
- Миграции, climate policy и formula service вне scope.

### ATB-02a — form↔API round-trip

- PipeFormValues и TankFormValues получают необязательный максимум.
- API→form возвращает сохранённое значение.
- Form→API отправляет число либо явный null для очистки.
- Для underground pipe отправляется null; для tank поле сохраняется при любом
  поддержанном placement.
- Inline/table projection пока не меняется.

### ATB-02b — видимая форма и валидация

- Реестр получает max_ambient_temperature без default и с явной справочной
  подсказкой.
- Label ambient_temperature становится минимальной границей во всех heat
  contexts.
- TemperatureEnvironmentStep показывает два доступных с клавиатуры числовых
  поля, кроме воздушных полей underground pipe.
- Максимум необязателен. Если заполнен, применяется диапазон и max ≥ min.
- Изменение любой границы перевалидирует вторую.
- Поле добавляется в form registry, но до ATB-03a не включается в table
  registry/default-visible.
- Не добавляется новый CSS, если существующая form anatomy укладывает поля.

### ATB-02c — inline form preservation

- Pipe/tank inline projection включает max_ambient_temperature.
- Открытие существующей строки в form panel и сохранение другого поля не
  удаляет максимум.
- Table renderer и настройки колонок пока не меняются.

### ATB-03a — таблица и сохранённые настройки

- В heat-таблице обе колонки видимы по умолчанию и имеют однозначные labels.
- Рендер и copy возвращают максимум.
- Нормализация сохранённого layout добавляет новую default-visible колонку
  только если её не было в старом columns snapshot. Остальные visibility,
  order и widths сохраняются.
- Пользователь может после миграции скрыть максимум; последующее чтение не
  включает его снова.
- Table settings version не повышается и не сбрасывает весь layout.
- Underground pipe показывает прочерк.
- До ATB-03b новая колонка не объявляет sort/filter capability.
- Электрическая таблица не получает новую колонку.

### ATB-03b — table parity и confirmation

- Максимум получает числовые sort/filter semantics, такие же как другие
  температурные параметры.
- Настройки колонок различают minimum и maximum.
- Confirmation summary показывает обе границы, если максимум заполнен.
- Формулы, query keys и table virtualization не меняются.

### ATB-04 — Excel и project CSV

- Export/template содержит отдельные колонки минимума и максимума.
- Import принимает новые явные заголовки; старый «T° среды» остаётся alias
  минимума.
- Пустой максимум остаётся пустым, ноль сохраняется как 0.
- Export→import сохраняет обе границы и не меняет вычисляемые результаты.
- Формат старых файлов остаётся совместимым; schema version не повышается без
  доказанной необходимости.

### ATB-05 — отчёт

- Все релевантные pipe/tank таблицы отчёта получают отдельные min/max headings.
- Пустое или неприменимое значение — прочерк, а не 0.
- Текст отчёта не утверждает, что максимум участвовал в расчёте.
- PDF/HTML проверяются визуально на переполнение и перенос заголовков.

### ATB-QA — сквозная приёмка

- Новый E2E проверяет create/edit/reopen, table visibility и validation.
- Отдельный regression proof сравнивает расчёт одного payload с максимумом и
  без него.
- Проверяются outdoor pipe, underground pipe, outdoor tank и tank с
  underground placement.
- Обязательные desktop viewports: 1000×768, 1280×800, 1440×900.
- Console errors/warnings и failed non-static network requests отсутствуют.
- Запускаются focused backend/frontend проверки и formula-qa quick.
- Артефакты прогона идут в датированную audit-папку, не в корень.

### ATB-DOC — закрытие документации

- Этот README меняет статус с «запланировано» на «реализовано» только после
  зелёного ATB-QA.
- Обновляются пользовательские скриншоты в answers/05.
- В heat-loss-quality-tz-assessment пропуск max_ambient_temperature отмечается
  закрытым без копирования динамических totals.
- В docs/tech-debt закрывается только вопрос видимости/трассировки. Методика
  тёплого периода остаётся отдельным нерешённым вопросом.
- Незапущенные проверки не называются зелёными.

## Финальная приёмка

Пакет завершён только если одновременно выполняется следующее:

1. Пользователь видит и редактирует обе границы на поддерживаемом объекте.
2. Минимум остаётся климатическим/ручным расчётным входом.
3. Максимум сохраняется без default и явно обозначен справочным.
4. Формульные результаты одинаковы с максимумом и без него.
5. Значение переживает reopen, heat recalculation, table query и обменные
   форматы.
6. Существующий пользовательский table layout не сбрасывается целиком.
7. Отчёт показывает обе границы без ложного утверждения об использовании.
8. Underground pipe не показывает воздушные границы; tank сохраняет их.
9. Focused proof, desktop browser proof и formula regression green на одном
   HEAD.
10. Документация обновлена последним docs-only слайсом.
