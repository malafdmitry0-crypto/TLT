
Предоставленный файл `Расчет_спецификации_трубы_самрег29_05_26.xlsx` должен рассматриваться не как уже согласованная часть исходного объёма работ, а как новое уточнение/расширение требований.

В текущем SRS была описана базовая логика спецификации:

- автоматическое формирование спецификации;
- группировка кабеля по марке;
- суммирование длины кабеля;
- добавление минимального набора аксессуаров;
- сортировка позиций;
- использование активного варианта CO;
- отображение спецификации в отчёте.

Это покрывает базовый продуктовый сценарий: пользователь получает ведомость материалов по результатам электрорасчёта.

Однако предоставленный Excel-файл содержит существенно более детальную предметную методику
## Что нового содержит Excel

Файл содержит не только пример результата, а отдельную модель формирования спецификации для саморегулирующихся кабелей:

- перечень конкретных марок ТТН/ТТВ/ТТХ;
- номенклатурные коды;
- поставщика;
- правила расчёта количества кабеля;
- правила расчёта соединительных комплектов;
- правила расчёта коробок;
- условия по диаметру трубы;
- условия по К1i, К2i, Кiu;
- параметры горячего резервирования Rгр;
- минимальную длину секции для применения К2i;
- расчёт лент, хомутов, герметиков, наклеек, вводов;
- отдельные позиции ЗИП;
- условия включения позиций в спецификацию;
- формулы вида L1, L2, Fl1, Fl2, Nk1, Nk2, Kr1, Kr2 и т.д.

Это уже не базовая спецификация, а отдельный расчётный модуль спецификации по ТНП.

## Почему это выходит за рамки SRS

В SRS не была зафиксирована такая детализация:

- не был описан полный состав номенклатуры из Excel;
- не были описаны формулы расчёта каждой позиции;
- не были описаны переменные К1i, К2i, Кiu, LК2i, Rгр как обязательные пользовательские входы;
- не были описаны правила расчёта коробок по диаметру трубы и количеству секций;
- не были описаны правила расчёта ЗИП;
- не были описаны правила выбора конкретных комплектов КСН, КСВ, СКВ;
- не были описаны правила агрегации по температурному классу;
- не были описаны правила применения условий Ex, агрессивной среды, индикации, резервирования;
- не были описаны тестовые сценарии приёмки именно этой методики.

Более того, в исходных документах часть методик прямо была обозначена как требующая отдельного предоставления/согласования. Это означает, что на момент фиксации SRS эти правила не являлись полностью определёнными и не могли быть включены в оценку как реализуемый объём.

## Почему одного Excel-файла недостаточно

Excel-файл нельзя считать полноценной постановкой задачи сам по себе.

Он может быть использован как источник примеров, справочник или черновик методики, но для разработки требуется текстовое описание бизнес-логики.

Причины:

- В Excel нет явного статуса: это норматив, пример, черновик или один из вариантов?
- Не указано, какие листы являются обязательными источниками истины.
- Не указано, какие строки/формулы должны быть реализованы, а какие справочные.
- Не описаны входные данные, которые должен вводить пользователь.
- Не описаны дефолтные значения.
- Не описаны правила валидации.
- Не описаны ошибки и сообщения пользователю.
- Не описано поведение при неполных данных.
- Не описано, как это должно работать для разных типов кабелей.
- Не описано, как это должно работать для труб и резервуаров.
- Не описано, какие позиции должны попадать в отчёт.
- Не описано, какие позиции должны быть редактируемыми.
- Не описаны критерии приёмки.
- Не описаны контрольные примеры с ожидаемым результатом.

Поэтому для реализации нужен не только экземпляр Excel-файла, а отдельная постановка задачи.

## Что нужно запросить у заказчика

Для корректной оценки и реализации необходимо запросить текстовое описание методики.

Минимально нужно получить (примерный план не является запросом):

1. Назначение методики
2. Область применимости
   Для каких типов объектов:

   - трубы;
   - резервуары;
   - только надземные;
   - подземные;
   - все варианты CO.

   Для каких типов кабеля:

   - ТЛТ;
   - ТТН/ТТВ/ТТХ;
   - одножильный;
   - трёхжильный;
   - минеральная изоляция;
   - skin.

3. Полный список входных параметров

   Например:

   - Ex;
   - К1i;
   - К2i;
   - Кiu;
   - LК2i;
   - Rгр;
   - агрессивность среды;
   - температурный класс;
   - диаметр трубы;
   - длина секции;
   - количество секций;
   - количество ниток;
   - марка кабеля.

4. Источник каждого параметра

   Нужно понять, откуда значение берётся:

   - из теплотехнического расчёта;
   - из электрорасчёта;
   - из формы пользователя;
   - из справочника;
   - из дефолта;
   - из админской базы;
   - из Excel.

5. Формулы расчёта позиций

   Для каждой позиции спецификации нужно текстово описать:

   - условие включения;
   - формулу количества;
   - единицу измерения;
   - округление;
   - группировку;
   - источник номенклатурного кода;
   - поведение при отсутствии данных.

6. Правила округления

   Особенно важно для коробок, комплектов, лент, хомутов, ЗИП.

7. Правила группировки

   Например:

   - группировать по марке;
   - по температурному классу;
   - по диаметру трубы;
   - по варианту CO;
   - по объекту;
   - суммировать или выводить отдельными строками.

8. Правила для ошибок

   Что делать, если:

   - не выбран кабель;
   - нет диаметра;
   - нет количества ниток;
   - не задан Rгр;
   - не задан К2i;
   - объект не рассчитан;
   - выбран неподдержанный тип кабеля.

9. Контрольные примеры

   Нужны минимум 3-5 эталонных проектов:

   - один простой объект;
   - несколько объектов с одной маркой;
   - разные диаметры;
   - разные температурные классы;
   - разные значения К1i/К2i/Кiu;
   - проект с ЗИП;
   - проект с ошибками.

   Для каждого примера нужен ожидаемый результат спецификации.

10. Критерии приёмки

    Например:

    - какие позиции обязаны появиться;
    - какие количества должны совпасть;
    - допустимая погрешность;
    - какие сценарии считаются успешными;
    - какие сценарии должны блокироваться.

## Если рассматривать это как часть MVP

Если заказчик рассматривает реализацию данной детальной спецификации как обязательную часть MVP, то это должно быть зафиксировано как блокер MVP, возникший не по причине разработки, а по причине позднего предоставления ключевой предметной документации.

Файл `Расчет_спецификации_трубы_самрег29_05_26.xlsx` был предоставлен только 29 мая. До этой даты не было формализованного источника, описывающего:

- полный состав номенклатуры спецификации;
- формулы расчёта каждой позиции;
- условия включения комплектов, коробок, лент, хомутов, вводов и ЗИП;
- дополнительные входные параметры вроде К1i, К2i, Кiu, LК2i, Rгр;
- правила округления, группировки и обработки ошибок;
- эталонные контрольные примеры для проверки результата.

Соответственно, эта логика не могла быть корректно оценена, спроектирована, реализована и протестирована в рамках исходного плана MVP. Для расчётных модулей и спецификации наличие формальной методики является обязательным входным условием: без неё разработчик не может самостоятельно определить бизнес-правила, потому что такие правила являются предметной ответственностью заказчика.

В период ожидания недостающей документации разработчик продолжал работу над другими согласованными частями продукта, включая функциональность, выходящую за минимальный MVP, чтобы не останавливать проект. Это означает, что появление новой обязательной методики на позднем этапе не является следствием бездействия или ошибки разработки.

Отдельно важно зафиксировать, что пустая форма спецификации также была передана только 29 мая. До этого момента у разработчика не было ни полной методики расчёта спецификации, ни утверждённой формы результата, по которой можно было бы заранее спроектировать структуру данных, интерфейс, экспорт, отчёт и критерии приёмки.
