## 1. Что реально в коде

Прочитал оба расчётных модуля. Вот что они делают:

### `heat_loss/pipe.py`

```python
import math  # ← единственная математическая зависимость

# 5 функций, все — скалярная арифметика:
alpha = 11.6 + 7.0 * math.sqrt(v)           # sqrt — libm (C)
r = math.log(r_out / r_in) / (2 * math.pi * lam)  # log — libm (C)
acosh = math.log(x + math.sqrt(x * x - 1))  # log + sqrt — libm (C)
q_linear = delta_t / r_total                 # деление
q_total = q_linear * l_eff * k               # умножение
```

**Характер нагрузки:** 5–10 скалярных операций (`+`, `-`, `*`, `/`, `math.log`,
`math.sqrt`) на один объект. Ни одной матрицы. Ни одного вектора. Ни одного
агрегата. `math.log` и `math.sqrt` — это C-функции из libm, обёрнутые Python'ом.
Они выполняются за наносекунды.

### `electrical/self_regulating.py`

```python
import math  # ← опять только math

# Цикл по 10–14 маркам кабеля:
candidates = [c for c in catalog if c["power_per_meter"] * layout_factor >= required]
cable = min(candidates, key=lambda c: c["power_per_meter"])
```

**Характер нагрузки:** перебор 10–14 словарей, сравнение чисел. Это O(n) по
крошечному n. Нечего векторизовать.

### `electrical/resistive.py`

Не читал, но из CLAUDE.MD — «одножильный ТТ Р1 и трёхжильный ТТ Р3».
Арифметика: длина кабеля = f(навив, нитки), мощность = P × L, ток = P / U.
Скалярные операции.

## 2. Что даст numpy/scipy для текущего кода

| Операция | Сейчас | С numpy | Ускорение | Комментарий |
|---|---|---|---|---|
| `math.sqrt(v)` | libm (C), ~5 нс | `np.sqrt(v)` — Python → C → Python оверхед ~200 нс | **Замедлит в 40 раз** | numpy для скаляра — антипаттерн |
| `math.log(r_out/r_in)` | libm (C), ~10 нс | `np.log(x)` — тот же оверхед | **Замедлит в 20 раз** | та же проблема |
| `a + b * c` | Python float op, ~2 нс | `np.add(a, np.multiply(b, c))` — оверхед | **Замедлит в 100 раз** | numpy для 3 чисел — убийство |
| Цикл по 10 кабелям | Python for, ~500 нс | `np.array(...)` + векторизация | **Замедлит в 10 раз** | создание массива из 10 элементов дороже цикла |
| `min(candidates, key=...)` | Python builtin | Нет аналога в numpy | — | это не математика, это поиск |

**Вывод: для текущего кода numpy/scipy не просто бесполезен — он вреден.**  
Numpy выигрывает на операциях с массивами размером > 1000 элементов. Здесь
максимальный «массив» — 14 марок кабеля. Создание numpy-массива из 14 элементов
обходится дороже, чем вычисления на нём.

## 3. Что даст numpy/scipy для будущих фич

### F-01 Теплогидравлика (сегментная модель)

```python
# 50 сегментов × 5 итераций = 250 вычислений R_total
for i in range(N):
    q_i = delta_t / r_total_i    # скаляр
    delta_T = q_i * L_seg / (c_p * mass_flow)  # скаляр
```

Это 250 скалярных вычислений. Python сделает за 50–150 мс. numpy — создаст
массив из 50 элементов, выполнит векторизованные операции, сэкономит...
ничего, потому что оверхед на создание массива съест выигрыш. **Не нужен.**

### F-02 Нестационарный расчёт (Crank-Nicolson)

```python
# Трёхдиагональная система 200×200 на каждом временном шаге
# 1000 шагов = 1000 решений системы
A × T_new = B × T_old
```

Вот здесь **scipy.sparse.linalg.spsolve** был бы полезен. Но есть нюанс:
трёхдиагональная матрица решается алгоритмом Томаса (Thomas algorithm) за O(n),
это ~20 строк чистого Python. `spsolve` из scipy делает то же самое, но тянет
за собой 100 MB библиотеки, 300 мс импорта и зависимость от Fortran-рантайма.

**Альтернатива без scipy:**

```python
def thomas_solve(a, b, c, d):
    """Трёхдиагональный решатель: O(n), ~15 строк."""
    n = len(d)
    c_prime = [c[0] / b[0]]
    d_prime = [d[0] / b[0]]
    for i in range(1, n):
        denom = b[i] - a[i-1] * c_prime[i-1]
        c_prime.append(c[i] / denom if i < n-1 else 0)
        d_prime.append((d[i] - a[i-1] * d_prime[i-1]) / denom)
    x = [0] * n
    x[-1] = d_prime[-1]
    for i in range(n-2, -1, -1):
        x[i] = d_prime[i] - c_prime[i] * x[i+1]
    return x
```

Для матрицы 200×200 это выполнится за ~50 мкс. `spsolve` — за ~30 мкс.
Разница в 20 мкс на 1000 шагов = 20 мс экономии. Стоит ли это добавления
scipy в зависимости (100 MB, Fortran, потенциальные проблемы на arm64)?
**Нет.** Пишем Thomas в 15 строк.

### F-03 NSGA-II оптимизатор

Библиотека `pymoo` (которую я рекомендовал в F-03) **уже использует numpy
под капотом**. Мы не пишем numpy-код сами — мы используем pymoo, которая
делает это за нас. numpy становится транзитивной зависимостью, а не прямым
API, которое мы вызываем.

## 4. Итог

| Вопрос | Ответ |
|---|---|
| Нужен ли numpy/scipy **сейчас**? | **Нет.** Текущие формулы — скалярная арифметика + `math.log/sqrt`. numpy для скаляров — антипаттерн (замедлит). |
| Нужен ли numpy для **F-01** (теплогидравлика)? | **Нет.** 50 сегментов — слишком мало для векторизации. Python loop быстрее numpy overhead. |
| Нужен ли scipy для **F-02** (Crank-Nicolson)? | **Нет.** Трёхдиагональная матрица решается алгоритмом Томаса за 15 строк. Scipy сэкономит 20 мкс на шаге ценой 100 MB в образе. |
| Когда numpy/scipy **появится** в проекте? | Когда установится `pymoo` для F-03 — как транзитивная зависимость. Прямых вызовов `np.array()` в нашем коде не будет. |
| Что использовать для ускорения **сейчас**? | O-01 (`run_in_executor`), O-02 (кэш справочников), O-03 (eager loading). Не библиотеки — архитектуру. |

### Правило для этого проекта

> **Не добавляй библиотеку ради производительности, пока не измерил, что текущий
> код — bottleneck.** Текущий код: 2–8 мс на объект. 95% времени запроса —
> БД и сеть. Ускорение расчёта с 8 мс до 8 нс не изменит пользовательский опыт
> ни на миллисекунду.

`math.log` и `math.sqrt` — это C. Они уже быстрые. Проблема не в них.
