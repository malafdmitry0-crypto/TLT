## Введение

Система HeatCalc сегодня — это зрелый MVP, закрывающий базовый контур
теплотехнического и электротехнического расчёта: трубопроводы, резервуары,
подбор кабеля ТЛТ/ТТ/резистив, 4 варианта CO, спецификация, отчёт. Архитектурно —
монолит FastAPI + React SPA под Docker, 799 backend-тестов, отлаженный CI.

Следующий шаг — переход от «инструмента инженера-одиночки» к **отраслевой
платформе**, встроенной в экосистему проектной организации: BIM-модели на входе,
SCADA-контроллеры на выходе, ML-оптимизация внутри, полный audit trail и
юридически значимый документооборот. Это превращает HeatCalc из калькулятора
в **цифровой двойник системы электрообогрева** на всех этапах жизненного цикла:
проектирование → строительство → эксплуатация → демонтаж.

Ниже — 15 конкретных инженерных предложений, сгруппированных по 12 направлениям.
Каждое содержит: проблему, инженерное описание, технический контур, аналоги из
реальных продуктов и оценку сложности. Предложения спроектированы как **независимые
модули**, которые можно реализовывать параллельно разными командами.

Ни одной строчки кода в этом документе. Только архитектура, модели данных,
алгоритмические решения и инженерные оценки.

## F-01. Теплогидравлическая модель трубопровода с учётом остывания продукта по длине

**Категория:** Расчётное ядро

**Приоритет:** P0 — стратегический

**Аналоги:** Schlumberger OLGA (динамическая теплогидравлика многофазных потоков),
DNV GL Synergi Pipeline Simulator (стационарный тепловой профиль трубопровода),
Bentley AutoPIPE (thermal profile along pipe with fluid cooling).

**Проблема, которую решаем:**

Текущая модель считает каждый трубопровод как изотермический сегмент —
температура продукта постоянна по всей длине. Для коротких участков (десятки
метров) это допустимо. Для магистральных трубопроводов (километры) продукт
остывает по длине, и теплопотери на последнем километре существенно ниже,
чем на первом. Результат: ошибка подбора кабеля до 15–30% на длинных участках —
переобогрев в начале трассы (перерасход энергии) и потенциальный недогрев в конце
(риск замерзания). Ни «Тепломаг», ни западные калькуляторы (Thermon CompuTrace)
этого не учитывают.

**Инженерное описание:**

Пользователь указывает для трубопровода дополнительные параметры: расход
продукта (м³/ч или т/ч), теплоёмкость продукта (кДж/(кг·К), из справочника или
вручную), плотность. Система разбивает трубопровод на N расчётных сегментов
(N = max(2, floor(L / 100м)) — не менее 2, шаг не более 100 м по длине).

Для каждого сегмента i решается связанная система:

- Теплопотери сегмента: Q_i = q_i × ΔL × K, где q_i вычисляется по текущей
  формуле цилиндрической стенки, но T_продукта_i — локальная температура в
  начале сегмента, а T_среды_i — локальная температура окружающей среды (если
  трасса проходит через разные климатические зоны — берётся из линейной
  интерполяции между заданными точками).
- Остывание продукта: ΔT_i = Q_i / (c_p × ṁ), где c_p — теплоёмкость,
  ṁ — массовый расход.
- T_продукта_{i+1} = T_продукта_i − ΔT_i.

Итеративный решатель сходится за 3–5 проходов (метод простой итерации; для
typical pipelines сходимость гарантирована, поскольку теплопотери слабо зависят
от T_продукта — разница λ(T) на 5–10 °C пренебрежима).

Результат для каждого сегмента: локальное q_i (Вт/м), локальное Q_i (Вт),
локальная температура продукта. В UI — график «Температура продукта по длине»
(Plotly.js) и таблица сегментов. Для электрорасчёта система либо подбирает
единый кабель с запасом по максимальному q (традиционный подход), либо —
опционально — разные марки кабеля по сегментам (оптимизация стоимости при
значительном градиенте температур).

Дополнительный режим: «Обратный расчёт» — задана минимально допустимая
температура продукта в конце трубопровода, требуется определить необходимую
мощность обогрева.

**Технический контур:**

Затрагиваются: backend `formulas/heat_loss/pipe.py` (добавляется класс
`PipeSegmentSolver`), Pydantic-схемы `PipeHeatLossParams` (новые поля:
`flow_rate`, `specific_heat_capacity`, `density`), API эндпоинт
`POST /calc/heat/pipe-thermal-profile` (возвращает массив сегментов),
фронтенд-компонент `ThermalProfileChart.tsx`. Зависимости: `numpy` (уже есть),
`scipy` для sparse-матриц (опционально — простой итеративный решатель обходится
без scipy). Модель данных: результаты хранятся как JSONB-массив сегментов в
`heat_calculation.results.segments`. Сложность: Medium.

**Почему это «продвинуто»:**

Ни один из известных калькуляторов греющего кабеля (Тепломаг, Thermon
CompuTrace, nVent TraceCalc) не считает остывание продукта по длине — они
работают в предположении постоянной температуры. Это даёт HeatCalc уникальное
конкурентное преимущество при проектировании магистральных трубопроводов
(нефть, газ, химпродукты) протяжённостью > 1 км.

**Риски и ограничения:**

- Расход продукта и теплоёмкость — данные, которых у проектировщика может не
  быть на ранних стадиях. Решение: поля опциональны; если не заданы — работает
  текущая изотермическая модель с уведомлением «для протяжённых трасс рекомендуется
  задать расход продукта для теплогидравлического расчёта».
- Для газопроводов модель требует учёта эффекта Джоуля-Томсона (охлаждение газа
  при расширении) — это отдельная задача, не входит в данную фичу.
- Сходимость итераций для edge-случаев (L → 0, расход → 0) требует тестирования.

## F-02. Расчёт нестационарных тепловых режимов

**Категория:** Расчётное ядро

**Приоритет:** P1 — тактический

**Аналоги:** ANSYS Fluent/CFX (полный CFD для переходных процессов — overkill),
COMSOL Multiphysics Heat Transfer Module (метод конечных элементов для
нестационарной теплопередачи), отечественный «Логос-Тепло» (РФЯЦ-ВНИИЭФ,
конечно-элементный тепловой анализ).

**Проблема, которую решаем:**

Текущий расчёт — строго стационарный: «вот труба с температурой +80 °C,
окружающая среда −40 °C → теплопотери 42 Вт/м». Но инженеру критически важно
знать ответы на нестационарные вопросы:

- Пусковой прогрев: сколько времени потребуется, чтобы прогреть продукт в трубе
  от −40 °C до +5 °C (минимальная температура перекачки) при включённом обогреве?
- Аварийное остывание: при отключении питания, через сколько часов продукт
  остынет до температуры застывания? Это определяет требования к резервному
  питанию (ДГУ, ИБП) и регламент реагирования аварийной бригады.
- Циклический режим: трубопровод периодически заполняется горячим продуктом
  (например, раз в сутки при сливе цистерн), между циклами — охлаждается.
  Какова средняя температура стенки за цикл?

Ни один коммерческий калькулятор греющего кабеля не решает эти задачи. Инженеры
вынуждены либо делать грубые оценки «на глаз» (с коэффициентом запаса 2–5×),
либо заказывать дорогостоящий CFD-расчёт в ANSYS (недели работы, стоимость
контракта от 500 тыс. руб.).

**Инженерное описание:**

Решается одномерное нестационарное уравнение теплопроводности в
цилиндрических координатах методом конечных разностей (схема Кранка-Николсона,
безусловно устойчивая, второй порядок точности по времени и пространству):

∂T/∂t = a × (∂²T/∂r² + (1/r) × ∂T/∂r) + q_внутр / (ρ × c_p)

где a = λ/(ρ·c_p) — температуропроводность материала; q_внутр — внутренний
источник тепла (греющий кабель), моделируется как граничное условие на внешней
поверхности трубы (под изоляцией).

Расчётная сетка: ~50–200 узлов по радиусу (стенка трубы + слои изоляции),
адаптивный временной шаг (от 1 секунды в начале переходного процесса до 10 минут
на стабилизировавшемся участке). Начальное условие: равномерная температура
T(r, t=0) = T_начальная. Граничные условия: на внутренней поверхности трубы —
конвективный теплообмен с продуктом (коэффициент теплоотдачи от скорости потока);
на внешней поверхности изоляции — условие третьего рода с α_внеш.

Пользователь в форме «Нестационарный расчёт» задаёт: начальную температуру,
конечную температуру (или время моделирования), мощность обогрева (берётся из
результата подбора кабеля либо задаётся вручную), скорость потока (0 для
статического режима — труба заполнена, но не течёт). Система выдаёт:

- График «Температура продукта от времени» с аннотированными точками:
  «+5 °C достигнута через 3 ч 47 мин».
- График «Теплопотери от времени» (убывают по мере прогрева).
- Для аварийного режима: «Время до застывания: 8 ч 12 мин при T_заст = +15 °C».
- Таблицу временных срезов (каждые N минут) с возможностью экспорта.

Результаты кэшируются как time-series JSONB, чтобы не пересчитывать при повторном
открытии.

**Технический контур:**

Новый backend-модуль `formulas/heat_loss/transient.py` с классом
`CrankNicolsonSolver`. Зависимости: `scipy.sparse` для разреженных матриц
(трёхдиагональная система на каждом временном шаге), `scipy.sparse.linalg.spsolve`.
Pydantic-схемы: `TransientHeatParams`. API: `POST /calc/heat/transient` →
`TransientHeatResult { time_points: [{t, T_product, q_avg}], critical_times: {...} }`.
Фронтенд: новый компонент `TransientCalcPanel.tsx` с Plotly.js для графиков.
Модель данных: `heat_calculation.transient_results` (JSONB, опционально).
Сложность: High (7 спринтов — требует глубокого тестирования на аналитических
решениях: прогрев бесконечного цилиндра, остывание сферы; валидация против
ANSYS-модели на 2–3 тестовых кейсах).

**Почему это «продвинуто»:**

Прямой аналог отсутствует в сегменте «калькуляторы греющего кабеля». Это выводит
HeatCalc на территорию CFD-пакетов начального уровня (COMSOL-lite), но с фокусом
на конкретную инженерную задачу, а не на универсальный решатель. Разработка
стоимостью ~4–5 млн рублей создаёт функционал, за который проектные институты
платят 500 тыс.+ рублей за один CFD-расчёт на сторону.

**Риски и ограничения:**

- Численная устойчивость на резких градиентах (влажный грунт → воздух,
  фазовый переход). Фазовые переходы (замерзание/таяние) сознательно исключены
  из first release — это задача с подвижной границей (задача Стефана), сложность
  на порядок выше. Будет явно указано в UI: «без учёта фазовых переходов».
- Верификация модели требует эталонных расчётов в ANSYS/COMSOL или аналитических
  решений — это отдельная работа, ~2–3 недели инженера-теплофизика.
- Для очень длинных труб (L > 10 км) 1D-модель теряет точность — пренебрегаем
  продольной теплопроводностью, что допустимо для большинства практических
  задач (число Пекле >> 1).

## F-03. Многокритериальный оптимизатор кабельной системы

**Категория:** Интеллектуальный подбор кабеля

**Приоритет:** P0 — стратегический

**Аналоги:** AspenTech Aspen Capital Cost Estimator (оптимизация CAPEX/OPEX
технологических схем), Bentley AutoPIPE (multi-criteria stress vs cost
optimization), отечественный «СТАРТ-Проф» (оптимизация трубопроводных опор
по критериям прочности и стоимости), Ansys optiSLang (многокритериальная
оптимизация с surrogate models).

**Проблема, которую решаем:**

Текущий автоподбор выбирает первую подходящую марку кабеля по одному критерию:
«минимальная мощность ≥ P_треб». Это не различает ситуацию:

- ТЛТ-50 (50 Вт/м, цена 420 руб./м, срок службы 15 лет, КПД 92%)
- ТТ Р1-60 одножильный (60 Вт/м, цена 280 руб./м, срок службы 20 лет, КПД 97%)

По мощности оба подходят, но по экономике жизненного цикла (цена + энергия +
замена) резистивный кабель может быть в 1.6 раза выгоднее на горизонте 20 лет.

Инженер сегодня вручную перебирает 3–5 вариантов кабеля для каждого из 50+
объектов — это часы рутины. Результат субъективен («я всегда беру ТЛТ, привык»)
и невоспроизводим.

**Инженерное описание:**

Оптимизатор получает на вход для каждого объекта проекта:

- Теплопотери q (Вт/м) и Q_итого (Вт)
- Температурные ограничения (T_продукта, T_среды)
- Геометрию (длина, диаметр — влияет на минимальный радиус изгиба кабеля)
- Вектор весов критериев от пользователя (слайдеры в UI: «Цена важнее надёжности»)

Для каждой допустимой марки кабеля из активной базы вычисляются 5 критериев:

1. **CAPEX** (руб.): цена кабеля × длина + цена аксессуаров + стоимость монтажа
   (нормо-часы × ставка)
2. **OPEX_20yr** (руб.): годовое энергопотребление × 20 лет × тариф,
   дисконтированное к NPV с учётом ставки дисконтирования
3. **Надёжность** (баллы 0–100): на основе MTBF из каталога, приведённая к шкале
4. **Доступность** (дни): срок поставки со склада (из внешней БД)
5. **Энергоэффективность** (безразмерная): КПД кабеля × коэффициент запаса

Решается многокритериальная задача оптимизации методом NSGA-II (Non-dominated
Sorting Genetic Algorithm) из библиотеки `pymoo`. На выходе — множество
Парето-оптимальных решений (конфигураций кабеля для каждого объекта).
Решения ранжируются по взвешенной сумме с весами пользователя.

UI: интерактивная Парето-диаграмма (Plotly.js scatter matrix — 5 осей,
каждая точка = одна конфигурация кабеля). Пользователь кликает по точке →
видит детализацию (марка, цена, энергопотребление). Кнопка «Применить ко
всем объектам» — выбирает для каждого объекта наилучшую марку по текущим весам.

Дополнительно: режим «Сравнение с текущим выбором» — тепловая карта (heatmap):
строки = объекты, столбцы = критерии, ячейки зелёные (оптимизатор предлагает
лучше) / красные (текущий выбор хуже по критерию).

**Технический контур:**

Backend: новый модуль `services/cable_optimizer.py`. Зависимость: `pymoo` (легковесная,
чистый Python, Apache 2.0). Оптимизация запускается асинхронно (фоновый таск Celery/RQ),
результаты кэшируются в `optimization_results` таблице. Внешняя БД (`cables_external`)
дополняется полями: `price_per_meter`, `mtbf_hours`, `efficiency`, `supply_lead_time_days`,
`min_bend_radius_mm`, `installation_labor_hours_per_100m`. Справочник монтажных норм:
`installation_norms.json` (ставки нормо-часов по типам кабеля и условиям прокладки).
Фронтенд: `CableOptimizerPanel.tsx` с Plotly.js для Парето-фронта и ECharts для
тепловой карты. Сложность: Medium.

**Почему это «продвинуто»:**

Текущий подбор — «бери первое подходящее». Оптимизатор — «покажи все
разумные варианты и дай выбрать по тому, что действительно важно для проекта».
Прямых аналогов в сегменте калькуляторов греющего кабеля нет. Thermon CompuTrace
показывает 2–3 альтернативы, но без численной оптимизации. HeatCalc получает
инструмент, который инженер-сметчик может использовать для обоснования выбора
перед заказчиком: «вот 5 вариантов, вариант В на 18% дороже в CAPEX, но
экономит 34% электроэнергии за 20 лет».

**Риски и ограничения:**

- Качество оптимизации на 100% зависит от полноты данных во внешней БД: если
  нет цен и MTBF, оптимизатор вырождается в однокритериальный. Решение: для
  марок без данных — исключать из оптимизации с пометкой «недостаточно данных».
- NSGA-II для 100 объектов × 30 марок кабеля (~3000 переменных) может требовать
  десятков секунд. Решение: запуск в фоне, кэширование, инкрементальный пересчёт
  только изменённых объектов.
- Веса критериев — субъективны. Решение: предустановленные профили («Бюджетный»,
  «Надёжный», «Энергоэффективный», «Быстросборный») как стартовые точки.

## F-04. WebGL-визуализатор трубопроводных трасс с тепловыми картами

**Категория:** 3D / Визуализация

**Приоритет:** P1 — тактический

**Аналоги:** AVEVA E3D (3D-визуализация технологических трубопроводов с
привязкой к данным), Trimble SysQue (MEP-системы в 3D поверх AutoCAD),
CesiumJS (геопространственная 3D-визуализация с тепловыми картами),
отечественный nanoCAD СПДС (3D-модель трассы с атрибутивной информацией).

**Проблема, которую решаем:**

Таблица из 80 строк с колонками «Ø108×4.0, δ=50 мм, q=42 Вт/м» не даёт
пространственного понимания проекта. Инженер (и особенно его руководитель /
заказчик) не видит:

- Где на трассе сосредоточены основные теплопотери?
- Какие участки подвержены максимальному ветровому воздействию?
- Как соотносятся диаметры труб и толщины изоляции на разных участках?
- Есть ли участки, где кабель подобран с чрезмерным запасом (переобогрев)?

3D-визуализация превращает таблицу в наглядную модель трассы, где каждый
трубопровод — цилиндр, цвет которого кодирует удельные теплопотери (синий =
минимальные, красный = критические). Это инструмент не столько для расчёта,
сколько для **коммуникации** — защита проекта перед заказчиком, презентация
руководству, выявление аномалий «на глаз».

**Инженерное описание:**

Сцена 3D строится на основе данных объектов проекта. Пользователь задаёт
(опционально) координаты объектов в пространстве — либо через ручной ввод
XYZ для каждого объекта в таблице, либо через импорт из BIM (F-05).
Если координаты не заданы — система автоматически раскладывает объекты
вдоль виртуальной трассы (горизонтальная линия с поворотами через каждые
10 объектов для читаемости, либо древовидная структура по подключению).

Каждый трубопровод отображается как цилиндр: диаметр = наружный диаметр трубы +
2 × толщина изоляции (визуальный масштаб — логарифмический для различимости
10 мм и 500 мм изоляции на одном экране), длина пропорциональна
pipe_length. Цвет цилиндра — continuous colormap от синего (q < 10 Вт/м)
до красного (q > 100 Вт/м), вычисляется в vertex shader (WebGL).

Резервуары — соответствующие 3D-примитивы (цилиндр, box, сфера) с цветовым
кодированием суммарных теплопотерь.

Дополнительные слои наложения (toggled checkboxes):

- **Ветровая нагрузка:** стрелки-векторы направления и силы ветра, цвет —
  α_внеш (зелёный — штиль, оранжевый — сильный ветер).
- **Глубина заложения:** для подземных участков — полупрозрачная плоскость
  грунта на уровне 0, труба под ней — darker shade.
- **Температурный профиль (F-01):** градиент цвета вдоль одного цилиндра,
  от T_входа до T_выхода.

Взаимодействие: OrbitControls (вращение, зум, панорамирование), клик по
цилиндру → подсветка + tooltip с ключевыми параметрами (имя, q, Q, марка
кабеля), двойной клик → переход к строке в таблице исходных данных.

Экспорт: скриншот текущего вида в PNG (для вставки в пояснительную записку),
данные сцены в glTF (для импорта в сторонние 3D-вьюеры).

**Технический контур:**

Фронтенд: `@react-three/fiber` + `@react-three/drei` (React-обёртки над Three.js).
Новый компонент `Trajectory3DViewer.tsx` на отдельной вкладке рабочего стола
«3D-трасса». Геометрия: цилиндры через `ExtrudeGeometry` вдоль сплайна
(CatmullRom), либо упрощённо — `CylinderGeometry` с трансформациями. Цветовой
шейдер: custom `ShaderMaterial`, uniform-переменная `u_q_min`, `u_q_max`,
vertex color вычисляется как `mix(u_color_low, u_color_high, (q - u_q_min) /
(u_q_max - u_q_min))`. Данные объектов подтягиваются через TanStack Query,
мемоизируются в геометрию. Никаких backend-изменений — чисто фронтенд-фича.
Зависимости: `three`, `@react-three/fiber`, `@react-three/drei` (уже популярны,
суммарно ~300 kB gzipped). Сложность: Medium.

**Почему это «продвинуто»:**

Ни «Тепломаг», ни Thermon CompuTrace, ни nVent TraceCalc Pro не имеют 3D.
Это шаг от «инженерной таблицы» к «цифровому двойнику». На презентации
заказчику — открыть 3D-трассу, показать тепловую карту: «вот здесь у нас
критический участок, мы предлагаем усилить изоляцию до 80 мм — смотрите,
цвет уходит из красного в жёлтый». Убойный аргумент.

**Риски и ограничения:**

- Координаты объектов: если не заданы — авто-раскладка может выглядеть
  неестественно для сложных разветвлённых трасс. Решение: для сложных
  проектов — обязательный импорт из BIM (F-05) либо ручная расстановка
  в 3D-редакторе (drag-n-drop цилиндров на сцене — future scope).
- Производительность: 200+ цилиндров с кастомными шейдерами на старом
  ноутбуке заказчика. Решение: InstancedMesh (один draw call на все цилиндры
  одного типа) + adaptive degradation (при FPS < 20 — отключать шейдер,
  показывать flat color).
- Мобильные устройства: 3D through WebGL на смартфоне — нецелевая платформа
  для данной фичи. PWA (F-09) получит упрощённый 2D-вид.

## F-05. Импорт из BIM-моделей (IFC 4.0) — автоматическое извлечение объектов

**Категория:** BIM / CAD интеграция

**Приоритет:** P0 — стратегический

**Аналоги:** Autodesk Revit + Insight (извлечение энергетической модели здания
из BIM), Solibri Model Checker (извлечение элементов из IFC + проверка правил),
отечественный Renga BIM (импорт/экспорт IFC для российских объектов), Trimble
Connect (облачная платформа для BIM-данных с API извлечения).

**Проблема, которую решаем:**

Проектные институты (НИПИ) моделируют трубопроводы в Revit / nanoCAD /
КОМПАС-3D / AVEVA E3D. В BIM-модели завода 200+ трубопроводов и 30+
резервуаров — с диаметрами, длинами, материалами изоляции, привязкой к
координатам. Сегодня инженер вручную перепечатывает эти параметры из
BIM-модели в HeatCalc, по 5–10 минут на объект. Для проекта из 200 труб это
15–30 человеко-часов монотонной работы, чреватой опечатками.

BIM-мандат для госзаказчиков РФ (Постановление Правительства № 331 от
05.03.2021) вступает в полную силу с 2026 года — все объекты госзаказа
обязаны проходить экспертизу в форме информационной модели. Импорт из BIM —
это не «nice to have», а обязательное условие для работы с госзаказчиком.

**Инженерное описание:**

Пользователь загружает IFC-файл (Industry Foundation Classes, ISO 16739,
версии 2×3 и 4.0) либо файл в формате КОМПАС-3D (CDW/SPW — через
промежуточную конвертацию в IFC штатным конвертером КОМПАС, либо напрямую
через API).

IFC-парсер (Python `ifcopenshell`) извлекает элементы следующих классов:

- `IfcPipeSegment` → Трубопровод: диаметр (`IfcPipeSegment.NominalDiameter` или
  геометрический параметр профиля), длина (вычисляется из геометрии —
  расстояние между портами соединения), материал стенки (из `IfcMaterial`),
  позиция в пространстве (XYZ начальной и конечной точки).
- `IfcTank` → Резервуар: тип геометрии (цилиндр / параллелепипед / сфера —
  определяется анализом геометрического представления), габариты (диаметр,
  высота, ширина — из параметров `IfcAdvancedBrep` или `IfcExtrudedAreaSolid`),
  позиция.
- Слои изоляции: извлекаются из `IfcCovering` с типом `INSULATION`, привязанного
  к элементу через `IfcRelCoversBldgElements`. Толщина и материал — из
  `IfcMaterialLayer` в составе `IfcMaterialLayerSetUsage`.

Правила маппинга «IFC Property Set → параметр HeatCalc» конфигурируются в
JSON-файле `ifc_mapping_rules.json` — это позволяет адаптировать импорт под
стандарты конкретного заказчика (у Газпрома одни property sets, у Роснефти —
другие, у западных EPC — третьи).

На выходе — список объектов HeatCalc, готовых к тепловому расчёту. Для каждого
объекта заполнены: геометрия, материал, изоляция, координаты. Не хватает:
температур (продукта, среды) — они задаются пользователем глобально на проект
через общие первичные данные (US-G-08).

Диалог импорта показывает: общее количество найденных элементов, сколько
успешно смаппилось, сколько пропущено (с причиной — «неизвестный класс»,
«не удалось извлечь диаметр»), предложение вручную донастроить маппинг для
пропущенных элементов.

Импорт не замещает существующие объекты, а добавляет новые. Конфликт имён
разрешается суффиксом «(BIM)».

**Технический контур:**

Backend: новый модуль `services/bim_import_service.py`. Зависимость:
`ifcopenshell` (open-source, LGPL, доступен для Linux/macOS/Windows,
скомпилированное расширение ~5 MB). Загрузка файла: `POST
/api/v1/projects/{id}/objects/import-ifc` (multipart form). Парсинг IFC —
потоковый (не загружать весь файл в память; typical IFC model — 50–500 MB).
Геометрические вычисления (длина из координат портов) — numpy.
Маппинг-правила: `reference_data/ifc_mapping_rules.json`, версионируются.

Модель данных: без изменений в основных таблицах. В объект добавляется
опциональное поле `bim_source: { ifc_guid, ifc_class, source_file }` для
трассировки. Для хранения координат: поле `position` (JSONB: `{x, y, z, ...}`)
в `object_params`.

Сложность: High (8 спринтов). Основная сложность — не в парсинге IFC (это
делает библиотека), а в геометрической интерпретации: IFC допускает множество
способов описания одной и той же геометрии (CSG, B-rep, extruded solid,
tessellated), и универсальный экстрактор «диаметр трубы из любой геометрии» —
это исследовательская задача. Прагматичный подход: поддержать 3 самых
распространённых представления (IfcExtrudedAreaSolid, IfcMappedItem,
IfcFacetedBrep) и для остальных выдавать «геометрия не поддерживается —
укажите параметры вручную».

**Почему это «продвинуто»:**

Прямая интеграция с BIM — это входной билет на рынок госзаказа с 2026 года.
Ни «Тепломаг», ни западные аналоги не имеют BIM-импорта. Тот, кто сделает
это первым, получает ~70% рынка проектных институтов нефтегазового сектора РФ,
обязанных работать в BIM.

**Риски и ограничения:**

- Разнообразие BIM-авторских систем: Revit экспортирует IFC с одной структурой
  property sets, AVEVA — с другой, КОМПАС — с третьей. Потребуется фаза
  нормализации: 2–3 месяца тестирования на реальных моделях заказчиков.
- Качество исходных BIM-моделей: во многих проектах изоляция не
  моделируется вообще (экономия времени BIM-моделлера). Решение: после импорта —
  подсветка объектов без изоляции, предложение задать глобально.
- Размер IFC-файлов (100+ MB) — загрузка через HTTP может быть медленной.
  Решение: chunked upload (Resumable.js) + фоновая обработка с прогресс-баром.

## F-06. Экспорт проектных данных в CAD-системы (DXF / CDW)

**Категория:** BIM / CAD интеграция

**Приоритет:** P1 — тактический

**Аналоги:** EPLAN Electric P8 (автоматическая генерация электрических схем
по спецификации), SEE Electrical (автоматическая раскладка кабельных трасс
на плане), отечественная «nanoCAD СПДС» (генерация схем трубопроводов из
табличных данных).

**Проблема, которую решаем:**

После расчёта и подбора кабеля в HeatCalc инженер должен перенести результаты
в CAD-систему для оформления проектной документации: план трассы с нанесёнными
греющими кабелями, схема подключения, кабельный журнал. Сегодня это делается
вручную: открывается nanoCAD, чертится линия трассы, вдоль неё ставятся
текстовые пометки «ТЛТ-50, 55 м». Для 80+ участков трассы это дни ручной
работы с риском ошибок в маркировке.

**Инженерное описание:**

HeatCalc генерирует CAD-файлы в формате DXF (Drawing eXchange Format,
поддерживается nanoCAD, КОМПАС, AutoCAD, BricsCAD и всеми российскими CAD)
со следующими слоями (layers):

- `HC-TRACE` — геометрия трассы (полилинии по координатам объектов, если
  заданы; если координат нет — схематическая прямая развёртка с равным
  шагом)
- `HC-CABLE-LABEL` — текстовые метки у каждого сегмента: марка кабеля,
  длина, мощность
- `HC-HEAT-ZONES` — зоны обогрева (прямоугольники вокруг групп объектов с
  одинаковым кабелем)
- `HC-JUNCTION-BOX` — места установки соединительных коробок (условные
  обозначения)
- `HC-SPEC-TABLE` — таблица-спецификация как AutoCAD Table entity

Шаблоны оформления (толщины линий, шрифты по ГОСТ 2.304, рамка по
ГОСТ 2.301) настраиваются в профиле проекта и сохраняются.

Для КОМПАС-3D — дополнительный формат CDW (через КОМПАС-Макро API, требует
Windows-сервер с установленным КОМПАС) или промежуточный XML-формат КОМПАС
(документирован частично, но достаточен для отрисовки линий и текста).

Пользовательский поток: на странице «Отчёт» → кнопка «Экспорт чертежа
(DXF)» → диалог: выбор масштаба, слоёв, формата листа → скачивание файла.
Файл сразу открывается в CAD-системе инженера.

**Технический контур:**

Backend: новый модуль `services/cad_export_service.py` с классом `DXFExporter`.
Зависимость: `ezdxf` (Python, MIT license, зрелая, активная, поддержка DXF R2018).
Алгоритм: для каждого объекта → создать полилинию, добавить MTEXT с параметрами,
сгруппировать в блоки по типу кабеля. Файл может быть большим (200+ объектов →
5000+ entities) — генерация ~1–2 секунды, кэшируется в `/tmp`.
API: `GET /api/v1/projects/{id}/export/dxf?scale=1:100&layers=all`

Для CDW: опционально — `kompas-api` (Python-обёртка над КОМПАС-Макро API,
требует Windows-сервер) либо генерация КОМПАС-XML напрямую (менее надёжно,
но не требует лицензии КОМПАС на сервере).

Сложность: Medium (4 спринта для DXF; CDW — ещё +2 спринта при наличии
лицензии КОМПАС).

**Почему это «продвинуто»:**

Ни один калькулятор греющего кабеля не генерирует CAD-чертежи автоматически.
Это превращает HeatCalc из «калькулятора» в «инструмент автоматизированного
проектирования» — прямой конкурент связке «Excel + ручное черчение в nanoCAD»,
которая сегодня является стандартом де-факто в российских ПТО.

**Риски и ограничения:**

- DXF — формат, но не стиль оформления. У каждого заказчика свои требования
  к чертежам (рамка, штамп, шрифт). Решение: настраиваемые шаблоны через
  параметры проекта или профиль организации (F-15).
- КОМПАС-XML обратно не совместим между версиями КОМПАС-3D v19 и v21.
  Решение: поддержка версий через конфигурацию, в первом релизе — только DXF.
- Качество авто-раскладки без координат объектов: схематическая прямая —
  не годится для реальных трасс. Решение: для полноценных чертежей требуются
  координаты из BIM-импорта (F-05) или ручного ввода.

## F-07. Версионирование проектов (Git-like снапшоты, diff, merge)

**Категория:** Коллаборация и версионирование

**Приоритет:** P1 — тактический

**Аналоги:** Git (контентно-адресуемое версионирование с криптографическими
хэшами), Onshape (CAD-версионирование с возможностью отката к любой точке
истории и сравнения версий), Autodesk Vault (PDM-система с audit trail и
версионированием инженерных данных), Google Docs Version History (мгновенные
снапшоты с визуальным diff).

**Проблема, которую решаем:**

Инженер итерирует проект: «Вариант с минватой 50 мм → нет, много потерь.
Поменял на ППУ 60 мм. Пересчитал. Добавил ещё 3 трубы. Сменил кабель
с ТЛТ-50 на ТТ Р1-60...» Через неделю руководитель спрашивает: «А почему
мы отказались от минваты? У нас на складе её 2 км осталось». Инженер не помнит.
Нет возможности сравнить текущее состояние с позавчерашним.

Отсутствие версионирования — это не только неудобство, но и **юридический
риск**: невозможно доказать, кто и когда внёс изменение, приведшее к ошибке
в расчёте (авария на объекте → расследование → «покажите původní
расчёт»).

**Инженерное описание:**

Система автоматически создаёт снапшот (snapshot) проекта при каждом значимом
действии:

- Добавление / изменение / удаление объекта
- Запуск электрорасчёта
- Изменение общих первичных данных
- Ручной снапшот пользователем («Сохранить версию» с комментарием, аналог
  `git commit -m`)

Снапшот — это полная копия состояния проекта на момент времени: объекты
(с params), результаты heat_calc, результаты electrical_calc для всех CO,
активный CO, спецификация, общие первичные данные, версии справочников и
коэффициентов.

Хранение: контентно-адресуемое (content-addressable storage). Состояние
проекта сериализуется в JSON, хэшируется (SHA-256), сохраняется в таблицу
`project_snapshots (id, project_id, snapshot_hash, parent_hash, timestamp,
user_id, comment, state_jsonb)`. Одинаковые состояния (например, два снапшота
подряд без изменений) дают одинаковый хэш → дедупликация на уровне хранения
(повторный снапшот не создаётся).

Функции UI:

- **Timeline:** вертикальная шкала снапшотов с датами и комментариями.
  Клик → восстанавливается read-only представление проекта на тот момент
  (отдельная модалка или параллельная вкладка «Просмотр версии»).
- **Diff:** сравнение двух снапшотов. Выводится: список добавленных объектов
  (зелёный), удалённых (красный), изменённых (жёлтый). Для изменённого
  объекта — по полям: «Толщина изоляции: 50 → 60 мм (+20%)», «q: 42 → 35
  Вт/м (−16.7%)», «Марка кабеля: ТЛТ-50 → ТЛТ-40». Diff визуализируется
  как side-by-side таблица.
- **Rollback:** восстановление состояния из снапшота как новой версии
  (текущее состояние не теряется — создаётся новый снапшот с parent_hash =
  восстанавливаемого, комментарий: «Откат к версии от 03.05.2026, причина:
  ошибка в подборе изоляции»).
- **Blame:** для каждого параметра объекта — «кто и когда последний раз менял»
  (аналог `git blame`). Выводится как tooltip при наведении на поле в форме.

**Технический контур:**

Backend: новый сервис `services/versioning_service.py` с методами
`create_snapshot(project_id, comment)`, `diff_snapshots(hash_a, hash_b)`,
`restore_snapshot(hash)`. Модель данных: таблица `project_snapshots` +
индексы на `(project_id, timestamp)`, `(snapshot_hash)` UNIQUE.

Объём хранения: снапшот проекта со 100 объектами — ~500 KB JSON. 100
снапшотов = 50 MB. Для 1000 проектов × 100 снапшотов = 50 GB — приемлемо
для PostgreSQL (JSONB compressed). Дедупликация по хэшу сокращает объём
в ~3 раза (соседние снапшоты отличаются на 2–3 объекта).

Diff-алгоритм: рекурсивное сравнение двух JSONB-деревьев через `deepdiff`
Python-библиотеку. Результат диффа кэшируется.

API: `POST /api/v1/projects/{id}/snapshots` (создать), `GET .../snapshots`
(список), `GET .../snapshots/diff?from=<hash>&to=<hash>` (сравнение),
`POST .../snapshots/{hash}/restore` (восстановить).

Фронтенд: `VersionTimeline.tsx` (Ant Design Timeline), `VersionDiffPanel.tsx`
(кастомная side-by-side таблица), интеграция в меню проекта.

Сложность: Medium (5 спринтов).

**Почему это «продвинуто»:**

Ни «Тепломаг», ни западные калькуляторы не имеют версионирования. Это
поднимает HeatCalc на уровень промышленных PDM/PLM-систем (Autodesk Vault,
Siemens Teamcenter), но без их монструозной сложности — только то, что нужно
инженеру для воспроизводимости и аудита расчётов.

**Риски и ограничения:**

- Хранение снапшотов требует дискового пространства и политики retention
  (удаление снапшотов старше 90 дней? настраивается администратором).
- Diff для 100+ объектов — вычислительно лёгкая операция, но UI должен быть
  продуман: как показать 50 изменённых объектов на одном экране? Решение:
  группировка изменений по типу (геометрия / изоляция / кабель / результаты),
  фильтрация по значимости (>5% изменения q/Q).
- Снапшоты включают версию справочников — если справочники обновляются
  администратором, старый снапшот может ссылаться на несуществующие марки
  кабеля. Решение: справочники хранить как `reference_snapshots` (иммутабельные
  копии на момент снапшота) — либо просто сохранять `reference_version_id`.

## F-08. Расчёт совокупной стоимости владения (TCO)

**Категория:** Экономика и TCO

**Приоритет:** P0 — стратегический

**Аналоги:** nVent RAYCHEM TraceCalc Pro (базовый модуль расчёта
энергопотребления), Thermon CompuTrace (TCO-калькулятор с ценами на
электричество и обслуживание), Bentley AutoPIPE (lifecycle cost analysis
для трубопроводных систем), отечественная сметная программа «Гранд-Смета»
(расчёт стоимости монтажа по нормативам).

**Проблема, которую решаем:**

Инженер подбирает кабель по техническим критериям. Но решение о закупке
принимает не инженер, а **руководитель проекта** или **заказчик**, для
которого главный критерий — деньги. Диалог типичен:

— «Почему ТЛТ-50, а не ТТ Р1-60? ТЛТ в 1.5 раза дороже за метр!»
— «Потому что у ТЛТ КПД выше и срок службы больше.»
— «Насколько больше? В рублях? За 20 лет?»

Текущий инструмент не даёт ответа на этот вопрос. Инженер вынужден
вручную считать в Excel: цена кабеля, цена монтажа, годовое
энергопотребление, дисконтирование... Это часы работы для проекта
из 50+ объектов.

**Инженерное описание:**

TCO-калькулятор работает на уровне варианта расчёта (CO1..CO4). Для каждого
варианта вычисляются:

**CAPEX (капитальные затраты, рубли):**

- Стоимость кабеля = Σ (цена_i × длина_i) для всех объектов
- Стоимость аксессуаров = Σ (количество × цена) из спецификации
- Стоимость монтажа = Σ (нормо-часы_i × ставка_нормо-часа) для всех объектов

Цены берутся из расширенной внешней БД (поле `price_per_meter` для кабелей,
`price_per_unit` для аксессуаров). Тариф нормо-часа задаётся в общих
первичных данных проекта (по умолчанию — 2500 руб./час для РФ, 2026).

**OPEX (операционные затраты, рубли):**

- Годовое энергопотребление = Σ (P_total_i × 8760 часов × K_загрузки) / 1000
  [кВт·ч], где K_загрузки — коэффициент использования (по умолчанию 0.5 —
  средний за год с учётом сезонности)
- Годовые затраты на электроэнергию = годовое потребление × тариф (руб./кВт·ч,
  из общих первичных данных)
- Годовые затраты на обслуживание = количество объектов × трудоёмкость ТО
  (чел.-часов/год) × ставка
- Затраты на замену кабеля: в год ожидаемой замены (срок_службы_кабеля) —
  CAPEX кабельной части заново

**NPV (чистая приведённая стоимость, рубли):**

NPV = CAPEX_initial + Σ_{t=1..T} (OPEX_t / (1 + r)^t) + CAPEX_replacement_t / (1 + r)^t

где T — горизонт расчёта (по умолчанию 20 лет), r — ставка дисконтирования
(по умолчанию 12% — типично для нефтегазовых проектов РФ).

UI: страница «Экономика» (или вкладка в электрорасчёте). Верхняя панель —
гистограмма CAPEX + OPEX (стековая, 4 столбца = CO1..CO4). Нижняя панель —
таблица: строки = варианты CO, столбцы = CAPEX / OPEX_год / OPEX_20yr / NPV
/ Срок окупаемости доп. CAPEX. Минимальный NPV подсвечивается зелёным.

Дополнительно: waterfall chart («каскадная диаграмма») — от начального CAPEX
через ежегодные затраты к NPV, для одного варианта. График «Накопленные затраты
по годам» — пересечение кривых CO1 vs CO2 показывает год окупаемости более
дорогого варианта.

Все параметры (тариф, ставка, горизонт, K_загрузки) — редактируемые,
результат пересчитывается на лету на фронте (формулы простые, бэкенд не нужен).

**Технический контур:**

Основная логика — на фронте (чистые функции в `utils/tcoCalculator.ts`),
поскольку все исходные данные (цены, мощности, длины) уже есть в состоянии
проекта. Бэкенд-изменения минимальны: внешняя БД дополняется ценовыми полями
(см. F-03). API для получения цен: `GET /api/v1/references/cable-prices`
возвращает массив `{cable_mark, price_per_meter, updated_at}`.

Справочник тарифов на электроэнергию: `reference_data/energy_tariffs.json` —
по регионам РФ (можно взять из открытых данных ФАС). Монтажные нормы:
`reference_data/installation_labor_norms.json` — нормо-часы на 100 м кабеля
по типам и условиям прокладки (надземно / подземно / в помещении).

Фронтенд: новый компонент `TcoPanel.tsx` с Recharts для графиков. Интегрируется
как отдельная вкладка в электрорасчёт («Экономика») или как секция в
сравнении вариантов CO. Сложность: Low (3 спринта — в основном фронтенд).

**Почему это «продвинуто»:**

Текущий инструмент — «технический калькулятор». TCO превращает его в
«инструмент принятия инвестиционных решений». Это поднимает целевую
аудиторию с инженера ПТО до руководителя проекта и технического директора —
людей с бюджетом.

**Риски и ограничения:**

- Точность TCO на 100% зависит от точности цен в БД. Устаревшая цена на
  кабель → NPV искажён → неверное решение. Решение: поле `price_updated_at`,
  предупреждение в UI «цены старше 90 дней».
- Тарифы на электроэнергию для промпотребителей — коммерческая тайна,
  открытые данные ФАС — только ориентир. Решение: возможность ручного ввода
  тарифа для проекта.
- Монтажные нормы варьируются между подрядчиками в разы. Решение:
  настраиваемые нормы в проекте/профиле организации.

## F-09. Мобильное PWA-приложение для полевого инженера

**Категория:** Мобильность и полевая работа

**Приоритет:** P1 — тактический

**Аналоги:** Autodesk BIM 360 Field (полевая инспекция строительства с
фотофиксацией, привязкой к модели, офлайн-режимом), PlanGrid (строительный
punch list с чек-листами и синхронизацией), отечественный «СтройКонтроль»
(полевой контроль строительства с фото и GPS), «Мобильный обходчик» от 1С
(офлайн-чекины на оборудовании).

**Проблема, которую решаем:**

Инженер на стройплощадке должен верифицировать: «Соответствует ли смонтированная
система обогрева проекту?» Сегодня его инструменты: бумажная распечатка
спецификации (которая намокает / теряется), ручка, телефон для фото.
Интернета на площадке часто нет (КСП в тундре, нефтепровод в тайге).

Результат: акт приёмки заполняется по памяти вечером в бытовке, фотографии
монтируемых участков разбросаны по галерее телефона без привязки к объектам
проекта, идентификация кабельных бухт — визуально («вроде ТЛТ-50, вон та
бухта в углу»). Ошибки монтажа (перепутан кабель между участками) выявляются
только при пусконаладке — ценой дорогостоящих переделок.

**Инженерное описание:**

HeatCalc PWA — это не отдельное приложение, а **режим полевого инженера**
внутри существующего веб-приложения, доступный с мобильного устройства.
Ключевые возможности:

- **Офлайн-режим:** Service Worker кэширует данные активного проекта
  (объекты + спецификация + отчёт). При заходе на площадку без интернета —
  все данные доступны в IndexedDB. Действия накапливаются в очереди и
  синхронизируются при появлении сети (Background Sync API).

- **Чек-лист монтажа:** для каждого объекта проекта — список контрольных
  точек: «Изоляция соответствует проекту?», «Марка кабеля подтверждена?»,
  «Шаг навива соблюдён?», «Соединительная муфта герметична?». Каждый пункт —
  переключатель «✓ / ✗ / N/A». По completion — объект отмечается как
  «верифицирован» (зелёный значок в общем проекте).

- **Сканирование маркировки:** камера телефона → сканирование QR-кода
  или Data Matrix с бухты кабеля → автоматическая сверка с проектной
  маркой. При несовпадении — красный alert: «Ожидается ТЛТ-50, сканирован
  ТЛТ-40 — замените бухту!» (движок: `jsQR` на WebAssembly, работает
  офлайн).

- **Фотофиксация:** снимок смонтированного участка камерой телефона →
  автоматическая привязка к объекту, GPS-координаты из EXIF, временна́я
  метка. Фото сохраняется локально, при синхронизации загружается в
  объектное хранилище (MinIO / S3) и привязывается к объекту в БД.

- **Голосовые заметки:** «Участок 14: труба под землёй на глубине
  не 1.5 м, а 1.2 м — нужен пересчёт» → распознавание речи (Web Speech
  API, работает офлайн в Chrome) → текстовая заметка к объекту.

- **Push-уведомления:** руководитель в офисе назначает полевому инженеру
  задачу «Верифицировать участки 14–27» → push-уведомление на телефон
  (через Service Worker Push API).

**Технический контур:**

Фронтенд: PWA-обвязка существующего React-приложения. `vite-plugin-pwa`
(Workbox) для генерации Service Worker с настройкой кэширования API-ответов
и статики. IndexedDB-слой через `idb` (Promise-based обёртка) или
`Dexie.js` (более удобное API). Синхронизация: очередь действий в IndexedDB,
при online — `navigator.onLine` + Background Sync → отправка накопленных
POST/PUT запросов.

Бэкенд: API для синхронизации — существующие эндпоинты, плюс batch-эндпоинт
`POST /api/v1/projects/{id}/sync` (принимает массив полевых действий: фото,
заметки, статусы чек-листа). Медиа-файлы: `POST .../objects/{id}/media`
(multipart), хранятся в MinIO (S3-совместимое хранилище) или локальной
файловой системе (dev).

Новые таблицы БД: `field_verifications (id, project_id, object_id, user_id,
checklist_items JSONB, notes TEXT, verified_at)`, `object_media (id,
object_id, media_type, s3_key, gps_lat, gps_lng, captured_at)`.

Сложность: Medium (5 спринтов). Основная сложность — надёжность офлайн-
синхронизации: конфликты (полевой инженер изменил статус объекта, в это же
время офисный инженер пересчитал кабель), разрешение конфликтов
(last-write-wins с уведомлением о конфликте).

**Почему это «продвинуто»:**

Ни один инструмент для расчёта греющего кабеля не имеет мобильного
компонента. Это мост между «спроектировали в офисе» и «построили в поле».
Сокращает время приёмки системы обогрева на площадке с 3–5 дней до
4–6 часов за счёт мгновенной верификации и отсутствия ручного ввода
данных задним числом.

**Риски и ограничения:**

- iOS-ограничения PWA (нет Background Sync, ограниченный Service Worker
  cache, нет Web Speech API offline). Решение: деградация — на iOS
  функционал работает только онлайн, без фоновой синхронизации.
- Качество камеры и освещения на площадке: QR-код на грязной, заснеженной
  бухте может не читаться. Решение: fallback — ручной ввод серийного
  номера.
- GPS-точность в условиях плотной застройки / внутри цеха — до 10–15 м.
  Решение: ручная коррекция координат в интерфейсе.

## F-10. Интеграция с АСУ ТП — экспорт конфигураций контроллеров и мониторинг

**Категория:** Интеграция с АСУ ТП / SCADA

**Приоритет:** P1 — тактический

**Аналоги:** Siemens SIMATIC PCS 7 Engineering (генерация конфигурации
контроллеров из проектных данных), nVent RAYCHEM NGC-30/NGC-40 (фирменная
система управления обогревом с автоматической загрузкой конфигурации из
TraceCalc Pro), ABB 800xA (интеграция engineering data → controller
configuration), отечественные ОВЕН ПЛК + OwenConfigurator (импорт настроек
из CSV).

**Проблема, которую решаем:**

После проектирования системы обогрева в HeatCalc инженер-проектировщик
передаёт результаты (спецификацию, схему, таблицу мощностей) инженеру-КИПиА,
который программирует контроллеры (ПЛК) для управления обогревом. Передача —
бумажная или через Excel. Инженер КИПиА вручную набивает уставки температур,
мощности зон, аварийные пороги в конфигураторе контроллера. Ошибка в одной
цифре → зона недогрета / перегрева → авария на производстве.

Обратная связь отсутствует: если смонтированная система обогрева работает
не так, как рассчитано (например, реальные теплопотери выше проектных из-за
брака изоляции), проектировщик об этом не узнает — до следующего проекта
с теми же ошибками.

**Инженерное описание:**

Фича состоит из двух частей: **экспорт** (design → controller) и **мониторинг**
(controller → design feedback).

**Часть 1 — Экспорт конфигураций:**

Для каждого поддерживаемого контроллера — адаптер, генерирующий файл
конфигурации из результатов расчёта HeatCalc:

- **ОВЕН ПЛК (наиболее распространён в РФ):** экспорт CSV-файла для
  OwenConfigurator: таблица зон обогрева (номер зоны, имя, уставка
  температуры, макс. мощность, тип датчика, аварийный порог).
  Маппинг: 1 объект HeatCalc = 1..N зон обогрева (N = количество сегментов
  из F-01, либо 1 зона на объект).

- **Siemens S7-1200/1500:** экспорт XML для TIA Portal — структура
  данных блока (DB) с массивами зон. Требует лицензионный TIA Portal
  для последующей загрузки, но генерация XML — без лицензии.

- **Termodat (российский производитель терморегуляторов):** экспорт
  бинарного файла конфигурации в фирменном формате (опционально, через
  реверс-инжиниринг или партнёрство).

- **OPC UA (универсальный):** генерация OPC UA Nodeset XML — зоны обогрева
  как объекты в адресном пространстве OPC UA. Поддерживается любым
  OPC UA-клиентом (SCADA-системы: MasterSCADA, WinCC, InTouch).

Пользователь на странице «Электрорасчёт» выбирает: «Экспорт → Конфигурация
контроллера», тип контроллера, маппинг объектов на зоны. Скачивается файл
конфигурации.

**Часть 2 — Мониторинг (цифровой двойник):**

Обратный поток: контроллер (или SCADA) периодически отправляет в HeatCalc
данные фактических температур и потребляемой мощности по каждой зоне обогрева:

- MQTT-топик: `heating/{project_id}/{zone_id}/telemetry` (JSON с
  температурой, мощностью, статусом)
- Альтернативно: REST `POST /api/v1/projects/{id}/telemetry` (батч-эндпоинт,
  массив измерений)

HeatCalc сохраняет телеметрию в TimescaleDB (расширение PostgreSQL для
временны́х рядов, высокая производительность записи и запросов по времени).
На странице мониторинга для каждого объекта:

- График «Проектная vs Фактическая температура» — две линии, расхождение > X%
  подсвечивается
- График «Проектная vs Фактическая мощность обогрева»
- Индикатор статуса: 🟢 норма, 🟡 отклонение < 5%, 🔴 аномалия (> 10%)

Система автоматически формирует отчёт «Анализ эффективности системы обогрева»
для экспорта: таблица зон с отклонениями, рекомендации (усилить изоляцию на
зоне 14, пересмотреть марку кабеля на зоне 27).

**Технический контур:**

Экспорт: новый модуль `services/controller_export_service.py` с
плагинной архитектурой (адаптеры в `exporters/` — `owen.py`, `siemens.py`,
`opcua.py`, каждый реализует интерфейс с методом `generate_config(project,
zone_mapping)`). OPC UA: `asyncua` Python-библиотека для генерации
Nodeset XML (сервер не требуется — только генерация файла).
API: `GET /api/v1/projects/{id}/export/controller-config?type=owen`

Мониторинг: TimescaleDB как дополнительный контейнер в docker-compose
(либо hypertable в существующем PostgreSQL через расширение `timescaledb`).
MQTT-брокер: VerneMQ или Mosquitto (лёгкие, open-source). API для
телеметрии: новый эндпоинт `POST /api/v1/projects/{id}/telemetry`,
middleware для MQTT → HTTP bridge.

Фронтенд: `ControllerExportDialog.tsx` (Ant Design Modal с выбором типа
контроллера и маппингом), `MonitoringDashboard.tsx` (графики через ECharts
с подпиской на обновления через WebSocket / Server-Sent Events).

Сложность: High (8 спринтов — две независимые части; экспорт — 3 спринта,
мониторинг — 5).

**Почему это «продвинуто»:**

Это превращает HeatCalc из «инструмента этапа П» (проектирование) в
«инструмент всего жизненного цикла»: П → С (строительство) → Э (эксплуатация).
nVent RAYCHEM пытается делать это через свою закрытую экосистему (TraceCalc →
NGC контроллеры), но только для своего оборудования. HeatCalc может стать
открытой альтернативой, поддерживающей любые контроллеры.

**Риски и ограничения:**

- Маппинг «объект HeatCalc → зона обогрева в контроллере» — не 1:1.
  Один объект может требовать нескольких зон (разные температурные режимы
  по длине), несколько объектов могут быть объединены в одну зону.
  UI маппинга может быть сложным. Решение: начать с простого маппинга
  1:1, затем добавлять гибкость.
- MQTT/телеметрия требует сетевой связности контроллера с сервером
  HeatCalc — на многих объектах это невозможно (закрытый контур АСУ ТП).
  Решение: офлайн-режим — экспорт логов контроллера на флешку, ручная
  загрузка CSV-файла телеметрии в HeatCalc для анализа.
- Интеграция с Siemens TIA Portal требует глубокого знания формата XML
  экспорта — может потребоваться партнёрство с системным интегратором
  Siemens.

## F-11. Предиктивный подбор теплоизоляции на основе машинного обучения

**Категория:** AI / Аналитика

**Приоритет:** P2 — на вырост

**Аналоги:** Autodesk Revit + Generative Design (ML-генерация вариантов
планировки с оптимизацией по заданным критериям), AspenTech Aspen IQ
(ML-модели для предсказания параметров технологических процессов на основе
исторических данных), McKinsey's ML-решения для нефтегаза (предиктивный
анализ отказов оборудования по историческим данным), отечественная
«Цифровая нефть» (Газпром нефть — предиктивная аналитика для нефтедобычи).

**Проблема, которую решаем:**

Подбор толщины и материала теплоизоляции — итеративный процесс: инженер
пробует 50 мм → q = 42 Вт/м → «много»; 60 мм → q = 35 Вт/м → «нормально»;
80 мм → q = 26 Вт/м → «слишком дорого, и так сойдёт». Этот процесс
повторяется для каждого объекта. Для 100 труб это часы рутины.

При этом в базе данных HeatCalc накоплены **реальные расчёты и утверждённые
проектные решения** (история из F-07). Это ценнейший датасет: для каждой
комбинации «диаметр трубы × температура продукта × климат × тип изоляции»
известно, какую толщину изоляции в итоге утвердил инженер. Можно обучить
модель, которая по входным параметрам объекта **предсказывает наиболее
вероятную толщину и материал изоляции**, которые «одобрил бы опытный
инженер».

**Инженерное описание:**

**Датасет:** извлекается из таблицы `heat_calculations` (обезличенно):
- Признаки (features): `outer_diameter`, `pipe_length`, `T_product`,
  `T_ambient`, `insulation_material`, `wind_speed`, `is_underground`,
  `soil_thermal_conductivity`, количество слоёв изоляции, `pipe_material`,
  `climate_region`
- Целевые переменные (targets): `insulation_thickness` (регрессия),
  `insulation_material` (классификация)

**Модель:** ансамбль градиентного бустинга — LightGBM (быстрее и точнее
XGBoost на табличных данных, меньше памяти, хорошо работает на малых
выборках от 500 записей). Две модели:
- Регрессор: предсказание толщины изоляции (мм)
- Классификатор: предсказание материала изоляции (6 классов)

**Обучение:** batch-процесс по расписанию (раз в неделю или по накоплению
+100 новых утверждённых проектов). Запускается в фоне (Celery Beat).
Модель сохраняется в формате ONNX (Open Neural Network Exchange) для
выполнения инференса без GPU в рантайме.

**Инференс:** при добавлении нового объекта → параллельно с обычным
расчётом теплопотерь вызывается `POST /calc/ml/predict-insulation`
→ возвращается:
```json
{
  "recommended_thickness_mm": 72,
  "confidence_interval_mm": [62, 82],
  "recommended_material": "mineral_wool",
  "material_confidence": 0.87,
  "similar_cases_count": 14,
  "expected_q_w_per_m": 31.5,
  "explanation": "Основано на 14 аналогичных трубопроводах Ø108 мм
                  в климатической зоне Москвы с T_продукта 80°C."
}
```

В UI формы SC-03 рядом с полем «Толщина изоляции» появляется подсказка:
«Рекомендация ML: 72 мм (уверенность 82%, на основе 14 похожих проектов).
Нажмите, чтобы применить.» Клик → поле заполняется рекомендованным значением.

**Мониторинг дрейфа модели:** раз в месяц автоматически сравнивается точность
предсказаний на новых проектах. При падении R² ниже порога — уведомление
администратору о необходимости переобучения.

**Технический контур:**

Обучение: Python-скрипт `services/ml/train_insulation_model.py` с
`lightgbm`, `scikit-learn` (разбиение train/test, кросс-валидация, расчёт
метрик). Запускается Celery-таском. Пайплайн обучения логируется в
`ml_training_runs` таблице (метрики, размер датасета, версия модели).
Инференс: `services/ml/predictor.py` — загрузка ONNX-модели через
`onnxruntime`, преобразование признаков из Pydantic-схемы → numpy array,
предикт. Модель хранится в БД (бинарное поле) или в S3/MinIO.

Датасет: SQL-запрос, материализованное представление `mv_ml_training_data`
(обновляется перед обучением), с фильтрацией выбросов (изоляция 0 мм,
T > 600°C — явные ошибки) и нормализацией.

Фронтенд: компонент `MLInsulationHint.tsx` — небольшой callout под полем
толщины изоляции. При отсутствии достаточного количества похожих случаев
(< 5) — подсказка не показывается, чтобы не вводить в заблуждение.

Сложность: Medium (4 спринта — основная работа в подготовке датасета
и валидации модели, а не в коде).

**Почему это «продвинуто»:**

ML в нишевом инженерном B2B-продукте — это сильный дифференциатор.
Ни «Тепломаг», ни западные TraceCalc/CompuTrace не имеют предиктивных
моделей. Для заказчика это выглядит как «искусственный интеллект,
который учится на опыте всех проектов компании и подсказывает инженеру».
При достаточном объёме данных (> 1000 размеченных проектов) точность
предсказаний может достигать ±8–12% — сопоставимо с точностью инженера,
но мгновенно.

**Риски и ограничения:**

- Холодный старт: для обучения нужно минимум 300–500 записей с
  утверждёнными параметрами изоляции. На старте у одного заказчика —
  десятки, этого мало. Решение: предобучить на синтетических данных
  (рассчитанных по формулам с оптимальной толщиной методом перебора),
  затем дообучать на реальных проектах.
- Доверие инженеров к «чёрному ящику»: «Почему модель предложила 72 мм,
  а не 70?» Решение: обязательный explainability — вывод «similar cases»
  с конкретными параметрами соседей и величиной их вклада (SHAP values),
  указание confidence interval.
- Смещение данных: если все проекты от одного заказчика (например,
  «Газпром» с завышенными нормами), модель будет давать завышенные
  рекомендации для другого заказчика. Решение: fine-tuning модели под
  профиль организации (F-15).

## F-12. Автоматический нормативный контроль (rule engine)

**Категория:** Нормативно-правовая база

**Приоритет:** P0 — стратегический

**Аналоги:** Solibri Model Checker (автоматическая проверка BIM-модели на
соответствие строительным нормам), SmartPlant P&ID Engineering Rules
(rule-based проверка технологических схем на соответствие стандартам),
отечественная «Экспертиза-Онлайн» (платформа для прохождения государственной
экспертизы проектной документации).

**Проблема, которую решаем:**

Проектная документация на систему электрообогрева до передачи заказчику
проходит экспертизу (Главгосэкспертиза для госзаказа, внутренняя
экспертиза для корпоративных проектов). Эксперт проверяет проект на
соответствие десяткам нормативных документов:

- СП 61.13330.2012 «Тепловая изоляция оборудования и трубопроводов»
- СП 50.13330.2012 «Тепловая защита зданий» (для обогрева резервуаров)
- ПУЭ (Правила устройства электроустановок) — раздел 6: «Электрическое
  отопление»
- ГОСТ Р 50571 «Электроустановки низковольтные»
- ВНТП, СТО конкретного заказчика (Газпром, Роснефть, Транснефть)

Сегодня инженер проверяет compliance вручную (держит нормативы в голове или
рядом на полке). Результат: человеческий фактор — пропуск требования →
отрицательное заключение экспертизы → возврат проекта на доработку →
потеря 2–4 недель и репутационные издержки.

**Инженерное описание:**

Декларативный rule engine, где каждое правило — JSON-объект вида:

```json
{
  "rule_id": "SP61_5.2_min_thickness",
  "description": "Минимальная толщина теплоизоляции по СП 61.13330 п. 5.2",
  "source": "СП 61.13330.2012",
  "clause": "п. 5.2, таблица 1",
  "severity": "error",
  "condition": {
    "field": "outer_diameter",
    "operator": "in_range",
    "value": [0, 0.057],
    "then": {
      "field": "insulation_thickness",
      "operator": "gte",
      "value": 0.030,
      "unit": "m",
      "message": "Для труб диаметром до 57 мм минимальная толщина изоляции — 30 мм (СП 61.13330 п. 5.2)"
    }
  }
}
```

Правила группируются по источникам (СП 61, ПУЭ, ГОСТ Р) и хранятся
версионно в `reference_data/regulations/` как JSON-файлы. Администратор
через панель `/admin/regulations` может: просматривать правила,
активировать / деактивировать (если заказчик соблюдает не все нормы,
а только выбранные), редактировать параметры.

Проверка запускается:
- **Автоматически** при сохранении объекта (результат — иконка ✅/⚠️/⛔
  в строке таблицы)
- **По кнопке «Проверить проект»** на рабочем столе — полный прогон
  всех правил по всем объектам + общие проверки проекта (суммарная
  мощность не превышает выделенную, падение напряжения в допустимых
  пределах)

Результат — «Лист соответствия нормативам» (Compliance Report):
- Сводка: «Пройдено: 42 / Предупреждений: 3 / Нарушений: 2»
- Таблица нарушений: объект, правило, пункт норматива, текущее значение,
  требуемое значение, severity
- Экспорт листа в PDF (для приложения к проектной документации)

Отдельный режим: «Предэкспертный прогон» — симуляция проверки внешним
экспертом, с максимально строгими порогами и всеми активными правилами
(включая обычно отключённые).

**Технический контур:**

Rule engine: Python, кастомный интерпретатор правил в `services/rule_engine.py`.
Правила компилируются в вызываемые функции (через `compile()` или `eval()` —
**внимание**: требуется sandbox-изоляция, только разрешённые операторы,
белый список полей). Альтернативно — библиотека `durable_rules`
(open-source rule engine, но может быть overkill для нашей задачи).

Правила: `reference_data/regulations/sp61.json`, `pue.json`, `gost_r.json`
и т.д. Версионируются (Git-like в `regulations` репозитории или в БД).

API: `POST /api/v1/projects/{id}/compliance-check` → возвращает
`ComplianceReport`. Кэшируется до следующего изменения объекта.

Фронтенд: `CompliancePanel.tsx` — вкладка на рабочем столе или доступ
из меню. Таблица нарушений с сортировкой по severity и возможностью
раскрыть детали.

Сложность: Medium (4 спринта). Основная сложность — не в движке
(интерпретатор правил пишется за 2–3 дня), а в **наполнении базы
правил**. Требуется инженер-нормоконтролёр, который переведёт
положения СП/ГОСТ/ПУЭ в формат JSON-правил. Оценка: 40–60 правил
для первой версии, ~2–3 недели работы инженера-теплотехника или
нормоконтролёра проектного института.

**Почему это «продвинуто»:**

Автоматический нормоконтроль — это прямая экономия 2–4 недель на
каждом проекте (время между подачей на экспертизу и получением
замечаний). Для проектного института, сдающего 20–30 проектов в год,
это экономия 40–120 недель инженерного времени. Ни один российский
калькулятор греющего кабеля такой проверки не делает. Это превращает
HeatCalc из «инструмента расчёта» в «инструмент обеспечения качества».

**Риски и ограничения:**

- База правил требует постоянной актуализации: СП 61 обновляется
  каждые 3–5 лет. Решение: модель подписки на обновления нормативной
  базы (как услуга — «пакет актуализации нормативов», 50 тыс. руб./год).
- Некоторые нормы сформулированы не в виде точных порогов, а как
  «рекомендуется» или «по согласованию с заказчиком». Такие правила
  помечаются severity: "warning", не блокируют экспертизу.
- Внутренние СТО заказчиков (Газпром, Роснефть) — коммерческая тайна,
  не могут быть включены в стандартную поставку. Решение: custom rules
  как часть white-label (F-15), загружаются администратором заказчика.

## F-13. Электронная подпись и криптографический audit trail

**Категория:** Безопасность и комплаенс

**Приоритет:** P0 — стратегический

**Аналоги:** СБИС / Контур.Диадок (электронный документооборот с ЭЦП по
ГОСТ, полный audit trail), 1С:Документооборот (ЭЦП + цепочки согласования
+ версионирование), DocuSign (международная ЭЦП, но без ГОСТ), отечественная
«КриптоПро DSS» (серверная ЭЦП с поддержкой ГОСТ Р 34.10-2012).

**Проблема, которую решаем:**

Расчёт системы электрообогрева — это **проектный документ**, на основании
которого заказывается оборудование на миллионы рублей и монтируется система,
отказ которой может привести к остановке нефтепровода (убытки ~10 млн руб./сутки).
Юридически значимый документ должен быть **подписан** уполномоченным лицом
(ГИП — главный инженер проекта).

Сегодня HeatCalc генерирует отчёт, который инженер:
1. Экспортирует в PDF
2. Распечатывает
3. Подписывает шариковой ручкой
4. Сканирует
5. Прикладывает скан к проектной документации

Этот процесс дискредитирует саму идею «цифрового инструмента»: цифровой
расчёт → бумажная подпись → скан. Юридически скан подписи имеет слабую
доказательную силу. При возникновении аварии и расследовании невозможно
доказать, что подписант видел именно эту версию расчёта, а не изменённую
post factum.

Кроме того, для соответствия 152-ФЗ «О персональных данных» и требованиям
корпоративной безопасности заказчиков (Газпром, Роснефть) нужен **полный
audit trail**: кто, когда, с какого IP, какие именно данные изменил в
проекте — и эти логи должны быть защищены от модификации (tamper-evident).

**Инженерное описание:**

**Электронная подпись (ЭЦП):**

Подпись ставится на **версионированный снапшот проекта** (F-07). Процесс:

1. Инженер (или ГИП) нажимает «Подписать проект» на странице отчёта
2. Система формирует `signable_document.json` — канонизированное
   JSON-представление проекта (RFC 8785, JCS — JSON Canonicalization
   Scheme) + метаданные (идентификатор подписанта, дата/время, цель
   подписи — «Утверждение расчётов», «Согласование спецификации»)
3. Вычисляется хэш документа: ГОСТ Р 34.11-2012 (Streebog-256, 256 бит)
4. Хэш передаётся на подписание:
   - **Вариант А (без КриптоПро):** чистая Python-реализация ГОСТ
     Р 34.10-2012 (`pygost` библиотека). Приватный ключ хранится в
     зашифрованном виде в профиле пользователя (защита паролем).
     Юридическая сила — ограниченная (не сертифицированный СКЗИ).
   - **Вариант Б (с КриптоПро):** интеграция с КриптоПро CSP через
     PKCS#11. Полноценная квалифицированная ЭЦП с сертифицированным
     ключом. Требует установки КриптоПро на сервере (Linux, через
     `libp11` или `gostcrypto`).
5. Отсоединённая подпись (detached signature, формат CMS/PKCS#7)
   сохраняется в БД: `project_signatures (id, snapshot_hash, signer_id,
   signature_type, certificate_chain_pem, signature_der, signed_at,
   purpose)`
6. Проверка подписи: любой пользователь с доступом к проекту может
   нажать «Проверить подпись» → система пересчитывает хэш снапшота
   и проверяет подпись криптографически. Результат: «Подпись
   действительна. Подписал: Иванов И.И. Дата: 08.05.2026 16:34.
   Сертификат выдан: УЦ Газпрома, действителен до 12.2027.»

**Криптографический audit trail:**

Каждое действие в системе (создание/изменение/удаление объекта, запуск
расчёта, изменение общих данных, подписание) создаёт запись в таблице
`audit_log`:

```sql
audit_log (
  id UUID,
  event_hash BYTEA,        -- SHA-256(event_data)
  prev_event_hash BYTEA,   -- цепочка хэшей → Merkle tree
  project_id UUID,
  user_id UUID,
  action VARCHAR(64),
  entity_type VARCHAR(32),
  entity_id UUID,
  changed_fields JSONB,    -- {field: [old_value, new_value]}
  ip_address INET,
  user_agent TEXT,
  created_at TIMESTAMPTZ
)
```

Цепочка хэшей (`prev_event_hash`) образует **Merkle-подобную структуру**:
каждая запись хэширует своё содержимое + хэш предыдущей записи в рамках
проекта. Это делает невозможным удаление или изменение записи «задним
числом» без обнаружения — любое изменение порушит цепочку хэшей. Проверка
целостности (`GET .../audit/verify-integrity`) пересчитывает хэши от
первой записи до последней и сравнивает с хранимыми.

Дополнительно: корневой хэш Merkle tree проекта раз в сутки публикуется
во внешний immutable storage: либо в Ethereum-подобный смарт-контракт
(дорого, избыточно), либо в открытый лог (Twitter-бот, RSS-фид), либо —
прагматично — записывается в отдельную append-only таблицу, защищённую
на уровне БД (триггер, запрещающий UPDATE/DELETE).

**Технический контур:**

ЭЦП: `pygost` для ГОСТ-криптографии (чистый Python, Apache 2.0, включает
ГОСТ Р 34.10/34.11). Для PKCS#11 интеграции — `python-pkcs11`. Ключи
пользователей: таблица `user_keys (user_id, public_key_pem,
encrypted_private_key, certificate_chain)`, приватный ключ зашифрован
AES-256-GCM с ключом, производным от пароля пользователя (PBKDF2-SHA256).

Audit trail: PostgreSQL триггер для автоматического захвата изменений в
ключевых таблицах (альтернатива: application-level логирование в сервисах,
что даёт более богатый контекст). `event_hash` вычисляется в приложении
и проверяется при чтении.

API: `POST /api/v1/projects/{id}/sign` (создать подпись), `GET
.../signatures` (список подписей), `GET .../audit-log` (список событий
с фильтрацией), `POST .../audit/verify-integrity` (проверка цепочки).

Сложность: High (7 спринтов — аудит и ЭЦП по ГОСТ требуют тщательного
тестирования и документирования для сертификации).

**Почему это «продвинуто»:**

Юридически значимый документооборот внутри инженерного калькулятора —
это переход из категории «софт для инженеров» в категорию «корпоративная
информационная система». С ЭЦП и audit trail HeatCalc может быть внедрён
в контур СУПД (системы управления проектной документацией) заказчика —
это требование № 1 для контрактов с «Газпромом» и «Роснефтью».

**Риски и ограничения:**

- Квалифицированная ЭЦП (вариант Б) требует сертификации СКЗИ в ФСБ —
  и для библиотеки (`pygost` не сертифицирована), и для всей системы
  в целом. Это процесс 6–12 месяцев и стоимостью 3–5 млн рублей.
  На первом этапе — только вариант А (неквалифицированная ЭЦП для
  внутреннего документооборота заказчика).
- Приватные ключи пользователей на сервере — это модель «серверной
  подписи», требует доверия к серверу. Для полной юридической силы
  нужна клиентская подпись (ключ на токене пользователя) — это отдельная,
  более сложная задача.
- Хранение ключей: скомпрометированный сервер → скомпрометированы
  все подписи. Решение: HSM (Hardware Security Module) или Vault
  (HashiCorp Vault с KMIP) для production-развёртывания.

## F-14. Публичное REST API и marketplace расширений

**Категория:** Платформизация / API-first

**Приоритет:** P1 — тактический

**Аналоги:** Autodesk Platform Services (бывш. Forge) — публичное API для
работы с BIM-данными, OAuth 2.0, marketplace приложений, документация
на developer.autodesk.com. Trimble Connect API (REST API для интеграции
с внешними инструментами проектирования). AVEVA NET API (корпоративное
API с SDK для интеграции). Отечественная «Система ГРАД» (API для обмена
градостроительными данными между системами).

**Проблема, которую решаем:**

Крупные проектные институты (НИПИ) и EPC-подрядчики имеют собственные
IT-экосистемы:

- **1С:ERP / SAP** — управление закупками: нужно передать спецификацию
  кабеля в систему закупок для формирования заказа поставщику
- **Сметные программы** (Гранд-Смета, Smeta.RU) — нужны объёмы работ
  (метры кабеля, количество муфт) для расчёта сметы
- **Календарно-сетевое планирование** (Primavera, MS Project) — нужны
  данные о готовности разделов проекта для отслеживания прогресса
- **Внутренние дашборды руководства** — «сколько проектов в работе,
  сколько метров кабеля запроектировано за квартал»

Сегодня интеграция — это ручной экспорт CSV из HeatCalc и импорт в другую
систему. Это fragile, неавтоматизировано и требует человека-«мостика».

**Инженерное описание:**

HeatCalc API — это не просто «открыть существующие internal endpoints».
Это проектирование полноценного публичного API по стандартам OpenAPI 3.1
с версионированием, аутентификацией, rate limiting, SDK и developer
portal.

**API-дизайн:**

- Базовый URL: `https://api.heatcalc.io/v1/`
- Аутентификация: API Keys (статический ключ для server-to-server) +
  OAuth 2.0 Authorization Code flow для third-party приложений
- Формат: JSON (RFC 8259), даты в ISO 8601, ошибки в RFC 7807 (Problem
  Details)
- Версионирование: major version в URL (`/v1/`), minor — в заголовке
  `API-Version: 2026-05`
- Пагинация: cursor-based (`?cursor=xxx&limit=50`), Link header

**Эндпоинты (первая очередь):**

```
GET    /v1/projects                    # список проектов
POST   /v1/projects                    # создать проект
GET    /v1/projects/{id}               # детали проекта
GET    /v1/projects/{id}/objects       # список объектов
POST   /v1/projects/{id}/objects       # добавить объект
PUT    /v1/projects/{id}/objects/{oid} # изменить объект
POST   /v1/projects/{id}/calc/electrical/batch  # запустить электрорасчёт
GET    /v1/projects/{id}/specification # получить спецификацию
GET    /v1/projects/{id}/report        # получить отчёт (HTML/JSON)
GET    /v1/references/cables           # справочник кабелей
GET    /v1/references/climate          # климатический справочник
```

**Webhook'и:**

Пользователь (через UI или API) регистрирует webhook: URL, на который
HeatCalc будет отправлять HTTP POST при наступлении события. Типы событий:
`project.updated`, `calculation.completed`, `specification.generated`,
`report.exported`. Подпись webhook'а — HMAC-SHA256 с секретом (для
верификации на стороне приёмника). Повторы с экспоненциальной задержкой
при failure.

**Marketplace расширений:**

Каталог расширений — это не App Store, а **реестр проверенных интеграций**
(маркетплейс для B2B, где каждое расширение — это сертифицированный
коннектор):

- «1С: Предприятие — Коннектор HeatCalc» (разработка партнёра или
  собственная)
- «Telegram Bot для уведомлений о статусе расчёта»
- «Power BI Connector для аналитики проектов»
- «Smeta.RU — прямая выгрузка объёмов»

Технически marketplace — это: GitHub-репозиторий с манифестом расширения
(JSON: название, описание, автор, эндпоинты API, которые используются),
dev-портал (статический сайт на базе Redoc/Scalar с документацией),
песочница (sandbox-tenant для разработчиков расширений).

**SDK:**

Автоматически генерируемые клиентские библиотеки из OpenAPI-спецификации
через `openapi-generator-cli`:
- Python: `pip install heatcalc-client`
- TypeScript: `npm install @heatcalc/client`
- C# (для 1С-интеграций через .NET)
- Go (для cloud-native интеграций)

**Технический контур:**

API Gateway: FastAPI уже является API-фреймворком — добавляем отдельный
FastAPI-роутер `/v1/public/` с публичной аутентификацией. API Keys:
таблица `api_keys (id, key_hash, tenant_id, permissions JSONB, rate_limit,
created_by, expires_at)`. Middleware для аутентификации по `Authorization:
Bearer heatcalc_xxx` или `X-API-Key`.

Rate limiting: Redis token bucket, конфигурируемый per-API-key (10 req/s
для базового, 100 req/s для корпоративного).

Webhook'и: таблица `webhook_subscriptions`, Celery-таск для отправки
с retry (3 попытки с задержкой 30с, 5мин, 30мин).

Документация: `redoc` или `scalar` для рендеринга OpenAPI spec как
dev-портала. Хостится статически на `https://developer.heatcalc.io`.

Сложность: Medium (5 спринтов — API сам по себе прост, основная работа —
документирование, SDK-генерация, dev-portal, webhook-инфраструктура).

**Почему это «продвинуто»:**

Публичное API превращает HeatCalc из **продукта** в **платформу**.
Это разница между «софтом, который продаётся по лицензии за 100 тыс.
руб./год» и «экосистемой, в которой партнёры создают ценность, а
владелец платформы получает процент». API-first подход — это также
защита от конкурентов: если проектный институт построил 5 интеграций
вокруг HeatCalc API, стоимость перехода на «Тепломаг» становится
запретительной.

**Риски и ограничения:**

- Поддержка обратной совместимости API — это контракт с внешними
  разработчиками. Любое breaking change → нарушение работы интеграций.
  Решение: строгое версионирование, депрекация с уведомлением за 6
  месяцев, мониторинг использования deprecated-эндпоинтов.
- Безопасность: публичное API увеличивает поверхность атаки. Решение:
  penetration testing, OWASP API Security Top 10 audit, WAF (Web
  Application Firewall) в production.
- Конкуренция с внутренними API заказчика (SAP, 1С) — это не столько
  технологическая, сколько политическая задача: integration partner
  manager со стороны HeatCalc для работы с IT-департаментами заказчиков.

## F-15. Мультитенантная SaaS-архитектура с white-label

**Категория:** Платформизация / API-first

**Приоритет:** P2 — на вырост

**Аналоги:** Figma Enterprise (многопользовательская SaaS с white-label:
кастомный домен, логотип, цвета), Miro Enterprise (white-label для
корпоративных клиентов с изоляцией данных), отечественный «Битрикс24»
(мультитенантный SaaS с возможностью размещения на собственном домене
клиента).

**Проблема, которую решаем:**

Текущая модель развёртывания — **один инстанс на одного заказчика**
(on-premise или dedicated cloud VM). Это не масштабируется коммерчески:

- 50 проектных институтов = 50 Docker-инстансов = 50 × поддержка,
  50 × мониторинг, 50 × обновление. Административный ад.
- Каждый институт хочет свою кастомизацию: логотип, цвета, домен
  (`heatcalc.giprotumen.ru`), свои справочники, свои роли, свои
  нормативные правила.
- On-premise — это высокий порог входа: чтобы попробовать продукт,
  нужно развернуть Docker, PostgreSQL, Redis — мелкие ПТО на это
  не пойдут.

SaaS снижает порог входа до «зарегистрировался и начал работать»,
уменьшает стоимость поддержки в 50 раз (один инстанс вместо 50),
позволяет модели подписки с ежемесячной оплатой (recurring revenue).

**Инженерное описание:**

Переход от single-tenant к multi-tenant архитектуре:

**Изоляция данных (tenant isolation):**

Подход — **Row-Level Security (RLS)** в PostgreSQL. Все данные всех
тенантов хранятся в одних таблицах, но каждая строка имеет поле
`tenant_id`. PostgreSQL RLS-политика гарантирует, что пользователь
тенанта А ни при каких обстоятельствах не видит данные тенанта Б
(даже при прямом SQL-запросе, даже при баге в application logic):

```sql
ALTER TABLE projects ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON projects
  USING (tenant_id = current_setting('app.current_tenant_id')::UUID);
```

`app.current_tenant_id` устанавливается в начале каждого запроса
middleware'ом из JWT или API-ключа.

**White-label кастомизация:**

Таблица `tenant_settings` (JSONB) хранит кастомизацию для каждого
тенанта:

```json
{
  "branding": {
    "logo_url": "https://s3.heatcalc.io/tenants/gipro/logo.png",
    "primary_color": "#1a5276",
    "secondary_color": "#2980b9",
    "company_name": "Гипротюменнефтегаз",
    "company_short": "ГТНГ"
  },
  "domain": "heatcalc.gtng.ru",
  "features": {
    "bim_import": true,
    "tco_calculator": true,
    "ml_insulation": false,
    "custom_regulations": true,
    "max_projects": 500,
    "max_users": 50
  },
  "regulations": "custom_gazprom_rules.json",
  "reference_overrides": {
    "energy_tariff": 4.85,
    "labor_rate": 3200
  }
}
```

Фронтенд загружает настройки тенанта при старте и применяет:
CSS-переменные из `primary_color`/`secondary_color`, логотип в header,
название компании в title. Feature flags управляют видимостью модулей
(через серверный рендеринг меню).

**Кастомный домен и TLS:**

Клиент указывает свой домен (`heatcalc.gtng.ru`) → Caddy получает
запрос, извлекает tenant из домена (либо через таблицу маппинга
`tenant_domains (domain, tenant_id)`, либо через wildcard- TLS с
on-demand сертификатами Let's Encrypt). Caddy автоматически выпускает
SSL-сертификат для кастомного домена.

**Деgraded multi-tenancy:**

Для клиентов, которым нужна 100% изоляция (Газпром, Роснефть —
данные не могут физически находиться на одном сервере с данными
других компаний), сохраняется опция dedicated инстанса. Но даже
в dedicated-режиме используется единая кодовая база и механизм
white-label — просто tenant = 1 на инстанс.

**Billing (на вырост):**

Таблица `subscriptions (tenant_id, plan, started_at, expires_at)`.

Планы:
- **Free:** 1 проект, 10 объектов, только встроенная БД кабелей, без
  BIM, без TCO, без ЭЦП — для мелких ПТО
- **Pro:** 50 проектов, 500 объектов, расширенная БД, BIM, TCO —
  25 000 руб./мес.
- **Enterprise:** безлимитные проекты, white-label, кастомный домен,
  dedicated инстанс (опционально), нормативные правила заказчика,
  приоритетная поддержка — от 150 000 руб./мес.

**Технический контур:**

PostgreSQL RLS: добавляется `tenant_id UUID NOT NULL` во все основные
таблицы (`projects`, `objects`, `heat_calculations`,
`electrical_calculations`, `specifications`, `project_snapshots`,
`audit_log`). Миграция существующих single-tenant данных: создаётся
дефолтный тенант.

Middleware: `TenantMiddleware` — извлекает tenant из домена, JWT или
API-ключа, валидирует доступ пользователя к тенанту (через
`user_tenants` связку), устанавливает `app.current_tenant_id`.

Фронтенд: динамическая загрузка брендинга через API
`GET /api/v1/tenant/settings` (публичный эндпоинт, без аутентификации,
по домену). CSS-переменные внедряются в `<style>` через React Context
или CSS-in-JS.

Инфраструктура: Caddy с динамической конфигурацией (Caddy API для
добавления доменов на лету) или ingress-контроллер в K8s. MinIO для
изолированного хранения ассетов тенантов (separate bucket per tenant).

Сложность: High (9 спринтов). Миграция существующей схемы на
multi-tenant — это сквозное изменение, затрагивающее каждую таблицу,
каждый запрос, каждый тест (799 тестов нужно адаптировать под
tenant context).

**Почему это «продвинуто»:**

SaaS + white-label — это не технологическая фича, а **бизнес-модель**.
Она превращает HeatCalc из «вендора ПО» в «сервис-провайдера» с
предсказуемой recurring-выручкой. Для проектных институтов SaaS
снижает порог входа в 5–10 раз: не покупать лицензию за 1 млн рублей,
а платить 25 тыс. руб./мес. — решение принимается на уровне начальника
отдела, а не гендиректора.

**Риски и ограничения:**

- RLS с комплексными запросами (JOIN с агрегатами) может деградировать
  по производительности. Решение: индексы с `tenant_id` первым столбцом,
  мониторинг планов запросов, опциональный `statement_timeout` per tenant.
- Data residency: для некоторых заказчиков (оборонка, Росатом) данные
  должны физически храниться на сервере в РФ. SaaS на AWS/GCP не подходит.
  Решение: собственная инфраструктура в дата-центре РФ (Selectel,
  DataLine) либо гибридная модель — приложение SaaS, но данные в
  dedicated БД.
- Сложность миграции с single-tenant на multi-tenant — риск регрессии
  всего функционала. Решение: поэтапная миграция: сначала RLS как
  опциональный слой (tenant_id = NULL → без ограничений для обратной
  совместимости), затем включение enforcement per-tenant.

## Архитектурный срез

Реализация предложенных фич требует нескольких **сквозных архитектурных
изменений**, затрагивающих сразу несколько модулей. Ниже — 5 ключевых
решений, которые должны быть приняты на старте, поскольку они определяют
фундамент для многих фич.

### АР-1. Переход на событийно-ориентированную архитектуру (Event-Driven)

**Затрагивает:** F-07 (версионирование — автоснапшоты), F-10 (телеметрия
и мониторинг), F-13 (audit trail), F-14 (webhook'и)

**Суть:** синхронные REST-вызовы между сервисами заменяются на асинхронные
события через message broker (Redis Pub/Sub для начала, RabbitMQ или
NATS для прода). При сохранении объекта → emits `object.updated` → на
это событие подписаны: сервис версионирования (создать снапшот), сервис
аудита (записать audit-запись), webhook-диспетчер (отправить
подписчикам).

**Обоснование:** разделение концернов (расчёт не должен ждать, пока
запишется audit trail) и горизонтальная масштабируемость (каждый
обработчик события — отдельный процесс).

### АР-2. TimescaleDB для временны́х рядов

**Затрагивает:** F-02 (нестационарный расчёт — временные срезы),
F-10 (телеметрия — поток измерений от контроллеров), F-11 (история
предсказаний модели)

**Суть:** для данных с временно́й меткой (измерения температуры,
результаты transient-расчётов, метрики модели ML) вместо PostgreSQL
JSONB использовать TimescaleDB — расширение PostgreSQL, автоматически
партиционирующее таблицы по времени (hypertable). Это даёт:
- Сжатие временны́х рядов (до 10× экономии места)
- Автоматическое удаление старых партиций (retention policy)
- Оптимизированные временны́е агрегаты (`time_bucket`, `first`, `last`)

**Обоснование:** без TimescaleDB 10 000 зон обогрева × 1 измерение
в минуту = 14.4 млн строк в день — PostgreSQL справится, но
аналитические запросы («средняя температура за последний месяц»)
будут замедляться. TimescaleDB решает это «из коробки», оставаясь
в экосистеме PostgreSQL (те же индексы, те же миграции Alembic).

### АР-3. Микросервисный слой для вычислительно-ёмких задач

**Затрагивает:** F-01 (теплогидравлический решатель), F-02
(нестационарный решатель), F-03 (генетический оптимизатор NSGA-II),
F-11 (обучение ML-модели)

**Суть:** вынести вычислительно-ёмкие задачи из основного FastAPI-процесса
в отдельные worker-процессы (Celery workers) или микросервисы. Причина:
- FastAPI работает в async event loop — блокирующая операция (расчёт
  нестационарной модели на 60 секунд) заблокирует весь event loop,
  остальные запросы встанут
- Обучение ML-модели требует CPU/GPU и может занимать минуты-часы —
  API должен вернуть `202 Accepted` с task_id, а не висеть

**Обоснование:** это не преждевременная оптимизация — текущий
`calculation_service.py` уже выполняет расчёты синхронно, и для
базовых теплопотерь (миллисекунды) это ок. Но для transient-солвера
(секунды-десятки секунд) синхронный подход неприемлем.

### АР-4. Объектное хранилище (S3/MinIO) для бинарных артефактов

**Затрагивает:** F-05 (IFC-файлы, 50–500 MB), F-06 (DXF/CDW-файлы),
F-09 (фото с площадки), F-13 (подписанные документы), F-15 (логотипы
и ассеты тенантов)

**Суть:** все бинарные артефакты (файлы > 1 MB) хранить не в БД (pg
Large Object / BYTEA), а в S3-совместимом объектном хранилище — MinIO
для on-premise, AWS S3 или Яндекс Object Storage для облака. В БД —
только метаданные (s3_key, content_type, size, uploaded_by).

**Обоснование:** хранение 500 MB IFC-файла в PostgreSQL — это насилие
над СУБД. Бэкапы раздуваются, репликация замедляется, вакуум страдает.
Объектное хранилище решает это с дешёвым хранением, CDN-раздачей,
presigned URL для скачивания.

### АР-5. Плагинная архитектура для кастомизаций заказчика

**Затрагивает:** F-05 (правила маппинга IFC → HeatCalc), F-10
(адаптеры контроллеров), F-12 (нормативные правила заказчика), F-14
(marketplace расширений), F-15 (white-label кастомизации)

**Суть:** любая кастомизация, специфичная для заказчика, не должна
требовать правок в core-коде. Вместо этого — плагинные точки
(plugin hooks), расширяемые через конфигурацию:

- `reference_data/ifc_mapping_rules/{customer}.json` — правила маппинга
- `reference_data/regulations/{customer}.json` — нормативные правила
- `exporters/` — адаптеры контроллеров (каждый — отдельный Python-модуль)
- `tenant_settings.features` — feature flags для включения/отключения
  модулей

**Обоснование:** без плагинной архитектуры каждое требование заказчика
(«добавьте наш внутренний СТО в проверку compliance») превращается в
ветку в Git, merge conflict и риск регрессии для всех остальных
заказчиков. Plugin hooks изолируют кастомизации и позволяют заказчикам
(или партнёрам) создавать расширения без участия core-команды.
