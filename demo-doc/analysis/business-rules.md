# Бизнес-правила и ограничения системы

## Методология

Каждое бизнес-правило описано по шаблону:
- **ID** — уникальный идентификатор (BR-XXX-NN)
- **Категория** — домен правила
- **Приоритет** — Critical / High / Medium / Low
- **Условие** — «Если [контекст], то [действие]»
- **Обоснование** — почему правило существует
- **Реализация** — где в коде применяется

---

## Категория AUTH — Авторизация и доступ

### BR-AUTH-01: Гостевая сессия

| Атрибут | Значение |
|---------|----------|
| **Приоритет** | Critical |
| **Условие** | Если пользователь обращается к API без `Authorization` заголовка, он обязан передать `X-Session-Id` заголовок для идентификации |
| **Нарушение** | 401 Unauthorized — "Session ID required for guest access" |
| **Обоснование** | Гостевой режим позволяет внешним подрядчикам работать без регистрации, но анонимный доступ запрещён — каждая сессия должна быть идентифицируемой |
| **Реализация** | `app/api/dependencies.py: get_current_user()` |

### BR-AUTH-02: Срок жизни токенов

| Атрибут | Значение |
|---------|----------|
| **Приоритет** | Critical |
| **Условие** | Access token действует **30 минут**. Refresh token действует **7 дней**. После истечения refresh token пользователь обязан повторно пройти аутентификацию |
| **Нарушение** | 401 Unauthorized — "Token expired" |
| **Обоснование** | Баланс между безопасностью (короткий access token минимизирует окно для компрометации) и UX (длинный refresh token не требует частого логина) |
| **Реализация** | `app/core/config.py: ACCESS_TOKEN_EXPIRE_MINUTES=30, REFRESH_TOKEN_EXPIRE_DAYS=7` |

### BR-AUTH-03: Изменение пароля

| Атрибут | Значение |
|---------|----------|
| **Приоритет** | High |
| **Условие** | Пароль хранится только в виде bcrypt-хеша с salt rounds ≥ 12. Исходный пароль нигде не логируется |
| **Нарушение** | Запрет компилятора/линтера на хранение raw пароля |
| **Обоснование** | Требование информационной безопасности нефтяной компании |
| **Реализация** | `app/services/auth.py: hash_password()` — `bcrypt.hashpw()` |

### BR-AUTH-04: Права доступа к проектам

| Атрибут | Значение |
|---------|----------|
| **Приоритет** | Critical |
| **Условие** | Гость видит **только свои** проекты (по session_id). Сотрудник и Администратор видят **все** проекты системы |
| **Нарушение** | 403 Forbidden — "Access denied to this project" |
| **Обоснование** | Гостевые проекты могут содержать конфиденциальные данные подрядчиков; сотрудники видят их для координации работ |
| **Реализация** | `app/services/project.py: get_projects(user, session_id)` |

### BR-AUTH-05: Экспорт только для зарегистрированных

| Атрибут | Значение |
|---------|----------|
| **Приоритет** | High |
| **Условие** | Экспорт файлов (PDF, DOCX, XLSX) доступен только пользователям с ролью `employee` или `admin`. Гости получают только HTML-предпросмотр |
| **Нарушение** | 403 Forbidden — "Export requires employee role or higher" |
| **Обоснование** | Файловые отчёты являются юридически значимыми документами; их выпуск должен быть привязан к идентифицированному сотруднику |
| **Реализация** | `app/api/v1/reports.py: require_role(["employee", "admin"])` |

## Категория CALC — Расчёты теплопотерь

### BR-CALC-01: Диапазон температур процесса

| Атрибут | Значение |
|---------|----------|
| **Приоритет** | Critical |
| **Условие** | Температура технологической среды: **от −60°C до +350°C** |
| **Нарушение** | 422 Unprocessable Entity — "Process temperature out of valid range" |
| **Обоснование** | Диапазон применимости использованных теплофизических уравнений; значения за пределами диапазона дают физически некорректные результаты |
| **Реализация** | `app/schemas/objects.py: PipeParamsSchema` — Pydantic Field constraints |

### BR-CALC-02: Диапазон температур окружающей среды

| Атрибут | Значение |
|---------|----------|
| **Приоритет** | Critical |
| **Условие** | Минимальная температура окружающей среды: **от −60°C до +50°C** |
| **Нарушение** | 422 Unprocessable Entity |
| **Обоснование** | Соответствует климатическим условиям нефтяных месторождений России (Сибирь: до −55°C) |
| **Реализация** | `app/schemas/objects.py: PipeParamsSchema.min_ambient_temperature` |

### BR-CALC-03: Разность температур

| Атрибут | Значение |
|---------|----------|
| **Приоритет** | Critical |
| **Условие** | Температура процесса **обязана превышать** минимальную температуру окружающей среды: `t_process > t_ambient` |
| **Нарушение** | 422 — "Process temperature must be higher than ambient temperature" |
| **Обоснование** | Физический смысл: кабельный обогрев предотвращает замерзание; если процесс холоднее воздуха — обогрев не нужен |
| **Реализация** | `app/schemas/objects.py: PipeParamsSchema.model_validator()` |

### BR-CALC-04: Толщина изоляции

| Атрибут | Значение |
|---------|----------|
| **Приоритет** | High |
| **Условие** | Минимальная толщина каждого слоя изоляции: **10 мм**. Максимальная суммарная толщина: **500 мм** |
| **Нарушение** | 422 Unprocessable Entity |
| **Обоснование** | Технологические ограничения: тонкие слои неэффективны и некорректно моделируются уравнением цилиндрической стенки; толще 500 мм не применяется на практике |
| **Реализация** | `app/schemas/objects.py: InsulationLayerSchema` |

### BR-CALC-05: Диаметр трубы

| Атрибут | Значение |
|---------|----------|
| **Приоритет** | Critical |
| **Условие** | Наружный диаметр трубы: **от 10 мм до 2000 мм** |
| **Нарушение** | 422 — "Pipe diameter out of range" |
| **Обоснование** | Диапазон реальных технологических трубопроводов нефтяной отрасли (от байпасных линий до магистральных труб) |
| **Реализация** | `app/schemas/objects.py: PipeParamsSchema.outer_diameter_mm` |

### BR-CALC-06: Коэффициент запаса мощности

| Атрибут | Значение |
|---------|----------|
| **Приоритет** | High |
| **Условие** | Коэффициент запаса `safety_factor`: **от 1.0 до 2.5**. Значение по умолчанию: **1.1** |
| **Нарушение** | 422 при попытке установить значение за пределами диапазона |
| **Обоснование** | 1.0 означает нулевой запас (неприемлемо для промышленных объектов); 2.5 — максимально обоснованный запас по отраслевым нормам |
| **Реализация** | `app/api/v1/admin.py: update_coefficient()` |

### BR-CALC-07: Автоматический расчёт при создании объекта

| Атрибут | Значение |
|---------|----------|
| **Приоритет** | High |
| **Условие** | При создании объекта (`POST /objects`) расчёт теплопотерь и подбор кабеля запускаются **автоматически** в рамках той же транзакции |
| **Нарушение** | — (системное поведение, не ошибка пользователя) |
| **Обоснование** | UX-требование: пользователь должен сразу видеть результат, не нажимая отдельную кнопку "Рассчитать" |
| **Реализация** | `app/services/calculation.py: create_object_with_calc()` |

### BR-CALC-08: Инвалидация спецификации

| Атрибут | Значение |
|---------|----------|
| **Приоритет** | Medium |
| **Условие** | При любом изменении объекта проекта (обновление параметров, удаление, добавление нового) существующая спецификация **удаляется** и должна быть сгенерирована заново |
| **Нарушение** | — (система автоматически инвалидирует) |
| **Обоснование** | Спецификация является производной от расчётов; устаревшая спецификация вводит в заблуждение и может привести к неверным закупкам |
| **Реализация** | `app/services/calculation.py: invalidate_specification()` |

## Категория CABLE — Подбор кабеля

### BR-CABLE-01: Логика подбора кабеля

| Атрибут | Значение |
|---------|----------|
| **Приоритет** | Critical |
| **Условие** | Система подбирает кабель с наименьшей удельной мощностью `power_per_meter`, при которой: `power_per_meter × pipe_length ≥ total_heat_loss` |
| **Нарушение** | Если подходящего кабеля нет — 422 "No suitable cable found for required power" |
| **Обоснование** | Оптимизация стоимости: выбирается минимально достаточная мощность, чтобы не переплачивать за избыточный кабель |
| **Реализация** | `app/formulas/electrical/self_regulating.py: calc_self_regulating()` |

### BR-CABLE-02: Запас длины кабеля

| Атрибут | Значение |
|---------|----------|
| **Приоритет** | High |
| **Условие** | Длина кабеля = `pipe_length × 1.1` (запас 10% на монтажные петли, крепёж, соединительные муфты) |
| **Нарушение** | — (система всегда применяет коэффициент 1.1) |
| **Обоснование** | Монтажный норматив для саморегулирующегося кабеля в соответствии с техническими рекомендациями поставщиков |
| **Реализация** | `app/formulas/electrical/self_regulating.py` — константа `CABLE_LENGTH_FACTOR = 1.1` внутри функции `calc_self_regulating()` |

### BR-CABLE-03: Максимальная рабочая температура кабеля

| Атрибут | Значение |
|---------|----------|
| **Приоритет** | Critical |
| **Условие** | Кабель может быть выбран только если `cable.max_temperature > t_process` |
| **Нарушение** | Кабели с `max_temperature ≤ t_process` исключаются из кандидатов |
| **Обоснование** | Требование безопасности: кабель не должен деградировать от температуры процесса |
| **Реализация** | `app/formulas/electrical/self_regulating.py: filter_cables()` |

### BR-CABLE-04: Приоритет справочника

| Атрибут | Значение |
|---------|----------|
| **Приоритет** | Medium |
| **Условие** | При подборе кабеля сначала просматривается **расширенный каталог** (БД, `cables_extended`). Если каталог пуст — используется базовый справочник из JSON (`cables_tlt.json`) |
| **Нарушение** | — (fallback-логика) |
| **Обоснование** | Позволяет администратору расширять каталог кабелями поставщиков, не меняя базовый JSON-справочник |
| **Реализация** | `app/services/calculation.py: load_cable_catalog()` |

## Категория SPEC — Спецификация

### BR-SPEC-01: Группировка позиций

| Атрибут | Значение |
|---------|----------|
| **Приоритет** | High |
| **Условие** | Позиции спецификации группируются по **марке кабеля**. Все объекты с одинаковой маркой объединяются в одну строку с суммарной длиной |
| **Нарушение** | — (автоматическое поведение) |
| **Обоснование** | Стандарт оформления заявки на материалы в нефтяной промышленности: поставщик принимает заказ по маркам, не по отдельным трубопроводам |
| **Реализация** | `app/formulas/specification/builder.py: build_basic_specification()` |

### BR-SPEC-02: Автодобавление аксессуаров

| Атрибут | Значение |
|---------|----------|
| **Приоритет** | Medium |
| **Условие** | К каждой позиции кабеля автоматически добавляются стандартные аксессуары из каталога (концевые муфты, сальниковые вводы, монтажная лента) в количестве, рассчитанном по нормативу на 100 м кабеля |
| **Нарушение** | — |
| **Обоснование** | Исключает ручной расчёт комплектации; норматив утверждён главным инженером |
| **Реализация** | `app/formulas/specification/builder.py` — таблица нормативов аксессуаров |

### BR-SPEC-03: Уникальность спецификации

| Атрибут | Значение |
|---------|----------|
| **Приоритет** | High |
| **Условие** | На один проект — **одна актуальная спецификация**. Повторная генерация перезаписывает предыдущую |
| **Нарушение** | — (UPSERT в БД) |
| **Обоснование** | Предотвращает путаницу между версиями спецификации; история версий — в бэклоге |
| **Реализация** | `app/services/specification.py: generate_or_update()` |

## Категория ADMIN — Администрирование

### BR-ADMIN-01: Неудаляемость администратора

| Атрибут | Значение |
|---------|----------|
| **Приоритет** | Critical |
| **Условие** | В системе должен существовать **хотя бы один** активный пользователь с ролью `admin`. Попытка удалить последнего администратора отклоняется |
| **Нарушение** | 400 Bad Request — "Cannot delete the last admin account" |
| **Обоснование** | Защита от ситуации «заблокированная система», когда никто не может войти и восстановить доступ |
| **Реализация** | `app/services/admin.py: delete_user()` |

### BR-ADMIN-02: Диапазоны коэффициентов

| Коэффициент | Мин | Макс | По умолчанию | Описание |
|-------------|-----|------|--------------|----------|
| `safety_factor` | 1.0 | 2.5 | 1.1 | Общий коэффициент запаса мощности |
| `wind_factor` | 1.0 | 1.5 | 1.05 | Поправка на ветровую нагрузку |
| `location_indoor` | 0.7 | 1.0 | 0.8 | Поправка для закрытых помещений |
| `location_outdoor` | 1.0 | 1.3 | 1.0 | Поправка для открытой местности |
| `ground_conductivity` | 0.5 | 3.0 | 1.5 | Теплопроводность грунта (Вт/(м·°C)) |

**Приоритет:** Critical  
**Обоснование:** Значения за пределами диапазона не имеют физического смысла и могут привести к опасно заниженным расчётам мощности кабеля.

### BR-ADMIN-03: Мгновенное применение коэффициентов

| Атрибут | Значение |
|---------|----------|
| **Приоритет** | High |
| **Условие** | Изменение коэффициента **немедленно** применяется ко **всем новым** расчётам. Существующие расчёты не пересчитываются автоматически — требуется явный запрос на пересчёт |
| **Обоснование** | Принцип явного управления: автоматический пересчёт всех проектов при изменении коэффициента создаёт неожиданные изменения в чужих проектах |
| **Реализация** | Коэффициенты читаются из БД при каждом расчёте; кэш инвалидируется при обновлении |

### BR-ADMIN-04: Деактивация пользователя

| Атрибут | Значение |
|---------|----------|
| **Приоритет** | High |
| **Условие** | Администратор может деактивировать пользователя (`is_active = false`). Деактивированный пользователь не может войти в систему, но его проекты и данные сохраняются |
| **Нарушение** | 401 — "Account is disabled" при попытке входа |
| **Обоснование** | Данные не удаляются при увольнении сотрудника — расчёты остаются в истории компании |
| **Реализация** | `app/services/auth.py: authenticate_user()` — проверка `is_active` |

## Категория DATA — Целостность данных

### BR-DATA-01: Каскадное удаление

| Атрибут | Значение |
|---------|----------|
| **Приоритет** | Critical |
| **Условие** | При удалении проекта каскадно удаляются: все объекты, расчёты и спецификация проекта |
| **Обоснование** | Предотвращение «осиротевших» записей в БД |
| **Реализация** | `app/models/*.py` — `cascade="all, delete-orphan"` в SQLAlchemy relationships |

### BR-DATA-02: Неизменность результата расчёта

| Атрибут | Значение |
|---------|----------|
| **Приоритет** | High |
| **Условие** | Результат расчёта (`calculations`) хранится как снимок на момент вычисления. При изменении параметров объекта старый результат **не перезаписывается** — создаётся новая запись (предыдущая становится историей) |
| **Обоснование** | Аудиторский след: можно установить, какой результат был актуален в момент формирования конкретной спецификации или отчёта |
| **Реализация** | `app/services/calculation.py: save_calculation()` — INSERT, не UPDATE |

### BR-DATA-03: Уникальность email пользователя

| Атрибут | Значение |
|---------|----------|
| **Приоритет** | Critical |
| **Условие** | Email пользователя должен быть уникальным в системе и соответствовать формату RFC 5321 |
| **Нарушение** | 409 Conflict — "User with this email already exists" |
| **Реализация** | `app/models/user.py` — `UniqueConstraint` на поле email; Pydantic `EmailStr` валидация |

### BR-DATA-04: Сортировка объектов

| Атрибут | Значение |
|---------|----------|
| **Приоритет** | Low |
| **Условие** | Порядок объектов в проекте определяется полем `sort_order`. При создании объект получает `sort_order = max(sort_order) + 1`. Порядок может быть изменён через `POST /objects/reorder` |
| **Обоснование** | Пользователи организуют объекты в порядке их расположения на объекте (слева направо, сверху вниз) — это важно для читаемости отчёта |
| **Реализация** | `app/services/project_object.py: reorder_objects()` |

## Категория UI — Поведение интерфейса

### BR-UI-01: Автосохранение не используется

| Атрибут | Значение |
|---------|----------|
| **Приоритет** | Medium |
| **Условие** | Изменения параметров объекта применяются только после явного нажатия кнопки «Сохранить». Нет автосохранения по потере фокуса или изменению поля |
| **Обоснование** | Инженерные расчёты требуют детерминированного поведения; пользователь должен явно подтвердить, что набор параметров завершён |

### BR-UI-02: Валидация на клиенте

| Атрибут | Значение |
|---------|----------|
| **Приоритет** | High |
| **Условие** | Клиентская валидация (Ant Design Form Rules + Zod/Yup) дублирует серверную Pydantic-валидацию. Оба уровня должны быть синхронизированы |
| **Обоснование** | UX: ошибка должна показываться мгновенно, без round-trip к серверу; серверная валидация — финальный барьер от некорректных данных |

### BR-UI-03: Отображение статуса валидации объекта

| Атрибут | Значение |
|---------|----------|
| **Приоритет** | High |
| **Условие** | Объекты с `is_valid = false` **визуально выделяются** в таблице (красный цвет строки, иконка предупреждения) |
| **Обоснование** | Пользователь должен немедленно идентифицировать проблемные объекты, не читая каждую строку |
