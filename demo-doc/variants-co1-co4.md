# СО1..СО4 — четыре варианта системы обогрева

**СО** = **«Система Обогрева»**. Это **параллельные варианты расчёта** одного
и того же объекта (или группы объектов) в рамках одного проекта.

## Зачем они

Инженеру часто нужно **сравнить несколько конфигураций** до финального выбора:

- другая марка кабеля;
- разная мощность (например, ТЛТ-25 vs ТЛТ-40);
- с учётом / без учёта коэффициента запаса другой величины;
- кабель от альтернативного поставщика;
- двухконтурная vs одноконтурная система обогрева.

Вместо того чтобы создавать 4 проекта-клона, в одном проекте хранятся
**4 изолированных расчёта**. Можно быстро переключаться, сравнивать
ток / мощность / длину / стоимость, выбирать лучший и по нему
формировать спецификацию.

## Как это устроено технически

Каждая таблица с вариативными расчётами содержит поле
`variant_number: int ∈ [1..4]`.

| Таблица | Как используется |
|---|---|
| `electrical_calculations` | `variant_number` + `UNIQUE(object_id, variant_number)` — для одного объекта ровно 4 записи максимум |
| `specifications` | `variant_number` — под каждый вариант отдельная спецификация |

**Upsert-логика**: при повторном расчёте того же `(object_id, variant_number)`
запись обновляется, а не дублируется (см.
`backend/app/services/calculation_service.py`, метод `calc_electrical`).

**Чем СО отличаются друг от друга:** всем. Это **независимые** расчёты —
может быть другой кабель, параметры, даже подмножество объектов. Единственное
что общее — сам проект и теплопотери объектов (они считаются один раз и не
зависят от варианта).

## Почему именно 4

Из ТЗ (пункт 4.3.2): *«Расчёт, сравнение, сохранение нескольких вариантов
CO1..CO4»*. Ровно 4 — это прямое требование заказчика.

Инженерно — достаточно: обычно сравнивают 2–3 серьёзных варианта, 4-й
остаётся «запасной».

Технически расширить до 5–6 — изменить один `ge=1, le=4` в Pydantic-схеме
плюс кнопки в UI. Но пока ТЗ не просил — и так работает.

## Где это видно в UI

### Страница «Электрорасчёт» (`/workspace/elec-calc`)

В левой колонке — сегментированный переключатель `СО1 | СО2 | СО3 | СО4`.
Клик → весь список объектов и их расчёты перезагружаются для выбранного
варианта. Реализация: `frontend/src/pages/ElecCalcPage.tsx`, хук
`useState<number>(1)` для variant.

### Страница «Спецификация» (`/workspace/specification`)

Аналогичный переключатель внизу. Каждый вариант — своя BoM (bill of materials).
Реализация: `frontend/src/pages/SpecificationPage.tsx`.

### По умолчанию

Открывается **СО1**. Если пользователь ничего не переключал — работает
«как если бы вариантов не было», и спецификация по СО1 идёт в отчёт.

## API

Поле `variant_number` передаётся в теле запросов:

```http
POST /api/v1/calc/electrical
{
  "object_id": "<uuid>",
  "cable_type": "self_regulating",
  "variant_number": 2,          ← номер варианта
  "data": { ... }
}

POST /api/v1/calc/electrical/batch?project_id=<uuid>&variant_number=3
```

По умолчанию `variant_number = 1`.

## FAQ

**Можно ли скопировать СО1 в СО2 чтобы подправить?**
Нет, функции копирования в MVP нет. Надо запустить расчёт СО2 заново
(автоподбор или ручной выбор).

**Что будет, если я удалю объект после того, как считал СО1 и СО2?**
Записи `electrical_calculations` каскадно удаляются (ON DELETE CASCADE на
`object_id`). Все варианты пропадут вместе с объектом.

**Может ли в разных СО быть разный набор объектов проекта?**
Пока нет: алгоритм пакетного расчёта (`batch_calc_electrical`) проходит
по всем валидным объектам проекта. Можно **вручную** посчитать кабель
только для части объектов — для остальных запись варианта просто не будет
создана.

**Идёт ли в отчёт только один вариант?**
Да. В отчёте по умолчанию используется СО1 (в будущем можно сделать выбор
активного варианта на уровне проекта).
