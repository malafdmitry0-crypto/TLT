# Источники документации

**Обновлено:** 2026-07-19

Документы проекта описывают два разных состояния: целевой продуктовый контракт
и фактически реализованное поведение. Они не взаимозаменяемы. При проверке
всегда фиксируйте цепочку `требование -> текущий контракт -> код -> тесты`.

## Иерархия источников

| Уровень | Источники | Для чего использовать |
|---|---|---|
| Целевые требования | `ТЗ/README.md`, `ТЗ/`, первичные материалы `docs/tnp/`, подтверждённые product decisions | Что продукт должен делать |
| Текущий функциональный контракт | `docs/business-logic-contract.md`, `docs/api.md`, `docs/db_schema.md`, профильные SRS/QA-документы | Какое поведение заявлено реализованным сейчас |
| Реализация и evidence | backend/frontend-код, миграции, unit/integration/e2e, `codex-docs/business-formula-contracts.json` | Доказательство фактического поведения |
| Навигация и статус | `AGENTS.md` (вход для AI), `frontend/AGENTS.md`, `docs/domains/`, `codex-docs/project-map.md`, `codex-docs/requirements-map.md`, `TO_DO.md`, `CLAUDE.MD` | Куда идти за деталями; не самостоятельный нормативный источник |
| История | датированные аудиты, proposal/status-документы и сохранённые evidence-снимки | Почему принималось решение; не использовать как текущий контракт без повторной проверки |

Если целевое требование и реализация расходятся, это implementation gap. Код не
переопределяет утверждённое требование, а исторический документ не
переопределяет текущий контракт.

Внутри уровня целевых требований подтверждённое product decision имеет
приоритет над более ранним пунктом ТЗ/SRS, если решение явно пересматривает этот
пункт. Для электротехнических решений PDL-ER-01…41 заменяют модель фиксированных
`СО1…СО4` на до пяти именованных UUID ЭР. Старый текст допустим только с явной
пометкой `legacy`/`historical`; использовать его как текущий лимит или UI-контракт
запрещено.

## Исторические и генерируемые материалы

- Датированный audit/status-файл остаётся evidence своего среза, но текущий
  статус нужно перепроверять по контракту, коду и тестам.
- Неутверждённые продуктовые идеи сведены в
  `docs/analysis/product-proposal-ledger.md`; они не являются backlog или ТЗ.
- Сырые Playwright/QA snapshots должны жить в ignored report-каталогах. В
  `docs/` переносится только curated evidence, на которое есть явная ссылка.
- Демо-поставка формируется по `docs/playbooks/demo-release.md`; параллельная
  редактируемая копия основных документов не является источником истины.
- Локальные planner board/plan/tickets являются генерируемыми отчётами и не
  должны храниться рядом с расчётной документацией.
