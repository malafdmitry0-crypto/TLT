# Анализ входных полей: ТНП «Список переменных» vs форма SC-03

Сопоставление листа **«Список переменных»** из
`ТНП/Расчет_спецификации_трубы_самрег29_05_26.xlsx` с тем, что приложение
**фактически собирает** (форма SC-03 «Геометрия/Теплоизоляция/Температура»,
страница «Электрорасчёт», результаты расчёта, справочники). Цель — показать,
каких полей нам не хватает для полного расчёта спецификации.

Дата анализа: 2026-06-08.

> **UX-правка 2026-06-08 (выполнено):** из видимой формы SC-03 убраны
> электрические/метаданные-поля `supply_voltage`, `min_switch_temperature`,
> `steam_tracing`, `vapor_temperature` (стали `hidden` для сохранения round-trip).
> `supply_voltage` и `vapor_temperature` редактируются на странице
> «Электрорасчёт» (recalc-контролы: U для резистивных, T проп. для ТТ);
> `min_switch_temperature`/`steam_tracing` — метаданные (Excel/таблица/дефолты),
> в формулах не участвуют. В секции «Геометрия трубы» остались только
> теплорасчётные поля (геометрия, стенка, `safety_factor`/Кзап, локальные
> элементы, `q_additional` у резервуара). `tsc` чистый, фронтенд-тесты зелёные.

Легенда: ✅ есть · ⚠️ есть, но не там / неполно · ❌ отсутствует.

**Вывод по секции 1:** все пользовательские входы есть. Различие только в
размещении: `w` (навив), «Среда воздействия» (агрессивность) и «Схема
соединения» собираются на странице **Электрорасчёт**, а не в SC-03 — это
соответствует архитектуре (кабельные параметры отделены от теплопотерь,
US-G-19). Поля под условием (`H`, `λгр`) появляются при подземном размещении.

## 2. Секция «Расчётные параметры на каждую поз. электрорасчёта»

Это **результаты** электрорасчёта на каждую позицию (не пользовательский ввод).

| Переменная | Наименование | Где сейчас | Статус |
|---|---|---|:--:|
| M,секц | Марка греющего кабеля | результат → `cable_mark` | ✅ |
| L,секц | Длина нагревательной секции | результат → `installed_cable_length` (суммарно) | ⚠️ |
| N,секц | Кол-во нагревательных секций | результат → `num_circuits` | ⚠️ |
| T,секц | Температурный класс (**низкий/средний/высокий**) | вывод из серии (ТТН/ТТВ/ТТХ) | ⚠️ |
| Ns,секц | Кол-во ниток (параметр N алгоритма) | результат → `num_circuits` | ⚠️ |

**Внимание — два расхождения для спецификации:**

1. **`N,секц` (секции) и `Ns,секц` (нитки) — это РАЗНЫЕ величины** в источнике,
   но в текущей модели есть только одно поле `num_circuits`. Формулы BOM
   опираются на `N,секц` (кол-во секций): `Fl = Σ N,секц·R,гр`,
   `Nk = Σ ceil(N,секц/3)`. Нужно зафиксировать, что в нашей реализации
   считается «секцией», и не путать с нитками навива.
2. **`T,секц` имеет ТРИ значения** (низкий/средний/высокий = ТТН/ТТВ/ТТХ для
   Q1/Q2/Q3), а реализованный `full_builder` различает только два класса
   (низк./выс.) для выбора КСН vs КСВ. Для комплектов 2 семейства достаточно
   (КСН=низк., КСВ=средн.+выс.), но сам класс — трёхзначный; стоит хранить три
   значения, если позже появятся правила, зависящие от «среднего».

## 3. Секция «Указанные требования» — ⚠️ ГЛАВНЫЙ ПРОБЕЛ

Зелёный блок листа. Это параметры уровня позиции/проекта, **которых сейчас нет
в карточке объекта** — именно они управляют условным подбором аксессуаров.

| Переменная | Наименование | Где сейчас | Статус |
|---|---|---|:--:|
| Ex | Тип зон по взрывоопасности (да/нет) | SC-03 → «Классификация зоны» (Безопасная/…) — **близко, но не связано с BOM** | ⚠️ |
| K1i | Индикация питающих на коробках (да/нет) | — | ❌ |
| K2i | Доп. индикация в конце нагр. секции (да/нет) | — | ❌ |
| Kiu | Доп. индикация сверху коробки (да/нет) | — | ❌ |
| L,K2i | Мин. длина секции для применения K2i | — | ❌ |
| R,гр | Коэффициент горячего резервирования | — | ❌ |

Текущая реализация `full_builder` принимает эти параметры как
`SpecificationOptions` с дефолтами (R,гр=1.0, Ex=нет, индикаторы=нет), а на
странице спецификации Сотруднику доступны только **Ex** и **R,гр**. Поля
**K1i / K2i / Kiu / L,K2i** в UI пока не выведены — при дефолтах используются
только базовые коробки (Nk1/Nk2/Nk7/Nk8), а варианты «-С/-С1» (Nk3…Nk6, Nk9…Nk12)
недостижимы.

## 4. Что «у нас должно быть» (сводка пробелов)

Чтобы полная спецификация считалась по всем условиям ТНП, нужно добавить сбор
блока **«Указанные требования»**:

| Поле | Тип | Уровень | Куда добавить |
|---|---|---|---|
| Ex (взрывозона) | да/нет | объект или проект | связать с «Классификация зоны» SC-03 или вынести в опции спецификации |
| K1i (индикация на коробках) | да/нет | позиция/проект | новое поле |
| K2i (индикация в конце секции) | да/нет | позиция/проект | новое поле |
| Kiu (индикация сверху коробки) | да/нет | позиция/проект | новое поле |
| L,K2i (мин. длина для K2i) | число, м | проект | новое поле |
| R,гр (горячее резервирование) | число | позиция/проект | новое поле |

Плюс уточнить две расчётные величины:
- **N,секц vs Ns,секц** — развести «кол-во секций» и «кол-во ниток» (или явно
  зафиксировать, что `num_circuits` = секции).
- **T,секц** — хранить трёхзначный класс (низкий/средний/высокий).

## 5. Вспомогательные поля формы вне списка ТНП

SC-03 собирает поля, которых нет в листе переменных (это нормально —
расширение/служебные): «Материал покрытия», «Макс. T° окр. среды»,
«Макс. допуст. T° продукта», «Режим tm изоляции», «Режим λ трубы»,
«Среда» (environment normal/…), «Размещение». Они не мешают, но «Среда»
(environment) ≠ «Среда воздействия на кабель» (aggressive_product) — это два
разных параметра, их не следует путать.

## 6. Открытые вопросы к заказчику

1. **Уровень параметров «Указанные требования»**: задаются на проект целиком,
   на CO-вариант или на каждую позицию электрорасчёта? (Влияет на UI и хранение.)
2. **Ex**: использовать существующую «Классификацию зоны» объекта (Безопасная/
   взрывоопасная) как источник Ex, или это отдельный флаг уровня проекта?
3. **N,секц vs Ns,секц**: подтвердить определение «секции» и «нитки» и какое из
   значений идёт в формулы коробок/комплектов.
4. **R,гр**: единое значение на проект или разное по позициям; диапазон/дефолт.
5. **L,K2i**: единица и типовое значение (для срабатывания -С коробок).
